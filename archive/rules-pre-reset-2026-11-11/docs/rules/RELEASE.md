# 构建、发布与交付

本文件只包含当前生效的构建、测试和交付要求。Android 与 Web 的平台细节分别由 `ANDROID.md`、`WEB.md` 和对应细则补充。

## 1. 构建

### 1.1 Android

默认使用 `./gradlew assembleRelease --offline`；Windows 使用等价的 `gradlew.bat`。优先复用当前 JDK、Android SDK、Gradle、D8 和缓存，只有缺少必要依赖时才联网补齐。

### 1.2 构建输入

构建前保护用户已有修改、上一个可回滚产物和当前签名输入。候选构建写入候选位置，不覆盖稳定产物；只生成 APK，不以 XAPK 作为 MOD 交付物。

### 1.3 构建结果

报告必须绑定源码输入、项目/包名、版本、产物路径、文件大小、SHA-256、签名和验证结果。`BUILD SUCCESSFUL`、退出码或复制成功本身不能证明稳定交付。

## 2. 验证

### 2.1 候选验证

候选允许按实际开发需要多次构建。每次候选都必须使用对应 APK 做定向测试；旧 APK 的测试结果不得转移给新 APK。

### 2.2 Android 运行验证

影响 Android 运行行为的改动，按影响范围执行 Kotlin→D8→DEX→APK、签名、契约检查、独立 AVD 安装和真实 GUI 验证。共享 AVD 与正式构建资源必须串行。

### 2.3 Web 验证

影响 Web 行为的改动，执行项目实际使用的模块校验、定向测试、移动端 GUI 检查和部署后访问检查。静态检查不能替代浏览器中的真实行为验证。

### 2.4 结果分级

报告明确区分 `PASS`、`FAIL`、`BLOCKED` 和 `NOT RUN`。未完成必要运行验证的产物只能称为候选，不能称为稳定版。

## 3. Android 正式交付

### 3.1 门禁

只有通过必要签名、契约和运行验证的同一份 APK 才能正式发布。发布前冻结构建输入，并记录 APK SHA-256 与 `release-manifest.json`。

### 3.2 四渠道

正式 Android APK 使用同一份已验证文件交付到 OneDrive、Google Drive、GitHub Releases 和 Kubuntu 本地 SSH/SFTP 目录。任何渠道失败都单独记录和重试，不重建 APK，也不把部分成功写成全部完成。

### 3.3 发布工具

优先使用 `scripts/publish_four_channels.py`：普通构建不上传；正式发布显式使用 `--publish`；仅更新本地 SSH/SFTP 使用 `--local-only`；检查使用 `--check`；预演使用 `--dry-run`。

### 3.4 Release

每个经过验证的 APK 使用唯一更新标签 `android-update-<正式版本>-<SHA256前8位>` 创建 GitHub Release。已有 Release 不覆盖、不删除；同标签仅在 SHA-256 相同的情况下按幂等处理。

## 4. Web 正式部署

### 4.1

Web 修改完成必要测试后，按当前 Git 流程提交并推送 `main`，再部署到线上站点并检查实际页面、关键功能和资源加载。

### 4.2

源码仓库是唯一功能修改入口；`web/_deploy/site` 只接受同步后的部署内容，不直接实现游戏功能。

## 5. 报告与安全

### 5.1

交付报告记录构建环境、耗时、源码输入、产物身份、验证边界、Git 状态、部署状态和未解决阻碍；动态环境事实放入 FACTS 或任务记录。

### 5.2

凭据、私钥、远端配置和个人路径不得进入仓库、日志或 Release 附件。禁止强推、破坏性历史重写、删除用户存档或发布未经验证的候选包。

## 6. Android 发行版写作格式

本节**仅适用于 GitHub Releases 渠道**，规定 GitHub Release 标题、正文、下载说明和版本状态的统一写法。OneDrive、Google Drive、SSH/SFTP 等其他渠道只提供经过验证的 APK 和对应的 SHA-256 校验值，不上传、不维护、不要求附带本节发行说明或其他文档。它只规范已经确定的发行信息，不替代构建、签名、安装和 GUI 验收门禁。

### 6.0 渠道边界

1. GitHub Release 是唯一需要填写完整发行说明、版本摘要、验证结果、SHA-256 和下载信息的公开文字渠道。
2. OneDrive、Google Drive、SSH/SFTP 只传 APK 和 SHA-256 校验值；不得因为这些渠道没有发行说明而判定发布不完整。
3. 其他渠道的 SHA-256 校验值可以作为同名 `.sha256` 文件或渠道文本提供；除 APK 和校验值外，不附加 Markdown、变更日志、截图、测试报告或内部日志，除非用户另有明确要求。
4. GitHub Release 中可以列出其他渠道“已上传/未上传”的内部交付状态，但不能把其他渠道改造成第二套发行说明渠道。
5. 同一份 APK 在 GitHub 与其他渠道的文件内容、大小和 SHA-256 必须一致；任何渠道不得重新打包或重新签名。

### 6.1 发布文字的基本原则

1. 先写玩家能得到什么，再写实现细节；使用简体中文，语言准确、短句优先。
2. 每一段只表达一个事实、一个变更或一个操作要求；不要把多个版本、多个 APK 或多个渠道混写。
3. 所有版本号、构建号、包名、文件名、SHA-256、时间和渠道状态必须来自同一份已验证的发布清单；不得手工凭记忆填写。
4. 发行说明只描述本次发行与当前仍有效的使用信息，不写开发流水账、内部讨论、Agent 交接、R 编号、已归档规则、失效方案或未公开的个人路径。
5. 不把“已编译”“已上传”“链接可访问”写成“功能已验证”；构建、安装、启动、功能和发布状态分别表述。
6. 未完成必要运行验证的 APK 必须称为“候选版”或“测试版”，不得称为“稳定版”“正式版”或“推荐日常使用”。
7. 不使用绝对化宣传语，例如“完全无 bug”“所有设备均兼容”“百分之百稳定”“绝对不会丢档”；改用有范围、有证据的描述。
8. 不公开签名私钥、令牌、内部服务器地址、个人目录、未脱敏日志和可还原用户存档的敏感内容。

### 6.2 标题格式

正式稳定版标题使用：

```text
Android <版本号>｜<一句话主题>
```

候选版使用：

```text
Android <版本号>-候选 <候选序号>｜<测试主题>
```

热修复使用：

```text
Android <版本号>｜热修复：<修复主题>
```

标题规则：

1. `<版本号>` 必须与 APK 内实际版本名一致；不得用 Git 分支名、任务编号或日期代替版本号。
2. `<一句话主题>` 建议不超过 24 个汉字，只说明玩家可感知的主要变化。
3. 标题不得包含内部任务编号、分支名、提交哈希、渠道状态或未验证的质量承诺。
4. 同一版本的四个发布渠道必须使用同一个正式标题和同一个 APK 身份。

### 6.3 正式发行说明的固定顺序

正式版、候选版和热修复的正文必须按以下顺序书写；不适用的段落写“无”，不得随意改变顺序：

1. 版本信息。
2. 面向玩家的摘要。
3. 本次新增与改进。
4. 问题修复。
5. 兼容性与限制。
6. 已知问题与风险。
7. 安装、更新与回滚说明。
8. 验证范围与结果。
9. 文件校验与下载渠道。
10. 反馈与问题报告方式。

### 6.4 版本信息格式

发行说明开头必须使用以下字段，字段名保持不变：

```text
版本：<versionName>
构建：<versionCode>
包名：<applicationId>
发行类型：稳定版 / 候选版 / 测试版 / 热修复
发布日期：<YYYY-MM-DD>
目标基线：<官方 Android 基线>
APK 文件：<完整文件名>
```

规则如下：

1. `版本`、`构建`、`包名`必须来自最终 APK 或正式构建清单。
2. `发行类型`只能使用实际状态；候选版不能写成稳定版。
3. `发布日期`使用发布动作发生地的日历日期，不使用构建开始时间冒充发布日期。
4. `目标基线`必须说明本次兼容的官方游戏/Android 基线；不确定时写“待验证”，不得猜测。
5. 文件名必须包含可识别的版本信息，但不得用会变化的本地路径作为文件名。

### 6.5 玩家摘要格式

摘要只回答三个问题：这是什么版本、玩家最直接得到什么、是否建议日常使用。推荐格式：

```markdown
## 本次更新

本版本主要改进：<一句话概括玩家可感知变化>。

适用范围：<设备、Android 版本、存档或功能范围>。

使用建议：<稳定版可日常使用 / 候选版仅建议测试 / 测试版仅用于定位问题>。
```

摘要不得把内部实现细节、代码文件名或调试过程放在第一段，也不得省略候选版的测试性质。

### 6.6 变更与修复的写作格式

新增、改进和修复分别使用短条目，每条采用“结果 + 范围”的格式：

```markdown
## 新增与改进

- <玩家可使用的功能>：<使用入口或生效条件>。
- <体验改进>：<具体改善了什么，不夸大范围>。

## 问题修复

- 修复 <可观察问题>：<修复后的实际行为>。
- 修复 <界面/存档/兼容问题>：<影响范围和限制>。
```

写作要求：

1. 一条只写一个变化；同一条不得同时混入多个无关模块。
2. 使用“修复”前必须有对应测试或运行证据；只有推测原因时写“正在调查”或放入已知问题。
3. 不写“优化大量代码”“重构完成”“性能大幅提升”等无法由玩家验证的空泛表述；应写具体页面、操作、时间、资源或兼容行为。
4. 涉及游戏机制时，必须写清真实前置、适用阶段和是否影响旧存档；不能用“自动解锁”“直接跳过”等容易误解的措辞掩盖阶段变化。
5. 涉及 GUI 时，说明入口、页面、按钮状态、刷新条件和已验证的屏幕范围；不能仅凭内部字段变化宣称界面修复。
6. 涉及自动购买器、调度器或重置时，说明玩家手动设置是否保留、实际生效节拍、阶段保护和存档重载行为。

### 6.7 兼容性、已知问题与风险格式

兼容性必须单独列出，不得把“能够安装”写成“功能完全兼容”：

```markdown
## 兼容性与限制

- Android 版本：<已验证范围>
- ABI：<已验证 ABI>
- 原版基线：<版本或提交>
- 存档：<是否兼容旧存档，是否建议备份>
- 已验证设备/模拟器：<设备或 AVD>
- 未验证范围：<明确列出>

## 已知问题与风险

- <问题>：<触发条件、影响、临时规避方式>。
- 无：仅在确实没有已知问题且验证范围足够时使用。
```

规则如下：

1. 未测试的设备、Android 版本、ABI、存档或渠道必须列为“未验证”，不得写“兼容”。
2. 已知问题必须说明严重程度和是否影响存档；涉及存档时必须提示备份。
3. 如果存在可能导致数据损失、卡死、错误阶段推进或 UI 与内部状态不一致的问题，发行版不得标记为稳定版，除非规则允许且风险已明确接受并记录。
4. 不得为了让发行说明看起来完整而编造“无已知问题”。

### 6.8 安装、更新与回滚格式

安装说明必须足够让新手完成操作，并明确数据风险：

```markdown
## 安装与更新

1. 下载与设备 ABI 匹配的 APK，并核对 SHA-256。
2. 安装前备份游戏存档；跨版本更新前尤其如此。
3. 使用系统安装器覆盖同包名旧版本，或先按本版本说明卸载。
4. 首次启动后检查版本号、语言、存档和核心功能。

## 回滚

如需回滚：

1. 先导出或复制存档。
2. 卸载当前版本前确认已保存存档。
3. 安装上一份已验证 APK。
4. 恢复存档后检查阶段、资源、自动购买器和设置。
```

如果版本不支持覆盖安装、存档格式发生变化、需要清除数据或不能安全回滚，必须在安装说明开头突出说明，不得埋在文末。

### 6.9 验证结果格式

发行说明只公布与该 APK 身份绑定的验证结果，使用以下格式：

```markdown
## 验证结果

- 构建：PASS / FAIL / BLOCKED / NOT RUN
- 签名：PASS / FAIL / BLOCKED / NOT RUN
- 安装与启动：PASS / FAIL / BLOCKED / NOT RUN
- 核心功能：PASS / FAIL / BLOCKED / NOT RUN
- 存档读写：PASS / FAIL / BLOCKED / NOT RUN
- 真实 GUI：PASS / FAIL / BLOCKED / NOT RUN
- 180 分钟目标：PASS / FAIL / BLOCKED / NOT RUN / 不适用

验证边界：<设备、系统、存档、测试时长和未覆盖内容>
```

1. 只有在相应证据存在时才能写 `PASS`。
2. `NOT RUN` 表示尚未执行，`BLOCKED` 表示有明确阻碍，`FAIL` 表示已执行但未通过；三者不能互换。
3. 任一必要门禁为 `FAIL` 或 `BLOCKED` 时，不能在标题或摘要中称为稳定版。
4. 不得把静态检查、构建成功、上传成功或截图存在单独当成真实 GUI/核心功能通过。
5. 测试证据应记录 APK SHA-256、测试日期、设备/AVD、关键存档和截图/日志位置；敏感信息先脱敏。

### 6.10 文件校验与渠道格式

GitHub Release 下载区必须以同一份已验证 APK 为准，并使用以下格式：

```markdown
## 文件与下载

文件：<完整 APK 文件名>
大小：<字节数或可读大小>
SHA-256：<完整 64 位十六进制值>
签名校验：<结果和验证方式>

- GitHub Releases：<状态/链接>
- 其他渠道：仅提供 APK + SHA-256 校验值
```

1. SHA-256 必须写完整值，不能只写前八位；前八位只可用于 Release 标签或内部索引。
2. GitHub Release 必须标明实际 Release 状态；其他渠道只提供 APK 和对应 SHA-256，不要求发布同样的文案。
3. 渠道失败时写明失败渠道和重试状态，不重建同一版本 APK，也不更换文件哈希后继续沿用原说明。
4. GitHub 链接必须指向实际文件或实际 Release；其他渠道只提供文件和校验值，不要求公开链接进入发行说明。占位符、失效链接和仅对内部可见的个人路径不得进入 GitHub 发行说明。

### 6.11 热修复与撤回说明

热修复必须说明相对于上一稳定版的差异、适用范围、是否需要重新安装和是否影响存档。撤回或替换版本时使用单独说明：

```markdown
## 版本状态

状态：继续发布 / 暂停发布 / 已撤回 / 已替换
影响版本：<版本和 SHA-256 前缀；完整值放在验证记录>
原因：<可公开、可验证的原因>
用户建议：<继续使用 / 更新 / 备份后回滚 / 暂停启动>
```

不得静默删除 Release、覆盖原 APK 或修改历史发行说明来掩盖问题。需要撤回时保留可追溯记录，并把新的推荐版本与旧版本明确区分。

### 6.13 发布前文字检查

发布前必须逐项检查：

1. 标题、版本名、构建号、APK 文件名和 `release-manifest.json` 一致。
2. 发行类型与实际验证门禁一致，没有把候选版写成稳定版。
3. 新增、修复、兼容性和已知问题都能追溯到对应代码、测试或运行证据。
4. 安装、备份、回滚和存档风险已经说明。
5. SHA-256 是完整值，四渠道状态分别准确。
6. 没有 R 编号、内部路径、凭据、流水账、归档内容、失效规则或未验证承诺。
7. 所有中文术语遵守教程规则；`Infinity`、`Eternity` 等游戏术语使用项目统一译名。
8. Markdown 标题层级、列表、代码块、链接和换行正确；在 GitHub Release 预览中检查可读性。
9. 发行说明只对应这一份 APK；重新构建产生新 SHA-256 时必须重新生成对应说明。

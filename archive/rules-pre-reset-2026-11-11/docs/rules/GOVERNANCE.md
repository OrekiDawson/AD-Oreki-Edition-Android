# 规则维护

权威：本文件。范围：活动规则的新增、修改、冲突处理和归档。历史编号、旧登记表和被取代正文不在本文件中，统一放在 `archive/`。

## 1. 新增与修改

### 1.1 先查重

新增规则前先检查现有核心规则、专项规则和长期证据文档。相同要求修订原位置，不追加平行正文。

### 1.2 明确边界

每条生效规则说明适用范围、触发条件、动作、成功判定、例外和失败处理。动态环境事实、任务状态、PID、哈希和一次性日志放入 FACTS、任务或报告，不写入常驻规则。

### 1.3 用户要求优先

用户明确要求可以替代同级旧规则；涉及安全、真实性、存档和工作区保护的条款不得被普通效率规则绕过。无法确定冲突时，只暂停受影响路径并报告，不自行删除相互冲突的有效规则。

## 2. 编号

### 2.1 层级格式

活动规则统一使用连续层级编号：一级 `1.`，二级 `1.1`，三级 `1.1.1`。编号只表达当前文档结构，不承担历史任务编号功能。

### 2.2 来源标识

R 编号、用户日期和提交号可以作为括号中的来源标识，但不能替代正文层级，也不能据此创建跳号章节。

### 2.3 修改旧规则

修订原规则时保留当前章节编号；如果章节职责改变，先在同一文档内完成重排，再更新索引链接。不得因为历史编号而保留已失效正文。

## 3. 归档

### 3.1 唯一归档目录

本仓库所有历史规则、废止规则、旧版索引和仅用于追溯的规则说明统一放在 `docs/rules/archive/`。

### 3.2 归档流程

规则被取代时：

1. 从活动正文删除已失效内容；
2. 检查是否仍有追溯价值；
3. 将完整旧文件移动到 `docs/rules/archive/`；
4. 在活动索引中只保留当前权威入口，必要时加一句替代说明；
5. 检查所有 Markdown 链接和规则镜像。

### 3.3 归档隔离

归档目录不参与常驻加载。活动规则不得复制归档正文，不得引用归档文件作为当前执行依据，不得在归档文件中追加新的生效规则。

## 4. 镜像与验证

### 4.1 Android/Web 镜像

Android 与 Web 的同名核心规则应保持一致；平台差异写入对应平台规则或 `WEB_ANDROID_DIFFERENCES.md`，不在镜像中静默分叉。

### 4.2 修改后检查

规则维护后至少检查：

1. 活动索引没有指向归档文件；
2. 活动正文没有“已废止”“已被取代”的规则段落；
3. 章节编号连续且层级正确；
4. 相对链接存在并指向当前文件；
5. 同名镜像没有互相冲突的有效条款。

### 4.3 规则改动边界

规则维护不触发无关 APK 构建、部署或存档操作；只运行链接、编号、同步和冲突检查。

## 5. README 约束

### 5.1

README 只保留当前有效的用途、使用方式、目录边界、构建/运行入口和交付要求。

### 5.2

README 不是开发流水账、变更日志或任务交接文档；不得出现 R 开头的任务/轮次编号、归档、已废止、失效、旧版本、历史规则或被取代内容，也不得复制规则正文、一次性环境事实或未验证结论。

### 5.3

规则以规则入口为准，事实以 `FACTS.md` 或验证记录为准；README 只提供链接和简要说明。按 GitHub 项目常见标准检查项目定位、目标读者、快速开始、环境前提、用法、目录、贡献、许可证、安全和反馈入口；修改后检查四个仓库 README 的一致性、链接、路径、命令和版本描述。

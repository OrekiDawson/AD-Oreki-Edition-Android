# Lead / Subagent 调度与文件交接规范

> 长期强制规则。由仓库根 `AGENTS.md` §18 引用。适用于 AD-Oreki-Edition Android 主线及 Lead 统一协调的 Web、Wiki、FACTS、CI/CD 子任务。与仓库技术/安全/停工/发布规则冲突时，以更严格的已生效规则为准。本文不创建新 Goal，不改变当前轮次与计时。

## 1. 职责与基本原则

- **Lead**：维护当前 Goal 的任务队列、优先级、依赖、资源所有权；决定委派；负责跨 Agent 协调、合并、最终验收、合规构建与发布，并向用户给出有内容的简体中文回复。
- **Subagent**：依照明确的文件任务书独立实施、做最小必要验证、保存成果、通过结果文件交接。不得自行扩大任务范围、创建新 Goal 或擅用独占资源。
- **优先复用**：已有同类且空闲的 Agent > 能胜任的其他现有空闲 Agent > 必须新增时才创建。新增前检查实际 Activation 容量及 `maxActiveSubagents` 配置，不默认槽位无限。
- **有效并行**：只并行有价值、已授权、依赖满足、互不冲突的任务。不为占满槽位制造任务，不为了省调度而让 Lead 包揽多个可独立交付的长任务。
- **停止优先**：用户明确暂停或系统安全限制 > 高峰全员停工（`AGENTS.md` §7）> 低谷期持续开发与交付。禁止用其他模型、自动化或 GitHub 操作绕过高峰停工；外部无法取消的任务仅如实记录。
- **现行优先级**：玩家 P0、真实通关与游戏机制正确性优先；独立 Wiki、FACTS、静态分析可在不抢占主线资源时并行。正式 CI/CD、签名和发布门禁不因并行而放宽。

## 2. 有效任务队列

复用当前已有 `tasks/` 台账，不新建平行任务管理系统。每项任务至少记录：

| 字段 | 约束 |
| --- | --- |
| task_id / goal_id | 既有轮次和唯一子任务 ID；不改历史编号 |
| owner / priority | 执行者、真实优先级 |
| state | READY / ASSIGNED / RUNNING / WAITING / BLOCKED / REVIEW / DONE / FAILED / CANCELLED |
| dependencies | 必需的前置任务、源码或验收结果 |
| inputs | 固定 Commit、事实文件、报告及来源 |
| files / resources | 允许修改的文件、worktree、独占资源及冲突边界 |
| handoff / result | 输入任务书和结果报告的可访问路径 |
| acceptance | 最小必要验收、交付物与失败条件 |

状态定义：

- **READY**：已授权、依赖满足、资源可用，可以派发。
- **ASSIGNED**：已明确分配并交付任务书，不能冒充正在执行。
- **RUNNING**：接收方已读取任务书且实际开工。
- **WAITING**：等待必要外部事件或结果；保留等待对象和恢复条件。
- **BLOCKED**：有具体阻塞及证据，不用空泛「环境问题」代替。
- **REVIEW**：Subagent 已交结果文件，Lead 尚未验收。
- **DONE**：Lead 核对实际代码/证据并确认满足完成标准。
- **FAILED / CANCELLED**：真实失败或有授权的取消，保留现场。

任务完成、Agent completion、Lead 单回合结束、整个 Goal 完成是四个不同概念。

## 3. 派发前的固定流程

1. **判断是否允许执行**：先检查用户暂停、停工时段、权限与安全门禁。禁止窗口内不调度、不新建任务。
2. **盘点任务**：读取现有台账，找出全部 READY 项及依赖；按 P0/P1、关键路径、资源和成本排序。
3. **盘点 Agent**：调用实际存在的 `list_agents` 或等价接口，确认身份、状态、在办任务、最近工作树、可否复用、Activation 占用；不得凭记忆推断 Agent 空闲。
4. **匹配与冲突检查**：优先同专业现有空闲 Agent；确认编辑文件不会重叠，AVD/真机/构建/签名/发布资源不会竞争；短小任务可由 Lead 直接处理。
5. **写任务书**：先把文件写入接收方可读的位置，检查文件确实存在且版本正确。
6. **通知与领取**：通过 `send_message` 或实际支持的接口发送任务 ID、任务书路径、结果报告路径和优先级。接收方先读取文件，再回复领取或明确阻塞。
7. **更新台账**：根据真实领取、开工和执行进展更新 ASSIGNED / RUNNING；不能在发出消息时假定对方已经执行。

只有确有并行收益、现有 Agent 无法胜任且容量允许，才新建 Agent。不得重建已可恢复的同名角色。

## 4. 文件交接协议（强制）

### 4.1 Lead 提交任务书

沿用仓库既有 `tasks/`、`reports/` 和历史交接格式。推荐按轮次存放，如 `tasks/<Goal-ID>/<task-id>.md`，但有既定可用路径时必须复用，避免擅改目录。文件至少写明：

- Goal、任务 ID、责任 Agent、派发时间与优先级。
- 目标、范围、完成标准与不做事项。
- 已核实背景、证据链接、必读规则和适用版本。
- 允许改动的文件与目录、禁止触碰的文件、独占资源及其他 Agent 所有权。
- 前置条件、实施方向、最小必要验证及预期产物。
- 结果报告的**准确路径**，以及遇到阻塞时如何报告。
- `PASS / FAIL / BLOCKED / NOT RUN` 的真实判定依据。

聊天消息不能替代任务书。不要把整个 `AGENTS.md`、FACTS 或历史报告复制进任务文件，使用明确链接或路径引用即可。

### 4.2 Worktree 可达性

- Lead 和 Subagent 在不同 worktree 时，未提交文件不会自动同步。必须使用双方真实可读的共享交接目录，或先通过安全的 Git 提交/分支同步；发送前确认可读取。
- 不在其他 Agent 正写的工作树中擅自写文件，不依赖未核实的工作目录或虚构路径。
- 任务书变更后通知接收方重新读取新版本；重要范围变更先协调文件所有权。
- 避免同一份任务书由多个 Agent 同时写。Lead 负责派发文件；Subagent 负责自己的结果报告。

### 4.3 Subagent 结果报告

完成、失败、取消或阻塞前先保存代码和证据，再写结果文件。报告至少包括：

- 实际完成内容和修改文件。
- 源码 Commit SHA / PR / 可追溯证据，以及报告或构建产物路径。
- 实际执行的测试、环境、结果；未执行必须写 `NOT RUN`。
- 风险、未完成项、明确阻塞及可复现线索。
- 文件与独占资源是否已安全释放，能否继续接新任务。
- 下一个任务的建议与依赖，但不得自行把建议标为已授权。

Subagent **先落盘再通知** Lead。完成消息只写任务 ID、结果状态、文件路径、需要的协助，禁止以「已完成」一句话代替交付。

### 4.4 Lead 验收与接力

Lead 必须打开结果报告，对照任务书检查源码、Commit、PR、CI/AVD/设备证据；合格才将 REVIEW 改为 DONE。拒收或待补充须给明确原因和下一步。收到 completion 不等于主 Goal 完成，也不能静默结束本应给用户回复的正常回合。

## 5. 何时触发重新调度

以下事件均触发**一次有意义的调度判断**：

- Subagent 完成、失败、阻塞、取消或主动变为空闲。
- PR/CI/CD/构建/部署返回关键结果。
- 已确认新的 Bug 或收到用户新任务。
- 长跑到达关键检查点、阻塞解除、资源释放。
- Lead 的当前任务完成或转入 WAITING。

每次按「允许执行？→ 队列 READY？→ Agent 可复用？→ 资源无冲突？→ 文件交接 → 派发/验收」顺序判断。

存在 READY 任务且现有合适 Agent 可用时，默认接力派发；无 READY 项则允许 Agent 空闲、由正式机制释放 Activation 或 Lead 正常结束当前回合。**禁止无任务自我唤醒、无限轮询、虚假进度和空消息循环**。不要假定 Harness 的某个通知必然送达；若发现通知丢失，记录版本和复现证据，并通过正式支持的状态查询恢复。

## 6. Lead 与 Subagent 的工作划分

Lead 优先处理：任务拆分与排序、跨树/跨端冲突、共享资源、PR 集成、发布门禁、真实最终验收和用户沟通。

Subagent 优先处理：可独立交付的 Android crash/logic/UI/performance 排查、Web 对齐、Wiki 译文与编辑、FACTS 拆分、静态工具和独立 CI 修复。

Lead 要自行实施预计较长的独立任务时，先检查是否有合适空闲 Agent；如果可以安全委派，默认委派。几行小修改、必须由 Lead 持权操作、强耦合集成、或委派成本大于收益时，可由 Lead 直接执行，但不应让其他有价值 READY 任务因此无人负责。

## 7. 文件、运行和发布资源隔离

- 每位 Agent 使用独立 worktree 或既有明确隔离空间。每个可写文件/目录在同一时段只设一位 owner；共同变更由 Lead 协调顺序或独立 PR。
- AVD、真机、长跑存档、正式构建输出、签名环境、正式部署和发布为独占资源；读日志或查看已有报告不等于获得写入权限。
- 180 分钟真新档长跑期间不得以测试、验证、定位为由抢占设备、清除游戏数据、重启应用、替换 APK 或篡改存档。
- Android/Web/Wiki 代码和文档可以隔离并行，但必须满足各自的 Required Checks、保护环境和许可证要求；不以主线 BLOCKED 为由暂停无冲突工作。
- 失败保留工作树、未提交代码、证据与恢复点；禁止强推、销毁别人的成果、删除有效历史或规避安全门禁。

## 8. Agent 容量与成本

- 按实际 DSH/Harness 支持的 `list_agents`、`send_message`、Activation 管理机制操作；默认容量、可恢复/释放条件必须现场核实。
- 遇容量满额：先复用现有 Agent，再检查已结束但占位的实例；仅通过官方支持机制释放，必要时排队，不盲目调高容量或改底层状态。
- API 费用、上下文消耗、任务重复率与成果质量共同决定并行度。不为「所有 Agent 在线」而制造工作，不为省 Token 牺牲 P0 的必要调查。
- 重要状态及时给用户清晰中文回复；中间通知不过量；用户可见正常回合不能在完成大量工具调用后无内容结束。

## 9. 跨仓 Wiki / 翻译专项

Wiki editorial 与 translation 并行前必须明确每批具体文章的文件所有权；翻译、语义核对、语言润色、导航分别有清楚的责任边界。同一文章不得被两个 Agent 同时重写。

任务书注明原版 Wiki 链接、修订 ID、许可、术语表、文章清单、验收标准；结果写出每篇实际文件、章节/公式/表格核对、真实 REVIEWED 状态、PR 与 Quartz/移动端验证。不得把「结构检查通过」直接冒充逐句语义校对，也不得仅用聊天汇报翻译篇数。

## 10. 最小回归与长期维护

规则实施后至少实际验证：

1. 同一现有 Subagent 连续承接 A、B 两项不同任务；B 使用新的文件任务书，未无故创建同类 Agent。
2. Subagent 完成 → 结果报告落盘 → Lead 读取验收 → 触发下一次调度决策。
3. 两项文件编辑冲突被识别并隔离；长跑独占 AVD 不受其他 Agent 干扰。
4. 无 READY 任务时不会空转；暂停/高峰窗口不会继续调度。
5. DONE、PR 合并、构建 PASS 与正式发布各有真实独立证据，不互相代替。

只在需要时追加最小验证，不扩大为项目全量回归。任务与证据按原台账归档，`AGENTS.md` 只保留权威入口与核心禁令；本文件负责详细协议。任何实际例外必须记录原因、资源所有权和结果，不得默默放宽。

## 11. DeepSeek 低余额暂停与恢复

`AGENTS.md` §19 是权威预算保护规则。**使用 DeepSeek 的项目任务，实际可用余额 < ¥10.00 时，一律进入 `LOW_BALANCE_PAUSED`**，不得仅停止新建 Subagent 却让 Lead 继续调用模型，更不得更换其他模型继续开发。

- **检查时机与来源**：新一轮付费执行、恢复暂停、派发 Agent 前、长工作流的自然检查点。优先通过 DeepSeek 官方 `GET https://api.deepseek.com/user/balance`（使用已有安全注入的 API Key）读取 `currency=CNY` 的 `total_balance`，以精确十进制判断是否 **< ¥10.00**。`is_available=true` 只表示尚可调用 API，不代表余额满足 ¥10 阈值；缺失 CNY 金额、接口失败或凭据不可用时记录 `BALANCE_UNKNOWN`，暂停新的付费调用。余额查询不要自己耗费 LLM Token 或高频空转。**用户确认 DeepSeek 官方会在低于 ¥10 时给用户发短信**；这只是用户侧告警，Lead 不能默认自动读取短信。用户明确转述低余额短信时立即按停工规则执行；不要求短信读取权限、转发个人短信或公开手机号。
- **安全暂停**：Lead 停止队列 READY → ASSIGNED 派发，通知所有 Agent 保存未提交工作、精简结果报告及真实运行状态，按正式 Harness 机制关闭 Subagent 与 Activation；Lead 自己也停止 AI 任务。只做停止所必需的最小安全收尾，不继续源码开发、PR 操作或新建任务。
- **后台例外**：已经在运行、确认不调用任何收费 LLM 的 systemd 真新档长跑、非 AI 构建、日志采集、既有 CI 任务或备份可以保留。不可因暂停而清除设备数据、终止真实长跑、伪造状态，也不可把“后台任务”当作启动新工作的借口。含 DeepSeek/其他 LLM 调用的工作流不能适用例外。
- **恢复条件**：可信确认可用余额达到 ¥10.00 或以上，且用户未暂停、处于允许开发时段、独占资源和 CI 权限条件均满足；从原任务队列及文件交接记录接续，不重发 `/goal`，不清空历史。
- **记录**：写入可交接的预算状态与检查时间，不记录 API Key、余额接口认证信息或支付凭证；必要用户说明简短列出已关闭 Agent 和保留运行的非 Token 后台任务。

此规则在任务调度中具有**优先于继续开发与两小时发行目标**的地位；不会更改正式构建、验签、发布安全门禁。

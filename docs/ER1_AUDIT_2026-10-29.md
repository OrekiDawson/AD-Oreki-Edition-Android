## 缺陷 1（致命）· AU2/AU3/AU4 的分支条件写反，把「已无限过」变成「没无限过」

### 证据

`AntimatterDimensionAutobuyerState.g()` 补丁后的实际控制流（`work/mod/.../autobuyer/AntimatterDimensionAutobuyerState.smali`）：

```
    move-result v0            # v0 = d() = 「对应普通挑战是否完成」
    if-eqz v0, :oreki_au_inf   # 挑战没完成 → 跳去查 hasInfinity
    goto :cond_0               # 挑战已完成 → 直接放行（原有路径）
    :oreki_au_inf
    invoke-static {}, OrekiAuto;->hasInfinity()Z
    move-result v0
    if-nez v0, :oreki_au_er    # hasInfinity 为真 → 跳去查 orekiEarly
    goto :oreki_au_ok          # hasInfinity 为假 → 走 ok（返回 false）
    :oreki_au_er
    invoke-static {}, OrekiAuto;->orekiEarly()Z
    move-result v0
    :oreki_au_ok
    if-eqz v0, :cond_1         # 最终判定
```

**逻辑错误**：`orekiEarly()` 的语义是「`infinities == 0` → true」（首次无限**之前**）。
但它被写在「`hasInfinity()` 为真」之后才求值 —— 也就是只有**已经无限过**时才会去问
「是不是还没无限过」，答案必然是 false。

结果：
- `hasInfinity() == true`（已无限过）→ 进入 `:oreki_au_er` → `orekiEarly()` 返回 false
  → **g() 返回 false，自动购买器被关闭**。
- `hasInfinity() == false`（还没无限过）→ 直接 `goto :oreki_au_ok`，`v0` 仍是挑战判据 false
  → **g() 也返回 false**。

**两条路径都返回 false**。也就是说这一批 AU2/AU3/AU4 的 `orekiEarly` 扩展**不但没打开开局自动化，
还把已存在的「首次无限后解锁」功能（AU2/AU3/AU4 的既有价值）一并弄坏了**。

对照 `work/base_decoded/.../AntimatterDimensionAutobuyerState.smali`（原始）确认原意：
`g()` 返回 `isUnlocked || 对应挑战完成`；AU2 的既有补丁（HEAD `891e1e3`）是
`if-eqz v0, :oreki_au_inf / goto :cond_0 / :oreki_au_inf / hasInfinity / if-eqz v0, :cond_1`
—— 语义正确（hasInfinity 为真 → 落到 `if-eqz v0, :cond_1`，v0=true → 不跳转 → 放行）。
**本轮新增的 `if-nez v0, :oreki_au_er` 把它改坏了。**

`DimBoostAutobuyerState.g()` / `GalaxyAutobuyerState.g()` 同型（锚点 `if-eqz p0, :cond_0`），
`TickspeedAutobuyerState.g()` 同型（锚点 `if-eqz p0, :cond_1`）。

### 修复

`orekiEarly()` 必须与 `hasInfinity()` **并列求值**（或关系），而不是嵌套在 hasInfinity 为真的分支里：

```
    move-result v0            # v0 = 挑战判据
    if-nez v0, :oreki_au_ok   # 挑战已完成 → 放行
    invoke-static {}, OrekiAuto;->hasInfinity()Z
    move-result v0
    if-nez v0, :oreki_au_ok   # 已无限过 → 放行
    invoke-static {}, OrekiAuto;->orekiEarly()Z
    move-result v0
    :oreki_au_ok
    if-eqz v0, :cond_1
```

## 缺陷 2（致命）· CrunchAutobuyerState.g() 的注入点选错，AU4 放宽**完全无效**

### 证据

`CrunchAutobuyerState.g()` 原始结构（`work/base_decoded/.../CrunchAutobuyerState.smali`）：

```
    invoke-static {}, Lkajfosz/antimatterdimensions/celestials/pelle/c;->q()Z   # isDoomed
    move-result p0
    if-eqz p0, :cond_0        # 未 Doomed → 走挑战 12 判据
    ... return p0              # Doomed 分支：原样返回
    :cond_0
    const/16 p0, 0xc
    ... challenge 12 ...
    move-result p0
    return p0                  # ← 唯一出口
```

本轮 `build_mod.py` 的 `patch_autobuyer_crunch_after_infinity()` 用
`body.rfind("\n    return p0")` 定位注入点。`g()` 里有**两个** `return p0`：
Doomed 分支的 `return p0`（第 18 行）与末尾的 `return p0`。
`rfind` 取到的是**末尾那个**，因此注入块被插在：

```
    :oreki_au4_inf
    invoke-static {}, OrekiAuto;->hasInfinity()Z
    move-result p0
    if-nez p0, :oreki_au4_er
    return p0                  # ← hasInfinity 为真时在这里 return，orekiEarly 永不求值
    :oreki_au4_er
    invoke-static {}, OrekiAuto;->orekiEarly()Z
    move-result p0
    return p0
```

即：`hasInfinity()` 为真 → `return p0`（true）→ **正常**；
`hasInfinity()` 为假 → `orekiEarly()` → true → `return p0`（true）→ 也正常。

**结论：Crunch 的注入点在语义上恰好是「或」关系、逻辑正确**（与 AU2/AU3 不同）。
但它**没有修好任何东西**，因为真正卡住大坍缩自动器的是别的东西 —— 见缺陷 3。

## 缺陷 3（致命）· `enableEarly()` 每帧无条件把 5 类自动购买器重开，剥夺玩家关闭权

### 证据

`OrekiStageAuto.enableEarly()` 被 `onAutoBuyerTick()` **每帧**调用
（`onAutoBuyerTick` 注入在 `Game.autoBuyerTick` 入口，`build_mod.py:1885`），
方法内对 8 个维度 autobuyer + 速度 + 维度提升 + 星系 + 大坍缩
**无条件** `invoke-virtual {v6, v7}, AutobuyerState;->i(Z)V`（`i(true)` = 置 isActive=true）。

原版 `AutobuyerState.j()V`（UI 开关）是 `isActive = !isActive`（翻转）。
玩家在「自动化」页关掉任一自动购买器后，`enableEarly()` 会在**下一帧**把它重新打开。

**玩家永久失去关闭任何自动购买器的权利** —— 这是真实可用性缺陷，必须修。

另外 `enableEarly()` 还写 `Player$Options.autobuyersOn = true`，
这同样剥夺玩家关闭「自动购买器总开关」的权利（原版 `Options.c()` 读的就是这个字段，
`AutobuyerState.c()` 的 canTick 第一步就检查它）。

### 修复方向

必须用**持久标志**记住「玩家主动关闭过」，且只在「从未关闭过」时启用一次。
标志存在哪里？两个约束：
1. **不得**写进 `player.json`（存档兼容性要求，见缺陷 4）；
2. 跨会话要有效 → 用 `SharedPreferences`（`oreki_prefs`），与 `StageAssist` 同款模式。

## 缺陷 4 · 首次无限之后 `enableEarly()` 不应继续回写（当前恰好满足，但要加守卫）

`orekiEarly()` = `infinities == 0`，与 `hasInfinity()` 互补。
`onAutoBuyerTick()` 中 `if-nez v0, :oreki_sa_early` 的分支方向是**对的**：
`hasInfinity()` 为真 → 跳到 `:oreki_sa_early` → 调 `enableEarly()`；
`hasInfinity()` 为假 → 落到 Doomed/eternities 检查 → 走 IP 倍率 / interval / ID1 那条老路。

**但这是反的！** HEAD 版本的语义是：
```
    invoke-static {}, OrekiAuto;->hasInfinity()Z
    move-result v0
    # 首次无限之前：全部保持原版（开局仍全手动）
    if-eqz v0, :oreki_sa_ret      # 没有无限过 → 直接返回
    ... 老逻辑（IP 倍率 / interval / ID1）...
```
即 **hasInfinity 为真 → 执行老逻辑**（这是 AU5/AU6/AU7 的窗口：已无限过、还没永恒）。

本轮把这一行改成了 `if-nez v0, :oreki_sa_early`，
于是 **hasInfinity 为真（已无限过）→ 跳到 `:oreki_sa_early` → 只调 `enableEarly()` → 直接 return**，
**把 AU5/IP 倍率、AU6/interval 自动升级、AU7/ID1 自动购买整条链全部跳过了**。

而 hasInfinity 为假（还没无限过）→ 落到 `isDoomed` 检查 → `eternitiesZero` 检查
→ 调 `enableIpMultAutobuyer()` / `upgradeCrunchInterval()` / `tryBuyId1()` —— 这三个方法
在还没无限过时基本都无效（`upgradeCrunchInterval` 检查 `player.brake`；`tryBuyId1` 检查
`player.brake` + ID1 的 1e1100 门槛），但 `enableIpMultAutobuyer` 会把 IP 倍率自动购买器打开。

**这是第二个致命回归：AU5/AU6/AU7 三个已上线的功能被本轮改动整体废掉。**

正确结构应是**两个分支并存**，而不是互斥：

```
    invoke-static {}, OrekiAuto;->hasInfinity()Z
    move-result v0
    if-nez v0, :oreki_sa_early     # 还没无限过 → 开局自动化分支
    ... 老逻辑（AU5/AU6/AU7）...   # 已无限过 → 原有链
    goto :oreki_sa_ret
    :oreki_sa_early
    invoke-static {}, OrekiStageAuto;->enableEarly()V
    :oreki_sa_ret
```

注意 `hasInfinity()` 为假时要跳到 `:oreki_sa_early`，为真时要走老逻辑 —— 条件必须反过来。

## 缺陷 5 · `orekiEarly()` 与 `hasInfinity()` 的关系是「否命题」，不是「互补」

`hasInfinity()` = `infinities > 0`，`orekiEarly()` = `!hasInfinity()` = `infinities == 0`。
两者**严格互补**，即 `hasInfinity() || orekiEarly()` 恒为 true。

这意味着：**只要把 `orekiEarly()` 作为额外的放行条件接进 `g()`，那个 `g()` 就永远返回 true**
（除非被 Pelle 禁用拦下）。AU2/AU3/AU4 的解锁门会被完全打开。

这是**期望行为**（Mod 定制：开局就允许自动化），但必须意识到它的后果：
- 维度提升（DimBoost） autobuyer 在开局会立刻尝试购买维度提升 → 触发 softReset → **清零反物质**。
- 星系（Galaxy） autobuyer 同理。
- Android 端**没有 Web 的 AD4「首次永恒前保留反物质」**（`rg "保留反物质|AD4" scripts/` 无命中）。

所以在 Android 上，**一旦把 DimBoost/Galaxy autobuyer 在开局打开，反物质会被反复清零，
永远攒不到 1.797e308，`canCrunch` 永远 false → 永远无法完成首次无限。**

这是比「判定写反」更根本的机制缺口，必须在合批修复里处理（见 `docs/` 的修复设计）。

## 缺陷 6 · 存档兼容性核查（结论：当前改动不破坏存档）

- `isActive` 是 `AutobuyerState` 的**既有**字段（`private isActive:Z`），本来就参与存档序列化。
  `enableEarly()` 只是改它的值，不新增字段 → **不破坏老存档**。
- `OrekiAuto.orekiEarly()` 是**静态方法**，不写任何字段 → 不污染存档。
- `enableEarly()` 若要加「玩家关闭过」的持久标志，**不能**加到 `Player` / `Player$Auto`
  （会进 `player.json`），必须放 `SharedPreferences`。

## 与 Web 端的对齐结论（机制等价）

Web 端 `src/core/oreki-early-automation.js` + `src/game.js:tryOrekiEarlyRoutine()` 的做法是
**直接调原版购买函数**（`buyMaxDimension` / `buyMaxTickSpeed` / `requestDimensionBoost` /
`requestGalaxyReset` / `bigCrunchResetRequest`），**不是**去改 autobuyer 的 `g()` 解锁门。

Web 端靠 AD4（`src/core/oreki-keep-antimatter.js`）保证「首次永恒前维度提升/星系重置不清零反物质」。

Android 端要机制等价，需要：
1. 开局自动化能真正买到维度（改 g() 门 或 直调购买路径）；
2. 开局阶段有「保留反物质」等价物（Android 目前没有）；
3. 大坍缩在开局能触发（Web 端是 `bigCrunchResetRequest(true)` 手动触发，因为
   原版 interval 150000ms 太久）。

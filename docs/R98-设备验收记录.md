## FAIL：§7.1 顶部永恒点数未隐藏

截图 `android/reports/R98/06-1inf-gated.png`（1080×2400）实测仍显示：

- 顶部 **「你拥有 0 永恒点数。」** ← 应隐藏
- 底部动作行 **「永恒」** 圆按钮 ← 无限阶段不应出现
- 底部页签 **「时间」** ← 永恒层级页签，不应出现

### 根因（可信推断，有静态依据）

`work/base_decoded_321/smali_classes2/kajfosz/antimatterdimensions/MainActivity.smali:34923`：

```smali
iget-object v2, v0, Lkajfosz/antimatterdimensions/MainActivity;->t2:Landroid/widget/TextView;
invoke-static {}, Lf82;->j()Z
move-result v5
invoke-static {v2, v5}, Lq51;->E(Landroid/view/View;Z)V
```

原版**每帧**用 `f82.j()` 重设 `t2` 可见性。而 `f82.j()` 只读
`Player.eternities > 0 || f82.p()`，该字段在本版本可能被初始化为非零
（R94 实测新档读到 11）。因此：

1. MOD 侧一次性把 `t2` 置 `GONE`（`narrowed=1`）；
2. 同一帧内原版随后按 `j()=true` 把它重新显示；
3. 因为阶段未变化、脏标记已清，MOD 不再重试 → 最终停在"显示"。

即 R98 §1 点名的**「原版缓存/View 更新顺序错误」**：MOD 写入早于原版 UI 通道，
且只在事件时写一次，无法压过原版逐帧重设。

### 修复方向（下一轮）

门控必须在**主线程、原版 UI 通道之后**每帧对账（仅当目标 View 当前可见性错误时写入），
而不是只在阶段变化时写一次。需同时覆盖：

- 顶部永恒点数 `t2` / `0x7f0a05c6`
- 永恒统计块 `i6` / `0x7f0a05c8`
- 现实统计块 `o6` / `0x7f0a0e6a`
- 永恒页签 `jp4.p:Lll2;`
- 「时间」等永恒层级子页签、底部「永恒」动作按钮

`origE=unknown` 还需单独排查：`f82` 反射未解析成功，导致无法比对原版判据，
诊断日志失真（`eternitiesField=0` 也可能是读取失败被误记成 0）。

## 1. 顶部永恒点数：FAIL → PASS

**真实根因（已验证事实）**

# 追加记录：R98 第 48 轮（`f82` 反射根因修复 —— origE/origR 不再 unknown）

## 1. 真实根因（已验证事实，非推断）

原实现：
```kotlin
stagePredicateClassCache = cls("kajfosz.antimatterdimensions.f82")
```
两处同时出错：

1. **包名错**。`work/base_decoded_321/smali/f82.smali` 首行为
   `.class public abstract Lf82;` —— 该类位于**默认包**，类名就是 `f82`，
   不存在 `kajfosz.antimatterdimensions.f82`。
2. **短名机制被绕过**。构建生成的 `OrekiBaselineBindings.className()`：
   ```kotlin
   fun className(name: String): String =
       if (name.contains('.')) name else normalize(confirmed[name] ?: name)
   ```
   含 `.` 的名称**原样返回**，不会走版本映射。因此传全限定名既拿不到跨版本映射，
   又指向一个不存在的类 → 100% `ClassNotFoundException`。

真机上长期出现的 `origE=unknown, origR=unknown` 正是这条路径，而不是"原版没有该方法"。

## 2. 修复

```kotlin
// 改传短名 "f82"，交给 className() 做版本映射
stagePredicateClassCache = cls("f82")
```

## 3. 实机验证（APK `508d0f041b7ca1295e7a064688c2df46720cb2449e0faa1f421fcded533aa2e5`）

| `152. 2.5e4EP+21TT.txt` | EP=2.48e4, bigE=115 | `GUI_GATE_CHANGED to=eternity … origE=true, origR=false` | 反弹**已通** |

# 追加记录：R98 第 65 轮（§7.5 步骤 5 的触发条件与机制 —— 静态判定完成）

## 1. 目标

分支结构与归属判定完整读通，确定步骤 5 的**真实可测路径**。

## 2. `applyCrunchPolicy()` 分支结构（`OrekiStageAuto.kt` 1380–1470）

| 顺序 | 条件 | 行为 |
|---|---|---|
| 1 | `!decision.allow` | `writeManagedCrunchInterval(crunch, pauseSeconds, restoreDue, "pause:"+reason)`（`eternity-grow` 用 30 秒，其余 3600 秒） |
| 2 | `pauseReason != null` | `writeManagedCrunchInterval(crunch, resumeInterval, restoreDue, "resume:"+reason)` |
| 3 | `eternitiesZero() && crunchMode == MODE_TIME` | 一次性（`targetIntervalInitialized` 闩锁）写 5 秒，然后 `return` |
| 4 | `!isBroken()` | **每帧** `writeManagedCrunchInterval(crunch, 60.0, restoreDue, "pre-break")` |
| 5 | `crunchMode == MODE_TIME` | 原样放手 |
| 6 | `breakUpgradeBits` 为空 | 每帧写 1.0 秒（`break-empty`） |
| 7 | 其余（终局） | 一次性 `xHighest` 校准（`crunchPolicyInitialized` 闩锁），不改 mode |

常量：`PRE_BREAK_CRUNCH_SECONDS = 60.0`、`CRUNCH_PAUSE_SECONDS = 3600.0`、
`ETERNITY_GROW_CRUNCH_SECONDS = 30.0`、`POST_BREAK_RESUME_SECONDS = 5.0`。

## 3. 归属判定（`OrekiPlayerIntent`）

```kotlin
fun refreshCrunchInterval(current: Double, target: Double) {
    if (!current.isFinite()) return
    if (crunchIntervalWritten.isNaN()) { crunchIntervalWritten = current; return }   // 首次采纳基线
    if (sameInterval(current, crunchIntervalWritten) || sameInterval(current, target)) return
    if (!crunchIntervalPlayerOwned) {
        crunchIntervalPlayerOwned = true
        Log.i(TAG, "player changed crunch interval current=… modWrote=… target=… -> MOD stops rewriting until next strategy tick")
    }
}
fun mayRewriteCrunchInterval(): Boolean = !crunchIntervalPlayerOwned
```

`OrekiAutobuyerBeat`：
- `deferRestoreAt(now, intervalSec)`：**只登记一次**（`pendingRestoreAtMs != 0` 即返回 false），
  `gapMs = clamp(intervalSec,1..60) × 1000`，日志 `beat defer #N at=…ms gapMs=… dueAt=…ms`。
- `consumeRestoreDueAt(now)`：到点才返 true 且**只返一次**，日志 `beat due #N … waitedMs=…`。

# 追加记录：R98 第 71 轮（§7.5 步骤 5 为何在此存档上无法触发 —— 分支 3 早退根因）

## 1. 现象

第 66 轮点「时间间隔减少 40%」后间隔 32.400 → 0.327 秒，画面立即显示新值，
但**没有任何** `player changed crunch interval` 日志。第 71 轮重启后重复该操作，同样无日志。

## 2. 定位

`applyCrunchPolicy()` 的调用点在 `OrekiStageAuto.kt:281`，**每帧无条件执行**
（排在 `if (!GameApi.hasInfinity())` 早退之前）。因此不是"没被调用"。

分支顺序（第 65 轮已列）中**第 3 条**是关键：

```kotlin
if (OrekiStageAuto.eternitiesZero() && GameApi.crunchMode(crunch) == MODE_TIME) {
    if (!targetIntervalInitialized) {
        targetIntervalInitialized = true
        writeManagedCrunchInterval(crunch, POST_BREAK_RESUME_SECONDS, restoreDue, "eternity-zero")
        Log.i(TAG_AU4C, "policy -> interval=5s (target-driven, once)")
    }
    return          // ← 闩锁已置位后，此后每帧在此直接返回
}
```

启动日志证实：
```
03:59:30.320 OREKI_PLAYER_INTENT: crunch interval baseline adopted current=1.0
03:59:30.320 OREKI_AU4C: managed interval 1.0 -> 60.0 (pre-break)
03:59:30.342 OREKI_AU4C: managed interval 60.0 -> 5.0 (eternity-zero)
03:59:30.342 OREKI_AU4C: policy -> interval=5s (target-driven, once)
```

**结论（根因）**：`eternitiesZero()==true` 且 `crunchMode==MODE_TIME` 时，
`targetIntervalInitialized` 一次性写 5 秒后**永久早退**，
`writeManagedCrunchInterval` 不再被调用 ⇒ `OrekiPlayerIntent.refreshCrunchInterval`
不再被调用 ⇒ 玩家改间隔时**不会**产生归属判定日志，也**不会**被策略抢写。

## 3. 这意味着什么

- 在该状态下（首次永恒前的 TIME 模式），**玩家改间隔完全自由、策略零干预**——
  这本身符合 §5.3「不得在下一帧立即抢写」的最强形式（根本不写）。
- 因此该存档**无法**演示"改值 → 下一 tick 恢复"的时序；
  步骤 5 必须在 **`crunchMode != MODE_TIME` 且未 break** 的状态下测。

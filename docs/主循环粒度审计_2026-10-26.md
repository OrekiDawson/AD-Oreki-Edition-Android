**关键结构事实（[静态]）**：整段是**线性单趟**，每个业务入口只出现 1 次
（上表 `x1`），函数体内**没有对业务逻辑的循环**。
→ 一次 `a.f` 调用 = **一次**生产累积 + **一次**采购/晋升判定。

## 2. 分类表：连续 / 离散 / 帧级

判据：**签名里有没有 delta**。有 → 可按任意时长推进（连续）；没有 → 每次调用只决策一次（离散）。

| 机制 | 入口（`a.smali` 行） | 签名 | 类别 | 高 F 下的含义 |
|---|---|---|---|---|
| 反物质维度生产 | 13292 | `c(DZL…;)` **含 D** | **连续** | 可用 `pow` 折算长时段 |
| 无限维度生产 | 13252 | `h(DZL…;)` **含 D** | **连续** | 同上 |
| 时间维度生产 | 13208 | `d(DZL…;)` **含 D** | **连续** | 同上 |
| 复制器 | 13786 | `k(DDL…;)` **含 DD** | **连续** | 同上 |
| Ra 宠物 / momentum / Laitela | 11020 → `a.d(DZ)` | **含 D** | **连续**（但见 §3.2 的实测） | 与 F 无关（上轮实测） |
| 记录累加 | 11039 → `a.t(DD)` | 含 DD | **连续** | 现实/游戏两路 |
| Enslaved 时间储存 | 11483 `Enslaved.C(D)` | 含 D | **连续** | 按墙钟 |
| **自动购买器** | 13610 / 13625 / 13640 / 13644 | **无 delta**（`G()`、`E()`、`j()`、`B()`） | **离散** | **每帧最多一遍** |
| **大坍缩判定** | 14061 `prestige/e->l()` | **无 delta** | **离散** | 每帧最多一次 |
| **永恒判定** | 14064 `prestige/c->f()` | **无 delta** | **离散** | 每帧最多一次 |
| **现实判定** | 14071 `prestige/f->f()` | **无 delta** | **离散** | 每帧最多一次 |
| 黑洞相位 | 未定位（见 §5） | — | **[未验证]** | — |
| Glyph 效果/自动 | 12135 / 12142 / 14154 / 14166 | 多为无 delta | 混合 | 效果本身是纯函数，不影响累积 |
| Automator | 14397 `H(DL…)` | **含 D** | 连续/离散混合 | 未细分 |

**结论（[静态]）**：**生产是连续的，采购与晋升是离散的**，二者在同一帧里各执行一次。
这是一条**结构性的粒度上限**，与 Web 的观察方向一致，但**成因不同**（见 §6）。

## 3. 高 F 下是否存在决策粒度瓶颈

### 3.1 结构性判断（[推断]，证据充分但未运行验证）

设 F=10000、屏幕 60 fps、游戏速度因子 s：
一帧现实 16.7 ms → 游戏时间 `diff = 16.7 × s × 10000`。
以 s=1 计，一帧 = **167 000 ms ≈ 46 小时**游戏时间，
但这一帧内：自动购买器只跑 **1 遍**，大坍缩/永恒/现实各只判 **1 次**。

于是产生两类损失：
1. **采购损失**：维度等级与 Tickspeed 升级的购买次数被限制在「每帧一遍」，
   而反物质产量已按 46 小时累积 → 产量远超消费能力，实际进度落后于理论。
2. **晋升损失**：即使一帧内早已满足大坍缩/永恒条件，也只能在**这一帧结束时**触发一次，
   且触发后若立刻进入下一阶段，之前累积的「超出量」不折算成多次晋升。

### 3.2 但有一个已实测的反例需要警惕

上轮实测：Ra 宠物记忆增速**与 F 完全无关**（F=1 vs 10000 比值 1.0008）。
说明 **`a.d(DZ)` 拿到的 delta 不含 F**——即并非所有「含 delta 的入口」都吃 F。
因此不能从「签名含 D」直接推出「吃 F」。分类表里「连续」= 可折算长时段，
**不等于** 会被 F 放大。

### 3.3 一个可能的硬上限（[未验证]，高优先级）

`a.smali:10987` 调用 `tz->k(DDD)`（三分支 clamp），实参里出现落点
`a.smali:10985 const-wide v34, 0x4174997000000000 # 2.16E7`（= 21,600,000）。
若这个 clamp 作用于**游戏增量**，则单帧游戏时间被**硬截断在上限**，
超过某个 F 之后**再加倍率也不会有任何收益**。
**但这需要确认被 clamp 的到底是 `realDiff` 还是 `diff`** —— 本轮**未验证**，
不做结论。这是本轮最值得先测的一个点：它决定「加 F 是否还有意义」。

### 3.4 触发条件小结

| 条件 | 是否会放大粒度损失 |
|---|---|
| F 高 + 帧率低（后台、卡顿、省电） | **显著放大**（一帧覆盖更长游戏时间） |
| F 高但处于极早期（产量低） | 影响小（一帧内本就买不起几个） |
| 已买入 bulk-buy / max-buy | 影响减小（一次调用可买多个），但仍有上限 |
| 晋升后立即进入下一层 | 每次只晋升一层，超量作废 |

## 4. 重复执行的风险清单（微步设计必须避开）

| 机制 | 若被重复执行会怎样 | 依据 |
|---|---|---|
| 大坍缩 / 永恒 / 现实判定 | **重复晋升**：同一帧内多次重置，奖励按次给，进度跳跃 | `prestige/{e,c,f}` 的 `l()/f()` 是「满足即执行」 |
| 自动购买器 | 购买顺序变化、可能买到本不该解锁的项 | 无 delta，纯决策 |
| Enslaved 时间储存 | 重复计入现实时间 → 储存翻倍 | `Enslaved.C(D)` 含 D，若外层重复调用会重复累加 |
| 记录累加 `a.t(DD)` | `realTime*/time*` 翻倍 | 同上 |
| 成就检查 | 提前解锁（多数幂等，但时序类成就可能误判） | 未逐一核 |
| 黑洞相位 | 相位跳变、额外激活 | **[未验证]** |
| Ra / Laitela | 上轮实测其 delta 不含 F；若外层微步重复调用，会**按微步数翻倍** | 反例警示：不能因为「它不吃 F」就安全地重复调用 |

> 核心风险：**微步必须只重跑「纯累积」部分**，绝不能重跑任何「读状态→写状态」的决策函数。

## 6. 与 Web 的对照（只对齐口径，不套实现）

| 维度 | Web（据其源码） | Android（本轮） | 可比性 |
|---|---|---|---|
| 帧驱动 | 固定 `updateRate` 间隔 + `gameLoop(passDiff)` | 协程 `Game$gameTick$1` → `a.f` | **口径可比**（都按帧） |
| 帧内业务逻辑 | 线性一趟 | 线性一趟（4,480 行，各入口 x1） | ✅ 同构 |
| 采购/晋升 | 每帧一次 | 每帧一次 | ✅ 同构 |
| delta 含义 | `realDiff` 已含 F（Web 特有） | `realDiff` 纯墙钟，F 在 `diff` | ❌ **不可直接套用** |
| 特有路径 | R/a memory 等 sqrt(F) | 实测无 | ❌ 不可比 |
| 帧率假设 | 60 fps（注释明确） | **未取证**（Compose 协程调度，非固定 60） | ⚠️ 需实测 |

**可直接比较的指标**：每帧业务入口调用次数、每帧采购尝试次数、晋升判定次数、
「一帧覆盖的游戏时间 / 该帧实际完成的采购次数」比值。
**不可比较的指标**：任何以 Web `realDiff` 语义写出的公式；任何假设 60 fps 的吞吐估算。

## 7. 限定微步方案（Android 专属设计，不实现）

### 7.1 目标
在**不改变任何决策函数调用频率**的前提下，让「连续累积类」机制按子步推进，
使高 F 下产量与消费能力对齐；并对每帧计算量设硬上限。

### 7.2 白名单（只允许细分这些）
依据 §2 分类表，仅纳入「签名含 delta 且不读写决策状态」的入口：

| 允许 | 依据 |
|---|---|
| `dimension/antimatter/a->c(D…)` | 纯累积（产量） |
| `dimension/infinity/a->h(D…)` | 纯累积 |
| `dimension/time/a->d(D…)` | 纯累积 |
| `infinity/replicanti/b->k(DD…)` | 纯累积 |

**必须先做前置验证**：这三个 `a->c/h/d` 内部是否**顺带**触发了购买或成就
（若触发，则不能纳入白名单）。本轮**未逐行核实**，标 **[未验证]**。

### 7.3 黑名单（绝不可重复执行）
`prestige/{e,c,f}` 的判定、所有 `autobuyer/*`、`Enslaved.C(D)`、`a.t(DD)`（记录）、
`a.d(DZ)`（Ra/Laitela）、成就检查、UI 刷新、黑洞相位。

### 7.4 子步数控制
```
k = clamp(floor(diff / TARGET_STEP), 1, MAX_STEPS)
每步 dt = diff / k
预算：MAX_STEPS 由「单帧计算时间上限」反推（不按 F 线性放大）
超预算时退回 k=1（即当前行为），并记录一次「降级」
```
- `TARGET_STEP` 取「一次采购能消化掉的游戏时间」量级（需实测标定，见 §8）。
- `MAX_STEPS` 必须**与 F 解耦**：否则 F 越大越卡，收益被 CPU 吞掉。
- 只在 `dt > TARGET_STEP` 时启用；低 F 下行为与现在**完全一致**（零回归面）。

### 7.5 边界处理
| 场景 | 方案 |
|---|---|
| 超大 delta（休眠恢复） | 先走现有 `clamp`，再按 §7.4 分步；不绕过 clamp |
| 离线结算 | **本期不动**（离线已有自己的 tick 循环，改动风险高） |
| 暂停/恢复 | 恢复首帧不分步（避免一次性补算），只按当前 delta |
| 异常中断 | 子步必须幂等；任一步抛异常 → 中止剩余子步并保留已累积值 |
| UI | 子步内不刷新 UI，只在帧末刷新一次 |

### 7.6 收益 / 风险 / 可行性

| 项 | 评估 |
|---|---|
| 预期收益（[推断]） | 高 F 下产量与采购对齐；早期「首个无限」可能显著加快。**量级未测** |
| 重复奖励风险 | 低（白名单只含累积函数）——**前提是 §7.2 的前置验证通过** |
| 语义风险 | 中：若某 `a->c/h/d` 内部暗含一次性事件（成就/解锁），分步会**多次触发** |
| 性能风险 | 中：`MAX_STEPS` 与帧预算不匹配会造成掉帧，反而变慢 |
| 可行性 | **中**：架构清晰（单帧线性），但需先完成 §5 的三个未验证项 |

## 10. 结论（一句话版）

Android 存在与 Web **同构但成因不同**的决策粒度上限：**生产按 delta 连续累积，采购与晋升每帧一次**；
是否造成真实进度损失**尚未实测**，且被两个未知量左右——`tz->k` 的 clamp 对象、自动购买器的单帧购买力。
微步方案技术上可行且回归面可控（只对白名单函数分步），但**必须先把白名单三项的内部副作用核实清楚**，
否则会把一次性事件变成多次触发。

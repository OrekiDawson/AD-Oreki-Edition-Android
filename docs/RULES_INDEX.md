**禁止**在本文件里复述规则内容。复述会立刻产生第二个源，两边不一致时无人能判断哪个有效。

### 1.3 新增一条长期规则的动作顺序

1. 分类：判断属于全局 / 项目 / 任务三层中的哪一层
2. 定级：按第 3 节分到 P0~P6
3. 查重：在第 6 节清单里搜同类规则，有则合并，不新开
4. 查冲突：与高优先级规则是否矛盾（第 7 节）
5. 写入正文：写进对应落点，编号沿用十进制层级
6. 更新索引：在本文第 6 节补一行
7. 提交核验：中文 commit → Push → 远端核验

**不得跳过 3、4 直接追加**。这是本次重组要终止的行为模式。

## 2. 优先级定义

### 2.1 P0 安全、权限与用户授权

最高优先级，任何项目、任何 Agent、任何效率优化都不得违反。含：用户明确授权边界；禁止未授权部署、发布与不可逆操作；Git 数据保护与危险操作禁令；文件、密钥、账号与敏感数据保护；杀毒软件与系统安全；设备、AVD 与真机操作限制；保护其他 Agent 的未提交工作。

### 2.2 P1 真实性、证据与时间

含：禁止编造执行结果、测试结果与完成状态；严格区分【实测】【读码】【推断】【未知】；当前时间必须来自真实系统时钟；中国大陆默认北京时间；Agent 间机器时间用 ISO 8601；文件与面向用户输出用可读自然时间；禁止模型推测补造时间；重要结论保留可追溯证据。

### 2.3 P2 任务责任与可追溯性

含：正式任务须有独立任务单；须写明创建者 / 负责 / 实际执行者 Agent ID；任务单禁第一人称；状态、交付物与验收结果明确；建单后先提交、Push、核验远端再分派；不得覆盖在途任务与他人未提交修改；创建 / 接收 / 开始 / 完成 / 验收须区分。

### 2.4 P3 多 Agent 协作效率

含：控制单回合时长；长命令、构建与批量操作拆分；按 busy / queueBusy 动态派发；避免向忙态 Agent 堆任务；降低无意义重复上报；记录消息发送、入队、接收、确认、执行、完成时间；避免争抢同一资源；只优化有证据的瓶颈，不擅自重构平台底层通信。

### 2.5 P4 开发执行与资源管理

含：快速迭代；优先最小有效改动与真实测试；合理使用专项 Agent；控制并行任务、内存、构建与模拟器资源；避免无意义重复构建；先查工作区与在途任务；保护硬链接文件；使用可靠的构建、签名与测试流程。

### 2.6 P5 项目功能与业务要求

仅本项目（AD: Oreki Edition）：双端功能与进度等价；默认 10000 倍速；180 分钟内完成真正终局；智能自动购买器统一调度；用户配置的自动操作间隔不得绕过；教程唯一正文数据源；教程全中文化；原版导航结构保持一致；真实新档端到端测试不得伪造。

**其他项目按各自目标单独维护，不将 AD 专属要求强加给无关项目。**

### 2.7 P6 文档、报告与交付规范

含：四仓库 README 维护；README 与真实代码一致；Linux / macOS 使用说明；中文 Git 提交信息；任务单、执行报告与交付文档格式；APK、构建产物与文件交付要求；文件命名与目录规范。

6. **记忆文件不能代替实际生效的 Agent 指令**

4. 同级冲突时，优先采用更具体且适用范围更明确的规则

7. 涉及用户授权范围变化时，必须取得用户明确授权
8. 无法确定如何处理时，暂停冲突部分，不擅自采用风险更高的解释

### 7.2 与 AGENTS.md §1 的关系

`AGENTS.md §1` 已规定「用户当轮指令 > 本文件 > 玩法标准 > 平台 AGENTS > 历史报告」，并规定冲突时「识别 → 报告影响 → 由用户裁决，不得静默删除或弱化平台安全约束」。

本节的 P0~P6 是**同一原则的细化**，不是替代：§1 管「文件之间谁大」，本节管「同一文件内哪条优先」。两套同时生效，冲突时以更严格的一方为准。

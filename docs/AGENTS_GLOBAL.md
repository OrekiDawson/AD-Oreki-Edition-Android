## 2. 本文件是三处同一份文件（2026-10-29 用户要求，长期有效）

本文件同时存在于**三个位置**，且是**同一个文件的三个硬链接**（同一 inode，字节级实时一致）：

| 位置 | 路径 | 用途 |
|---|---|---|
| 工作区根（**权威源**） | `AD-Oreki-Unified/AGENTS.md` | 本机唯一编辑入口，所有修改在这里做 |
| Web 仓库内镜像 | `web/AD-Oreki-Edition/docs/AGENTS_GLOBAL.md` | 随 Web 仓库提交/推送，clone 后仍可读 |
| Android 仓库内镜像 | `android/AD_Oreki_Edition_Android/docs/AGENTS_GLOBAL.md` | 随 Android 仓库提交/推送，clone 后仍可读 |

**为什么这样做**（2026-10-29 之前的问题）：
两个平台仓库的 `AGENTS.md` 都写着「规则源 = 工作区根 `AGENTS.md` §6.2 / §7 / §6.1」，
但工作区根**不是 git 仓库**，那份文件从未进入任何 repo。于是任何人 clone 任一仓库后，
这些引用全是**悬空指针** —— 看得到「规则源」，却打不开规则本身。

**强制纪律**：

1. **只改工作区根那一份**。三处是硬链接，改任一处三处同时变化；但为保持入口唯一，
   约定只在 `AD-Oreki-Unified/AGENTS.md` 上编辑。
2. **不得用「另存为 / 新建同名文件」的方式替换镜像**。那会打断硬链接（inode 变化），
   造成三处内容分叉。要改内容就直接编辑原文件。
3. **不得让任一仓库的镜像变成普通副本**。每次涉及本文件的提交前，跑
   `python scripts/check_agents_sync.py` 校验三处 inode 一致 + SHA-256 一致。
4. 若校验失败（例如某次 `git checkout` 覆盖了镜像导致硬链接断裂），
   以工作区根为准，用 `python scripts/check_agents_sync.py --fix` 重建硬链接，再提交。
5. 两端平台 `AGENTS.md` 里指向本文件的相对引用统一写
   `docs/AGENTS_GLOBAL.md`（仓库内可点开），需要强调权威性时附注「权威源 = 工作区根 `AGENTS.md`」。

## 3. 核心目标与优先级（所有工作共同的衡量标准）

1. **第一优先级：缩短通关所需的现实时间。**
   以玩家现实时间内能否更快推进游戏阶段为首要标准；优先减少无意义等待、重复操作、
   低价值 grind 和不必要人工干预。评估自动化、数值、机制优化时，关注从当前进度到
   下一阶段再到通关的实际时间。**不因代码更接近原版、计算更精确或改动更复杂就认定更好。**
   无法直接测通关时间时，用有代表性的阶段推进速度、等待时间、操作次数与瓶颈变化作代理指标，
   并明确推断范围。
2. **第二优先级：爽玩体验。**
   更快获得有意义的成长反馈，减少挫败与无聊重复。优先改善真正影响体验的瓶颈
   （自动化不够聪明、等待逻辑不合理、重复操作多、关键反馈不清）。不把帧率、执行频率、
   倍率数字或功能数量当作体验改善。保留玩家主动选择的挑战、策略决策与有意义的阶段目标；
   多方案可行时选现实时间收益更高、操作更少、反馈更清楚且副作用更少的方案。
3. **第三优先级：跨端体验一致。**
   Web 与 Android 是同一游戏的两套实现：核心规则、数值语义、自动化行为与玩家预期应一致；
   **不要求源码结构、UI 布局、技术实现或平台 API 相同**。每个差异判定为真实缺陷 / 合理平台差异 /
   待确认问题；修一端时检查另一端同类问题与共享修复思路；不盲目移植代码。
   **宣称跨端一致必须给出两端各自的证据；单端通过 ≠ 双端验证。**
4. **第四优先级：敏捷开发与快速迭代。**
   短周期、可验证、可回滚；每轮优先解决一个最高价值问题；尽快形成最小可用修复并针对性验证；
   证据足以决策就行动，不做不改变方案的无限调查；不为重构而重构、不为指标制造无价值工作；
   高风险操作（存档、工作树、签名、发布产物）先保护现场再按可恢复步骤实施；
   有效改动做与风险相称的回归，通过后走对应平台既有发布规则。

### 3.1. 通关验收标准（用户 2026-10-29 重申，长期有效，**本节是验收口径的唯一源**）

- **唯一成功标准：真实新档**（清空 localStorage / 全新安装，不预置任何标记）**在 180 分钟现实时间内
  抵达真实终局**（`isGameEnd` / `endState >= 1`）。**Reality 不是终点**，必须继续推进天神 → Pelle → 终局。
- 默认加速 **10000×**；**消除所有时间墙**，但保留大部分手动玩法与有意义的阶段目标，做到**新手 0 门槛可通**。
- **双端所有挑战（普通 / 无限 / 永恒 …）必须「进入即完成」并有真实结算**：不得只翻状态位、
  不写完成数、不给奖励。
- **Web 与 Android 同时开发且行为等价一致**；Web 移动端适配必须用安卓模拟器 Chrome 实测真实页面。
- **不接受只有计划、审计报告、测试工具或「下轮再做」的交付**：每轮必须有可运行产物
  （Web 已部署、Android 已构建 APK）。
- **一次处理多个瓶颈**，不要串行等一个瓶颈收尾才动下一个。

## 4. 统一决策方法（每项候选改动逐条自问）

1. 能否缩短通关或阶段推进的现实时间？
2. 能否让玩家少等待、少重复操作、获得更好爽玩体验？
3. 是否保持两端核心行为一致？不一致的原因？
4. 能否用更小的改动达到同样效果？
5. 怎样用最少但足够有力的测试证明有效？
6. 是否有存档、进度、资源、自动化副作用或跨端回归风险？
7. 验证成功后，如何以最短安全路径进入下一轮？

不要求精确数字作答；结合证据合理判断，区分已证实 / 经验推断 / 待验证假设。

## 5. 收益评估与停止条件

- 优先处理：玩家影响大 × 现实时间收益高 × 验证成本低。
- 调查不再影响方案选择时，立即停止扩展调查。
- 无法证明玩家收益（含代理指标也无法判断）的改动，不做——不为改而改。
- 难以直接测量的收益，明确说明限制，选足以支持决策的最小测试。
- 修复显著增加风险或维护成本时，比较实际收益再定，不默认复杂方案更优。

## 6.1. 编程方法论：快速迭代闭环（2026-10-28 R5.3 用户确立，长期有效，**本节是方法论细则的唯一源**）

> 分工：§1~§5 定义「做什么、为什么」；本节定义「怎么做、做到什么程度才算交付」。
> 最高目标仍是 §3 的**真实通关收益**——能否缩短真实通关时间 / 减少操作与无意义等待 / 修复阻塞 /
> 防止已交付成果退化。没有明确收益的工作一律降优先级；**不为代码整洁、抽象完美或工具链统一做无收益重构**。

**每轮十步闭环**：
1. 读状态（交接文档、三仓库状态、未提交修改、当前发布版本、环境记录）
2. 选瓶颈（只选当前收益最高、范围明确的一项）
3. 快速定位（`rg`；Android 先走 REA，见 §6 与 Android §0-I）
4. 立可验证假设（当前行为 / 预期行为 / 可能根因 / 最小测试）
5. 先测后改（能复现就先记基线，不凭感觉改）
6. 最小修复（只改必要代码，不顺带重构无关模块）
7. 定向回归（先直接相关，再可能受影响的套件）
8. 验证真实交付（Android：Gradle 构建 + `oreki_test` 安装运行；Web：部署副本 + 线上核验）
9. 记录证据（命令、退出码、结果、提交状态、产物 SHA-256）
10. 交付并继续（更新交接记录 → 提交可验证成果 → 自动推进下一项）

**「完成调查」「脚本通过」「构建成功」都不等于交付**；按任务目标还须验证实际运行行为、部署状态与发布文件。

**测试范围按影响面选，不机械全跑**：纯函数→单元+边界；机制/计时→公式、边界、倍率切换、历史记录；
smali 改动→静态契约+AVD 实机；存档字段→旧档/导入/重置/缺字段/版本兼容；UI→真实页面、触控、滚动、
导航、横竖屏与多视口；跨端机制→两端可比的初始态/倍率/窗口；发布流程→失败退出码、旧产物保护、校验、回滚。
**代码未变可复用既有结果**，不为形式重复耗时验证；测试失败先定位原因，只修相关问题。

**工具分工**：REA（APK/smali/调用链/运行状态/补丁核验）、`rg`（文本搜索）、Gradle Wrapper 8.10.2

测部署副本 → 推送 Pages → 核验线上资源与部署文件一致。
**本地构建成功 ≠ 安装成功 ≠ 功能正确 ≠ 云端同步完成**，报告必须分环节记录真实结果。

**自动推进与必须暂停**：普通、可逆、范围明确的修复无需逐项确认，完成一项即交付并继续下一项。
必须暂停：真实支付/计费；真实玩家存档或不可逆数据操作；无法安全回滚的变更；明显改变挑战难度/平衡/进度规则
且目标不明；关键运行证据缺失且继续修改可能造成重大损害。被环境阻塞时先做不依赖它的工作，不让整轮停摆。

## 6.3. 代码搜索纪律：优先 ripgrep（2026-10-28 用户确立，长期有效，**本节是 rg 规则的唯一源**）

   `/c/Users/Oreki/scoop/shims/rg`）。不可用时先查 PATH，再按 `environment/测试环境记录.md` 记录的方式修复，
   **记录原因**，不得默默退回低效方式。
2. **默认用 rg 搜索**：本工作区源码、配置、脚本、测试、文档的文本检索一律先 `rg`。
   - `rg -n <pattern>` 定位行号；`rg -l <pattern>` 只列文件；`rg -c` 计数。
   - 常用排除：`-g '!work/**' -g '!build/**' -g '!node_modules/**' -g '!**/*.apk' -g '!upstream/**'`
     （`work/`、`build/`、`upstream/`、部署副本属于可重建或第三方内容，按需显式包含）。
   - 中文/多字节模式加 `-F`（字面量）或注意编码；`rg` 默认按 UTF-8，Windows 生成的 GBK 日志先转码。
3. **先定位再精读**：用 rg 找到文件与行段后，再用 Read 读取该区段；禁止为了找几个符号而整目录逐文件读取
   或使用 PowerShell 全盘 `Select-String` 扫描。
4. **不把 rg 当二进制分析器**：APK / DEX / ARSC / SQLite / `.odl` 日志等用专用手段

5. **rg 不能替代核验**：命中行只是线索，仍需源码调用链、smali/REA 取证与运行测试；

## 6.4. 充分利用 REA 反编译取证（2026-10-29 用户确立，长期有效，**本节是 REA 使用强度的唯一源**）

> 用户原话：「要充分利用 REA 反编译。」
> 与 Android `AGENTS.md §0-I`（REA 强制前置的流程细则）互补：§0-I 规定**什么时候必须跑**，
> 本节规定**跑完之后必须用到什么程度**。执行顺序、失败处理、证据记录仍以 §0-I 为准。

1. **REA 是取证工具，不是打卡工具**。跑过 `rea.sh doctor` 不等于用好了 REA。
   凡涉及 Android 侧以下判断，**必须**先取 REA 证据再下结论：
   混淆类名 / 方法签名 / 字段与常量取值 / 调用链与引用者数量 / 运行期行为 /
   某个分支是否真的存在。禁止只凭 `rg` 命中行、类名猜测或「看起来像」就改 smali。
2. **优先用 REA 解决「找不到、对不上、不敢改」三类问题**：
   - 找不到：原版类被 R8 混淆成 `a` / `qk4` / `n43` / `jw0` 这类短名，`rg` 搜语义名必然落空，
     用 `search-android-classes` 按语义名反查真实类名；
   - 对不上：搞不清 smali 里哪个方法对应源码语义时，用 `inspect-android-method` 拿反编译体比对；
   - 不敢改：改共享常量/字段前，用 REA 反查**引用者清单与数量**（例如某常量被 6 处引用、
     其中含其他子系统的 `<clinit>`，就足以否决一次改动）。
3. **结论必须可追溯到证据**：报告中引用 REA 的 `evidence_id` 与 `authority`
   （如 `shipped-artifact`、`confidence`），或贴出反编译体片段 + `文件:行号`。
   只写「已用 REA 确认」而不给证据标识的结论，按未取证处理。
4. **复用已有证据，不重复解包**：同一 APK / 同一方法已有 `evidence_id` 时优先复用；
   需要新证据时先说明为什么旧证据不足。避免每轮重新 `apktool d` 全量解包。
5. **REA 与 rg 互补，不互相替代**：`rg` 负责在已知路径上快速定位文本；
   REA 负责给出「混淆世界里的真实身份与调用关系」。两者结论冲突时以 REA 的
   反编译体 + 运行证据为准，并记录冲突原因。
6. **不是 Android 专属借口**：Web 侧遇到压缩/混淆产物（构建后的 bundle、部署站文件）时，
   同样优先用可复现的反编译/还原手段定位，而不是猜。

   `git worktree` 目录会各自检出一份**独立 inode** 的 `FACTS.md`，最容易误当成镜像去改：
   ```
   2026-10-31 实测：web/_wt_deploy/docs/FACTS.md  inode 844424933070372  ← 独立副本，非硬链接
                    web/AD-Oreki-Edition/docs/FACTS.md  inode 3940649674859546  ← 硬链接三处之一
   git worktree list  →  _wt_deploy (detached HEAD 6e90ede) / _wt_head (detached HEAD df6ef9d)
   ```
   在这些 worktree 里改 `FACTS.md` 会产生一条**分叉的历史**，且因为不在权威 inode 上，
   `check_agents_sync.py` 查不出来。**要改事实，先 `cd` 回工作区根。**
2. **什么必须写进去**（满足任一条即写）：
   - 同一个坑踩了**两次以上**，或排查耗时 **20 分钟以上**才搞清的机制；
   - 一旦被改回就会**静默返工**的根因（例如跳转极性、语言三处默认值、`pLog10(0)=0`）；
   - 环境硬事实（工具路径、不在 PATH 的命令、代理端口、AVD 名称）；
   - 原版机制的关键语义（含文件:行号），尤其是「看起来像 bug 其实是原版行为」的那类；
   - 已测出的**数值天花板**（再跑也不会涨的量），用来阻止「再多跑一会儿」式的无效优化。
3. **每条必须带证据等级**，四选一并写在行尾：`[实测]` / `[读码]` / `[推断]` / `[未知]`。
   **禁止**把 `[推断]` 写成 `[实测]`，也禁止省略等级。
4. **每条必须可追溯**：给出文件:行号、命令、或数据文件路径。写不出出处的「我记得」不算事实。
5. **推翻就改那一条**，不要在旁边追加新说法；两条并存会让后来的会话不知道该信哪个。
6. **只写长期有用的**：轮次状态、临时路径、一次性调试输出、待办清单**不写**（那些属于
   `handoff/` 与任务列表）。
7. **每轮收尾检查**：本轮如果产生了上面第 2 条列举的东西，`FACTS.md` 必须同步更新，
   否则视为「交付未完成」，与 §6.2 的文档纪律同级。
8. `FACTS.md` 与 `AGENTS.md` 冲突时，以 `AGENTS.md` 为准；`FACTS.md` 与**代码**冲突时，
   以代码为准，并回来改 `FACTS.md`。


## 19. 移动端适配：控件触控尺寸不得偏小（2026-10-30 用户确立，长期有效，**本节是触控尺寸的唯一源**）

> 用户原话：「移动端适配要注意控件大小，不要像选项内有些控件偏小」。

1. **判定基准（两条都要满足）**：
   - **绝对下限**：窄屏（`max-width: 620px`）下所有**可点元素**命中区不小于 **44 × 44 CSS px**
     （WCAG 2.5.5 / iOS HIG 下限；Android Material 建议 48dp ≈ 44 CSS px）；相邻可点元素间距 ≥ **8px**。
   - **相对一致（用户 2026-10-30 补充：「是和同页面其他按钮相比」）**：**同一页面内、同一层级的控件必须同高同宽基准**。
     不允许出现「主按钮 44、旁边同类按钮 25」这种参差。判定方法是把同页所有同类可点元素的
     高/宽列出来看分布：只允许 1~2 档（如主按钮 / 次级按钮），且档差不超过其自身高度的 20%。
     若某控件比同页其他按钮明显偏小，**以该页主按钮为基准**把它撑到同一档，而不是只满足 44px 就收工。
2. **覆盖范围**（不只按钮）：`button` / `.o-primary-btn` / 开关（toggle）/ 复选框 /
   下拉（`select`）/ 数字输入（`input[type=number]`）/ 加减按钮 / 页签 / 关闭叉 /
   自动购买器行内的「开启」与间隔输入。
3. **必须真的扩命中区**，不是只放大字号：用 `min-width` / `min-height` / `padding`
   把**可点区域**撑到 44px。文字可以不变大，但手指点到的地方必须够。
   若扩尺寸会撑破行宽，**先解决换行/自适应**（见 §19.4），不要靠缩小控件来省空间。
4. **不得用「整行变窄」的方式换空间**：窄屏下若一行放不下，正确做法是换行（`flex-wrap: wrap`）
   或改列布局，而不是把控件压到 44px 以下。
5. **验收方式（必须给数据，不许目测）**：在真机 / 模拟器视口（392×676 与 360×640 各一次）
   用 CDP 扫描可点元素的 `getBoundingClientRect()`，列出所有 `width < 44 || height < 44` 的项
   （类名 + 文本 + 实际尺寸），修完复扫到清单为空或只剩「有合理理由」的项。
   合理理由必须写进报告（例如「整行是一个大按钮，内部小元素不可单独点击」）。
6. **与既有规则的关系**：本节只管**尺寸**；「不横向溢出」由 `oreki.css` 的 620px 段负责；
   两者冲突时优先保证不溢出，其次保证 44px，最后才考虑美观。
7. 新增任何窄屏控件样式时，必须同时给出**该控件的实测尺寸**；没测过的写「未验证」。

### 20.1 目标优先级不得漂移（原 R20）

**最高优先级始终是：新存档从开始游戏到真正抵达游戏终局，现实耗时不超过 180 分钟**
（口径唯一源 = §3.1，本节不放宽）。

判断一项工作该不该做的**第一问**永远是「它让真终局更近还是更远」，而不是
「数字是否变好看」「是否更接近原版」「实现是否更优雅」。

- 「解锁 V / 进入 Ra / 进入莱特拉 / 解锁佩勒」**都不是通关**；唯一判据是原版终局状态（§3.1）。
- 若某轮所有工作都无法让真终局更近，**必须在报告里明说**，不得用「完成了若干优化」代替进展。

### 20.2 瓶颈价值排序（原 R21）

多个问题同时存在时，按**四个因素**综合排序（§5 已给前三个，本条补第 4）：

1. 对通关进度的**实际阻碍程度** —— 有证据地指出它是当前链路真正卡住的那一环。
2. 预计能**节省的现实时间** —— 换算到「距离 180 分钟还差多少」，不是抽象百分比。
3. 修改**风险与验证成本** —— 是否碰存档 / 签名 / 发布产物；要不要构建。
4. **对 Web / Android 的双端影响范围** —— 共享机制（影响面大）要先统一口径再动手。

**明令禁止**：「因为这个问题容易改，就先处理它」。容易修但不在关键路径上的，记入待办，
等关键路径清空后处理。

### 20.3 先证明瓶颈，再调整数值（原 R22）

修改**生产倍率、资源价格、解锁门槛、升级成本、进度条件**之前，**必须先确认实际瓶颈**。
这条是**前置条件**，不是建议（§4 第 1/5 问、§5 是其上层原则）。

- **「先证明」的标准**：有可复现的观测数据（字段真值 / 时间序列 / 阶段耗时），
  能指出卡在**哪一个判定**上，而不是「看起来慢」。
- **禁止用「降低门槛」掩盖其他系统故障**。典型错误模式：某自动化根本没跑起来
  （异常被 `catch` 吞掉、入口没接上），却去调低它本该产出的资源门槛 ——
  门槛降了故障还在，只是把问题推到下一环（R36 就踩过：EC 自动启动因 `ContinuationImpl(null)` NPE 被吞，
  表面看像资源不足）。
- **禁止引入**以下任一后果：数值溢出（超过 `Decimal.MAX_VALUE`）、软锁（再也推进不下去）、
  无法结算（挑战进了出不来 / 奖励发不出）、无法继续推进（下一个门槛永远达不到）。
- 调门槛必须**同步「显示值 + 判定分母」**（如 `v.js` 的 `requirement` 与 `progress` 分母），
  否则进度条永远到不了 1。

### 20.4 每项修改必须有可衡量收益（原 R23）

重要修改必须有**修改前后对比数据**（§5 说「无法证明收益则不做」，本条说**怎么证明**）：

| 指标 | 取法 | 适用 |
|---|---|---|
| 关键阶段解锁耗时 | 新档实测「首次达到 X」的时刻 | 机制 / 自动化 |
| 资源增长速度 | log10(资源)/秒，或每秒新增量级 | 产量 / 倍率 |
| 等待时间 | 两次有效操作之间的空转秒数 | 自动化 / 门槛 |
| 必要操作次数 | 玩家真正需要手动点击的次数 | UX / 自动化 |
| 挑战完成耗时 | 进入 → 结算的真实秒数 | 挑战链路 |
| 崩溃率与异常次数 | 控制台异常条数 / 每千帧 | 稳定性 |

- 没有可验证收益的改动，**不应仅凭主观感觉**判定为优化成功。
- 无法直接测量时，必须写明「用的是哪个代理指标、推断到哪」，**不得把代理指标写成直接结论**。
- 报告须区分 **【实测】/【读码】/【推断】/【未知】** 四级（与 §4 末段一致）。

### 20.5 双端共享玩法基准（原 R24）

原则见 §3 第 3 优先级与 `docs/SHARED_GAMEPLAY_STANDARD.md` §2，**本条只补执行要求**：

- **允许**平台差异：UI 布局、技术实现、平台 API、源码结构可以不同。
- **不允许**实质不一致：奖励、进度、挑战结果、终局条件不得「一端能过一端不能过」。
- 任何数值 / 门槛 / 倍率改动，**必须在同一轮或紧接着的一轮同步到另一端**，
  并在报告里列出「**另一端需同步的目标值**」清单。**单端通过 ≠ 双端验证。**
- 每处差异必须定性为**真实缺陷 / 合理平台差异 / 待确认问题**三类之一。

### 20.6 新存档优先，旧存档兼容（原 R25）

1. 核心进度测试**必须使用独立的新存档**（清空 `localStorage` / 全新安装 / 隔离 profile），
   并在报告写明「这是真实新档」。
2. **不得在用户真实存档上做实验**。实验一律走隔离存档、临时 profile、临时 AVD。
3. 修改**存档结构或核心逻辑**后，必须验证旧存档的**双向兼容**：
   能加载 → 不崩、不丢关键进度 → 保存后再次加载仍正常。
4. **不得为了通过测试而污染、覆盖或破坏已有存档。**

### 20.7 阶段性交付必须可运行（原 R26）

每个开发阶段都要留下**可以运行的成果**（§3.1 已禁「只有计划」，本条定交付**五项**）：

1. 实际修改了什么（文件 + 行号 + 关键 diff 要点）。
2. 哪些测试已通过（退出码 / 日志路径 / 字段真值）。
3. 哪些问题**仍未解决**（明确写出，不藏脚注）。
4. **当前版本如何运行与复现测试**（命令、端口、profile、AVD 名）。
5. 下一阶段最重要的阻塞。

不得以纯计划、纯审计、纯测试框架或「下一轮再实现」代替实际开发交付。

### 20.8 失败必须转化为可复用知识（原 R27）

重要失败必须记录**六项**（§18 定落地位置，本条定内容）：

1. 具体故障及**发生条件**（什么情况下触发）。
2. 已有证据（日志 / 字段值 / 复现步骤）。
3. 已尝试的修复方式。
4. 修复结果（有效 / 部分有效 / 无效）。
5. **已排除的错误方向**（最容易漏，但价值最高）。
6. 后续应避免的重复无效操作。

- 落地到 `FACTS.md` 对应章节 + 当轮 `handoff/` 报告。
- 被实测**推翻**的旧结论必须显式标注「已推翻」并写清推翻证据 ——
  否则下一轮会重新把它当事实（R36 发生过三次：EC9 资源墙、前置研究 151、`dilatedTime` 恒 0）。

### 20.9 自动化不得摧毁核心玩法（原 R28）

自动化只减少**重复劳动**，不删除游戏本身。

- **必须保留**原版核心逻辑：购买、挑战进入、挑战结算、奖励发放、重置、成就、阶段推进。
- **允许**自动化重复操作（买研究 / 买维度 / 反复进挑战）。
- **禁止**伪造进度、直接写结果字段（完成次数 / `completed` 位 / 解锁标志 / 终局状态）、
  绕过原始结算制造虚假通关（§3.1 已禁「只翻状态位」，本条给判定方法）。
- **判定标准**：把自动化关掉，手动操作仍能走到同一步。只能靠自动化写字段才推进 = 伪造。
- 「临时抬到门槛再还原」**只有**在能论证「真实完成那一刻该字段必然等于该值」、
  且结算后立即还原时才允许，并须在代码注释里写清论证
  （参考 `src/core/oreki-instant-challenges.js` 的 `maxAM` 处理）。

### 20.10 正式发布候选版本冻结（原 R29）

进入**正式构建与验收阶段**后必须**冻结源码**（§6.6 管「先 APK 后 push」的顺序，本条管一致性）。

- 冻结期内若仍有源码修改，必须依次：**重新构建 → 重跑受影响测试 → 重算 SHA-256 → 更新交付记录**。
- **不得**把修改前构建的 APK / Web 产物冒充修改后的版本。
- 冻结与解冻都要写进报告：冻结的 commit、解冻原因、重新验证结果。

### 20.11 交付必须有证据（原 R30）

**命令发送成功不等于任务完成**；「代码已提交」「APK 已构建」「已经解锁」都是中间状态，
不得冒充完整交付（§6.2.3 / §6.6 / §16 定要更新什么，本条定**最小证据形式**）：

| 行为 | 必须提供的证据 |
|---|---|
| Git commit | commit SHA + `git show --stat` 摘要 |
| Git push | push 输出、或 `git rev-list --count origin/main...HEAD` 为 0 |
| Pages 部署 | 线上 URL 实际打开结果（新闻关闭 / 侧栏 / 移动端布局 / 教程） |
| APK 构建 | 构建日志尾部 + 文件大小 + 版本号 + SHA-256 |
| 云端上传 | 上传后的远端列表或时间戳 |
| 设备安装 | `adb install` 输出 + 启动日志 |
| 实际运行测试 | 字段真值 / 截图 / 日志路径 |

### 20.12 超时必须升级处理（原 R31）

长时间无有效成果时，必须**主动**缩小范围、改执行方式或终止无效尝试；
**不得**无限等待 Agent、测试进程、构建任务或外部服务（§6.2.1 禁重复测试循环，本条定超时口径）。

超时后必须说明**五项**：① 已取得的成果（文件 / 数值 / 证据）；② 当前阻塞原因（卡在哪个判定）；
③ 已消耗墙钟时间；④ 是否存在可行替代路径；⑤ 主 Agent 接下来如何继续（谁接手、下一步做什么）。

## 21. 双端实现差异表：`WEB_ANDROID_DIFFERENCES.md`（2026-10-30 用户确立，长期有效，**本节是这套制度的唯一源**）

### 21.1 唯一文件与硬链接

- 唯一文件：`WEB_ANDROID_DIFFERENCES.md`，**同一 inode 三处硬链接**：
  1. 项目总根 `AD-Oreki-Unified/WEB_ANDROID_DIFFERENCES.md`

1. 每轮**开工先读**差异表，了解已有差异与未解决问题。
2. 每轮**收工按实际代码变更更新**差异表。

8. 每轮结束**核对三处仍是同一 inode**；`checkout / reset / pull / merge` 之后必须重查。

### 21.3 验证口径（不得放宽）

- 只有**真实运行证据**（AVD / 浏览器 / logcat / 采样 jsonl，且报告可查到命令与输出）才能标 `已验证`。

2. 全篇**没有终局判据**。真实判据 = **反物质 ≥ 1e1000**（`src/core/celestials/pelle/game-end.js`
   的 `OREKI_PELLE_END_TARGET_EXP`，`endState >= 1` 时 `isGameEnd` 置真）。

**可用性事实（写正文时必须照顾）**
- APK **不强制中文 locale**：系统语言为英文时底栏显示 `Dimensions`。正文写「点底栏『维度』」
  会让英文系统的新手点不到 ⇒ **关键页签一律中英双写**（「维度 / Dimensions」）。
- Android 教程**没有首次启动自动提示**，100% 靠玩家自己点，这是 §24.1 可发现性的真实风险点。

### 24.9 单一内容源（R40 定案，唯一实现路径）

**正文只允许存在于 `web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json`**，两端都从它派生：

- Web：`src/core/oreki-tutorial.js` 只做 `import` + 派生成渲染结构，**不得再写第二份正文**；
- Android：构建期由 `scripts/oreki_tutorial_gen.py` 读取该 JSON，生成
  `payload/assets/oreki_tutorial.txt`（每行 `FIELD|flag|text`），`TutorialActivity` 逐行
  `split("\\|", 3)` 解析。**不再把正文写进 smali `const-string`。**

为什么是 JSON 而不是解析 JS：Python 解析 JS 对象字面量只能靠正则，Web 侧字段一改就
**静默产出残缺教程**（能编过、能装上、界面空白或少章）；JSON 有 `json.load` 兜底，语法错在构建期直接报错。

为什么是 assets 而不是 smali：8~12 万汉字若逐段变 `const-string`，smali 会涨到 1.5~3 万行，
汇编变慢、易撞 65,535 常量池边界，且**内容错不会在汇编期暴露**。`assets/` 不走 aapt、不占资源 ID，
内容是数据不是代码。**代价**：仍然要重建 APK（内容在 APK 里）；不采用运行期下载，
因为现行教程页明确写「不需要联网」（`TutorialActivity.smali:141`），且运行期内容会与版本脱钩。

**构建期三层断言（缺一不可，实现见 `build_mod.py`）**
1. 一级：JSON 可解析、`schemaVersion` 匹配、`chapters` 非空、`id` 唯一且连续、十个字段类型正确；
2. 二级（发布构建）：`draft` 全为 `false`、`steps` 非空、`numbers[].src` 非空、无占位词、终局章含 `1e1000`；
3. 三级（回读比对）：重新读生成的 assets，按分隔符解回结构，与 JSON **逐字段比对**，不一致即中止构建。

字段契约与校验规则见 `web/AD-Oreki-Edition/docs/TUTORIAL_SCHEMA.md`。

**译名基准（写任何正文前必读）**：`web/AD-Oreki-Edition/docs/TUTORIAL_GLOSSARY.md`。
权威来源是 `android/AD_Oreki_Edition_Android/work/base_decoded/res/values-zh-rCN/strings.xml`
（原版 APK 官方简体中文字符串，4,516 行），表里每个词都标了官方出现次数，**0 次 = 禁止使用**。
三个已确认的高频错译：

| 错 | 对 | 官方次数 |
|---|---|---|
| 时间定理（TT） | **时间之理** | 75 次 / 错译 0 次 |
| 稀释时间（DT） | **膨胀时间** | 54 次 / 错译 0 次 |
| 大灾变（Armageddon） | **末日** | 30 次 / 错译 0 次 |

**英文只允许出现在两种位置**：中文后括注全称或缩写（`时间之理（TT）`）、
界面标签中英双写（`点击底栏「维度 / Dimensions」`，因 APK 不强制中文 locale）。
除此之外不许整句英文 —— 抓来的 wiki 攻略是英文的，只能用来理解机制，不能搬句子。

**Android 渲染硬约束**：目标篇幅下「一次 inflate 全部」不可用（约 500 个 TextView、单层线性布局
高 8~12 万 px）⇒ **必须一章一屏**：先解析章节列表，只渲染当前章，切章重建内容区。
必做项：分章 + 章节目录、字号三档、打开定位到当前阶段章。
明确放弃：表格渲染与行内加粗（在 smali 里手写 SpannableString 性价比极低，字段齐全优先于样式）。

**切换期铁律：不得造成信息倒退。** 单一内容源刚接入时，新章节绝大多数是 `draft: true`、`steps: []`，
而两端旧教程都已有内容（Web 7 章 39 小节、Android 10 章 2,665 字）。若直接切到新源，
玩家会从「有内容」掉到「只有 1 章有内容」。

所以：
1. 两端的旧正文**都不许删**——Web 保留为 `TUTORIAL_LEGACY_CHAPTERS` 导出；
   Android **旧 10 章的 smali `const-string` 原样留在原处**，生成器只产出新章节
   （不迁移旧文本，迁移留到正文补齐后再做，降低本轮风险）；
2. 渲染时排在新章节**之后**，加明显的分节标题「旧版教程（已停止维护，正在并入新版）」；
3. 删除时机由**团队负责人**决定，实现方不得自行加删除逻辑（默认行为是「总是写」）；
4. **验收口径（三条并列，缺一不可）**：
   - 玩家能读到的**章节数与可操作性**不得少于切换前；
   - 旧版段落必须显式声明「已停止维护」，**不得被当作达标的依据**；
   - **已知错误必须在旧版声明里点名**——天神解锁顺序写反、终局判据缺失、EC1~EC12 无内容。
     只写「可能过时」不够：新手照样会照着错的那段做。

第 4 条最后一项是本条最容易被糊过去的地方。「信息不倒退」若实现成「把已知错误原样保留并当正文」，
那是把倒退包装成达标。**旧内容本身是错的，这件事必须对玩家说出来。**

**发布门控：`OREKI_TUTORIAL_ALLOW_DRAFT`（两端必须同名，默认严格）**

设计原则是「失败即关闭」：**默认就严格，想带半成品构建必须显式放行**。
反过来（默认宽松、发布时记得加变量）一定会有人忘了加，然后带着 11 章空壳出厂。

| 取值 | 行为 | 用途 |
|---|---|---|
| **不设置（默认）** | `draft > 0` **中止构建**，打印 `draft=N/总章数` 与是哪几章 | 发布、合并、任何常规构建 |
| `=1` | 允许 `draft: true`，日志打印 `draft=N/总章数` 但不中止 | 仅本地迭代 / 需要装机验证渲染时 |

现在不设该变量跑构建**必然失败**（17 章里 11 章是 draft），这是正常的；
它能证明门控真的生效，也保证不会「以为写完了其实没写」。

**章节数一律不许硬编码。** 断言只能写成「`len(chapters)` 与 JSON 实际长度一致」+
「`id` 依次为 `ch00..ch(N-1)`」，N 从数组长度推导。
本文档写作当天这份 JSON 的章数已经变过三次（15 → 16 → 17），`draft:false` 数变过两次，
**任何写死的数字在下一次改章后都会立刻过期**。报告、文档里的完成度一律写「取现值命令」，不写死值：

```bash
python -c "import json,io;d=json.load(io.open('web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json',encoding='utf-8'));print(len(d['chapters']),[c['id'] for c in d['chapters'] if not c['draft']])"
```

## §25 子 Agent 数量与资源管理（长期强制规范，用户 2026-10-30 23:18 下达）

### 25.1 数量上限

**主 Agent 同时最多派出 3 个直接子 Agent。** 不得为追求并行数量无限增加；
**禁止子 Agent 嵌套派生其他 Agent**；不得用「多个间接任务」变相突破上限。

历史教训：R40 深夜一度同时挂着 **10 个**直接子 Agent（agent-a~agent-j），
导致同一模块被两人争写（`oreki-tutorial.js` 与 `validate_tutorial.mjs` 各被写过一版）、
重复检索同一批源码、以及 Android 侧两人同时改 `oreki_tutorial_gen.py`。
收敛到 3 个后反而推进更快 —— **并行度不等于吞吐量**。

### 25.2 固定三角色

| 角色 | 职责 |
|---|---|
| Agent A | Web 核心机制、自动购买器、路线择优 |
| Agent B | Android 功能开发、Smali、界面与双端同步 |
| Agent C | 独立测试、双端差异核对、教程与验收 |
| 主 Agent | 总体规划、协调、代码集成、构建、最终测试、GitHub 交付 |

可随任务调整分工，但**每个 Agent 必须有明确的交付目标与文件所有权**。

### 25.3 派发前六项检查

1. 当前是否已达 3 个上限；
2. 新任务是否有独立价值；
3. 是否与现有 Agent 重复；
4. 是否有明确的代码或测试交付物；
5. 是否有清晰的文件修改范围；
6. 是否值得消耗积分。

**主 Agent 能快速完成的，就不派 Agent。**

### 25.4 收回规则（必须按序执行，不许一刀切终止）

1. 盘点全部 Agent 的任务、进度、成果；
2. 优先保留**已产出有效代码或独立测试证据**的；
3. 识别重复研究、空转、无交付物的；
4. 安全收回多余任务，**先保护未提交成果**（提交 WIP 或留盘确认）；
5. 把有价值的工作整合进现有任务；
6. **不得因停止 Agent 而丢失已完成成果或未提交代码。**

### 25.5 资源协调

- 构建统一由主 Agent 协调，禁止并发 Gradle / apktool 构建；
- 同一 Android AVD 同一时刻只允许一个 Agent 操作；
- 重型构建与长时间实测错峰；
- 避免多个 Agent 重复检索同一批源码；
- Agent 超时或无有效产出，主 Agent 直接接管，不无限等待。

### 25.6 考核口径

不看 Agent 数量、派发次数、研究报告数量；只看**可集成代码、真实测试结果、可运行版本**。
每轮统计：直接子 Agent 数（≤3）、任务重复率（应力求为零）、实际代码交付、
独立测试证据（必须保留）、未提交成果（必须保护）、空转（及时收回）。

### 25.7 单文件单一 owner（由并发覆盖事故追加）

R40 深夜实测事故：`android/.../scripts/oreki_tutorial_gen.py` 在两小时内被两个 Agent
先后大改，后者的改写把前者 15 条 `selftest` 用例**整段覆盖丢失**。**这不报错**，
唯一迹象是「用例数从 15 变成别的数」——没人会去数。同一天 `oreki-tutorial.js` 与
`validate_tutorial.mjs` 也各被两人写过一版。

规范：**生成器、断言链、校验脚本这类「一次性大改就会覆盖同事成果」的文件，必须指定单一 owner。**
其他人要改，先在消息里申请。派发任务时把这一点写进文件所有权段，不要只说「不要碰某目录」。

## §26 断言设计规范

### 26.1 断言必须有会 raise 的入口

**反例（真实踩过）**：把旁路断言写成 `expect_fail(lambda: helper())`，而 `helper()`
只**返回问题清单**、不抛异常 —— 于是自测永远显示「没有被拦住」，断言形同不存在。
作者还以为自己测过了。

规范：
- 每个断言必须有一个**失败即抛异常或非零退出**的入口函数（`validate_xxx()`）。
- 「返回清单」的辅助函数（`_xxx_problems()`）**不得直接配 `expect_fail`**。
- 自测里每条断言至少一条**必须失败**的负例，且负例失败信息要能贴出来给人看。

### 26.2 断言的有效性不能依赖调用者记得怎么调

这与 `OREKI_TUTORIAL_STRICT` 默认关闭是同一类错误：守则写对了，但默认不生效等于没有守则。
**默认必须是 fail closed**（`OREKI_TUTORIAL_ALLOW_DRAFT` 默认严格，`=1` 才放行）。

### 26.3 只校验「内容的正确位置」不够，必须管住「内容可能出现的位置」

真实事故（两条，同一天）：
1. Web `src/core/oreki-tutorial.js:108` 写着「把 RM **灌注**给特蕾莎换**时间定理**」——
   一句话两个禁用译名。而译名断言只扫 JSON，完全看不见它。
2. Android `tutorial/TutorialProgress.smali:202` 写着「用**时间定理**点时间研究」——
   玩家每次进入永恒阶段都会在教程界面顶部看到，而它同样不在 JSON 里。

规范：新增「玩家可见但不在内容源里」的中文文案时，必须同时把它登记进扫描面
（Web：`validate_tutorial.mjs` 的 `PLAYER_VISIBLE_SOURCES`；Android：smali 全包旁路扫描）。
扫描面宁可宽——106 条全扫的代价可以忽略，漏一个文件的代价是不可见缺陷。

## §27 双端功能对等（Android 不得停滞的落地检查法）

用户长期要求：「Web 与 Android 必须同步推进功能开发，Android 不得沦为被动移植端」，
且明确「不允许用 UI 微调、文档更新、测试工具开发或单纯修复旧问题冒充功能开发进度」。

### 27.1 判定只有三态，禁止第四种写法

每个 Web 机制模块在 Android 侧的状态只允许三种记法：

| 记法 | 含义 | 证据要求 |
|---|---|---|
| **已有** | Android 有等价实现且在真实路径上生效 | 给出类/方法与调用点 |
| **确认缺失** | 调用链里确实没有这个动作 | **必须反证**：贴出该阶段 tick 的调用链原文，说明只有 A/B/C 动作 |
| **未知** | 搜过但无法判定 | 写明搜了什么、为什么判不了 |

**禁止**把 grep 0 命中写成「缺失」，也禁止把「有 4 处字符串提及」写成「已实现」。

### 27.2 为什么这条必须写死

同一天两个真实反例：
- `player.break` 在 Android 是 `Player.brake:Z`（setter `x0(Z)` @11107 / getter `m()Z` @10746）；
- `Pelle` 类在 DEX 里是 `.../pelle/c`，按原名 `inspect-android-method` 直接报
  `Exact class not found`，**不是 APK 缺类，是混淆改名**。

按 Web 的名字搜 Android，0 命中是常态。**「搜不到 ≠ 不存在」是这个项目最容易误判的一条。**

### 27.3 每轮必须做的一件事

每轮开发开始前读 `WEB_ANDROID_DIFFERENCES.md`，结束后把本轮涉及的机制差异写回去
（双端实现状态、数值差异、以及**Android 侧独立发现的事实**）。

后者尤其重要：R40 实测 Android 的 `prestige/f::o` L7445-7530 写的是中间值 `v15`，
**比 Web 版 `player.break = true` 更保守** —— 这是 Android 反向提供的信息，
不是移植产物。允许并鼓励 Android 先发现 Web 不知道的事，这才是「对等开发」而不是「跟随」。

### 27.4 覆盖差距必须量化，不能凭感觉

R40 实测基线（2026-10-30）：Web 自动化相关模块 **12 个 / 2,962 行**，
Android `oreki` 包机制类 **2 个 / 1,834 行**；`replicanti` / `eternityChall` /
`instantChallenge` / `sacrifice` 在 Android oreki 包内 **0 提及**。
细节见 `FACTS.md C.34`。

后续每轮用同一组命令复测（`ls src/core/oreki-*`、`grep -ril` 限定 oreki 包），
把数字写进差异表，而不是写「大致对齐」。

## §28 模拟器控制权：一台模拟器、一个控制者、主 Agent 自主启停、子 Agent 严格受限（用户 2026-10-31 11:25 补充令修订，**本节是唯一源**）

> **修订说明（2026-10-31 11:25）**：本节原为 11:02 版本，要求「主 Agent 启动模拟器也必须持有编号授权」。
> 该要求已被用户明确**废止**。现行规则：**主 Agent 自主启停，无需授权、审批或 AUTH 编号**；
> 子 Agent 的严格限制全部保留。凡引用「§28 一次授权」「§21 GLOBAL_STOP 需编号才能恢复」的旧表述一律作废，
> 以本节为准。事故记录不因规则修订而删除，见项目根 `EMULATOR_CONTROL.md`。

**起因是今天发生过的实际事故，不是预防性条款**：主 Agent 在 10:28:24 停掉 `oreki_test`，
10:28:57 把停止令发给 `r42-android-break`，该 Agent 在 **10:30:02** 用
`emulator.exe -avd oreki_test` 又把它启动了（证据见项目根 `EMULATOR_CONTROL.md` 的 INC-2026-1031-01）。
同一天内子 Agent 累计自行拉起 AVD **8 次**，其中一次用了 `nohup` 绕过任务管理。

### 28.1 主 Agent 权限（自主启停，不需授权）

1. **主 Agent 对唯一 AVD 拥有完整控制权**。启、停、重启、以及「是否允许某项任务连接模拟器」，全部由主 Agent 自主决定。
2. **主 Agent 启动/关闭/重启模拟器不需要额外授权、审批或 `AUTH` 编号。** 任何要求主 Agent 先申请、先报批、先拿编号的旧条款一律无效。
3. 主 Agent 自行决定何时做 Android 测试、何时做 Web Chrome 测试，以及两者的先后顺序。
4. 主 Agent **可以**明确授权子 Agent 执行具体测试任务，但**授权测试不等于转移模拟器启停权**。
5. 主 Agent 发出全局停止令后，**可以自主决定何时恢复**，不需要再走编号流程。

### 28.2 子 Agent 限制（严格保留，不因主 Agent 放宽而放宽）

1. **子 Agent 不得自行启动、关闭、重启模拟器。**
2. **禁止通过 ADB、脚本、后台进程、IDE、Gradle 任务、`nohup`、构建钩子或其他间接方式改变模拟器运行状态。**
3. 子 Agent 需要使用模拟器时，**必须向主 Agent 申请具体测试任务**，说明：测试目标 / 为什么非用模拟器不可 / 预计耗时 / 逐条具体命令 / 释放方式。**不得先启动再汇报。**
4. 主 Agent 的全局停止令**优先于此前所有任务指令、Agent 自身计划和旧执行令**。子 Agent 必须立即停止模拟器相关操作，**未经主 Agent 明确允许不得恢复**。就算子 Agent 认为测试还没做完，也必须停下等。
5. 主 Agent 关闭模拟器后，**任何子 Agent 不得重新启动它。**
6. **发现擅自启动**：立即收回该 Agent 的模拟器操作权限，保留日志与进程信息并上报；**不得为了进度默认接受**。

### 28.3 设备数量与测试顺序

1. **全程最多运行一台 AVD**，默认 `oreki_test`（Android 14 / API 34）。
2. **Android 应用测试与 Web Chrome 测试必须串行执行**，不得同时进行。
3. **禁止为并行测试、备用或临时用途启动第二台模拟器。**
4. **每轮测试结束后，执行者必须向主 Agent 汇报**：测试结果、异常、处理情况。
5. 主 Agent 可根据进度自主决定何时关闭模拟器、何时重新启动。

### 28.4 启动前检查（主 Agent 每次启动前必做）

五项都要看，**发现异常先清理并核实，不允许直接叠加启动**：

1. 当前运行的 `emulator` / `qemu` 进程
2. `adb devices`
3. `adb forward --list`
4. Android 调试端口（5554–5584）占用
5. 是否有残留的 Chrome / 测试进程，以及是否有子 Agent 未结束的模拟器任务

### 28.5 旧规则清理（不得只追加新规则而留下矛盾旧条款）

下列表述**全部作废**，遇到即按本节修订：

| 作废表述 | 现行规则 |
|---|---|
| 「主 Agent 启动模拟器也需要授权」 | 主 Agent 自主启停，无需授权 |
| 「§28 一次授权」 | 一个控制者、主 Agent 自主启停 |
| 「`GLOBAL_STOP` 期间主 Agent 也不得启动」 | 主 Agent 可自主恢复 |
| 「没有编号的授权一律无效」（套用于主 Agent） | 编号仅用于**子 Agent 测试授权**的记录 |
| 「用完 AVD 请自行关闭」（对子 Agent） | 子 Agent 无启停权，关闭也由主 Agent 执行 |

**事故记录、证据、历史时间线一律保留**（见 `EMULATOR_CONTROL.md` 事故台账），规则修订不抹除证据。

### 28.6 唯一台账

项目根 `EMULATOR_CONTROL.md`。启停前后**必须**在那里记录：状态、时间、AVD、操作者、原始核验输出。

- 主 Agent 的操作**只需登记，不需要编号**。
- `AUTH-YYYY-NNNN-NN` 编号**仅用于记录「授予子 Agent 的具体测试任务」**，不再用于限制主 Agent 自主启停。
- 台账里的状态、授权记录与事故记录**必须保留**，不因规则修订而清空。

### 28.7 判断「干净」看核心占用，不看台数

一台跑游戏的 AVD 可占 **5~6.6 核**（FACTS C.75，`r42-web-route` 实测）。
`emu kill` 掉一台**不等于**负载消失。任何「干净环境」的声明必须附三项原始读数：
`adb devices` 为空、`qemu` 进程为 0、CPU 占用贴近空载。

### 28.8 与已有规则的关系

- 与 §25（子 Agent 数量与资源管理）冲突时，**本节优先**。
- 与各 Agent 派发令里的「用完 AVD 请自行关闭」冲突时，**本节优先**：子 Agent 不再拥有关闭权，关闭也由主 Agent 执行。
- 与 Android `AGENTS.md` §2、§3 的 AVD 条款冲突时，**本节优先**；那两处只保留设备侧事实（包名、路径、坐标）。
- 本节不改变「一棵树一个构建根」（Android `AGENTS.md` §3-A-2），那条仍然有效。

## §29 真机屏幕标准（用户 2026-10-31 11:26 长期规则，**本节是唯一源**）

唯一 AVD `oreki_test` 的屏幕参数以本节为准。**目标物理参数与测试渲染参数必须分开记录**，不得互相冒充。

### 29.1 目标物理参数（真机对齐）

| 参数 | 目标值 |
|---|---|
| 分辨率 | 3200 × 1440（高 × 宽） |
| 屏幕比例 | 20:9 |
| 对角线 | 约 6.67～6.69 英寸 |
| 物理尺寸 | 70 × 155 mm |
| 屏幕密度 | 560 dpi（`xxxhdpi`） |
| X DPI / Y DPI | 526 / 526 |
| PPI | 526 |
| 刷新率 | 120 Hz |
| HDR | Dolby Vision、HDR10、HLG、HDR10+ |
| 色域 | 广色域 |
| EDID 型号 | QCM |
| EDID 构建日期 | 06.2006 |

### 29.2 AVD 配置要求

- 唯一 AVD 默认 `oreki_test`，Android 14 / **API 34**。
- 屏幕按 **1440 × 3200、560 dpi** 配置（`config.ini` 里 `hw.lcd.width=1440` / `hw.lcd.height=3200` / `hw.lcd.density=560`）。
- **默认竖屏**，保持 20:9。
- **不允许只调整模拟器外框尺寸来冒充真机屏幕** —— 必须有系统实际报告佐证。
- `120 Hz / HDR / 广色域` 属于真机能力参考：普通 AVD **不保证能完整模拟**，`hw.lcd.vsync=120` 只影响模拟器合成节拍，
  **不得据此声称「已验证 120 Hz 显示」**；HDR 与广色域在 AVD 上**一律标「模拟器不支持 / 未验证」**。

### 29.3 必须核验的实际显示数据（不得只看外框）

每次屏幕相关验收，必须记录下列**原始命令输出**：

| 项 | 命令 / 来源 |
|---|---|
| 物理显示分辨率 | `adb shell dumpsys display`（`DisplayDeviceInfo` 的 `real` 尺寸） |
| Android 实际逻辑分辨率 | `adb shell wm size` |
| density / densityDpi | `adb shell wm density` + `dumpsys display` 的 `density` |
| 应用窗口可用区域 | `dumpsys window displays` / `WindowMetrics` |
| 状态栏、导航栏 Insets | `dumpsys window` 的 `mStableInsets` / `InsetsSource` |
| 应用实际可用宽高与宽高比 | 由上述两项相减得出，写明算式 |
| 屏幕旋转后的尺寸变化 | `adb shell settings put system user_rotation` 后再取 `wm size` |

### 29.4 降采样规则

若 1440 × 3200 在软件渲染（`swiftshader`）下负载过高，**允许降采样测试，但必须同时满足**：

1. `config.ini` 里保留**目标物理参数**（1440 × 3200 / 560 dpi），不被降采样值覆盖；
2. 降采样只通过 `adb shell wm size` / `wm density` 在运行时施加；
3. 报告里**同时写明**「目标物理参数」与「本次测试渲染参数」两个数字，并注明后者是降采样；
4. **降采样结果不得冒充原生分辨率验证结论**。

### 29.5 验收结论写法

- 可写「已验证」：分辨率、density、逻辑窗口、Insets、应用可用区域、旋转 —— 这些 AVD 能如实报告。
- **必须写「模拟器不支持 / 未验证」**：HDR（Dolby Vision / HDR10 / HLG / HDR10+）、广色域、真实 120 Hz 面板刷新、EDID 型号与构建日期。
- 禁止把「设了 `hw.lcd.vsync=120`」写成「120 Hz 已验证」。

## §30 浏览器与标签页控制权（用户 2026-10-31 11:44 下达，**本节是唯一源**）

**起因是实测事故，不是预防性条款**：11:42:10 有子 Agent 启动了一个自动化 Edge 实例
（临时配置目录 `oreki-cdp-*`、调试端口 9376），到 11:49 累计 **57 个 msedge 进程 / 24 个子进程**，
CDP 报 21 个 target，其中 **2 个是空白 `/` 页**，另有 chatgpt.com、darkreader 帮助页等与任务无关的页面。
同期还并存着用户自己的 Edge（PID 14148，27 个子进程）。排查记录见 §30.5。

### 30.1 浏览器控制权

1. **主 Agent 统一管理 Edge 浏览器及其标签页。**
2. **子 Agent 不得在没有明确任务需要的情况下自行打开 Edge、新建标签页或新建浏览器窗口。**
3. **子 Agent 不得通过快捷键、命令行、脚本、自动化工具或其他间接方式绕过此规则。**
4. 主 Agent **可以**明确授权子 Agent 使用**指定标签页**完成**指定任务**。
5. **授权仅限指定任务**，不允许无限创建标签页或窗口。
6. **子 Agent 不得擅自关闭主 Agent 或其他 Agent 正在使用的标签页。**
7. **不得通过反复刷新、重复导航或循环打开标签页制造无效浏览器活动。**

### 30.2 标签页使用规则

- **优先复用**已打开的项目页面和测试页面。
- **同一个任务原则上使用一个标签页。**
- 需要多个页面时，**先向主 Agent 说明用途和数量**，批准后再开。
- **测试结束后汇报标签页用途及当前状态**（保留哪些、关掉哪些、为什么）。
- **禁止为了保持任务运行而持续新建空白标签页。**
- **禁止将浏览器标签页数量当作并行工作能力。**

### 30.3 主 Agent 的调度权

主 Agent 可以：查看当前 Edge 窗口和标签页；判断哪些标签页属于有效任务；要求子 Agent 停止创建标签页；
关闭**确认无用且不被其他任务占用**的标签页；为 Web 桌面、移动端、Android Chrome 测试分配独立时段。

**不得误关正在执行的有效任务或尚未保存的页面内容。** 关闭前必须先确认该 target 的 URL 与所属 Agent。

### 30.4 浏览器是共享测试资源

不是子 Agent 可以无限扩张的个人工作区。**优先复用、统一调度、避免重复打开。**

**自动化实例必须可追溯**：启动时带 `--user-data-dir=<临时目录>`，目录名里写清 Agent 名与端口，
例如 `oreki-cdp-<agent>-<port>`。没有可追溯标识的浏览器实例一律视为违规。

### 30.5 事故台账：INC-2026-1031-04（2026-10-31 11:44~11:52 实测）

**排查方法**（可复现）：

```powershell
# 进程总量与按调试端口分组
$e = Get-CimInstance Win32_Process -Filter "Name='msedge.exe'"; $e.Count
# 主进程（无 --type=）——区分「用户自己的 Edge」与「Agent 自动化实例」
$e | Where-Object { $_.CommandLine -notmatch '--type=' } |
  ForEach-Object { $_.ProcessId, $_.CreationDate, $_.CommandLine }
# 标签页清单（含扩展后台页，需人工剔除）
Invoke-RestMethod 'http://127.0.0.1:9376/json/list'
```

**实测读数（11:49）**：

| 项 | 值 |
|---|---|
| msedge 进程总数 | 57 |
| 浏览器主进程 | **2 个** |
| ├ PID 14148 | 11:22:57，默认配置目录、**无调试端口** → **用户自己的 Edge**，27 子进程 |
| └ PID 40328 | 11:42:10，`%TEMP%\oreki-cdp-1793418130962-9376`、**port 9376** → Agent 自动化实例，24 子进程 |
| 渲染进程 | 37 |
| CDP target | 21（其中 14 个是扩展后台页 `background.js` / `_generated_background_page.html`，非用户标签页） |

**进程创建时间分布**：11:22 十一个 → 零散 → **11:42 十五个** → **11:44 十二个** → 零星。
两次峰值对应「浏览器实例启动」与「渲染进程按需派生」，**不是逐秒递增的循环新建**。

**定性**：不是「无限循环开标签页」，而是**一次自动化实例启动 + 未复用已有项目页 + 留下空白页**。
问题性质是「缺少复用纪律」而非「失控」。这个区分很重要——它决定了处理方式是「立规矩 + 清理」，
而不是「杀进程止损」。

### 30.6 与已有规则的关系

- 与 §28（模拟器控制权）并列，互不覆盖：§28 管 AVD，§30 管浏览器。
- 与各 Agent 派发令里的「起个浏览器验证一下」冲突时，**本节优先**：先申请，再开。
- 本节不改变「Web 桌面验证不占模拟器」这一事实，但**浏览器标签页本身也是共享资源**。

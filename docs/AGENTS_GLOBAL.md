## 2. 本文件是三处同一份文件（2026-10-29 用户要求，长期有效）

本文件同时存在于**三个位置**，且是**同一个文件的三个硬链接**（同一 inode，字节级实时一致）：

| 位置 | 路径 | 用途 |
|---|---|---|
| 工作区根（**权威源**） | `AD-Oreki-Unified/AGENTS.md` | 本机唯一编辑入口，所有修改在这里做 |
| Web 仓库内镜像 | `web/AD-Oreki-Edition/docs/AGENTS_GLOBAL.md` | 随 Web 仓库提交/推送，clone 后仍可读 |
| Android 仓库内镜像 | `android/AD_Oreki_Edition_Android/docs/AGENTS_GLOBAL.md` | 随 Android 仓库提交/推送，clone 后仍可读 |

**为什么这样做**（2026-10-29 之前的问题）：
两个平台仓库的 `AGENTS.md` 都写着「规则源 = 工作区根 `AGENTS.md` §6.2 / §7 / §6.1」，
但工作区根**不是 git 仓库**，那份文件从未进入任何 repo。于是任何人 clone 任一仓库后，
这些引用全是**悬空指针** —— 看得到「规则源」，却打不开规则本身。

**强制纪律**：

1. **只改工作区根那一份**。三处是硬链接，改任一处三处同时变化；但为保持入口唯一，
   约定只在 `AD-Oreki-Unified/AGENTS.md` 上编辑。
2. **不得用「另存为 / 新建同名文件」的方式替换镜像**。那会打断硬链接（inode 变化），
   造成三处内容分叉。要改内容就直接编辑原文件。
3. **不得让任一仓库的镜像变成普通副本**。每次涉及本文件的提交前，跑
   `python scripts/check_agents_sync.py` 校验三处 inode 一致 + SHA-256 一致。
4. 若校验失败（例如某次 `git checkout` 覆盖了镜像导致硬链接断裂），
   以工作区根为准，用 `python scripts/check_agents_sync.py --fix` 重建硬链接，再提交。
5. 两端平台 `AGENTS.md` 里指向本文件的相对引用统一写
   `docs/AGENTS_GLOBAL.md`（仓库内可点开），需要强调权威性时附注「权威源 = 工作区根 `AGENTS.md`」。

## 3. 核心目标与优先级（所有工作共同的衡量标准）

1. **第一优先级：缩短通关所需的现实时间。**
   以玩家现实时间内能否更快推进游戏阶段为首要标准；优先减少无意义等待、重复操作、
   低价值 grind 和不必要人工干预。评估自动化、数值、机制优化时，关注从当前进度到
   下一阶段再到通关的实际时间。**不因代码更接近原版、计算更精确或改动更复杂就认定更好。**
   无法直接测通关时间时，用有代表性的阶段推进速度、等待时间、操作次数与瓶颈变化作代理指标，
   并明确推断范围。
2. **第二优先级：爽玩体验。**
   更快获得有意义的成长反馈，减少挫败与无聊重复。优先改善真正影响体验的瓶颈
   （自动化不够聪明、等待逻辑不合理、重复操作多、关键反馈不清）。不把帧率、执行频率、
   倍率数字或功能数量当作体验改善。保留玩家主动选择的挑战、策略决策与有意义的阶段目标；
   多方案可行时选现实时间收益更高、操作更少、反馈更清楚且副作用更少的方案。
3. **第三优先级：跨端体验一致。**
   Web 与 Android 是同一游戏的两套实现：核心规则、数值语义、自动化行为与玩家预期应一致；
   **不要求源码结构、UI 布局、技术实现或平台 API 相同**。每个差异判定为真实缺陷 / 合理平台差异 /
   待确认问题；修一端时检查另一端同类问题与共享修复思路；不盲目移植代码。
   **宣称跨端一致必须给出两端各自的证据；单端通过 ≠ 双端验证。**
4. **第四优先级：敏捷开发与快速迭代。**
   短周期、可验证、可回滚；每轮优先解决一个最高价值问题；尽快形成最小可用修复并针对性验证；
   证据足以决策就行动，不做不改变方案的无限调查；不为重构而重构、不为指标制造无价值工作；
   高风险操作（存档、工作树、签名、发布产物）先保护现场再按可恢复步骤实施；
   有效改动做与风险相称的回归，通过后走对应平台既有发布规则。

### 3.1. 通关验收标准（用户 2026-10-29 重申，长期有效，**本节是验收口径的唯一源**）

- **唯一成功标准：真实新档**（清空 localStorage / 全新安装，不预置任何标记）**在 180 分钟现实时间内
  抵达真实终局**（`isGameEnd` / `endState >= 1`）。**Reality 不是终点**，必须继续推进天神 → Pelle → 终局。
- 默认加速 **10000×**；**消除所有时间墙**，但保留大部分手动玩法与有意义的阶段目标，做到**新手 0 门槛可通**。
- **双端所有挑战（普通 / 无限 / 永恒 …）必须「进入即完成」并有真实结算**：不得只翻状态位、
  不写完成数、不给奖励。
- **Web 与 Android 同时开发且行为等价一致**；Web 移动端适配必须用安卓模拟器 Chrome 实测真实页面。
- **不接受只有计划、审计报告、测试工具或「下轮再做」的交付**：每轮必须有可运行产物
  （Web 已部署、Android 已构建 APK）。
- **一次处理多个瓶颈**，不要串行等一个瓶颈收尾才动下一个。

## 4. 统一决策方法（每项候选改动逐条自问）

1. 能否缩短通关或阶段推进的现实时间？
2. 能否让玩家少等待、少重复操作、获得更好爽玩体验？
3. 是否保持两端核心行为一致？不一致的原因？
4. 能否用更小的改动达到同样效果？
5. 怎样用最少但足够有力的测试证明有效？
6. 是否有存档、进度、资源、自动化副作用或跨端回归风险？
7. 验证成功后，如何以最短安全路径进入下一轮？

## 6.4. 充分利用 REA 反编译取证（2026-10-29 用户确立，长期有效，**本节是 REA 使用强度的唯一源**）

> 用户原话：「要充分利用 REA 反编译。」
> 与 Android `AGENTS.md §0-I`（REA 强制前置的流程细则）互补：§0-I 规定**什么时候必须跑**，
> 本节规定**跑完之后必须用到什么程度**。执行顺序、失败处理、证据记录仍以 §0-I 为准。

1. **REA 是取证工具，不是打卡工具**。跑过 `rea.sh doctor` 不等于用好了 REA。
   凡涉及 Android 侧以下判断，**必须**先取 REA 证据再下结论：
   混淆类名 / 方法签名 / 字段与常量取值 / 调用链与引用者数量 / 运行期行为 /
   某个分支是否真的存在。禁止只凭 `rg` 命中行、类名猜测或「看起来像」就改 smali。
2. **优先用 REA 解决「找不到、对不上、不敢改」三类问题**：
   - 找不到：原版类被 R8 混淆成 `a` / `qk4` / `n43` / `jw0` 这类短名，`rg` 搜语义名必然落空，
     用 `search-android-classes` 按语义名反查真实类名；
   - 对不上：搞不清 smali 里哪个方法对应源码语义时，用 `inspect-android-method` 拿反编译体比对；
   - 不敢改：改共享常量/字段前，用 REA 反查**引用者清单与数量**（例如某常量被 6 处引用、
     其中含其他子系统的 `<clinit>`，就足以否决一次改动）。
3. **结论必须可追溯到证据**：报告中引用 REA 的 `evidence_id` 与 `authority`
   （如 `shipped-artifact`、`confidence`），或贴出反编译体片段 + `文件:行号`。
   只写「已用 REA 确认」而不给证据标识的结论，按未取证处理。
4. **复用已有证据，不重复解包**：同一 APK / 同一方法已有 `evidence_id` 时优先复用；
   需要新证据时先说明为什么旧证据不足。避免每轮重新 `apktool d` 全量解包。
5. **REA 与 rg 互补，不互相替代**：`rg` 负责在已知路径上快速定位文本；
   REA 负责给出「混淆世界里的真实身份与调用关系」。两者结论冲突时以 REA 的
   反编译体 + 运行证据为准，并记录冲突原因。
6. **不是 Android 专属借口**：Web 侧遇到压缩/混淆产物（构建后的 bundle、部署站文件）时，
   同样优先用可复现的反编译/还原手段定位，而不是猜。

### 6.5.1 Gradle 增量构建与构建缓存（2026-11-02 用户确立，长期有效）

> 用户原话：「不得把 Android 每轮构建默认理解为必须从头完整执行全部任务。」

**一、事实基线（R66 实测，勿凭印象复述）**

| 项 | 现状 |
|---|---|
| `assembleRelease` | 历史上 `outputs.upToDateWhen { false }` 无条件执行；R66 起改为「指纹判定 + `onlyIf`」 |
| `org.gradle.caching` | `false`（未启用构建缓存） |
| `org.gradle.parallel` / `vfs.watch` | `false` |
| 反编译基线树 `work/base_decoded` | **27744 个文件 / 0.40 GB**（不是早期记的 11 万 / 1.7 GB） |
| 整棵树 `(path,size,mtime)` 滚动哈希 | **约 4.2 秒**（相对 8.5 分钟完整构建可忽略） |
| `scripts/payload` | 35 个文件，内容哈希约 17 毫秒 |
| `scripts/*.py` | 69 个文件，内容哈希约 150 毫秒 |

**二、规则**

1. **先判断再构建**：每轮先看哪些任务的输入真的变了，不为「确保最新」而无条件全量重跑。
2. **优先用增量**：能声明 `inputs`/`outputs` 的任务就声明；不能的（本项目的 Python 流水线）用
   `scripts/build_fingerprint.py` 这类**显式指纹**兜底，不得直接退回 `upToDateWhen { false }`。
3. **分级指纹，不哈希巨量只读输入**：小而常变的走内容 sha256；大而只读的（反编译树、原始 APK、keystore）
   走 `(路径, 体积, mtime)` 滚动哈希。
4. **文本文件哈希前做 CRLF→LF 归一化**：换行风格不影响 APK 字节，却会让指纹误判。
5. **`assembleRelease` 允许跳过**（输入指纹一致 + 候选 APK 存在）；
   **`installToRelease` / `publishRelease` 一律强制真实构建**（`taskGraph.whenReady` 置 `forceFullBuild`），
   增量跳过只服务开发期。
6. **安全阀不可省**：候选 APK 不存在 / 指纹文件缺失或损坏 → 一律视为 stale；
   `-PorekiForceBuild=1` 可强制重建；构建失败**不得**更新指纹基线（`--commit` 只在 `doLast` 执行）。
7. **区分任务结果**：`UP-TO-DATE`（输入未变跳过）、`FROM-CACHE`（缓存恢复）、`SKIPPED`（条件跳过）、
   `NO-SOURCE`（无源）、正常执行 —— 报告里不得混为一谈。
8. **配置缓存与构建缓存先评估副作用再启用**：本项目任务几乎全是 `Exec` 调外部 Python 脚本，
   输入输出没有 Gradle 原生声明，盲目开 `org.gradle.caching` 只会产生错误的缓存命中。
   未验证的优化只能记为【待验证】，**不得写成已实现**。
9. **失败先修具体任务**，不得一遇增量问题就退回全量重建，除非能证明增量判断不安全。
10. **每轮记录构建效率**：实际执行任务数、`UP-TO-DATE` / `SKIPPED` 数、完整构建耗时、与上轮差异。

**三、命令**

```bash
python scripts/build_fingerprint.py --show        # 看当前指纹与各段耗时
python scripts/build_fingerprint.py --check       # 判定是否 stale（Gradle 每次自动调用）
./gradlew assembleRelease                          # 输入未变 → SKIPPED（秒级）
./gradlew assembleRelease -PorekiForceBuild=1      # 强制真实构建
./gradlew installToRelease                         # 强制真实构建（发布链路）
```

**四、优化必须以官方文档为依据**

参考（按优先级）：

1. Android Developers 中文 · 优化构建速度 — https://developer.android.google.cn/build/optimize-your-build?hl=zh-cn
2. Android Developers 中文 · Build Analyzer — https://developer.android.google.cn/build/build-analyzer?hl=zh-cn
3. Gradle · Performance — https://docs.gradle.org/current/userguide/performance.html
4. Gradle · Best practices for performance — https://docs.gradle.org/current/userguide/best_practices_performance.html

对应到本项目的落实点：

| 官方原则 | 本项目做法 |
|---|---|
| 先用 Build Analyzer / 性能分析定位真实耗时，不凭感觉改配置 | `./gradlew assembleRelease --profile` 产出 `build/reports/profile/`；耗时分布见 §6.5.1 一 |
| 正确声明输入输出与任务依赖 | 每条 `Exec` 显式 `dependsOn`；无法用 Gradle 原生 input 的用 `build_fingerprint.py` 兜底 |
| 消除不必要的始终运行任务 | 逐个复核 `outputs.upToDateWhen { false }`：`assembleRelease` 已改为 `onlyIf`；`verifyRelease`/`verifyPatchContract` 保留（秒级、且是交付闸门） |
| 逐步启用增量 / Build Cache / Configuration Cache | 增量已启用并验证；Build Cache 与 Configuration Cache **尚未启用**，理由与前置条件见 Android `docs/GRADLE_BUILD.md §9.7`，不得写成已完成 |
| 耗时逻辑放执行阶段，不放配置阶段 | `build.gradle` 配置阶段只做路径与变量计算；所有 Python 调用都在 `Exec`/`doLast` 里 |
| 大型输入树分阶段、文件级检测 | 分级指纹：payload/脚本走内容哈希，`work/base_decoded` 走 `(path,size,mtime)` 滚动哈希（4.2 s / 27744 文件） |
| 确定性无副作用任务才可缓存 | 当前只有 `assembleRelease` 具备确定性，但它有外部写（apktool 重建 `work/mod`），**故不启用缓存** |
| 签名 / 发布 / 云盘复制必须明确执行 | `installToRelease` / `publishRelease` 由 `taskGraph.whenReady` 强制全量，永不跳过 |
| 确认无共享写入才并行 | `work/mod` 是共享工作树，**禁止并发构建**；`org.gradle.parallel=false` 保持不变 |
| 开发与发布用不同任务组合 | 开发用 `assembleRelease`（可跳过）；发布用 `installToRelease` / `publishRelease`（强制全量） |
| 不盲目升级 Gradle/AGP/JDK | 仍用仓库内 `tools/jdk/jdk-17.0.20.1+1`，本项无收益不动 |

**五、验收口径（用户 2026-11-02 指定，缺一不可）**

- **A** 输入未变化，连续构建时可跳过的任务显示 `UP-TO-DATE` 或 `FROM-CACHE`；
- **B** 修改一个真实 smali 输入后，相关任务重新执行，下游任务也重新执行；
- **C** 修改教程或构建脚本后，对应生成与检查任务正确失效，不得继续用旧结果；
- **D** 正常执行与缓存恢复的有效产物一致（SHA-256 核对）；**未启用 Build Cache 时，
  以「指纹恢复后 digest 一致 + 产物 SHA-256 不变」作为等价证明，并注明未使用 FROM-CACHE**；
- **E** 最终 APK 仍通过原有完整性、安装与运行验证。

### 6.5.2 语义夹具优先于「构建 + logcat」（2026-11-03 用户确立，长期有效）

> 用户原话：「不要再只检查 Smali 中是否存在某条指令。必须建立真正的语义夹具。」

**背景（本轮实测代价）**：R65 与 R66 各烧掉 6~7 次整包构建（每次 8~10 分钟），
原因全是同一个模式 —— **极性写反 → 编译通过 → 装机后日志不对 → 猜一处改一处**。
R67 定位到 R66 的 `stage=-1` 是**六处叠加**错误（fill 守卫 / leaf 边界 / 取反 / 名字越界 /
未接线返回值 / 缺算子），任何单点修复都看不到效果。

**规则**

1. **涉及分支极性的改动，必须先有夹具，再改代码**。适用范围：
   `fill/leaf/evalStage/nameOf/goalOf/tryEternity/allow/noteActed/noteNoop` 这类
   「比较 + 条件跳转」密集的方法。
2. **夹具必须跑真实数据**，不得只断言「某条指令存在」。合格形态：
   - 从生成产物（smali 数据表）解析出真实结构，用与目标平台**逐指令等价**的模型求值；
   - 与权威源（策略 JSON）逐项对照，随机环境批量比对；
   - 覆盖边界：等于 / 差一个最小步长 / 越界 / 负数 / NaN / 取反。
3. **夹具必须进构建断言**（`build_mod.py` 4b），失败即中止，不等到 apktool。
4. **夹具失败时改代码，不改期望**。确需改期望，必须在 commit message 写明「为什么旧期望是错的」。
5. 现有夹具（改动这些文件后必须全绿）：
   | 夹具 | 覆盖 | 项数 |
   |---|---|---|
   | `scripts/fixture_scheduler_semantics.py` | 调度间隔 / no-op / 严格档 / 预约 | 24 |
   | `scripts/fixture_strategy_semantics.py` | 策略数据表 / 六算子 / fail-closed / 全阶段正反例 / drives | 70 |
   | `scripts/fixture_eternity_gate.py` | 首次永恒三闸门（从 smali 提取助记符 + 用户判定表） | 11 |
6. **仍未验证的事不能写成已完成**：夹具证明的是「语义正确」，不是「运行期达到目标」。
   `eternities` 是否真的增长、`isGameEnd` 是否真的为真，必须另有运行期证据。

   | Android 仓库镜像 | `android/AD_Oreki_Edition_Android/docs/FACTS.md` |

   三处是同一 inode，**只改工作区根那一份**；不得用「另存为 / 新建同名文件」替换镜像（会断硬链接）。
   校验与重建统一走 `python scripts/check_agents_sync.py` / `--fix`（该脚本现已同时守护
   `AGENTS.md` 与 `FACTS.md` 两组文件）。

   ⚠ **上述「三处」之外的所有 `FACTS.md` 都是检出副本，不是权威源，禁止编辑。**
   `git worktree` 目录会各自检出一份**独立 inode** 的 `FACTS.md`，最容易误当成镜像去改：
   ```
   2026-10-31 实测：web/_wt_deploy/docs/FACTS.md  inode 844424933070372  ← 独立副本，非硬链接
                    web/AD-Oreki-Edition/docs/FACTS.md  inode 3940649674859546  ← 硬链接三处之一
   git worktree list  →  _wt_deploy (detached HEAD 6e90ede) / _wt_head (detached HEAD df6ef9d)
   ```
   在这些 worktree 里改 `FACTS.md` 会产生一条**分叉的历史**，且因为不在权威 inode 上，
   `check_agents_sync.py` 查不出来。**要改事实，先 `cd` 回工作区根。**
2. **什么必须写进去**（满足任一条即写）：
   - 同一个坑踩了**两次以上**，或排查耗时 **20 分钟以上**才搞清的机制；
   - 一旦被改回就会**静默返工**的根因（例如跳转极性、语言三处默认值、`pLog10(0)=0`）；
   - 环境硬事实（工具路径、不在 PATH 的命令、代理端口、AVD 名称）；
   - 原版机制的关键语义（含文件:行号），尤其是「看起来像 bug 其实是原版行为」的那类；
   - 已测出的**数值天花板**（再跑也不会涨的量），用来阻止「再多跑一会儿」式的无效优化。
3. **每条必须带证据等级**，四选一并写在行尾：`[实测]` / `[读码]` / `[推断]` / `[未知]`。
   **禁止**把 `[推断]` 写成 `[实测]`，也禁止省略等级。
4. **每条必须可追溯**：给出文件:行号、命令、或数据文件路径。写不出出处的「我记得」不算事实。
5. **推翻就改那一条**，不要在旁边追加新说法；两条并存会让后来的会话不知道该信哪个。
6. **只写长期有用的**：轮次状态、临时路径、一次性调试输出、待办清单**不写**（那些属于
   `handoff/` 与任务列表）。
7. **每轮收尾检查**：本轮如果产生了上面第 2 条列举的东西，`FACTS.md` 必须同步更新，
   否则视为「交付未完成」，与 §6.2 的文档纪律同级。
8. `FACTS.md` 与 `AGENTS.md` 冲突时，以 `AGENTS.md` 为准；`FACTS.md` 与**代码**冲突时，
   以代码为准，并回来改 `FACTS.md`。


## 19. 移动端适配：控件触控尺寸不得偏小（2026-10-30 用户确立，长期有效，**本节是触控尺寸的唯一源**）

> 用户原话：「移动端适配要注意控件大小，不要像选项内有些控件偏小」。

1. **判定基准（两条都要满足）**：
   - **绝对下限**：窄屏（`max-width: 620px`）下所有**可点元素**命中区不小于 **44 × 44 CSS px**
     （WCAG 2.5.5 / iOS HIG 下限；Android Material 建议 48dp ≈ 44 CSS px）；相邻可点元素间距 ≥ **8px**。
   - **相对一致（用户 2026-10-30 补充：「是和同页面其他按钮相比」）**：**同一页面内、同一层级的控件必须同高同宽基准**。
     不允许出现「主按钮 44、旁边同类按钮 25」这种参差。判定方法是把同页所有同类可点元素的
     高/宽列出来看分布：只允许 1~2 档（如主按钮 / 次级按钮），且档差不超过其自身高度的 20%。
     若某控件比同页其他按钮明显偏小，**以该页主按钮为基准**把它撑到同一档，而不是只满足 44px 就收工。
2. **覆盖范围**（不只按钮）：`button` / `.o-primary-btn` / 开关（toggle）/ 复选框 /
   下拉（`select`）/ 数字输入（`input[type=number]`）/ 加减按钮 / 页签 / 关闭叉 /
   自动购买器行内的「开启」与间隔输入。
3. **必须真的扩命中区**，不是只放大字号：用 `min-width` / `min-height` / `padding`
   把**可点区域**撑到 44px。文字可以不变大，但手指点到的地方必须够。
   若扩尺寸会撑破行宽，**先解决换行/自适应**（见 §19.4），不要靠缩小控件来省空间。
4. **不得用「整行变窄」的方式换空间**：窄屏下若一行放不下，正确做法是换行（`flex-wrap: wrap`）
   或改列布局，而不是把控件压到 44px 以下。
5. **验收方式（必须给数据，不许目测）**：在真机 / 模拟器视口（392×676 与 360×640 各一次）
   用 CDP 扫描可点元素的 `getBoundingClientRect()`，列出所有 `width < 44 || height < 44` 的项
   （类名 + 文本 + 实际尺寸），修完复扫到清单为空或只剩「有合理理由」的项。
   合理理由必须写进报告（例如「整行是一个大按钮，内部小元素不可单独点击」）。
6. **与既有规则的关系**：本节只管**尺寸**；「不横向溢出」由 `oreki.css` 的 620px 段负责；
   两者冲突时优先保证不溢出，其次保证 44px，最后才考虑美观。
7. 新增任何窄屏控件样式时，必须同时给出**该控件的实测尺寸**；没测过的写「未验证」。

### 20.1 目标优先级不得漂移（原 R20）

**最高优先级始终是：新存档从开始游戏到真正抵达游戏终局，现实耗时不超过 180 分钟**
（口径唯一源 = §3.1，本节不放宽）。

判断一项工作该不该做的**第一问**永远是「它让真终局更近还是更远」，而不是
「数字是否变好看」「是否更接近原版」「实现是否更优雅」。

- 「解锁 V / 进入 Ra / 进入莱特拉 / 解锁佩勒」**都不是通关**；唯一判据是原版终局状态（§3.1）。
- 若某轮所有工作都无法让真终局更近，**必须在报告里明说**，不得用「完成了若干优化」代替进展。

### 20.2 瓶颈价值排序（原 R21）

多个问题同时存在时，按**四个因素**综合排序（§5 已给前三个，本条补第 4）：

1. 对通关进度的**实际阻碍程度** —— 有证据地指出它是当前链路真正卡住的那一环。
2. 预计能**节省的现实时间** —— 换算到「距离 180 分钟还差多少」，不是抽象百分比。
3. 修改**风险与验证成本** —— 是否碰存档 / 签名 / 发布产物；要不要构建。
4. **对 Web / Android 的双端影响范围** —— 共享机制（影响面大）要先统一口径再动手。

**明令禁止**：「因为这个问题容易改，就先处理它」。容易修但不在关键路径上的，记入待办，
等关键路径清空后处理。

### 20.3 先证明瓶颈，再调整数值（原 R22）

修改**生产倍率、资源价格、解锁门槛、升级成本、进度条件**之前，**必须先确认实际瓶颈**。
这条是**前置条件**，不是建议（§4 第 1/5 问、§5 是其上层原则）。

- **「先证明」的标准**：有可复现的观测数据（字段真值 / 时间序列 / 阶段耗时），
  能指出卡在**哪一个判定**上，而不是「看起来慢」。
- **禁止用「降低门槛」掩盖其他系统故障**。典型错误模式：某自动化根本没跑起来
  （异常被 `catch` 吞掉、入口没接上），却去调低它本该产出的资源门槛 ——
  门槛降了故障还在，只是把问题推到下一环（R36 就踩过：EC 自动启动因 `ContinuationImpl(null)` NPE 被吞，
  表面看像资源不足）。
- **禁止引入**以下任一后果：数值溢出（超过 `Decimal.MAX_VALUE`）、软锁（再也推进不下去）、
  无法结算（挑战进了出不来 / 奖励发不出）、无法继续推进（下一个门槛永远达不到）。
- 调门槛必须**同步「显示值 + 判定分母」**（如 `v.js` 的 `requirement` 与 `progress` 分母），
  否则进度条永远到不了 1。

### 20.4 每项修改必须有可衡量收益（原 R23）

重要修改必须有**修改前后对比数据**（§5 说「无法证明收益则不做」，本条说**怎么证明**）：

| 指标 | 取法 | 适用 |
|---|---|---|
| 关键阶段解锁耗时 | 新档实测「首次达到 X」的时刻 | 机制 / 自动化 |
| 资源增长速度 | log10(资源)/秒，或每秒新增量级 | 产量 / 倍率 |
| 等待时间 | 两次有效操作之间的空转秒数 | 自动化 / 门槛 |
| 必要操作次数 | 玩家真正需要手动点击的次数 | UX / 自动化 |
| 挑战完成耗时 | 进入 → 结算的真实秒数 | 挑战链路 |
| 崩溃率与异常次数 | 控制台异常条数 / 每千帧 | 稳定性 |

- 没有可验证收益的改动，**不应仅凭主观感觉**判定为优化成功。
- 无法直接测量时，必须写明「用的是哪个代理指标、推断到哪」，**不得把代理指标写成直接结论**。
- 报告须区分 **【实测】/【读码】/【推断】/【未知】** 四级（与 §4 末段一致）。

### 20.5 双端共享玩法基准（原 R24）

原则见 §3 第 3 优先级与 `docs/SHARED_GAMEPLAY_STANDARD.md` §2，**本条只补执行要求**：

- **允许**平台差异：UI 布局、技术实现、平台 API、源码结构可以不同。
- **不允许**实质不一致：奖励、进度、挑战结果、终局条件不得「一端能过一端不能过」。
- 任何数值 / 门槛 / 倍率改动，**必须在同一轮或紧接着的一轮同步到另一端**，
  并在报告里列出「**另一端需同步的目标值**」清单。**单端通过 ≠ 双端验证。**
- 每处差异必须定性为**真实缺陷 / 合理平台差异 / 待确认问题**三类之一。

### 20.6 新存档优先，旧存档兼容（原 R25）

1. 核心进度测试**必须使用独立的新存档**（清空 `localStorage` / 全新安装 / 隔离 profile），
   并在报告写明「这是真实新档」。
2. **不得在用户真实存档上做实验**。实验一律走隔离存档、临时 profile、临时 AVD。
3. 修改**存档结构或核心逻辑**后，必须验证旧存档的**双向兼容**：
   能加载 → 不崩、不丢关键进度 → 保存后再次加载仍正常。
4. **不得为了通过测试而污染、覆盖或破坏已有存档。**

### 20.7 阶段性交付必须可运行（原 R26）

每个开发阶段都要留下**可以运行的成果**（§3.1 已禁「只有计划」，本条定交付**五项**）：

1. 实际修改了什么（文件 + 行号 + 关键 diff 要点）。
2. 哪些测试已通过（退出码 / 日志路径 / 字段真值）。
3. 哪些问题**仍未解决**（明确写出，不藏脚注）。
4. **当前版本如何运行与复现测试**（命令、端口、profile、AVD 名）。
5. 下一阶段最重要的阻塞。

不得以纯计划、纯审计、纯测试框架或「下一轮再实现」代替实际开发交付。

### 20.8 失败必须转化为可复用知识（原 R27）

重要失败必须记录**六项**（§18 定落地位置，本条定内容）：

1. 具体故障及**发生条件**（什么情况下触发）。
2. 已有证据（日志 / 字段值 / 复现步骤）。
3. 已尝试的修复方式。
4. 修复结果（有效 / 部分有效 / 无效）。
5. **已排除的错误方向**（最容易漏，但价值最高）。
6. 后续应避免的重复无效操作。

- 落地到 `FACTS.md` 对应章节 + 当轮 `handoff/` 报告。
- 被实测**推翻**的旧结论必须显式标注「已推翻」并写清推翻证据 ——
  否则下一轮会重新把它当事实（R36 发生过三次：EC9 资源墙、前置研究 151、`dilatedTime` 恒 0）。

### 20.9 自动化不得摧毁核心玩法（原 R28）

自动化只减少**重复劳动**，不删除游戏本身。

- **必须保留**原版核心逻辑：购买、挑战进入、挑战结算、奖励发放、重置、成就、阶段推进。
- **允许**自动化重复操作（买研究 / 买维度 / 反复进挑战）。
- **禁止**伪造进度、直接写结果字段（完成次数 / `completed` 位 / 解锁标志 / 终局状态）、
  绕过原始结算制造虚假通关（§3.1 已禁「只翻状态位」，本条给判定方法）。
- **判定标准**：把自动化关掉，手动操作仍能走到同一步。只能靠自动化写字段才推进 = 伪造。
- 「临时抬到门槛再还原」**只有**在能论证「真实完成那一刻该字段必然等于该值」、
  且结算后立即还原时才允许，并须在代码注释里写清论证
  （参考 `src/core/oreki-instant-challenges.js` 的 `maxAM` 处理）。

### 20.10 正式发布候选版本冻结（原 R29）

进入**正式构建与验收阶段**后必须**冻结源码**（§6.6 管「先 APK 后 push」的顺序，本条管一致性）。

- 冻结期内若仍有源码修改，必须依次：**重新构建 → 重跑受影响测试 → 重算 SHA-256 → 更新交付记录**。
- **不得**把修改前构建的 APK / Web 产物冒充修改后的版本。
- 冻结与解冻都要写进报告：冻结的 commit、解冻原因、重新验证结果。

### 20.11 交付必须有证据（原 R30）

**命令发送成功不等于任务完成**；「代码已提交」「APK 已构建」「已经解锁」都是中间状态，
不得冒充完整交付（§6.2.3 / §6.6 / §16 定要更新什么，本条定**最小证据形式**）：

| 行为 | 必须提供的证据 |
|---|---|
| Git commit | commit SHA + `git show --stat` 摘要 |
| Git push | push 输出、或 `git rev-list --count origin/main...HEAD` 为 0 |
| Pages 部署 | 线上 URL 实际打开结果（新闻关闭 / 侧栏 / 移动端布局 / 教程） |
| APK 构建 | 构建日志尾部 + 文件大小 + 版本号 + SHA-256 |
| 云端上传 | 上传后的远端列表或时间戳 |
| 设备安装 | `adb install` 输出 + 启动日志 |
| 实际运行测试 | 字段真值 / 截图 / 日志路径 |

### 20.12 超时必须升级处理（原 R31）

长时间无有效成果时，必须**主动**缩小范围、改执行方式或终止无效尝试；

## 21. 双端实现差异表：`WEB_ANDROID_DIFFERENCES.md`（2026-10-30 用户确立，长期有效，**本节是这套制度的唯一源**）

**为什么单列**：双端差异此前散落在 `FACTS.md §C.11`、各轮报告与口头结论里，

### 21.1 唯一文件与硬链接

- 唯一文件：`WEB_ANDROID_DIFFERENCES.md`，**同一 inode 三处硬链接**：
  1. 项目总根 `AD-Oreki-Unified/WEB_ANDROID_DIFFERENCES.md`
  2. `web/AD-Oreki-Edition/WEB_ANDROID_DIFFERENCES.md`

- **必须是硬链接**，不得用复制文件、软链接或各自维护独立版本。

### 21.2 维护时点（强制）

1. 每轮**开工先读**差异表，了解已有差异与未解决问题。
2. 每轮**收工按实际代码变更更新**差异表。

8. 每轮结束**核对三处仍是同一 inode**；`checkout / reset / pull / merge` 之后必须重查。

### 21.3 验证口径（不得放宽）

- 只有**真实运行证据**（AVD / 浏览器 / logcat / 采样 jsonl，且报告可查到命令与输出）才能标 `已验证`。

  仍然只是 `待验证`。

1. 旧教程写天神「按顺序解锁：薇 → 太阳神 → 莱特拉 → 佩勒」——
   真实顺序是 **特蕾莎 → 鹿颈长 → 无名氏 → 薇 → 太阳神 → 莱特拉 → 佩勒**，前三位缺失会让新手跳过。
2. 全篇**没有终局判据**。真实判据 = **反物质 ≥ 1e1000**（`src/core/celestials/pelle/game-end.js`
   的 `OREKI_PELLE_END_TARGET_EXP`，`endState >= 1` 时 `isGameEnd` 置真）。

**可用性事实（写正文时必须照顾）**
- APK **不强制中文 locale**：系统语言为英文时底栏显示 `Dimensions`。正文写「点底栏『维度』」
  会让英文系统的新手点不到 ⇒ **关键页签一律中英双写**（「维度 / Dimensions」）。
- Android 教程**没有首次启动自动提示**，100% 靠玩家自己点，这是 §24.1 可发现性的真实风险点。

### 24.9 单一内容源（R40 定案，唯一实现路径）

**正文只允许存在于 `web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json`**，两端都从它派生：

- Web：`src/core/oreki-tutorial.js` 只做 `import` + 派生成渲染结构，**不得再写第二份正文**；
- Android：构建期由 `scripts/oreki_tutorial_gen.py` 读取该 JSON，生成
  `payload/assets/oreki_tutorial.txt`（每行 `FIELD|flag|text`），`TutorialActivity` 逐行
  `split("\\|", 3)` 解析。**不再把正文写进 smali `const-string`。**

为什么是 JSON 而不是解析 JS：Python 解析 JS 对象字面量只能靠正则，Web 侧字段一改就
**静默产出残缺教程**（能编过、能装上、界面空白或少章）；JSON 有 `json.load` 兜底，语法错在构建期直接报错。

为什么是 assets 而不是 smali：8~12 万汉字若逐段变 `const-string`，smali 会涨到 1.5~3 万行，
汇编变慢、易撞 65,535 常量池边界，且**内容错不会在汇编期暴露**。`assets/` 不走 aapt、不占资源 ID，
内容是数据不是代码。**代价**：仍然要重建 APK（内容在 APK 里）；不采用运行期下载，
因为现行教程页明确写「不需要联网」（`TutorialActivity.smali:141`），且运行期内容会与版本脱钩。

**构建期三层断言（缺一不可，实现见 `build_mod.py`）**
1. 一级：JSON 可解析、`schemaVersion` 匹配、`chapters` 非空、`id` 唯一且连续、十个字段类型正确；
2. 二级（发布构建）：`draft` 全为 `false`、`steps` 非空、`numbers[].src` 非空、无占位词、终局章含 `1e1000`；
3. 三级（回读比对）：重新读生成的 assets，按分隔符解回结构，与 JSON **逐字段比对**，不一致即中止构建。

字段契约与校验规则见 `web/AD-Oreki-Edition/docs/TUTORIAL_SCHEMA.md`。

**译名基准（写任何正文前必读）**：`web/AD-Oreki-Edition/docs/TUTORIAL_GLOSSARY.md`。
权威来源是 `android/AD_Oreki_Edition_Android/work/base_decoded/res/values-zh-rCN/strings.xml`
（原版 APK 官方简体中文字符串，4,516 行），表里每个词都标了官方出现次数，**0 次 = 禁止使用**。
三个已确认的高频错译：

| 错 | 对 | 官方次数 |
|---|---|---|
| 时间定理（TT） | **时间之理** | 75 次 / 错译 0 次 |
| 稀释时间（DT） | **膨胀时间** | 54 次 / 错译 0 次 |
| 大灾变（Armageddon） | **末日** | 30 次 / 错译 0 次 |

**英文只允许出现在两种位置**：中文后括注全称或缩写（`时间之理（TT）`）、
界面标签中英双写（`点击底栏「维度 / Dimensions」`，因 APK 不强制中文 locale）。
除此之外不许整句英文 —— 抓来的 wiki 攻略是英文的，只能用来理解机制，不能搬句子。

**Android 渲染硬约束**：目标篇幅下「一次 inflate 全部」不可用（约 500 个 TextView、单层线性布局
高 8~12 万 px）⇒ **必须一章一屏**：先解析章节列表，只渲染当前章，切章重建内容区。
必做项：分章 + 章节目录、字号三档、打开定位到当前阶段章。
明确放弃：表格渲染与行内加粗（在 smali 里手写 SpannableString 性价比极低，字段齐全优先于样式）。

**切换期铁律：不得造成信息倒退。** 单一内容源刚接入时，新章节绝大多数是 `draft: true`、`steps: []`，
而两端旧教程都已有内容（Web 7 章 39 小节、Android 10 章 2,665 字）。若直接切到新源，
玩家会从「有内容」掉到「只有 1 章有内容」。

所以：
1. 两端的旧正文**都不许删**——Web 保留为 `TUTORIAL_LEGACY_CHAPTERS` 导出；
   Android **旧 10 章的 smali `const-string` 原样留在原处**，生成器只产出新章节
   （不迁移旧文本，迁移留到正文补齐后再做，降低本轮风险）；
2. 渲染时排在新章节**之后**，加明显的分节标题「旧版教程（已停止维护，正在并入新版）」；
3. 删除时机由**团队负责人**决定，实现方不得自行加删除逻辑（默认行为是「总是写」）；
4. **验收口径（三条并列，缺一不可）**：
   - 玩家能读到的**章节数与可操作性**不得少于切换前；
   - 旧版段落必须显式声明「已停止维护」，**不得被当作达标的依据**；
   - **已知错误必须在旧版声明里点名**——天神解锁顺序写反、终局判据缺失、EC1~EC12 无内容。
     只写「可能过时」不够：新手照样会照着错的那段做。

第 4 条最后一项是本条最容易被糊过去的地方。「信息不倒退」若实现成「把已知错误原样保留并当正文」，
那是把倒退包装成达标。**旧内容本身是错的，这件事必须对玩家说出来。**

**发布门控：`OREKI_TUTORIAL_ALLOW_DRAFT`（两端必须同名，默认严格）**

设计原则是「失败即关闭」：**默认就严格，想带半成品构建必须显式放行**。
反过来（默认宽松、发布时记得加变量）一定会有人忘了加，然后带着 11 章空壳出厂。

| 取值 | 行为 | 用途 |
|---|---|---|
| **不设置（默认）** | `draft > 0` **中止构建**，打印 `draft=N/总章数` 与是哪几章 | 发布、合并、任何常规构建 |
| `=1` | 允许 `draft: true`，日志打印 `draft=N/总章数` 但不中止 | 仅本地迭代 / 需要装机验证渲染时 |

现在不设该变量跑构建**必然失败**（17 章里 11 章是 draft），这是正常的；
它能证明门控真的生效，也保证不会「以为写完了其实没写」。

**章节数一律不许硬编码。** 断言只能写成「`len(chapters)` 与 JSON 实际长度一致」+
「`id` 依次为 `ch00..ch(N-1)`」，N 从数组长度推导。
本文档写作当天这份 JSON 的章数已经变过三次（15 → 16 → 17），`draft:false` 数变过两次，
**任何写死的数字在下一次改章后都会立刻过期**。报告、文档里的完成度一律写「取现值命令」，不写死值：

```bash
python -c "import json,io;d=json.load(io.open('web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json',encoding='utf-8'));print(len(d['chapters']),[c['id'] for c in d['chapters'] if not c['draft']])"
```

## §25 子 Agent 数量与资源管理（长期强制规范，用户 2026-10-30 23:18 下达）　⚠ 多 Agent 部分已由 §60 废止（2026-11-01）

### 25.1 数量上限

**主 Agent 同时最多派出 3 个直接子 Agent。** 不得为追求并行数量无限增加；
**禁止子 Agent 嵌套派生其他 Agent**；不得用「多个间接任务」变相突破上限。

历史教训：R40 深夜一度同时挂着 **10 个**直接子 Agent（agent-a~agent-j），
导致同一模块被两人争写（`oreki-tutorial.js` 与 `validate_tutorial.mjs` 各被写过一版）、
重复检索同一批源码、以及 Android 侧两人同时改 `oreki_tutorial_gen.py`。
收敛到 3 个后反而推进更快 —— **并行度不等于吞吐量**。

### 25.2 固定三角色

| 角色 | 职责 |
|---|---|
| Agent A | Web 核心机制、自动购买器、路线择优 |
| Agent B | Android 功能开发、Smali、界面与双端同步 |
| Agent C | 独立测试、双端差异核对、教程与验收 |
| 主 Agent | 总体规划、协调、代码集成、构建、最终测试、GitHub 交付 |

可随任务调整分工，但**每个 Agent 必须有明确的交付目标与文件所有权**。

### 25.3 派发前六项检查

1. 当前是否已达 3 个上限；
2. 新任务是否有独立价值；
3. 是否与现有 Agent 重复；
4. 是否有明确的代码或测试交付物；
5. 是否有清晰的文件修改范围；
6. 是否值得消耗积分。

**主 Agent 能快速完成的，就不派 Agent。**

### 25.4 收回规则（必须按序执行，不许一刀切终止）

1. 盘点全部 Agent 的任务、进度、成果；
2. 优先保留**已产出有效代码或独立测试证据**的；
3. 识别重复研究、空转、无交付物的；
4. 安全收回多余任务，**先保护未提交成果**（提交 WIP 或留盘确认）；
5. 把有价值的工作整合进现有任务；
6. **不得因停止 Agent 而丢失已完成成果或未提交代码。**

### 25.5 资源协调

- 构建统一由主 Agent 协调，禁止并发 Gradle / apktool 构建；
- 同一 Android AVD 同一时刻只允许一个 Agent 操作；
- 重型构建与长时间实测错峰；
- 避免多个 Agent 重复检索同一批源码；
- Agent 超时或无有效产出，主 Agent 直接接管，不无限等待。

### 25.6 考核口径

不看 Agent 数量、派发次数、研究报告数量；只看**可集成代码、真实测试结果、可运行版本**。
每轮统计：直接子 Agent 数（≤3）、任务重复率（应力求为零）、实际代码交付、
独立测试证据（必须保留）、未提交成果（必须保护）、空转（及时收回）。

### 25.7 单文件单一 owner（由并发覆盖事故追加）

R40 深夜实测事故：`android/.../scripts/oreki_tutorial_gen.py` 在两小时内被两个 Agent
先后大改，后者的改写把前者 15 条 `selftest` 用例**整段覆盖丢失**。**这不报错**，
唯一迹象是「用例数从 15 变成别的数」——没人会去数。同一天 `oreki-tutorial.js` 与
`validate_tutorial.mjs` 也各被两人写过一版。

规范：**生成器、断言链、校验脚本这类「一次性大改就会覆盖同事成果」的文件，必须指定单一 owner。**
其他人要改，先在消息里申请。派发任务时把这一点写进文件所有权段，不要只说「不要碰某目录」。

## §26 断言设计规范

### 26.1 断言必须有会 raise 的入口

**反例（真实踩过）**：把旁路断言写成 `expect_fail(lambda: helper())`，而 `helper()`
只**返回问题清单**、不抛异常 —— 于是自测永远显示「没有被拦住」，断言形同不存在。
作者还以为自己测过了。

规范：
- 每个断言必须有一个**失败即抛异常或非零退出**的入口函数（`validate_xxx()`）。
- 「返回清单」的辅助函数（`_xxx_problems()`）**不得直接配 `expect_fail`**。
- 自测里每条断言至少一条**必须失败**的负例，且负例失败信息要能贴出来给人看。

### 26.2 断言的有效性不能依赖调用者记得怎么调

这与 `OREKI_TUTORIAL_STRICT` 默认关闭是同一类错误：守则写对了，但默认不生效等于没有守则。
**默认必须是 fail closed**（`OREKI_TUTORIAL_ALLOW_DRAFT` 默认严格，`=1` 才放行）。

### 26.3 只校验「内容的正确位置」不够，必须管住「内容可能出现的位置」

真实事故（两条，同一天）：
1. Web `src/core/oreki-tutorial.js:108` 写着「把 RM **灌注**给特蕾莎换**时间定理**」——
   一句话两个禁用译名。而译名断言只扫 JSON，完全看不见它。
2. Android `tutorial/TutorialProgress.smali:202` 写着「用**时间定理**点时间研究」——
   玩家每次进入永恒阶段都会在教程界面顶部看到，而它同样不在 JSON 里。

规范：新增「玩家可见但不在内容源里」的中文文案时，必须同时把它登记进扫描面
（Web：`validate_tutorial.mjs` 的 `PLAYER_VISIBLE_SOURCES`；Android：smali 全包旁路扫描）。
扫描面宁可宽——106 条全扫的代价可以忽略，漏一个文件的代价是不可见缺陷。

## §27 双端功能对等（Android 不得停滞的落地检查法）

用户长期要求：「Web 与 Android 必须同步推进功能开发，Android 不得沦为被动移植端」，
且明确「不允许用 UI 微调、文档更新、测试工具开发或单纯修复旧问题冒充功能开发进度」。

### 27.1 判定只有三态，禁止第四种写法

每个 Web 机制模块在 Android 侧的状态只允许三种记法：

| 记法 | 含义 | 证据要求 |
|---|---|---|
| **已有** | Android 有等价实现且在真实路径上生效 | 给出类/方法与调用点 |
| **确认缺失** | 调用链里确实没有这个动作 | **必须反证**：贴出该阶段 tick 的调用链原文，说明只有 A/B/C 动作 |
| **未知** | 搜过但无法判定 | 写明搜了什么、为什么判不了 |

**禁止**把 grep 0 命中写成「缺失」，也禁止把「有 4 处字符串提及」写成「已实现」。

### 27.2 为什么这条必须写死

同一天两个真实反例：
- `player.break` 在 Android 是 `Player.brake:Z`（setter `x0(Z)` @11107 / getter `m()Z` @10746）；
- `Pelle` 类在 DEX 里是 `.../pelle/c`，按原名 `inspect-android-method` 直接报
  `Exact class not found`，**不是 APK 缺类，是混淆改名**。

按 Web 的名字搜 Android，0 命中是常态。**「搜不到 ≠ 不存在」是这个项目最容易误判的一条。**

### 27.3 每轮必须做的一件事

每轮开发开始前读 `WEB_ANDROID_DIFFERENCES.md`，结束后把本轮涉及的机制差异写回去
（双端实现状态、数值差异、以及**Android 侧独立发现的事实**）。

后者尤其重要：R40 实测 Android 的 `prestige/f::o` L7445-7530 写的是中间值 `v15`，
**比 Web 版 `player.break = true` 更保守** —— 这是 Android 反向提供的信息，
不是移植产物。允许并鼓励 Android 先发现 Web 不知道的事，这才是「对等开发」而不是「跟随」。

### 27.4 覆盖差距必须量化，不能凭感觉

R40 实测基线（2026-10-30）：Web 自动化相关模块 **12 个 / 2,962 行**，
Android `oreki` 包机制类 **2 个 / 1,834 行**；`replicanti` / `eternityChall` /
`instantChallenge` / `sacrifice` 在 Android oreki 包内 **0 提及**。
细节见 `FACTS.md C.34`。

后续每轮用同一组命令复测（`ls src/core/oreki-*`、`grep -ril` 限定 oreki 包），
把数字写进差异表，而不是写「大致对齐」。

## §28 模拟器控制权：一台模拟器、一个控制者、主 Agent 自主启停、子 Agent 严格受限（用户 2026-10-31 11:25 补充令修订，**本节是唯一源**）

> **修订说明（2026-10-31 11:25）**：本节原为 11:02 版本，要求「主 Agent 启动模拟器也必须持有编号授权」。
> 该要求已被用户明确**废止**。现行规则：**主 Agent 自主启停，无需授权、审批或 AUTH 编号**；
> 子 Agent 的严格限制全部保留。凡引用「§28 一次授权」「§21 GLOBAL_STOP 需编号才能恢复」的旧表述一律作废，
> 以本节为准。事故记录不因规则修订而删除，见项目根 `EMULATOR_CONTROL.md`。

**起因是今天发生过的实际事故，不是预防性条款**：主 Agent 在 10:28:24 停掉 `oreki_test`，
10:28:57 把停止令发给 `r42-android-break`，该 Agent 在 **10:30:02** 用
`emulator.exe -avd oreki_test` 又把它启动了（证据见项目根 `EMULATOR_CONTROL.md` 的 INC-2026-1031-01）。

### 28.1 主 Agent 权限（自主启停，不需授权）

1. **主 Agent 对唯一 AVD 拥有完整控制权**。启、停、重启、以及「是否允许某项任务连接模拟器」，全部由主 Agent 自主决定。
2. **主 Agent 启动/关闭/重启模拟器不需要额外授权、审批或 `AUTH` 编号。** 任何要求主 Agent 先申请、先报批、先拿编号的旧条款一律无效。
3. 主 Agent 自行决定何时做 Android 测试、何时做 Web Chrome 测试，以及两者的先后顺序。
4. 主 Agent **可以**明确授权子 Agent 执行具体测试任务，但**授权测试不等于转移模拟器启停权**。
5. 主 Agent 发出全局停止令后，**可以自主决定何时恢复**，不需要再走编号流程。

### 28.2 子 Agent 限制（严格保留，不因主 Agent 放宽而放宽）

1. **子 Agent 不得自行启动、关闭、重启模拟器。**
2. **禁止通过 ADB、脚本、后台进程、IDE、Gradle 任务、`nohup`、构建钩子或其他间接方式改变模拟器运行状态。**
3. 子 Agent 需要使用模拟器时，**必须向主 Agent 申请具体测试任务**，说明：测试目标 / 为什么非用模拟器不可 / 预计耗时 / 逐条具体命令 / 释放方式。**不得先启动再汇报。**
4. 主 Agent 的全局停止令**优先于此前所有任务指令、Agent 自身计划和旧执行令**。子 Agent 必须立即停止模拟器相关操作，**未经主 Agent 明确允许不得恢复**。就算子 Agent 认为测试还没做完，也必须停下等。
5. 主 Agent 关闭模拟器后，**任何子 Agent 不得重新启动它。**
6. **发现擅自启动**：立即收回该 Agent 的模拟器操作权限，保留日志与进程信息并上报；**不得为了进度默认接受**。

### 28.3 设备数量与测试顺序

4. **每轮测试结束后，执行者必须向主 Agent 汇报**：测试结果、异常、处理情况。

### 29.4 降采样规则

2. 降采样只通过 `adb shell wm size` / `wm density` 在运行时施加；
3. 报告里**同时写明**「目标物理参数」与「本次测试渲染参数」两个数字，并注明后者是降采样；
4. **降采样结果不得冒充原生分辨率验证结论**。

### 29.5 验收结论写法

- 可写「已验证」：分辨率、density、逻辑窗口、Insets、应用可用区域、旋转 —— 这些 AVD 能如实报告。
- **必须写「模拟器不支持 / 未验证」**：HDR（Dolby Vision / HDR10 / HLG / HDR10+）、广色域、真实 120 Hz 面板刷新、EDID 型号与构建日期。
- 禁止把「设了 `hw.lcd.vsync=120`」写成「120 Hz 已验证」。

### 30.7 实现契约：单实例 + 按 tag 复用（2026-10-31 13:10 落地并自证）

**唯一实现入口**：`web/_tools/lib/edge-launch.mjs`（`launchBrowser` / `openGame`）与
`web/_tools/lib/patch-launch.mjs`（猴补丁替换 `puppeteer.launch`）。**任何脚本都不许自己 `spawn` msedge。**

四条硬约束：

1. **实例身份与调用方解耦**。`launchBrowser()` 忽略调用方传的 `port`，一律用
   `SHARED_CDP_PORT = Number(process.env.OREKI_CDP_PORT || 9300)`。传进来的 port 只作为
   「共享端口探不到时的备选探测」，**永远不决定实例身份，永远不用于 spawn**。
   这样老脚本里写死的 9355/9356/9376 不再制造新实例。
2. **复用优先**。先 `GET /json/version`（1500 ms）探测，通了就 `puppeteer.connect`，
   返回 `reused: true`；复用分支的 `cleanup()` **只 `disconnect`，绝不 close/kill**。
3. **新建有硬上限**。新建前数 `tasklist /FI "IMAGENAME eq msedge.exe"`，超过
   `OREKI_MAX_EDGE_TOTAL`（默认 70，≈2 个实例）直接抛错拒绝启动。
4. **页面按 tag 复用，到上限就失败而不是抢占**。`openGame({ tag })` 把 tag 写进
   `index.html?orekiTag=<tag>`，下次同 tag 命中即复用；页面数超过 `OREKI_MAX_PAGES`（默认 6）
   直接抛错，**不抢占别人的页面**。
   —— 这一条是血换的：曾经有过「都没有就复用第一个页面」的档位，复用路径紧接着 `page.goto()`，
   跨 Agent 命中同一 Tab 会把对方正在跑的游戏页导航掉，受害方看到的是
   「采样断流 / `evaluate` hang 但 node 进程存活」，**极易被误判成游戏代码卡死**，
   从而把终局结论写反。宁可显式失败，也不能静默抢占。

**清理语义**：`cleanup()` 默认**只断开连接、不关闭共享实例**（`OREKI_CLOSE_ON_CLEANUP=1` 才真关）。
旧实现 cleanup 会 close + kill，于是「跑一次→建一个→用完关掉→下次再建」，虽然同一时刻只有 1 个实例，
但每次运行都是一次全新进程树，既慢又挡不住并发时各自新建。**收尾清场由主 Agent 显式执行。**

**自证用例**（改这个库必须跑，`pass: true` 才算改对）：

```bash
cd web/AD-Oreki-Edition && node serve.mjs 8099 &   # 静态服务
cd web && node _tools/_r42c/verify-reuse.mjs
```

实测读数（2026-10-31 13:05，同一进程连跑三次）：

| 调用 | reusedInstance | 页面总数 | 本 tag 页面 | 游戏可读 |
|---|---|---|---|---|
| 第 1 次 | false（新建） | 1 → 2 | 1 | true |
| 第 2 次 | **true** | 2 → 2 | 1 | true |
| 第 3 次 | **true** | 2 → 2 | 1 | true |

（页面总数含 1 个 Edge 内置页，所以「总数 = 1」不是有效判据，判据是「本 tag 页面恒为 1 且总数不增长」。）

**三次修正的教训，按顺序记下来**：

1. 只写规则不改代码 → 复发（12:15）。规则管不住 `Date.now()`。
2. 改了 `edge-launch.mjs` 但留了「复用第一个页面」的抢占档位 → 差点造出更隐蔽的假故障（误判为游戏卡死）。
3. `cleanup()` 仍会 close 自建实例 → 每次运行重新建实例，「复用」形同虚设，第 2、3 次全落空。
4. 主 Agent 每杀一次进程，下一次运行就必须重建实例 → **看起来像「一直在开浏览器」，其实有一半是止损动作自己造成的**。
   止损要一次性做到位，不要反复杀。


## §31 长期协作规则 v1（用户 2026-10-31 18:10 下达，长期有效，**本节是 Agent 调度与交付纪律的唯一源**）　⚠ 多 Agent 部分已由 §60 废止（2026-11-01）

> 本节优先级高于单一轮次任务中的一般性建议，也高于此前与本节冲突的旧条款（见文末「与旧条款的冲突裁决」）。
> 适用于主控 Agent、全部子 Agent、Web/Android 双端开发、测试、构建与发布。

### 一、Agent 调度：硬性上限 3 个

1. 同时活跃的子 Agent **最多 3 个**，主控 Agent 不计入。
2. **子 Agent 不得创建其他子 Agent**，禁止递归派生。
3. 创建新 Agent 前，主控必须盘点全部现存 Agent 状态，确保创建后仍不超过 3 个。
4. 每个 Agent 必须有明确任务、修改范围、交付标准，避免重复调查与文件冲突。
5. 标准分工（任务不适合并行时不必凑满 3 个）：
   - Agent A：Web 开发与浏览器验证
   - Agent B：Android 开发、REA 分析与 APK 构建
   - Agent C：教程中文化及双端一致性检查
   - 主控：游戏机制、智能自动购买器、协调、整合、验收、交付
6. 已超过 3 个时：立即停止新建 → 盘点任务/改动文件/进程/未提交成果 → 保留最多 3 个最有价值且不冲突的 → 对重复调查、空闲、重叠任务安全停止。
7. **不得粗暴终止正在写文件、构建或执行原子操作的进程**；先让其完成当前原子操作。
8. 主控负责整合全部成果，不得把协调工作继续层层转交。

### 二、开发原则：快速迭代，尽快交付

### 二、识别顺序（每次环境变化后按此顺序查，不许跳）

1. 操作系统代理设置 → 2. 终端环境变量（大小写都查）→ 3. `git config` 的 proxy → 4. 浏览器代理 → 5. 代理客户端进程与公开配置 → 6. `netstat -ano | rg LISTENING` 确认端口**真的在监听**。
   - 不得仅凭配置文件存在就认定代理可用；**必须用实际连接测试确认**。
   - 没有可用代理就明说，**不得伪造代理成功状态**。

### 三、分流策略

1. 大陆可正常访问的 → **直连**。
2. GitHub、Releases、海外代码托管、依赖源，直连失败或明显不稳 → 用现有代理。
3. 国内镜像、国内云服务、局域网 → 直连。
4. **`localhost` / `127.0.0.1` / 局域网 / 模拟器本地服务不得走外部代理**，`NO_PROXY` 必须设好，否则本地构建与模拟器调试会被自己的代理打断。
5. 不为单个站点失败改全局代理模式；有规则模式就用规则模式。

### 四、按工具分别配置（不许「设个环境变量就以为全都生效」）

- **Git**：`git -c http.proxy=… -c https.proxy=…` 单次命令级优先；持久化前先确认不影响其他仓库。
- **Gradle**：Wrapper 走 `gradle.properties` 的 `systemProp.http(s).proxyHost/Port`，或 `JAVA_TOOL_OPTIONS`；依赖仓库是否可达要单独判断。
- **npm / pip**：`npm config set proxy` / `pip --proxy`，单次命令级优先。
- **curl**：`-x/--proxy` 单次参数；`--noproxy '*'` 显式绕过。
- **浏览器**：区分系统代理与浏览器独立代理，二者可能不同。
- 优先**进程级 / 单次命令级**代理；改持久化配置前先备份，且不得把代理地址、账号、密码、令牌写进仓库。

### 五、验证与故障处理

每次经代理访问关键服务都要验证**实际结果**，至少区分：DNS 解析 → TCP 连接 → TLS 握手 → HTTP 状态码 → 业务是否真的完成（Git Push / 文件下载 / Pages 部署）。

故障处理顺序：测直连 → 测代理 → 对比两者 → 按错误类型选最小修复 → 修完用**真实业务操作**复验。

**禁止**：无限重试、频繁切换节点、无依据改 DNS/证书/系统网络、关闭 TLS 校验、把「代理连通测试成功」当成「Push / 下载 / 部署成功」。

### 六、凭据与安全

1. 日志、截图、提交、报告里**不得输出**代理账号/密码/令牌。
2. 不把代理凭据硬编码进源码或仓库配置。
3. 用户已有的代理配置**只读**，不擅自删除或覆盖。
4. 不擅自购买代理服务、不安装来源不明的代理客户端或证书。

### 七、与发布流程（§32）结合

1. GitHub 操作失败先判断是否需代理；**Push、Pages 部署、依赖下载必须分别验证**，不能互相替代。
2. Gradle 依赖下载失败，先判断具体仓库可达性，再决定代理或镜像。
3. 访问 `https://oreki.net/` 失败时，**先区分「部署失败」与「本地网络访问失败」**。
4. 代理导致的等待与失败要记实际耗时，**不重复走已知无效路径**（§32 四）。

1. Agent 完成后立即汇报六项：完成的功能 / 修改文件 / 提交与未提交改动 / 实际验证结果 / 遗留问题 / 当前进程。
2. 主控确认成果已保存、文件安全后**立即回收**；不为留住 Agent 安排无价值工作。
3. 回收前保留代码、日志、截图、测试结果与必要上下文；回收后确认进程与会话已释放。
4. 正在原子写入 / 生成文件 / Git 操作 / 正式构建的，**必须安全完成或安全中止**；**禁止粗暴杀进程**。
5. Agent 失联先查进程与文件状态再回收；**回收后不得自动重启重复任务**。

### 四、建新 Agent 前置检查（缺一不可）

盘点数量状态 → 回收 DONE 未 CLOSED → 能否交给现有 Agent → 任务是否重叠 → 文件与共享资源是否冲突 → 确认是独立且有价值的工作 → 创建后立即登记。

### 五、每轮收尾必答

本轮创建 N 个 / 当前活跃 N 个 / 已回收 N 个 / 是否有 DONE 未 CLOSED 或异常滞留 / 是否有遗留构建进程·浏览器·模拟器占用 / 是否有未提交成果未保存。

### 六、执行优先级（冲突时按此顺序）

1. 保护用户已有代码、未提交改动与有效构建产物
2. 遵守活跃 ≤3 硬限制
3. 防止共享文件 / AVD / Gradle / 浏览器冲突
4. 优先回收已完成或低价值 Agent
5. 名额分配给当前最重要的独立瓶颈
6. 尽快完成实际开发与交付

> 原则：子 Agent 是临时工作单元，不是永久驻场员工。创建必须有价值，任务必须有边界，完成必须交付，交付之后必须回收。

## §36 主 Agent 主动推进原则（用户 2026-10-31 20:01 下达，长期有效，**本节是主 Agent 工作方式的唯一源**）

> 一句话：**主 Agent 是项目执行负责人，不是传声筒、不是等待器、不是进度查询器。**
> §35 管的是「子 Agent 怎么生怎么死」，本节管的是「子 Agent 活着的时候主 Agent 在干什么」。

### 一、禁止无任务干等

主 Agent 不得在子 Agent 执行期间：

1. 无任务等待（什么都不做，只等消息）；
2. 反复询问子 Agent「进度如何」；
3. 仅靠轮询消息 / 轮询 TaskOutput 维持会话活性。

只要存在可以独立推进的工作，主 Agent 必须立即开展。**不得把全部可执行任务转交子 Agent 后自己停工。**

### 二、子 Agent 工作期间主 Agent 必须持续负责至少一个真实工作流

可选方向（优先选不与子 Agent 文件范围冲突的）：

1. 跨端机制对照与功能集成；
2. 真实通关瓶颈分析及根因修复；
3. 原版源码、原版 APK、REA 证据研究；
4. 测试环境、构建流水线、发布准备；
5. FACTS、规则冲突、跨端一致性维护；
6. 已完成成果的集成、验证与交付；
7. 验收探针 / 测试脚本的编写与自检（这条最容易漏，因为看起来「也是测试」）。

### 三、子 Agent 处于 ACTIVE / WAITING 时主 Agent 的行为

1. 继续推进其他独立任务；
2. 定期检查是否有**已完成成果可以立即集成**（不等全部结束）；
3. 发现阻塞时主动寻找其他可推进的瓶颈，而不是停下来等；
4. 不得因为某个 Agent 未完成就让整个项目停摆；
5. 不得为了避免等待而重复分配相同任务、或制造无意义改动充数。

### 四、存在依赖时的正确做法

后续工作确实依赖子 Agent 成果时：

1. 明确记录依赖关系（谁依赖谁、依赖哪个产物）；
2. 先完成所有不依赖该成果的工作；
3. 预先准备好集成、测试、发布步骤（脚本先写好、环境先验好）；
4. 等待条件解除后**立即**继续，不做二次准备；
5. 不得提前修改对方正在负责的文件。

共享资源（AVD / Gradle / 浏览器 / 同一工作树）仍按 §31~§35 的锁定规则串行使用。

### 五、子 Agent 完成后的即时集成（DONE 即处理，不堆积）

收到成果后立即：

1. 检查实际文件与提交（不信口头汇报，只认磁盘与 git）；
2. 确认成果是否符合任务目标（不达标就补，不假装通过）；
3. 尽快集成并做定向验证；
4. 解决跨端冲突；
5. 回收该 Agent（DONE → CLOSED）；
6. 立即安排下一个独立工作。

**禁止把多个已完成的成果长期堆积，等所有 Agent 全结束再统一处理。**

### 六、明确禁止的行为

1. 创建子 Agent 后一直等待；
2. 频繁发「进度如何」而不推进自己的工作；
3. 把所有可执行任务都转交子 Agent；
4. 子 Agent 完成后长期不集成、不验证；
5. 用 Agent 数量、任务数量、报告数量代替实际交付。

### 七、每轮核心验收（主控自答，答不上就是没做到）

1. 子 Agent 工作期间，主 Agent 有没有产出实际成果？
2. 是否存在本可并行、却被串行等待的任务？
3. 子 Agent 完成后是否及时集成并验证？
4. 是否因为无意义等待拉长了交付时间？

### 八、与 §31 / §35 的关系

- §31 管并发上限与共享资源；
- §35 管登记表、状态机、回收；
- §36 管主 Agent 自身的产出义务。
- 三者不冲突：**主 Agent 既要管住 Agent 数量，也要保证自己一直在干活。**
- 「所有 Agent 都在工作，项目才算真正推进」——主 Agent 自己也算一个必须工作的执行单元。

## §37 双小时强制交付机制（用户 2026-10-31 20:14 下达，长期有效，**本节是交付频率的唯一源**）

> 一句话：**任意连续两次有效交付之间不得超过 2 小时。2 小时是绝对上限，不是建议开发周期。能提前交付就立即交付。**
> §32 管单次发布耗时，§35 管 Agent 生命周期，§36 管主 Agent 不得干等；**§37 管用户能真正拿到可用成果的频率**。
> 规则冲突时遵循用户最新明确指令，**不得以其他规则为借口延迟有效交付**。

### 一、强制交付期限

1. WorkBuddy 在项目开发期间，**任意连续两次有效交付之间不得超过 2 小时**。
2. 项目启动后，**必须在 2 小时内完成首次有效交付**。
3. 从**上一次有效交付完成时间**开始，重新计算下一轮 2 小时期限。
4. **不得通过重启 Agent、切换任务、重新分配任务、重新开会或更换工作轮次重置计时。**
5. 2 小时是绝对上限，不是建议开发周期。能提前交付就立即交付。

### 二、有效交付定义（任选一种，即构成一次有效交付）

**Web 交付：**

1. 完成 Web 构建；
2. Push 到 GitHub；
3. 成功部署到 GitHub Pages；
4. 确认线上页面可以正常访问；
5. 记录部署版本和线上地址。

**Android 交付：**

1. 使用 Gradle 完成 APK 构建；
2. 完成必要的定向验证；
3. 将 APK 上传到 OneDrive 和小米云盘；
4. 记录 APK 版本、文件大小、SHA-256 和本地上传客户端状态；
5. 按现有规则，**双网盘不要求远程回读核验**。

两种交付满足任意一种即可，**不要求每次同时完成双端发布**。

### 三、明确不算交付的行为

以下行为**均不能单独算作**有效交付：

1. Commit 或 Push 到 GitHub；
2. 本地构建成功但没有部署或上传；
3. 只有测试、审计、分析、计划、报告；
4. APK 只保存在本地；
5. Web 只完成 Push，尚未完成 Pages 部署；
6. 仅完成代码修改，没有形成用户可实际使用的版本。

### 四、双端并行与交付切片

1. Web 和 Android **必须持续并行开发**，不能因为一端任务复杂而停止另一端。
2. 主 Agent 每轮开始时必须规划**不超过 2 小时的可交付任务切片**。
3. 优先选择能够**独立构建、部署或上传**的成果。
4. 不必等待另一端全部完成，**先完成的一端可以先交付**。
5. 不得为了追求双端同时发布而**错过 2 小时期限**。
6. 教程、自动购买器、剧情进度感知、挑战即时完成、移动端适配等功能**持续开发**，不得退化为长期只做审计和基础设施。

### 五、期限预警与强制切换

1. 距离交付期限**剩余 30 分钟**：停止扩展非必要新功能，集中集成、修复和交付。
2. 剩余 **15 分钟**：进入强制交付模式，优先完成**已经成熟的一端**。
3. Web 被阻塞 → 立即评估 Android 是否可以完成交付。
4. Android 被阻塞 → 立即评估 Web 是否可以完成交付。
5. **不得因为某个子 Agent 尚未完成而干等。**
6. 两端均阻塞时，主 Agent **必须亲自排查并选择最短的安全交付路径**。

### 六、主 Agent 责任

1. 主 Agent 对双小时交付期限承担**最终责任**。
2. **不得将交付责任完全转交给子 Agent。**
3. 子 Agent 执行期间，主 Agent 必须继续推进其他独立工作（见 §36）。
4. 主 Agent 必须**主动准备构建、验证、部署和上传**。
5. 不得以 Agent 数量、任务数量、Commit 数量、测试报告数量**替代实际交付**。
6. 每次交付后**立即规划下一轮交付**，不得出现无目标等待。

### 七、交付记录（每次必填）

| 项 | 内容 |
|---|---|
| 本轮开始时间 | |
| 上一次有效交付时间 | |
| 本轮交付完成时间 | |
| 本轮实际耗时 | |
| 交付平台 | Web / Android |
| Git Commit | |
| Web 线上地址 / Android APK 文件信息 | |
| 下一次交付的最晚截止时间 | |
| 当前距离下一次交付剩余时间 | |

**每轮状态报告必须明确说明是否满足双小时期限。**

### 八、与其他规则的关系

1. **§32 发布耗时预算**继续有效，约束单次发布过程；
2. **§35 子 Agent 生命周期**继续有效，约束 Agent 数量、回收和资源管理；
3. **§36 主 Agent 主动推进原则**继续有效，禁止主 Agent 干等子 Agent；
4. **§37** 约束实际用户可用成果的交付频率；
5. 规则冲突时遵循用户最新明确指令，**不得以其他规则为借口延迟有效交付**。

## §38 Microsoft Edge 性能与生命周期管理（用户 2026-10-31 20:19 下达，长期有效，**本节是浏览器资源的唯一源**）

### 一、核心原则

1. WorkBuddy 必须**主动管理** Microsoft Edge 的进程、标签页、内存、CPU 和后台活动。
2. **Edge 是开发机共享资源，不是可以无限创建的自动化工具。**
3. 必须优先复用现有浏览器实例和标签页，**禁止为每项任务重复启动浏览器**。
4. 不得为了追求自动化并行度而牺牲开发机整体性能。

### 二、浏览器实例管理

1. 优先复用已经运行的 Edge 和现有 CDP 实例。
2. 当前项目优先复用 `OREKI_CDP_PORT=9300`，但**必须先确认端口实际可用及对应进程**。
3. **禁止每个子 Agent 各自启动独立 Edge。**
4. 禁止为同一个 Web 页面重复创建多个浏览器实例。
5. 测试时优先复用现有标签页，及时关闭无用测试标签。
6. **不得擅自关闭用户正在使用的 Edge 窗口或标签页。**
7. 不得把用户浏览器与 WorkBuddy 自动化浏览器混为一谈。
8. 如果无法确认某个 Edge 实例是否属于用户，**先保留，不得直接终止**。

### 三、资源监控（浏览器自动化密集阶段主动检查）

- Edge 进程数量及进程树；
- 浏览器总内存占用；
- CPU 使用率；
- 标签页数量；
- 是否存在崩溃、无响应或持续高占用标签页；
- 是否存在重复的后台浏览器进程；
- CDP 实例是否被多个任务争抢。

**区分浏览器主进程、GPU 进程、渲染进程和后台服务进程，不得仅凭进程数量就判断异常。**

### 四、性能控制

1. 优先使用单个 Edge 实例和最少必要标签页。
2. 不需要的测试页面及时关闭。
3. 不要让多个 Agent 同时对同一浏览器实例执行互相冲突的操作。
4. 浏览器测试与 Android AVD 测试按共享资源锁定规则协调。
5. 对持续高 CPU 或内存占用的任务进行定位，**先判断是否为必要负载**。
6. 不得为了节省资源直接关闭用户的重要窗口。
7. **不得使用强制结束进程作为常规清理手段。**
8. 结束自动化任务后，清理其专属标签页和可确认归属的浏览器进程。

### 五、浏览器生命周期

1. 浏览器启动前**先盘点现有实例**。
2. 自动化任务结束后，优先释放任务创建的标签页和临时资源。
3. 如果浏览器仍承担后续**明确排期任务**，可以继续保留。
4. 如果浏览器无任务且属于 WorkBuddy 专用实例，应正常退出。
5. 用户自己的 Edge 实例**默认保持运行**。
6. CDP 端口释放前确认没有其他任务依赖。
7. 禁止无目的地让多个 Edge 实例长期驻留。

### 六、Agent 协作

1. **主 Agent 统一管理 Edge 实例和 CDP 端口。**
2. 子 Agent **不得擅自启动**新的共享浏览器实例。
3. 多个 Agent 需要浏览器时，由主 Agent 安排串行使用或明确的互不冲突操作。
4. Agent 结束时必须报告自己创建的标签页、浏览器进程及尚未结束的自动化任务。
5. 回收 Agent 时检查其浏览器资源是否已经释放。

### 七、性能异常处理

发现 Edge 出现异常高占用时：

1. 确认进程归属；
2. 定位对应标签页或自动化任务；
3. 检查是否存在重复实例、死循环、页面持续重载或无意义轮询；
4. **优先停止造成异常的自动化任务**；
5. 仅关闭明确属于 WorkBuddy 且不再需要的页面或实例；
6. 保存必要的测试日志和结果；
7. 恢复后继续项目开发，**不得让性能排查无限阻塞交付**。

### 八、每轮报告必答

- Edge 实例数量；
- WorkBuddy 专用实例数量；
- 用户实例是否保持原状；
- 标签页数量；
- 浏览器内存和 CPU 占用；
- CDP 端口及使用者；
- 是否存在异常进程或待清理资源；
- 下一轮是否需要继续占用 Edge。

### 九、与现有规则协同

遵守 §34 AVD 生命周期、§35 子 Agent 生命周期、§36 主 Agent 主动推进、§37 双小时强制交付。
**Edge、AVD、Gradle 和共享工作树均属于需要统一调度的开发资源。**

> 最终原则：浏览器够用即可，不重复启动；任务结束及时释放；用户正在使用的浏览器绝不擅自干扰。

## §39 子 Agent 持续工作与任务接续机制（用户 2026-10-31 20:42 下达，长期有效，**本节是子 Agent 持续工作的唯一源**）

### 一、核心原则

1. 子 Agent 应尽量**持续承担有实际价值的开发任务**，避免无意义等待、频繁停止、重新创建和重复熟悉项目。
2. 在不影响代码安全、资源管理和双小时交付的前提下，**优先保持有效工作连续性**。
3. Agent 不以数量和在线状态衡量价值，**以持续产生可集成成果衡量价值**。

### 二、任务接续机制

1. 每个子 Agent 接近完成当前任务时，应**主动检查自己负责范围内是否还有可独立推进的后续任务**。
2. 当前任务完成后，如果存在明确、有价值且不与其他 Agent 冲突的后续任务，**可以直接接续**，不必等待主 Agent 再次分配。
3. 后续任务必须属于**主 Agent 已授权的工作范围和项目目标**。
4. **不得擅自扩大文件修改范围、改变技术路线或执行未授权的发布操作。**
5. 没有合适后续任务时，向主 Agent 提交成果和可接续任务建议。
6. 主 Agent 应及时安排下一项任务，**避免 Agent 长时间闲置**。

### 三、持续工作优先级

子 Agent 应优先处理：

- 当前任务的剩余实现和集成。
- 同一功能范围内的后续缺陷修复。
- 双端机制一致性检查及实际差异修复。
- 原版源码、原版 APK、REA 的针对性研究。
- 教程内容与实际游戏机制同步。
- 自动购买器的真实执行闭环。
- 移动端适配和真实界面验证。
- 已完成代码的定向测试及回归修复。
- 对当前任务有直接价值的文档和 FACTS 更新。

**不得为了保持忙碌而制造无意义代码改动、重复审计或低价值报告。**

### 四、WAITING 状态管理

1. WAITING 必须说明**具体等待原因、依赖对象、解除条件和预计检查时间**。
2. 如果等待期间仍有不冲突的独立工作，**应立即继续执行**。
3. 不得因为共享 AVD、Gradle、Edge 或工作树暂时被占用，就**停止所有其他工作**。
4. 共享资源需要排队时，可以先处理**不依赖该资源**的代码、研究、分析和集成准备。
5. 等待超过 **10 分钟**时，主 Agent 必须重新评估任务安排。
6. 等待条件解除后，**立即恢复原任务**，不得无意义地继续等待。

### 五、任务完成与 Agent 回收

1. 完成一个子任务**不等于**必须立即结束 Agent。
2. 优先由主 Agent 安排同一领域内的下一项有效任务。
3. 如果后续任务不存在、依赖长期无法解除或 Agent 已无继续工作的价值，则及时结束并释放名额。
4. **DONE 但尚未实际结束的 Agent 仍计入活跃数量。**
5. 不得为了维持在线状态而保留没有实际任务的 Agent。
6. Agent 结束前必须**保存成果、报告未提交修改和遗留进程**。

### 六、主 Agent 调度责任

- 主 Agent 必须维护 **Agent 任务队列和依赖关系**。
- 尽量提前准备每个 Agent 的后续任务。
- Agent 完成前，主 Agent 应准备好下一项适合其能力和文件范围的任务。
- **优先复用已经熟悉项目的 Agent**，减少频繁创建新 Agent 的上下文成本。
- 继续遵守**最多 3 个活跃子 Agent**的限制。
- 不得为了填满名额而创建无价值任务。
- **不得让所有 Agent 都等待主 Agent 才能继续工作。**

### 七、与其他规则协同

- §35 负责 Agent 数量、状态和生命周期。
- §36 负责主 Agent 主动推进。
- §37 负责双小时强制交付。
- §38 负责 Edge 性能和生命周期。
- §39 负责子 Agent 的持续工作和任务接续。

当持续工作与及时交付发生冲突时，**优先保证有效交付**；当持续工作与资源安全发生冲突时，**优先保证资源安全**。

### 八、每轮状态报告

增加以下指标：

- 活跃 Agent 数量。
- 正在执行实际任务的 Agent 数量。
- WAITING Agent 数量及等待原因。
- 本轮完成的任务。
- 已接续的新任务。
- 空闲 Agent 数量及原因。
- 本轮回收 Agent 数量。
- 下一轮任务队列。

### 九、立即执行

完成规则同步后，盘点当前所有 Agent。对仍有价值的 Agent，安排连续且不冲突的下一项工作；对等待中的 Agent，检查是否存在可独立推进的任务；对无任务且无法合理接续的 Agent，及时回收。
**不要只提交规则修改报告，继续推进双端实际开发和下一次有效交付。**

> 最终原则：尽量让每个 Agent 持续做有价值的工作，而不是完成一个小任务就停下来重新排队。

## §40 子 Agent 强制终止与失联处置（用户 2026-10-31 21:39 下达，§39 补充，长期有效，**本节是强制关闭权限的唯一源**）

### 一、主 Agent 拥有最终管理权

1. 主 Agent 是子 Agent 的**唯一调度和生命周期管理者**。
2. 子 Agent 必须服从主 Agent 的**任务调整、暂停、取消和终止**指令。
3. 子 Agent 无响应、失联或无法继续执行时，主 Agent 有权**直接强制关闭**。
4. **不要求无限次发送消息，也不要求等待子 Agent 主动确认。**

### 二、强制关闭条件（出现任一即可）

- 连续**两次**发送有效消息均未收到响应，且间隔至少 **2 分钟**。
- Agent 执行进程无响应或已经异常退出。
- Agent 长时间卡死，无法推进任务。
- Agent 任务已取消，但仍持续占用资源。
- Agent 阻塞其他关键任务或影响双小时交付。
- Agent 失去继续执行的必要条件，且没有合理恢复方案。
- Agent 已经完成任务，但无法正常结束或释放资源。

### 三、强制关闭前的最小保护

在不影响紧急处置的前提下：

1. 记录 Agent ID、任务、文件范围和**最后响应时间**。
2. 检查是否存在**未提交修改**。
3. 检查是否存在正在写入的文件、构建或测试进程。
4. 尽可能保存已完成成果及必要日志。
5. 停止新的写入和工具调用。
6. 对可安全终止的 Agent 执行关闭。

如果 Agent 已经造成严重资源阻塞或影响交付，**可以跳过不必要的等待，立即终止**。

### 四、强制关闭后的资源回收

- 确认 Agent 不再运行。
- 检查其遗留进程和未完成操作。
- 确认共享工作树没有被遗留写入继续修改。
- **保留未提交成果，不得擅自丢弃。**
- 释放 Agent 名额。
- 更新 Agent 登记表，状态设为 **CLOSED**。
- 记录强制关闭原因及时间。

### 五、重新分配

- 任务仍然有价值时，可以交给现有 Agent 或新 Agent 接续。
- 接续前必须检查原 Agent 是否**已经彻底停止**，防止两个 Agent 同时修改同一文件。
- **优先复用已经熟悉项目的其他 Agent。**
- **不得因为等待失联 Agent 而延误 Android APK 发布或 Web 部署。**

### 六、权限边界

强制关闭 Agent **不等于**允许破坏其工作成果。不得因此执行无条件 `git reset`、`git clean`、强制覆盖文件或强杀用户自己的 Edge、Gradle、AVD 进程。
**必须区分 Agent 本身与它启动的独立构建、浏览器、模拟器进程**，避免误伤其他任务。

> 最终原则：主 Agent 可以立即结束失联或失效的子 Agent，不必等待其同意；但必须尽可能保护已经产生的代码和交付成果。


## §41 frame-observer 主动授权与观测（用户 2026-10-31 21:52 下达，长期有效，**本节是 Android 观测的唯一源**）

### 一、定位

- frame-observer 是 Android 端**唯一的画面 + 控件树观测通道**，不是可选项。
- 凡涉及 Android UI 验收（教程页是否深色、顶栏、两行 `ScrollableTabLayout`、按钮是否真的可点、画面是否卡死），
  **一律先用它取证据**，不允许凭「应该没问题」写结论。
- **「主动获取授权」= 主 Agent 自己把整条授权链路走完**，不把「你去点一下开始捕获」这类动作留给用户。

### 二、授权链路（每次 AVD 重启或投影被收回后必须重走）

1. adb 全路径：`C:/Users/Oreki/Android/sdk/platform-tools/adb.exe`（**不在 PATH**，必须写全）。
2. `adb devices` 必须看到 `emulator-5554  device`。
3. `adb forward tcp:8731 tcp:8731`，再用 `adb forward --list` 确认。
4. `curl -s -m 5 http://127.0.0.1:8731/stats` 探活。连不上或 `capturing=false` → 进第 5 步。
5. 冷启动：`am force-stop com.oreki.frameobserver` → `am start -n com.oreki.frameobserver/.MainActivity`。
6. **冷启动场景下 `/ui` 必定 503**（HTTP 服务随进程一起停，实测返回 `{"无障碍服务未连接"}`），
   所以这一步**必须用 `uiautomator dump`**，且 Git Bash 会做 MSYS 路径转换，**必须 `export MSYS_NO_PATHCONV=1`**，
   否则 `/sdcard/fo.xml` 会被改写成 `.../PortableGit/sdcard/fo.xml` 而静默失败：
   `adb shell uiautomator dump /sdcard/fo.xml` → `adb shell cat /sdcard/fo.xml`。
   按钮是 `com.oreki.frameobserver:id/btn_start`（文本「开始捕获」）。
7. 系统投影对话框由 `com.android.systemui` 弹，**文案是英文**：`START NOW`（`android:id/button1`）/ `CANCEL`（`android:id/button3`）。
   在这里才可以用 `/ui`（此时进程已起、a11y 若正常）或继续 `uiautomator dump` 拿 bounds → tap。
8. `/stats` 复核三项，全过才算授权成功：`capturing=true`、`frames_processed` 在增长、`actual_fps>0`。
9. **授权成功后必须把无障碍服务写回**：`am force-stop` 会把 `settings secure enabled_accessibility_services`
   清成 `null`、`accessibility_enabled` 变成 `0`（实测），不写回则 `/ui` 一直返回
   `503 {"error":"无障碍服务未连接"}`。命令：
   ```
   adb shell settings put secure enabled_accessibility_services      com.oreki.frameobserver/com.oreki.frameobserver.a11y.ObserverA11yService
   adb shell settings put secure accessibility_enabled 1
   ```
   写回后再用 `/ui` 复核一次，返回 JSON 数组才算恢复。

### 三、不可绕过的边界

- **不允许**用 `pm grant` 或任何等价手段伪造投影权限；MediaProjection 只能走系统对话框。
- 工具刻意**不提供** `POST /capture/start`，禁止我给它加远程触发接口来「省掉确认这一步」。
- 授权对话框只在设备前台可见：动手前用 `dumpsys window | rg mCurrentFocus` 确认 `MainActivity` 在前台。

### 四、自愈与失效判定

- 投影被系统收回（`MediaProjection.onStop`）表现为 `/stats` 的 `capturing=false`，或 `/stats` 直接不可达。
- AVD 重启、app 被 force-stop、系统回收前台服务 —— 这三种都要重走第二节。
- **连续两次走完第二节仍拿不到 `capturing=true`**，才允许报「frame-observer 不可用」，
  并附 `/stats` 原文 + `logcat` 相关行，不许只写一句失败。

### 五、观测纪律

- 控件树用 `/ui`：它**不等 idle**，专治 `uiautomator dump` 在动画画面上报 `could not get idle state`。
- 画面用 `/snapshot.jpg`（响应头带 `X-Frame-Id` / `X-Frame-Mono-Ns`）；**没看图不得断言画面正常**。
- 时序问题用 `/frame_at?t=<ns>` 回放；无障碍事件用 `/events?since=N`。
- **bounds 是物理像素 1440×1600，画面是 720×1600 半分辨率**，换算别搞错。
- 截图与控件树要落到 `android/reports/` 对应轮次目录，作为验收证据。

### 六、与采集中会话的关系

- 正在采集（`capturing=true` 且 `frames_processed` 持续增长）时，不得为图省事 force-stop；
  确需重启，先记录原因与当时的 `frames_processed`。
- 采集会话本身不是交付物，但它是 Android 端 UI 结论的**唯一证据源**，丢证据比丢帧严重。

> 最终原则：Android 端要看的、要点的、要证明的，先用 frame-observer 拿到证据再下结论；授权这一步由主 Agent 自己走完，不推给用户。

## §42 frame-observer 按需求可修改（用户 2026-10-31 22:00 下达，长期有效，**本节是修改该工具的唯一源**）

### 一、授权范围

- 用户已明确授权：**可以按需求修改 frame-observer**（源码、资源、构建脚本、文档均可改）。

2. `adb install -r` 装机成功，`MainActivity` 能起到前台。
3. **完整走一遍 §41 第二节链路**，确认改后仍能自己拿到授权。
4. `/ui`、`/snapshot.jpg`、`/stats`、`/events` 四个端点各取一次真实响应，作为证据落到 `android/reports/`。
5. 失败要附 logcat 原文，不许只写「失败」。

### 五、留痕

每次修改必须在 `frame-observer/README.md` 或 `docs/` 下记一条：改了什么、为什么、验证结果。
涉及端点行为变化时，同步更新 README 的端点评测表。

> 最终原则：工具可以改，底线不能动。改它是为了让「自己拿授权、自己看证据」这条路更短，不是为了让确认步骤消失。

## §43 Android SDK / AVD / adb 下载走国内官方源（用户 2026-10-31 22:51 下达，长期有效，**本节是 Android 工具链下载路径的唯一源**）

### 一、规则

下载 **AVD 系统镜像 / Android SDK / Build-Tools / Platform-Tools(adb) / Emulator / cmdline-tools** 时，
**直连 `developer.android.google.cn`，不使用代理**（`127.0.0.1:7897` 在这条链路上关掉）。

这是官方提供的中国大陆镜像域名，直连比走代理更快也更稳。

### 二、容易踩的坑：看到 google 就开代理

§33 写的是「GitHub 等海外域名直连失败才走代理」，但 `google.com` 系列域容易被**下意识**套上代理，
结果反而变慢甚至超时。判断依据只有一个 —— **看后缀**：

| 域名 | 走法 |
|---|---|
| `developer.android.google.cn` | **直连**（官方大陆镜像） |
| `dl.google.com`（SDK 实际下载的 CDN） | **直连**（§33 已实测可达，根路径 404 属正常） |
| `maven.google.com` / `dl.google.com/dl/android/maven2` | **直连** |
| `github.com` / `githubusercontent.com` / Releases | 直连失败或明显不稳时走代理 |

### 三、操作要求

1. **先清代理环境变量再调 `sdkmanager`**，否则会继承 shell 里的 `http_proxy` 走代理：
   ```
   unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY all_proxy
   ```
2. `sdkmanager` **不要**加 `--proxy=http --proxy_host=... --proxy_port=...`；不加就是直连。
3. **AVD 与系统镜像**：
   ```
   sdkmanager "system-images;android-34;google_apis;x86_64" "emulator" "platform-tools"
   ```
   下载完用 `avdmanager create avd` 建 AVD；镜像体积大（1~2 GB），**下载前先确认磁盘余量**。
4. adb 单独更新：`sdkmanager "platform-tools"`，装完用
   `C:/Users/Oreki/Android/sdk/platform-tools/adb.exe version` 核验版本真的变了（**不能只看安装日志**）。
5. Gradle 若需 Google 仓库，优先用直连地址；国内网络下 `maven.aliyun.com/repository/google` 可作备选。
   **改仓库地址要写进该仓的 `build.gradle` 并留痕**，不要只在本机改。

### 四、失败处理

- 直连 `developer.android.google.cn` 失败时，先换 `dl.google.com` 再试；两者都失败才考虑代理。
- 走代理也失败，就明确报「本次下载失败」并附实际报错原文，**不许写成「已下载」而实际没有**。
- 下载完成后必须核验落地：文件存在 + 体积合理 + `sdkmanager --list_installed` 或 `adb version` 输出包含目标版本。

### 五、与其它节的关系

- 本节是 §33（代理网络与大陆环境适配）在 **Android 工具链下载**这一具体场景上的细化，冲突时**以本节为准**。
- §33 的「端口必须实探、不得假设」仍然有效：代理端口变了照样要重新探测。
- 本条只覆盖**下载**；`git push`、Release 附件、网盘上传等仍按 §33 判断是否用代理。

> 最终原则：Android 工具链优先走 `developer.android.google.cn` 直连；判断走不走代理看域名后缀，不看是不是「google」。

## §44 Android 顶栏必须沿用官方 Current Tab 导航（Oreki 2026-10-31 23:46 下达，P0 永久架构约束，**不可被后续 Prompt、重构或重写规则文件覆盖**）

## §45 每轮启动与结束的子 Agent 全量收回、轮次互斥规则（Oreki 2026-11-01 01:07 下达，P0 强制流程，**不可被后续 Prompt 或重构覆盖**）

> 本节解决的是**调度权归属**问题：同一时刻只允许一个轮次拥有写操作调度权。
> 不分轮次就并发写同一棵树，是本项目历史上返工与「文件被覆盖」的主要来源。
> 本节在**轮次边界**（开轮 / 收轮）优先于 §39 的「子 Agent 持续工作」规则；
> 其余时刻 §39 照常生效。本节**不删除、不覆盖** §39 与 §40 的任何原文。

### 一、本轮启动顺序（严格串行，不得并行）

必须按下列顺序执行，**前一步未完成不得进入下一步**：

1. **枚举上一轮全部子 Agent**：记录 Agent ID、任务、最后响应时间、状态（运行中 / 等待 / 失联 / 已完成）。
2. **冻结新写操作**：在旧 Agent 未全部收回前，**严禁创建、启动或委派任何新子 Agent**，主 Agent 也不得开始大范围改写。
3. **保护已有成果**：先把未提交改动落盘备份（`git diff`、未跟踪文件清单、关键构建产物信息），确认可恢复。
4. **收回全部旧 Agent**：逐个终止或等待其正常退出；失联、超时、无法交接的**允许强制终止**。
5. **检查后台进程**：Agent 进程与它启动的**独立进程**是两回事，必须分别检查——Shell、Python、Node、Gradle、浏览器、模拟器、下载任务都算。
6. **确认控制权**：确认没有旧 Agent 仍在写项目、没有遗留的文件写操作、未提交成果仍在。
7. **创建新一轮 Agent**：至此才允许创建新 Agent。

### 二、本轮结束顺序

正式交付前**再次全量收回本轮全部子 Agent**，必要时强制终止。
收回后由**主 Agent 统一完成**：代码集成 → 最终测试 → 构建 → Git 提交 → Push 与部署 → APK 交付 → FACTS 更新。

禁止「子 Agent 还在跑，主 Agent 就先 push」；也禁止「一边收回旧 Agent，一边创建新 Agent」。

### 三、Agent 与后台进程必须分开检查

- 收回 Agent **不等于**它启动的后台进程自动结束。浏览器、静态服务、Gradle daemon、模拟器可能继续存活。
- 检查时必须区分「本轮起的进程」与「用户自己的窗口」：**不得误杀用户正在使用的 Edge 窗口、正在玩的游戏、正在同步的网盘客户端**。
- 允许保留**明确属于本轮、且后续还要用**的进程（如本地静态服务、adb server），但必须在汇报中列出 PID 与用途。

### 四、未提交成果保护（硬约束）

- **禁止**以「收回 Agent」「清理现场」「重新开始」为理由执行 `git reset --hard`、`git clean -fd`、`git checkout -- .` 或强制覆盖未提交文件。
- 本地工作区是**连续开发现场**，不是可随意清空的临时目录。
- 任何需要丢弃的改动，必须先备份成 diff 落到 `reports/` 下，并由 Oreki 明确同意后才可删除。

### 五、调度权互斥

- 同一项目任意时刻**只有一个轮次**拥有写操作调度权。
- 新轮次在旧轮次 Agent 全部收回前，**不得执行写操作**（读、测量、取证是允许的）。
- 同一文件禁止多个 Agent 无协调并发修改；构建（Gradle / 打包）必须**串行**，同一时间只允许一个正式构建。

### 六、异常处置

- 子 Agent 长时间无响应：先判定是「还在干活」还是「失联」，超过约定时限无输出即视为失联，**强制收回**。
- 子 Agent 报告完成但文件未变：以**实际文件内容**为准，不采信口头完成。
- 收回过程中若发现旧 Agent 正在写关键文件：先等其写入完成或中断并备份，再收回。

### 七、验收

每轮必须能回答并留痕：

- 上一轮共有几个子 Agent，各自 ID 与任务，**如何收回**的。
- 是否有强制终止，原因是什么。
- 遗留进程清单（PID + 用途 + 是否保留）。
- 未提交成果备份路径。
- 本轮结束时同样的四问再答一次。

### 八、与其它节的关系

- 与 §39（子 Agent 持续工作）、§40（强制终止与失联处置）**并列**：本节只管轮次边界的全量收放与互斥，**不替代** §39/§40 的日常条款。
- 轮次边界处若本节与 §39 冲突，**以本节为准**（先收回，再开工）。
- 与 §44（官方 Current Tab）无冲突，互不覆盖。

## 48. 时间信息真实性与时区规范（2026-11-01 用户确立，长期有效，**本节是时间记录的唯一源**）

### 一、基本立场

**时间是测量数据，不是语言模型可以自由创作的文本。**
任何时间必须来自系统时钟、程序日志、Git 元数据或其他可验证记录。

### 二、时间来源（硬约束）

1. 当前时间**必须从实际系统时钟读取**，不得由模型凭记忆、上下文或推测生成
2. 需要当前时间时，优先读操作系统时间；需要精确时间戳时，用程序实际生成的值
3. **不得把模型自身的时间感知当作系统时间来源**
4. 无法读取可靠时钟时，**明确标记时间未知**，不得补造

### 三、统一时区

- 项目默认本地时区：**`Asia/Shanghai`（UTC+08:00）**
- UTC 时间必须带 `Z` 后缀；本地时间必须带偏移或明确标注时区
- **不允许只写一个容易产生歧义的时间**（例如裸写「15:05」而不说明时区）
- 不得用 VPN、IP 归属地或模型推测的地理位置决定时区

### 四、本机取时间的正确方法（实测，2026-11-01）

| 用途 | 命令 | 实测输出 |
| --- | --- | --- |
| 本地时间 | `date +"%Y-%m-%dT%H:%M:%S%:z"` | `2026-11-01T12:40:43+08:00` |
| 本地时间（等价） | `date --iso-8601=seconds` | 同上 |
| UTC 时间 | `date -u +"%Y-%m-%dT%H:%M:%SZ"` | `2026-11-01T04:40:43Z` |

**⚠️ 禁止使用 `TZ=Asia/Shanghai date`**：本机 Git Bash 下实测会给出**错误结果**——
输出 `2026-11-01T04:39:52+08:00`，即把 UTC 时刻标上了 +08:00 偏移（早 8 小时且时区标注错误）。
系统时区本身已正确配置为 +0800，**直接用 `date` 即可，不要覆盖 `TZ`**。

`date +%Z` 在本机返回空串，**不要用它判断时区**。

### 五、五类时间字段必须区分

任务单与报告必须分别标注，**不得混用**：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| 创建时间 | 任务文件实际创建时间 | 文件系统 / 可验证记录 |
| 开始时间 | 实际开始执行时间 | 系统时钟 / 进程日志 |
| 完成时间 | 实际完成时间 | 系统时钟 |
| 验证时间 | 实际执行验证的时间 | 系统时钟 / 测试日志 |
| 报告时间 | 报告实际生成时间 | 系统时钟 |

**没有发生的事件不得提前填写时间。**

### 六、时间戳真实性

1. 时间戳必须来自系统时钟、程序日志、Git 元数据或其他可验证记录
2. **不得根据 Agent 回复时间反推实际执行时间**
3. **不得把文件修改时间直接当作任务完成时间**
4. **不得把 Git commit 时间直接当作代码实际完成时间**
5. 时间精度不得超过来源实际提供的精度
6. 发现系统时钟异常、时间倒退或时区不一致时，**标记异常并保留原始记录**

7. **取时的三级降级顺序（2026-11-01 由 android-scheduler-agent 的自我更正引出，强制）**：
   ① 能用取时脚本就用（`python scripts/oreki_time.py --human`）；
   ② 拿不到就用**文件 mtime**（`ls -la --time-style=+%H:%M`）或日志时间戳；
   ③ **两者都拿不到就写「未记录」，绝不写推测值**。

   **回写历史记录时，若无法核验当时时间，宁可不填，也不要用「大约」「差不多」填充。**
   编出来的时间不是「不准确」，是**伪装成证据**——后续 Agent 会拿它排序、推断因果，
   一旦基线是假的，所有下游结论都是假的，而且查不出来。

   **实际事故**（2026-11-01）：某份任务单的执行记录表整体偏了 1.5 小时以上，
   因为时间是回写时按「大概什么时候」填的。主 Agent 亦有同类错误，
   曾凭上下文推出「现在 15:52」，而系统时钟为 12:31，偏差 3 小时 20 分。

### 七、多 Agent 时间记录

- 各 Agent 使用**同一台开发机的系统时间基准**
- 子 Agent **不得自行猜测**其他 Agent 的开始或完成时间
- 主 Agent 汇总时**保留各来源原始时间戳**，不得为凑成整齐时间线而修改
- 并行任务**允许时间重叠**，不得强行排列成虚假的串行时间线

### 八、定时器时间

- 触发时间以**实际调度器记录**为准，执行时间以**实际进程/脚本记录**为准
- 必须区分**计划执行时间**与**实际执行时间**
- 延迟、跳过、重复触发**必须如实记录**

### 九、发现时间错误时的处理

1. 保留原始错误记录（不得篡改历史日志）
2. 标记错误字段及原因
3. 使用可靠来源重新核实
4. 修正报告，但**不得篡改历史原始日志**
5. 无法核实时保留未知状态

### 十、统一时间工具

跨仓库脚本统一使用 `scripts/oreki_time.py`（工作区根目录下），输出 ISO 8601：

```bash
python scripts/oreki_time.py              # 2026-11-01T12:40:43+08:00
python scripts/oreki_time.py --utc        # 2026-11-01T04:40:43Z
python scripts/oreki_time.py --stamp      # 文件命名用的 20261101-124043
```

脚本内部用 `datetime.now().astimezone()`，跟随系统时区，**不硬编码 +08:00**，
以避免「机器时区不是 +08:00 时给出错误偏移」。

## 49. 时间格式：机器通信与人类阅读分离（2026-11-01 用户确立，长期有效，**本节是时间格式的唯一源**）

> **本节修正 §48 的一处过度要求。** §48 曾要求报告也使用 ISO 8601，这是错的——
> ISO 8601 是**机器之间**传递时间的标准格式，不是所有文档都必须采用的展示格式。

### 一、核心原则

**机器读 ISO 8601，人读自然时间。**

四类场景必须区分，不得混为一谈：

| 场景 | 格式 | 示例 |
| --- | --- | --- |
| **Agent 之间通信** / API / 结构化数据交换 | **ISO 8601 带时区** | `2026-11-01T12:44:52+08:00` |
| **文件存储与文档展示**（任务单、README、开发记录、执行报告、交付文档） | **自然时间** | `2026年11月1日 12:44` |
| **文件名** | 紧凑可排序 | `20261101-124452` |
| **程序内部存储** | 时间戳 / ISO / 数据库原生类型（按技术需要） | — |

### 二、Agent 之间的时间通信

1. 必须明确时区或 UTC 偏移量
2. UTC 使用 `Z`
3. **不允许省略时区让接收方自行猜测**
4. 保留原始精度，**不得擅自补充不存在的秒/毫秒**
5. 转发时间信息时**不得改变原始时间含义**

### 三、文件与文档展示（人类阅读）

任务单、Markdown、README、开发记录、执行报告、交付文档、**巡检报告**，
默认使用可读性高的自然时间：

- `2026年11月1日 12:44`
- `2026年11月1日 12:44:52`
- `11月1日 12:44`（同年内简写）

精度按记录需要决定。

**禁止为了格式统一，把所有文档中的时间都强制写成 ISO 8601。**

### 四、程序内部存储

可选 Unix 时间戳 / 带时区 ISO / 数据库原生时间类型，但必须保证：

1. 时间值能准确还原
2. 时区信息明确
3. 本地时间与 UTC 不发生混淆
4. 输出到人类文档时**转换为可读格式**
5. 输出到 Agent 通信时**转换为 ISO 8601**

**不得为了格式统一而牺牲时间准确性。**

### 五、定时器与多 Agent

- Agent 之间交换时间 → ISO 8601
- 定时器配置 → 机器可解析格式（RRULE 等）
- 定时器执行日志与**面向用户的巡检报告 → 自然时间**
- 必须区分**计划触发时间**与**实际执行时间**
- 多 Agent 并行时**保留各自真实时间**，不得拼接虚假串行时间线
- 用户查看进度时**优先展示自然时间**，不直接暴露大量机器时间戳

### 六、时间来源真实性继续有效

本节不改变 §48 的任何真实性要求：必须读系统时钟、默认 `Asia/Shanghai`、
不得推测时区、五类时间字段分开记录、不得用回复时间/mtime/commit 时间冒充完成时间、
无法核实标未知、发现错误保留原始记录。

### 七、统一工具

`scripts/oreki_time.py`（工作区级，跨仓库共用）：

| 命令 | 输出 | 用途 |
| --- | --- | --- |
| `python scripts/oreki_time.py` | `2026-11-01T12:53:33+08:00` | Agent 通信 / 程序 |
| `... --human` | `2026年11月1日 12:53:33` | **文档 / 报告（默认选这个）** |
| `... --human-short` | `11月1日 12:53` | 同年内简写 |
| `... --stamp` | `20261101-125333` | 文件名 |
| `... --utc` | `2026-11-01T04:53:33Z` | UTC |
| `... --tz-check` | 诊断 | 核对偏移是否 +08:00 |

**已实测**：ISO 与自然时间两种输出代表同一时刻（解析回 datetime 后差值 0 秒）。

### 八、最终原则

> **时间的真实性由时钟和证据保证，时间的展示形式由阅读场景决定。**

## 50. 任务单更新的署名与贡献归属（2026-11-01 用户确立，长期有效，**本节是归属记录的唯一源**）

### 一、核心要求

**任务单每次更新必须记录更新者的 Agent ID。**
主 Agent 汇总提交时，**不得把子 Agent 的实际执行贡献归到主 Agent 名下**。

### 二、为什么必须有这条

任务单的 commit 由主 Agent 统一做（因为三处硬链接共用 inode，子 Agent 各自 commit 会让两个仓库同时变脏）。
但 **「谁提交」不等于「谁做的」**：
- commit author 只有一个人
- 而任务单里记录的执行、诊断、修复、验证可能来自多个 Agent

若不在文档里显式署名，几轮之后就无法分辨「这条结论是谁得出的」，
既无法追溯责任，也会让子 Agent 的实质贡献被稀释成主 Agent 的功劳。

### 三、记录格式（强制）

任务单「执行记录」表**必须至少四列**：

| 时间（自然时间） | 执行者 | 事件 | 证据 |
| --- | --- | --- | --- |
| 2026年11月1日 13:05 | android-agent | 实测 db 32→108 | `reports/r50/snapshots/a13_check.json` |

- **时间**：自然时间（AGENTS §49），读系统时钟
- **执行者**：Agent 名（`main` / `android-agent` / `web-agent` / `tutorial-agent` / `android-scheduler-agent` / `rea-agent`），
  **不得只写「主 Agent」笼统带过**
- **事件**：做了什么，不是「已处理」
- **证据**：文件路径 / commit / 日志片段

### 四、必须在任务单开头列「贡献者」

每份任务单的元信息表增加一行：

```
| 贡献者 | android-agent（主体实施与实测）、main（协调与验收） |
```

顺序按**实质贡献大小**排列，不按职级。

### 五、主 Agent 的义务

1. 代提交时，**在 commit 信息里点名实际执行者**（如「由 android-agent 实测确认」）
2. 回写子 Agent 的报告时，**保留其原话关键结论**，不要改写成自己的判断
3. 若主 Agent 推翻/修正了子 Agent 的结论，**必须同时记录两人的原始观点**（例：FACTS C.93.4 记录了四次被证伪的假设及提出方）
4. 不得把子 Agent 独立发现归因为「团队发现」而隐去具体是谁

### 六、子 Agent 的义务

1. 更新任务单时，在自己的条目里**写自己的名字**
2. 不要代别的 Agent 填「执行者」
3. 若引用他人的发现，注明来源（如「依据 rea-agent 的 `h()` 不解锁结论」）

### 七、违反示例（禁止）

- ❌ 执行记录只写时间与事件，不写执行者
- ❌ 子 Agent 做了全部实测，commit 与任务单都只署 main
- ❌ 把「android-agent 发现 `[Oreki AD1]` 补丁缺失」写成「我们发现」
- ❌ 修正他人结论时，只记新结论不记原结论与出处

### 八、与既有规则的关系

- 不改变「任务单 commit 由主 Agent 统一做」（硬链接约束下的必要安排）
- 不改变「Git 提交信息使用简体中文」
- 与 §48/§49 配合：**时间用自然时间，执行者必须真实**

## 52. 多 Agent 同仓库并发的 Git 纪律（2026-11-01 由 tutorial-agent 的竞态报告确立）

### 一、现象与真因

**现象**：`git add` 返回成功，紧接着 `git commit` 报 `nothing to commit`；重跑一次即正常。

**真因**：多个 Agent 同时在同一个仓库操作时，`git add` 与 `git commit` 之间的窗口里，
另一个 Agent 的 `git add` / `commit` 重写了 `.git/index`，把先前暂存的内容覆盖掉。

**曾误判**：早先把这个现象解释为「硬链接导致 git stat 缓存不识别变更」，用 `touch` 绕过。
`touch` 有时能"修好"是因为它顺带改动了 mtime 让缓存失效，但**根因是 index 竞态，不是硬链接**。

### 二、规则（强制）

1. **`git add` 与 `git commit` 必须在同一条命令里**（用 `&&` 连接），中间不插入任何其他操作。
   不要把 `add` 单独跑一次、再去跑别的、再回来 `commit`。

2. **提交前用 `git diff --cached --stat` 确认真的暂存上了**：
   输出为空说明 index 被覆盖，本次提交会变成空提交或漏文件，必须重来。

3. **任务单（`tasks/*.md`）的 commit 一律由主 Agent 做**。
   原因：三处硬链接共用同一 inode，子 Agent 各自 `add`/`commit` 必然互相干扰，
   且会让两个仓库的 index 同时变脏。
   子 Agent 只回写本地文件，然后向主 Agent 报告「已回写」。

4. 子 Agent 提交自己的**代码**时，也只提交自己负责的文件（用明确路径，不用 `-a` / `git add .`），
   避免把其他 Agent 的在途改动一起带走。

5. 遇到 `nothing to commit` 时**不要慌着 `--amend` 或 `reset`**，先 `git status` 看清状态，
   确认没有别人的改动被误加，再重跑 add+commit。

### 三、与硬链接的关系

硬链接文件（`docs/FACTS.md`、`docs/AGENTS_GLOBAL.md`）**确实**会有一个额外问题：
git 用 `(mtime, size, inode)` 判断变更，同一 inode 被外部改写后 stat 缓存可能未失效，
导致 `git status` 看不到变更。

**两个问题要分清**：

| 现象 | 真因 | 处理 |
| --- | --- | --- |
| `status` 看不到已改的硬链接文件 | stat 缓存 | `touch` 一下再 `add` |
| `add` 成功但 `commit` 说没有变更 | index 竞态 | 把 add+commit 合成一条命令重跑 |

**不要用一个方案去套另一个问题。**

## 53. 新增/修改的条件分支必须配可观测日志（2026-11-01 由 android-scheduler-agent 建议确立）

### 一、规则

**任何新增或修改的条件分支，必须配一条可观测日志**，且日志要**带上判定所依赖的实际值**。

不是「进入分支」这种空话，而是：

```
OREKI_CRUNCH: mode=0 amount=1e1000 am=1e1388 cmp=1 entered
OREKI_CRUNCH: mode=0 amount=1e1000 am=1e1388 cmp=-1 skipped
```

走进、走出各一条，带值。**没有日志的分支视为未验证。**

### 二、为什么是这条，而不是「做静态闸门」

**2026年11月1日一天内出现三次极性错误**：

| # | 位置 | 错误 | 发现方式 |
| --- | --- | --- | --- |
| 1 | `tryBuyId1` 循环头 | `if-le` 写成恒真 → 循环一次不执行 | `OREKI_ID_LOOP` **一行都没有** |
| 2 | `OrekiAutomationScheduler.allow` | wide 寄存器高半被当 int 读 → ART 拒收整类 | 装机启动崩溃 |
| 3 | `applyCrunchPolicy` 的策略分档 | `if-ne` 写反 → `mode==2` 也被挡掉 | `OREKI_AU4B` **一行都没有** |

**三次里有两次靠「日志缺失」发现**——这是最有判别力的信号：日志不该空的时候空了，说明代码根本没执行到。

而「静态检测极性错误」在技术上误报率极高（要判断 `if-*` 前一条 `cmp` 的语义、分支目标的命名意图），
**一个误报率高的闸门没人会认真看，等于没有**。

### 三、配套要求

1. **日志要节流**：高频路径不能用「每次打一条」，用静态计数器每 N 次打一条，或只在判定翻转时打
   （参考 `OREKI_HOLD` 的 `sHold` 翻转记录法）
2. **日志要能区分「没进去」和「进去了但条件不满足」**：前者没有日志，后者有带值的日志
3. **判定翻转才打**是首选形态——它天然节流，且能直接看出状态变化时机
4. 探针在问题定位后**可以移除，但结论必须写进 FACTS**，不要留下无注释的一次性日志

### 四、适用边界

- **不要求**每一行代码都打日志；只要求**新增或修改的分支**
- 既有代码不动（今天不改历史代码，避免混入第二个变量）
- 日志文案用中文，标签用 `OREKI_` 前缀便于 `rg` 过滤

### 五、与 §51 的关系

§51 禁止任务单使用第一人称；本节要求**代码日志可观测**。两者不冲突：
任务单是给人读的正式记录，日志是给排查用的运行期证据。

## 54. 环境安全与时间读取容错（2026-11-01 用户确立，长期有效）

### 一、时间读取的三级方案（按优先级）

| 级别 | 方案 | 说明 |
| --- | --- | --- |
| **主方案** | `python scripts/oreki_time.py` | **纯 Python `datetime.now().astimezone()`，不调用任何外部二进制**，不受杀软误报影响 |
| 备用 A | Windows PowerShell 的 `Get-Date -Format "yyyy-MM-ddTHH:mm:sszzz"` | 系统原生 |
| 备用 B | .NET `[DateTimeOffset]::Now.ToString("yyyy-MM-ddTHH:mm:sszzz")` | 系统原生 |
| 兜底 | **标记时间为【未知】** | 三者都失败时，绝不推测 |

**§48 的三级降级（脚本 → 文件 mtime → 未记录）在此升级为**：
**时间工具 → 系统原生接口 → 未记录**。mtime 只作为「事件发生时刻」的旁证，不替代当前时间。

### 二、Bash 里不要裸用 `date`

`date` 在 Git for Windows 下解析到 `/bin/date`（MSYS2 的 GNU coreutils），
属第三方二进制，可能被杀软拦截。**一律改用 `python scripts/oreki_time.py`。**

- 失败是「安全失败」：命令无输出，不会产生错误时间
- 但会导致该回合的时间记录缺失，故应主动避免

### 三、杀软误报的处理原则（硬约束）

**发现第三方工具被安全软件拦截时：**

1. **不得**关闭实时防护
2. **不得**恢复未经核验的隔离文件
3. **不得**把整个开发目录加入排除列表
4. **不得**批量放行未知程序
5. **不得**删除检测日志
6. **不得**下载来源不明的同名文件替换
7. **不得**把尚未确认的文件标记为「误报」
8. **不得**输出或泄露签名私钥、密码等敏感信息

**正确做法**：核验文件来源（路径、版本串、SHA-256）→ 记录检测名称与处理状态 →
由用户决定是否提交官方误报样本 → 期间改用**不依赖该工具**的等价方案。

### 四、已核验的环境事实（2026年11月1日，实测）

| 项 | 值 |
| --- | --- |
| `date` 路径 | `/bin/date`（Git for Windows / MSYS2） |
| 版本 | `GNU coreutils 8.32` |
| SHA-256 | `743228ae082e1128a2aff02414e114dc45a51f7461775bc5750d89307f3ccdac` |
| 大小 / mtime | 120177 B / 2026年10月27日 17:31 |
| 签名状态 | 【未知】 |
| 在装杀软 | Kaspersky、ESET、Windows Defender |
| Defender 威胁记录 | 无 |
| 卡萨斯基检测记录 | **【未知】**——未授权读取其私有日志 |
| 系统时区 | `China Standard Time`，`BaseUtcOffset = 08:00:00` |

**未宣称 `/bin/date` 为误报**——只记录它来源于 Git for Windows 且版本串与官方一致。

### 五、时间工具的抗干扰验证（实测）

```bash
# 模拟第三方工具完全不可用
PATH=/nonexistent python scripts/oreki_time.py --human
→ 2026年11月1日 14:04:59
exit=0
```

**结论**：即使 PATH 内所有外部命令都不可用，时间工具仍能正常输出。
**这条保证了「不因某个工具被误报就失去可靠时间来源」。**

### 六、Bash 工具报 `spawn EPERM` 时的降级

2026年11月1日实测出现：`Bash` 工具返回 `spawn EPERM`，连 `echo probe` 都无法执行，
而同会话的 Windows PowerShell 工具工作正常。

**降级顺序**：
1. 先重试一次 Bash（区分瞬时故障与持续故障）
2. 仍失败 ⇒ **改用 PowerShell 工具**执行 git / python / adb 等命令
3. **在任务单与报告中如实标注「本回合 Bash 不可用，已降级」**，不得静默切换
4. 不得因工具受限而跳过验证、简化证据或改变结论

**判断是不是宿主级问题**：多个 Agent 同时出现同一现象即为宿主级，需报告用户，不自行归因。

### 七、最终原则

> **杀毒软件负责保护系统，WorkBuddy 负责适应安全环境。**
> 不能为了自动化方便而降低系统安全标准，也不能因为某个工具被误报就失去可靠的时间来源。

## 55. 后台构建与 Agent 阶段性 Pause（2026-11-01 用户下达，P3 长期有效，**本节是后台耗时任务与回合控制的唯一源**）　⚠ 多 Agent 部分已由 §60 废止（2026-11-01）

**最终原则**：Agent 负责发起、监督和验收构建，**不应把宝贵的执行回合浪费在等待编译器上**。

### 55.1 标准流程

`启动后台构建 → 确认任务已启动 → 汇报构建信息 → 保存检查点 → Pause → 构建完成后恢复并验证`

「确认任务已启动」与「已提交启动命令」是两件事：必须看到进程真实存在（PID / 任务标识）才算启动，否则不得声称已启动。

### 55.2 适用场景

Gradle Release APK 构建；大型项目编译；耗时较长的批量处理；其他可独立运行、不需要 Agent 持续交互的耗时任务。

**后台化的边界**：短时间操作、需要持续交互的调试操作、必须保持原子性的操作，**不强制后台化**。

### 55.3 后台启动要求

1. 使用可靠的后台进程或任务管理方式
2. 保留构建进程 PID、任务标识与日志路径
3. **确认进程实际启动后才能汇报「已启动」**
4. **确保 Agent Pause 不会导致构建进程被终止**
5. **不得把仅仅提交了启动命令误报为构建已启动**

### 55.4 启动后立即汇报（八项）

负责 Agent ID；构建目标与任务编号；构建命令；进程 PID 或任务标识；日志文件位置；启动时间；当前状态；后续验证步骤。

**状态口径**：未完成一律标「构建中」，不得提前报成功。

### 55.5 阶段性 Pause　⚠ “停手等待”语义已由 §61 废止（2026-11-01）

完成启动确认与进度汇报后，在没有其他必须立即处理的任务时，**应主动 Pause**。

Pause 期间：后台构建继续运行；**不持续轮询构建进程**；**不反复读取日志**；**不重复发送进度更新**；**不占用模型回合等待构建结束**。

**Pause 不等于取消任务，不等于终止后台进程。**

**Pause 的准确定义（2026-11-01 补充，消除歧义）**：指 Agent 完成启动与汇报后，**主动停止当前工作、结束本轮执行并等待后续指令**。
- **不是**要求 WorkBuddy 提供特殊暂停 API
- **不是**要求 Agent 自动恢复
- **不是**要求轮询或等待后台任务完成

**独立性验证**：Agent 停手后，后台任务必须能够继续运行。不得依赖 Agent 持续占用前台 Bash 或持续发送心跳来维持任务。**无法确认后台任务能否脱离 Agent 独立运行时，不得贸然停手**——应先选可靠执行方式，或如实报告能力限制。

**不得擅自终止其他 Agent 已启动的有效任务**；任务失败时保留日志与现场，不得擅自清理或覆盖其他任务的数据。

### 55.6 构建完成后的恢复（七步，缺一不可）

1. 检查进程退出状态
2. 检查完整构建日志
3. 判断构建成功或失败
4. 验证 APK 文件是否存在
5. 验证 APK 签名与包信息
6. 按项目要求安装到 `oreki_test` 并执行测试
7. 更新任务单与执行记录

**不得只凭「APK 文件存在」认定构建成功。**

### 55.7 并发资源管理

## 56. 主 Agent 统一统筹与 Android-Agent 按需调用（2026-11-01 用户下达，P3 长期有效，**本节是协作模式的唯一源**）　⚠ 多 Agent 部分已由 §60 废止（2026-11-01）

这是**协作模式优化，不是永久放弃多 Agent 能力**。不得删除 Android-Agent，不得清空其历史记录、配置或工作目录。

### 56.2 主 Agent 职责（唯一调度者）

### 56.3 Android-Agent 按需调用规则

保留专项能力，仅在下列情况考虑调用：Smali 代码分析与修改；Android 专属问题定位；Gradle 构建问题分析；APK 签名、包信息与安装验证；Android 模拟器专项测试；主 Agent 明确需要独立视角或专项技术能力的任务。

### 56.4 Android-Agent 停手规则

### 56.5 任务分派与通信

### 56.6 禁止事项

1. 不得删除 Android-Agent
2. 不得清空其历史记录、配置或工作目录
3. **不得为减少忙态而强制终止其正在执行的有效任务**
4. 不得把尚未完成的任务直接转交并丢失上下文
5. 不得为形式上的并行制造无意义的子 Agent 任务

### 58.2 四档内存阈值与对应动作（可执行化）

| 内存占用 | 动作 | 本轮实例 |
|---|---|---|

### 58.3 判定纪律（防误判）

- **杀进程前必须核验进程归属**（PID + 命令行 + 日志路径三者对应），核验不通过不得杀。

## 61. 单 Agent 构建等待期间持续推进（2026-11-01 用户下达，P3/P4 长期有效，**本节是「等待任务时做什么」的唯一源**）

**规则编号**：§61
**名称**：单 Agent 构建等待期间持续推进工作
**优先级**：P3（协作效率）+ P4（执行与资源）
**适用范围**：全部后台长时间任务（apktool 构建、Gradle、Pages 部署、AVD 长跑、截图批处理）的等待窗口
**创建时间**：2026年11月1日 16:59
**最近更新时间**：2026年11月1日 16:59
**当前状态**：生效
**实际生效位置**：工作区根 `AGENTS.md`（三处硬链接）+ `RULES_INDEX.md` + `tasks/INDEX.md`
**来源或提出原因**：用户 2026-11-01 16:59「长期规则补充：单 Agent 构建等待期间持续推进工作」
**关联项目或任务**：R51 及其后全部轮次

### 61.1 核心原则

**单 Agent 不等于所有任务严格串行。** 等待构建结果期间必须主动推进不依赖该结果的工作，
采用「单 Agent 统一协调 + 安全任务交错执行」。**等待结果，不等待工作。**

### 61.2 三类等待窗口允许做的事

| 等待窗口 | 允许继续做 |
| --- | --- |
| Android 构建期间 | 检查 Web 源码与对应功能逻辑；分析既有 REA / frame-observer 日志；更新 `FACTS.md` / `WEB_ANDROID_DIFFERENCES.md` / 任务单；整理下轮测试用例与验收标准；检查 Git 状态与远端同步；**不改构建输入的**静态分析 |
| Web 构建/检查/部署期间 | 处理 Android 源码与 Smali 静态检查；核对双端功能与策略一致性；更新公共规则、差异文档、测试记录；整理 Android 后续构建任务 |
| AVD 运行观察期间 | 读源码、分析历史日志；更新文档与任务单；检查 Web 端静态逻辑；整理下一阶段测试方案 |

**AVD 观察期间的禁区**：不得执行会明显干扰 AVD 的高资源任务（新开第二个 AVD、再起一次构建、批量截图）。

### 61.3 禁止事项与安全边界

1. **构建输入冻结**：构建启动后记录 Git commit、工作区状态与源码版本；**构建过程中不得修改该次构建正在读取的源码输入**。
2. 确需改构建输入 → 等当前构建结束，再改，再启动新构建。
3. **Gradle 重型构建与 AVD 重型观察不得同时进行。**
4. 不得同时叠加多个高资源任务。
5. 严格遵守 §58 的 80% / 85% / 90% / 95% 内存阈值与 CPU/IO/进程数监控。
6. **不得为了填满等待时间而启动无价值任务。**
7. **不得因为正在等待构建而停止所有其他工作。**

### 61.4 后台构建任务管理（九项记录，缺一不可）

任务 ID / PID / 启动时间 / 对应 Git commit / 构建命令 / 日志路径 / 当前状态 / 退出码 / 最终产物路径与 SHA-256。

**结束后必须核验五项**：进程是否正常退出、退出码是否 0、日志有无真实错误、产物是否实际生成、产物版本与签名与 SHA-256 是否符合预期。

**不得仅凭「构建进程消失」或日志出现 `BUILD SUCCESSFUL` 就跳过产物核验。**

### 61.5 执行调度六步

1. 启动当前阶段必要的长时间任务。
2. 明确该任务的资源占用与源码输入边界。
3. 选择不依赖其结果、不干扰其运行的其他任务。
4. 持续推进 Web、Android、公共文档与测试工作。
5. 在合适节点检查后台任务。
6. 任务完成后核验结果，再进入依赖该结果的下一阶段。

## 62　Android 验收策略：日常实机优先，版本更新完整回归（2026-11-04 起生效）

### 62.1 背景与冲突声明

此前对 Android 每次改动都倾向跑完整 `probe_patches.py`（44 项静态探测）、
反复构建与 AVD 安装，导致工具链开销挤占生产功能开发时间。
自本节起按「修改风险」分级验收；**旧规则中与本节冲突的部分以本节为准**。

### 62.2 日常开发（默认路径）

适用：普通功能开发、UI 修改、自动购买器调整、游戏机制优化、Bug 修复。

- **不强制**执行完整 Android 回归测试。
- 优先使用 Android 实机做**针对性**验收：改了什么就重点验什么。
- 最低限度检查：应用能正常启动、存档正常、相关功能符合预期。
- **不要**为形式上的覆盖率反复跑几十项静态探测。
- **不要**无意义地重复构建、安装、重启模拟器。
- 但：日常修改必须有**真实生产代码变更 + 可运行交付**，不能只交审计或测试工具。

### 62.3 游戏版本更新（强制完整回归）

适用：游戏本体版本升级（如 3.19 → 3.20）。

必须执行完整版本回归，包括：

| 项 | 要求 |
|---|---|
| 补丁应用情况 | 全部补丁逐项确认，失败项必须列出而非跳过 |
| 游戏核心机制 | 反物质、无限、永恒主链可运行 |
| 自动购买器 / 自动化 | 三态、开关、间隔、目标驱动逻辑 |
| 挑战、奖励、进度结算 | 走原版真实结算，不伪造 |
| 存档兼容性 | 旧档可读、新档可写、重启保持 |
| DEX 注入与多 DEX | 槽位正确、无重复类、无缺失引用 |
| Android 实机 | 完整运行验收 |
| Web 对应功能 | 同步验证 |

**不得**仅凭"APK 构建成功"或"应用能启动"就宣布版本升级完成。

### 62.4 特殊情况（按风险决定范围）

| 场景 | 验证范围 |
|---|---|
| Gradle / AGP / Kotlin / JDK 等工具链升级 | 完整 Release 构建 + 实机启动 + 关键流程，**不强制**完整游戏机制回归 |
| 大规模 Kotlin 转译 | 检查 ABI、DEX、调用关系 + 实机验证 |
| 存档格式 / 底层游戏循环修改 | 扩大针对性测试范围 |
| 涉及多个核心系统的重大修改 | 按影响范围决定是否专项回归 |

### 62.5 执行原则

1. 实机验证优先于无意义的静态测试数量。
2. 测试范围与修改风险匹配。
3. **不允许**通过跳过必要验证掩盖真实缺陷。
4. 版本更新必须完整回归。
5. 不得把日常开发与版本更新混为一谈。
6. 不得为追求测试数量牺牲生产功能开发时间。

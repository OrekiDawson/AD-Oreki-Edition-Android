## 6.2. 交付与测试纪律（2026-10-28 R5.6 用户确立，**本节是以下三条的唯一源**）

> 与 §6.1 互补：§6.1 定「怎么做」，本节定三条**禁止性/强制性**红线。平台文件只放指针，不复写细则。

### 6.2.1 禁止无结果的重复测试循环

1. 全套回归**没有产出可读结果**时，先诊断再动手：查历史日志、进程状态、退出码、输出重定向、
   端口/浏览器/依赖冲突、报告生成环节，判断属于「真挂起 / 提前退出 / 结果不可见 / 断言无效 / 环境冲突」。
   **不得笼统归因为「游戏代码有问题」。**
2. 定位到第一个失败或卡住的项目后，**只单独复现该项**，记录命令、起止时间、耗时、退出码、关键输出；
   做一次有证据支持的根因修复，复测该项及其直接相关功能。
3. **禁止**在无新增证据、无代码变化、无配置/环境变化的情况下重复运行同一套完整回归。
4. 若一次有依据的修复仍不能解决：保留日志，标明「根因未确认」，**切到其他独立任务继续推进**，
   不得反复尝试同一命令或同一补丁。
5. 分层测试（按改动影响面选层级，不机械全跑）：
   - **L1** 静态检查 + 必要构建 + 最小启动验证；
   - **L2** 本轮改动的单项测试；
   - **L3** 本轮影响范围内的回归；
   - **L4** 发布前、且环境可用时的全套回归。
6. **失败 / 挂起 / 未执行必须分别记录**。全套回归不可靠时，如实报「完整回归未完成 + 原因」，
   在定向测试与构建充分的前提下**可以继续安全交付**，但不得谎称全套通过，也不得因非关键测试
   无限期阻塞其他可交付工作。
7. **区分既存失败与本轮引入**：用 `git worktree` 在 HEAD 上复跑同一项，把结果并排记录；
   低成本的抖动类测试需连跑 3 次再定性。

**R-README-01 README 是正式项目入口**

README 的首要读者是**第一次接触项目的陌生人**，不是项目维护者。读者应能只读 README 回答：
这是什么项目？解决什么问题？有哪些主要功能？当前发展到了什么状态？我如何开始使用？遇到问题去哪里？
不得假设读者已熟悉项目、仓库结构、内部术语或开发历史。

**R-README-02 先满足读者，再介绍技术**

README 必须按**目标读者的实际任务**组织信息。不得把开发者最关心的内容排在玩家入口之前，
不得把维护者的操作习惯当成所有读者的使用方式。每份 README 必须**显式写明目标读者**，
并据此安排章节顺序。

**R-README-03 README 不得成为内部知识库**

以下内容**原则上不得大段写入** README：每轮开发记录 / R 编号 / 任务编号 / Agent 交接记录；
一次性构建、测试与验收报告；内部调试日志、异常堆栈、历史事故；个人电脑绝对路径、临时 PID、
设备序列号与临时环境配置；完整内部开发规则与长期事实台账；大量源码实现细节、内部变量名与调度器细节；
已经过期的版本状态与历史设备测试数据。
这些内容放入 `tasks/`、`reports/`、`docs/`、`FACTS.md` 等专门文档。README 只保留
**理解项目、使用项目、开始开发所必需**的信息，并给出准确的进一步阅读入口。

**R-README-04 所有事实必须有依据**

README 中每项具体事实必须与当前仓库实际状态一致。**必须逐项核对**：当前版本与版本号含义；
功能是否真实实现；功能是否经过实际验证；安装包获取渠道与实际文件名；操作系统 / SDK / 浏览器 /
运行环境要求；构建命令与构建产物路径；API 地址、参数、响应与协议；在线地址、域名、部署方式；
存档保存位置与丢失风险；外部项目、上游项目与许可证信息。

状态必须可区分：**已实现 / 已验证 / 部分实现 / 尚未验证 / 计划目标**。
不得把目标写成成果，不得把「代码存在」写成「运行验收通过」，不得把历史测试结果冒充当前状态。
无法核实的内容**明确标注或删除，不得猜测补齐**。

**R-README-05 操作步骤必须真正可执行**

README 提供的安装、启动、构建、调用、备份、恢复、部署步骤，必须逐项检查：命令是否与当前仓库结构一致；
文件路径是否真实存在；参数是否正确；前置条件是否完整；步骤顺序是否正确；预期结果是否清楚；
失败时是否有合理排查入口。
**不得只列工具名称就声称已提供完整教程。**

**R-README-06 保持适当篇幅和信息密度**

不设机械行数限制，但每个章节必须对目标读者有实际价值：不为凑长度重复介绍同一功能；
不为追求短小删除必要步骤；不把内部文档整篇复制进 README；不使用大量空泛宣传语；
不堆砌无意义徽章、表格与目录；不为展示技术复杂度在首屏罗列内部实现细节。
README 应**易读、可导航、可执行**。

**R-README-07 链接必须真实有效**

所有内部文档、外部项目、下载入口、在线地址与相关资源链接必须核实：仓库内相对路径必须实际存在；
跨仓库链接必须指向正确仓库与正确文件；不得留下失效链接、旧分支路径、错误文件名，
或仅在维护者电脑上存在的路径。

**R-README-08 README 与专门文档分工明确**

README 负责：项目概览、主要功能、快速使用、必要注意事项、进一步阅读入口。
专门文档负责：完整开发环境配置；构建链与编译细节；API 协议与接口参数；测试规范与验收流程；
安全模型与权限细节；内部架构与设计说明；历史测试与开发记录。
README **链接**这些文档，**不复制**其正文。

**R-README-09 变更必须同步维护**

以下变化必须检查 README：新增 / 删除 / 改变主要功能；安装、启动、使用方式变化；
版本号或兼容性要求变化；构建工具链、构建命令与产物变化；API、协议或集成方式变化；
部署地址、部署流程与仓库职责变化；项目定位或目标读者变化。
**变化不影响 README 时，在任务记录中写明「无需更新」及理由**，不必为形式而改。
本条取代 §6.2.3.2 的十条（语义一致，覆盖更全）。

**R-README-10 README 必须通过独立验收**

不能因「已提交 / 章节齐全 / 篇幅较长」就认定合格。每次重写或重大修改后至少检查：
① 陌生读者能否理解项目定位；② 首屏是否准确表达项目价值；③ 目标读者能否找到自己的操作入口；

⑥ 是否存在过期、重复、内部化或无关内容；⑦ 链接与路径是否有效；
⑧ 是否与专门文档保持正确分工；⑨ 是否存在未验证内容被写成已完成；
⑩ 是否符合本规则的目标读者与信息层级要求。
**不得仅以 Markdown 格式检查代替内容验收。**

## 19. 移动端适配：控件触控尺寸不得偏小（2026-10-30 用户确立，长期有效，**本节是触控尺寸的唯一源**）

> 用户原话：「移动端适配要注意控件大小，不要像选项内有些控件偏小」。

1. **判定基准（两条都要满足）**：
   - **绝对下限**：窄屏（`max-width: 620px`）下所有**可点元素**命中区不小于 **44 × 44 CSS px**
     （WCAG 2.5.5 / iOS HIG 下限；Android Material 建议 48dp ≈ 44 CSS px）；相邻可点元素间距 ≥ **8px**。
   - **相对一致（用户 2026-10-30 补充：「是和同页面其他按钮相比」）**：**同一页面内、同一层级的控件必须同高同宽基准**。
     不允许出现「主按钮 44、旁边同类按钮 25」这种参差。判定方法是把同页所有同类可点元素的
     高/宽列出来看分布：只允许 1~2 档（如主按钮 / 次级按钮），且档差不超过其自身高度的 20%。
     若某控件比同页其他按钮明显偏小，**以该页主按钮为基准**把它撑到同一档，而不是只满足 44px 就收工。
2. **覆盖范围**（不只按钮）：`button` / `.o-primary-btn` / 开关（toggle）/ 复选框 /
   下拉（`select`）/ 数字输入（`input[type=number]`）/ 加减按钮 / 页签 / 关闭叉 /
   自动购买器行内的「开启」与间隔输入。
3. **必须真的扩命中区**，不是只放大字号：用 `min-width` / `min-height` / `padding`
   把**可点区域**撑到 44px。文字可以不变大，但手指点到的地方必须够。
   若扩尺寸会撑破行宽，**先解决换行/自适应**（见 §19.4），不要靠缩小控件来省空间。
4. **不得用「整行变窄」的方式换空间**：窄屏下若一行放不下，正确做法是换行（`flex-wrap: wrap`）
   或改列布局，而不是把控件压到 44px 以下。
5. **验收方式（必须给数据，不许目测）**：在真机 / 模拟器视口（392×676 与 360×640 各一次）
   用 CDP 扫描可点元素的 `getBoundingClientRect()`，列出所有 `width < 44 || height < 44` 的项
   （类名 + 文本 + 实际尺寸），修完复扫到清单为空或只剩「有合理理由」的项。
   合理理由必须写进报告（例如「整行是一个大按钮，内部小元素不可单独点击」）。
6. **与既有规则的关系**：本节只管**尺寸**；「不横向溢出」由 `oreki.css` 的 620px 段负责；
   两者冲突时优先保证不溢出，其次保证 44px，最后才考虑美观。
7. 新增任何窄屏控件样式时，必须同时给出**该控件的实测尺寸**；没测过的写「未验证」。

### 24.9 单一内容源（R40 定案，唯一实现路径）

**正文只允许存在于 `web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json`**，两端都从它派生：

- Web：`src/core/oreki-tutorial.js` 只做 `import` + 派生成渲染结构，**不得再写第二份正文**；
- Android：构建期由 `scripts/oreki_tutorial_gen.py` 读取该 JSON，生成
  `payload/assets/oreki_tutorial.txt`（每行 `FIELD|flag|text`），`TutorialActivity` 逐行
  `split("\\|", 3)` 解析。**不再把正文写进 smali `const-string`。**

为什么是 JSON 而不是解析 JS：Python 解析 JS 对象字面量只能靠正则，Web 侧字段一改就
**静默产出残缺教程**（能编过、能装上、界面空白或少章）；JSON 有 `json.load` 兜底，语法错在构建期直接报错。

为什么是 assets 而不是 smali：8~12 万汉字若逐段变 `const-string`，smali 会涨到 1.5~3 万行，
汇编变慢、易撞 65,535 常量池边界，且**内容错不会在汇编期暴露**。`assets/` 不走 aapt、不占资源 ID，
内容是数据不是代码。**代价**：仍然要重建 APK（内容在 APK 里）；不采用运行期下载，
因为现行教程页明确写「不需要联网」（`TutorialActivity.smali:141`），且运行期内容会与版本脱钩。

**构建期三层断言（缺一不可，实现见 `build_mod.py`）**
1. 一级：JSON 可解析、`schemaVersion` 匹配、`chapters` 非空、`id` 唯一且连续、十个字段类型正确；
2. 二级（发布构建）：`draft` 全为 `false`、`steps` 非空、`numbers[].src` 非空、无占位词、终局章含 `1e1000`；
3. 三级（回读比对）：重新读生成的 assets，按分隔符解回结构，与 JSON **逐字段比对**，不一致即中止构建。

字段契约与校验规则见 `web/AD-Oreki-Edition/docs/教程数据结构说明.md`。

**译名基准（写任何正文前必读）**：`web/AD-Oreki-Edition/docs/教程术语表.md`。
权威来源是 `android/AD_Oreki_Edition_Android/work/base_decoded/res/values-zh-rCN/strings.xml`
（原版 APK 官方简体中文字符串，4,516 行），表里每个词都标了官方出现次数，**0 次 = 禁止使用**。
三个已确认的高频错译：

| 错 | 对 | 官方次数 |
|---|---|---|
| 时间定理（TT） | **时间之理** | 75 次 / 错译 0 次 |
| 稀释时间（DT） | **膨胀时间** | 54 次 / 错译 0 次 |
| 大灾变（Armageddon） | **末日** | 30 次 / 错译 0 次 |

**英文只允许出现在两种位置**：中文后括注全称或缩写（`时间之理（TT）`）、
界面标签中英双写（`点击底栏「维度 / Dimensions」`，因 APK 不强制中文 locale）。
除此之外不许整句英文 —— 抓来的 wiki 攻略是英文的，只能用来理解机制，不能搬句子。

**Android 渲染硬约束**：目标篇幅下「一次 inflate 全部」不可用（约 500 个 TextView、单层线性布局
高 8~12 万 px）⇒ **必须一章一屏**：先解析章节列表，只渲染当前章，切章重建内容区。
必做项：分章 + 章节目录、字号三档、打开定位到当前阶段章。
明确放弃：表格渲染与行内加粗（在 smali 里手写 SpannableString 性价比极低，字段齐全优先于样式）。

**切换期铁律：不得造成信息倒退。** 单一内容源刚接入时，新章节绝大多数是 `draft: true`、`steps: []`，
而两端旧教程都已有内容（Web 7 章 39 小节、Android 10 章 2,665 字）。若直接切到新源，
玩家会从「有内容」掉到「只有 1 章有内容」。

所以：
1. 两端的旧正文**都不许删**——Web 保留为 `TUTORIAL_LEGACY_CHAPTERS` 导出；
   Android **旧 10 章的 smali `const-string` 原样留在原处**，生成器只产出新章节
   （不迁移旧文本，迁移留到正文补齐后再做，降低本轮风险）；
2. 渲染时排在新章节**之后**，加明显的分节标题「旧版教程（已停止维护，正在并入新版）」；
3. 删除时机由**团队负责人**决定，实现方不得自行加删除逻辑（默认行为是「总是写」）；
4. **验收口径（三条并列，缺一不可）**：
   - 玩家能读到的**章节数与可操作性**不得少于切换前；
   - 旧版段落必须显式声明「已停止维护」，**不得被当作达标的依据**；
   - **已知错误必须在旧版声明里点名**——天神解锁顺序写反、终局判据缺失、EC1~EC12 无内容。
     只写「可能过时」不够：新手照样会照着错的那段做。

第 4 条最后一项是本条最容易被糊过去的地方。「信息不倒退」若实现成「把已知错误原样保留并当正文」，
那是把倒退包装成达标。**旧内容本身是错的，这件事必须对玩家说出来。**

**发布门控：`OREKI_TUTORIAL_ALLOW_DRAFT`（两端必须同名，默认严格）**

设计原则是「失败即关闭」：**默认就严格，想带半成品构建必须显式放行**。
反过来（默认宽松、发布时记得加变量）一定会有人忘了加，然后带着 11 章空壳出厂。

| 取值 | 行为 | 用途 |
|---|---|---|
| **不设置（默认）** | `draft > 0` **中止构建**，打印 `draft=N/总章数` 与是哪几章 | 发布、合并、任何常规构建 |
| `=1` | 允许 `draft: true`，日志打印 `draft=N/总章数` 但不中止 | 仅本地迭代 / 需要装机验证渲染时 |

现在不设该变量跑构建**必然失败**（17 章里 11 章是 draft），这是正常的；
它能证明门控真的生效，也保证不会「以为写完了其实没写」。

**章节数一律不许硬编码。** 断言只能写成「`len(chapters)` 与 JSON 实际长度一致」+
「`id` 依次为 `ch00..ch(N-1)`」，N 从数组长度推导。
本文档写作当天这份 JSON 的章数已经变过三次（15 → 16 → 17），`draft:false` 数变过两次，
**任何写死的数字在下一次改章后都会立刻过期**。报告、文档里的完成度一律写「取现值命令」，不写死值：

```bash
python -c "import json,io;d=json.load(io.open('web/AD-Oreki-Edition/src/core/oreki-tutorial-data.json',encoding='utf-8'));print(len(d['chapters']),[c['id'] for c in d['chapters'] if not c['draft']])"
```

## §27 双端功能对等（Android 不得停滞的落地检查法）

用户长期要求：「Web 与 Android 必须同步推进功能开发，Android 不得沦为被动移植端」，
且明确「不允许用 UI 微调、文档更新、测试工具开发或单纯修复旧问题冒充功能开发进度」。

### 27.1 判定只有三态，禁止第四种写法

每个 Web 机制模块在 Android 侧的状态只允许三种记法：

| 记法 | 含义 | 证据要求 |
|---|---|---|
| **已有** | Android 有等价实现且在真实路径上生效 | 给出类/方法与调用点 |
| **确认缺失** | 调用链里确实没有这个动作 | **必须反证**：贴出该阶段 tick 的调用链原文，说明只有 A/B/C 动作 |
| **未知** | 搜过但无法判定 | 写明搜了什么、为什么判不了 |

**禁止**把 grep 0 命中写成「缺失」，也禁止把「有 4 处字符串提及」写成「已实现」。

### 27.2 为什么这条必须写死

同一天两个真实反例：
- `player.break` 在 Android 是 `Player.brake:Z`（setter `x0(Z)` @11107 / getter `m()Z` @10746）；
- `Pelle` 类在 DEX 里是 `.../pelle/c`，按原名 `inspect-android-method` 直接报
  `Exact class not found`，**不是 APK 缺类，是混淆改名**。

按 Web 的名字搜 Android，0 命中是常态。**「搜不到 ≠ 不存在」是这个项目最容易误判的一条。**

### 27.3 每轮必须做的一件事

每轮开发开始前读 `WEB_ANDROID_DIFFERENCES.md`，结束后把本轮涉及的机制差异写回去
（双端实现状态、数值差异、以及**Android 侧独立发现的事实**）。

后者尤其重要：R40 实测 Android 的 `prestige/f::o` L7445-7530 写的是中间值 `v15`，
**比 Web 版 `player.break = true` 更保守** —— 这是 Android 反向提供的信息，
不是移植产物。允许并鼓励 Android 先发现 Web 不知道的事，这才是「对等开发」而不是「跟随」。

### 27.4 覆盖差距必须量化，不能凭感觉

R40 实测基线（2026-10-30）：Web 自动化相关模块 **12 个 / 2,962 行**，
Android `oreki` 包机制类 **2 个 / 1,834 行**；`replicanti` / `eternityChall` /
`instantChallenge` / `sacrifice` 在 Android oreki 包内 **0 提及**。
细节见 `FACTS.md C.34`。

后续每轮用同一组命令复测（`ls src/core/oreki-*`、`grep -ril` 限定 oreki 包），
把数字写进差异表，而不是写「大致对齐」。

## 50. 任务单更新的署名与贡献归属（2026-11-01 用户确立，长期有效，**本节是归属记录的唯一源**）

### 一、核心要求

**任务单每次更新必须记录更新者的 Agent ID。**
主 Agent 汇总提交时，**不得把子 Agent 的实际执行贡献归到主 Agent 名下**。

### 二、为什么必须有这条

任务单的 commit 由主 Agent 统一做（因为三处硬链接共用 inode，子 Agent 各自 commit 会让两个仓库同时变脏）。
但 **「谁提交」不等于「谁做的」**：
- commit author 只有一个人
- 而任务单里记录的执行、诊断、修复、验证可能来自多个 Agent

若不在文档里显式署名，几轮之后就无法分辨「这条结论是谁得出的」，
既无法追溯责任，也会让子 Agent 的实质贡献被稀释成主 Agent 的功劳。

### 三、记录格式（强制）

任务单「执行记录」表**必须至少四列**：

| 时间（自然时间） | 执行者 | 事件 | 证据 |
| --- | --- | --- | --- |
| 2026年11月1日 13:05 | android-agent | 实测 db 32→108 | `reports/r50/snapshots/a13_check.json` |

- **时间**：自然时间（AGENTS §49），读系统时钟
- **执行者**：Agent 名（`main` / `android-agent` / `web-agent` / `tutorial-agent` / `android-scheduler-agent` / `rea-agent`），
  **不得只写「主 Agent」笼统带过**
- **事件**：做了什么，不是「已处理」
- **证据**：文件路径 / commit / 日志片段

### 四、必须在任务单开头列「贡献者」

每份任务单的元信息表增加一行：

```
| 贡献者 | android-agent（主体实施与实测）、main（协调与验收） |
```

顺序按**实质贡献大小**排列，不按职级。

### 五、主 Agent 的义务

1. 代提交时，**在 commit 信息里点名实际执行者**（如「由 android-agent 实测确认」）
2. 回写子 Agent 的报告时，**保留其原话关键结论**，不要改写成自己的判断
3. 若主 Agent 推翻/修正了子 Agent 的结论，**必须同时记录两人的原始观点**（例：FACTS C.93.4 记录了四次被证伪的假设及提出方）
4. 不得把子 Agent 独立发现归因为「团队发现」而隐去具体是谁

### 六、子 Agent 的义务

1. 更新任务单时，在自己的条目里**写自己的名字**
2. 不要代别的 Agent 填「执行者」
3. 若引用他人的发现，注明来源（如「依据 rea-agent 的 `h()` 不解锁结论」）

### 七、违反示例（禁止）

- ❌ 执行记录只写时间与事件，不写执行者
- ❌ 子 Agent 做了全部实测，commit 与任务单都只署 main
- ❌ 把「android-agent 发现 `[Oreki AD1]` 补丁缺失」写成「我们发现」
- ❌ 修正他人结论时，只记新结论不记原结论与出处

### 八、与既有规则的关系

- 不改变「任务单 commit 由主 Agent 统一做」（硬链接约束下的必要安排）
- 不改变「Git 提交信息使用简体中文」

## 51. 任务单禁止第一人称（2026-11-01 用户确立，长期有效，**本节是任务单文体的唯一源**）

### 一、核心规则

**`tasks/` 下的所有正式任务单禁止使用第一人称。**

任务单是项目管理与 Agent 协作的**正式记录**，不是个人叙述。
必须用客观、明确、可追踪的表达。

**禁止列表（中英文均适用）**：我 / 我们 / 我的 / 我方 / 由我负责 / 我已经完成 / 我计划 /
我认为 / I'll / We / My / Our，以及任何同义的第一人称表达。

### 二、改写对照

| 禁止 | 应改为 |
| --- | --- |
| 我负责修复自动调度器 | 负责 Agent：android-scheduler-agent；任务：修复自动调度器 |
| 我计划修改这个文件 | 计划修改文件：xxx |
| 我已经完成测试 | 执行状态：已完成；测试结果：通过 |
| 我发现一个问题 | 发现的问题：xxx |
| 我需要 Agent 3 协助 | 协作依赖：Agent 3 |
| 我认为应该先修复这个 Bug | 优先级：高；原因：xxx |
| 我将在下一轮继续 | 后续事项：xxx |

### 三、适用范围

1. `tasks/` 目录下全部任务单
2. 子 Agent 分派任务书（写入任务单的部分）
3. Agent 执行记录与任务状态更新
4. 验收记录与测试报告
5. 项目交付记录
6. 定时器生成的任务文件
7. 其他作为正式记录保存的 Markdown / TXT

**引用内容与自动生成的执行记录也应尽量转为客观表述。**

### 四、任务单标准字段（统一使用）

任务编号 / 任务标题 / 负责 Agent / 创建时间 / 开始时间 / 完成时间 / 任务目标 / 预期交付物 /
修改范围 / 执行要求 / 禁止事项 / 依赖关系 / 验收标准 / 验收方法 / 当前状态 / 执行结果 /
证据与验证记录 / 后续事项

**状态、责任、结果必须明确，不靠第一人称叙述表达。**

### 五、边界（不要过度清理）

以下**不适用**本规则：

- 普通聊天交流与 Agent 之间的自然语言沟通
- 代码注释（`// 我把它改成…` 这类在源码里是允许的）
- 用户明确要求采用第一人称的独立写作任务

**不得为了消除第一人称而牺牲表达准确性，也不得模糊责任归属。**

特别注意**术语误报**，以下都不算第一人称，不要改：
`自我锁定` / `自我引用` / `sSacCount:I`（smali 类型标注）/ `我们`在引述原文时

### 六、实施与检查

1. 新建任务单时按第四节字段写，不使用第一人称
2. 更新任务单时，新增条目同样遵守
3. **定时巡检**（整点 `:00` / 半点 `:30` 两个任务）已纳入本检查，每轮扫一次 `tasks/*.md`
4. 检查命令（避免术语误报）：

```bash
rg -n "(^|[^A-Za-z])我(?!们)" tasks/*.md     # 抓「我」但排除「我们」以外的误报需人工判断
rg -n "\b(I|We|My|Our|we|my|our)\b" tasks/*.md
```

发现后**人工判断**是否真第一人称（`自我锁定`、`sacCount:I` 之类是误报），只改真的。

### 59.1 文件性质

`WEB_ANDROID_DIFFERENCES.md` 是**双端一致性事实清单**，不是待办列表。它必须持续反映两端代码的真实状态；

### 59.2 五类标签（不得混用，用户 2026-11-01 指定）

| 标签 | 含义 |
|---|---|
| 【设计差异】 | 有意保留的平台差异（如 Android 独有商店/广告、Web 独有移动端适配） |

Web 文件路径 / Android 文件路径或 Smali 类 / 相关代码位置 / 验证证据 / 后续处理任务。
五类标签 + 这五项，缺一项即不合格。

### 59.4 证据门槛

- **不得仅凭 Git 提交记录或静态检查判断双端等价。** 重要行为必须有运行期证据（logcat / 存档字段真值 / 控件树 / 采样数据）。
- 只有读码证据的条目，一律写【待验证】，不许写「已验证」。

2. 本轮涉及 Web / Android 功能变化 → 收工前必须评估并更新该文件。
3. 已消除的差异改为【已解决】并写明证据，**过时结论必须删改，不得保留**。
4. 更新后核对三处 inode 与 SHA-256（`stat -c '%d %i %n'`），再中文 commit + Push + 核验远端。
5. 若发现其他 Agent 对该文件有未提交修改，先合并再提交，**不得直接覆盖**。

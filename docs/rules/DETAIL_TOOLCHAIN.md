## 6.3. 代码搜索纪律：优先 ripgrep（2026-10-28 用户确立，长期有效，**本节是 rg 规则的唯一源**）

> 用户 2026-10-28：「ripgrep 是持久工作纪律，不是每轮临时提醒。」慢速逐文件读取 / 全盘扫描属返工。

1. **每轮开始先确认**：`rg --version` 与 `which rg`（本机实测：ripgrep 15.2.0，
   `/c/Users/Oreki/scoop/shims/rg`）。不可用时先查 PATH，再按 `environment/测试环境记录.md` 记录的方式修复，
   **记录原因**，不得默默退回低效方式。
2. **默认用 rg 搜索**：本工作区源码、配置、脚本、测试、文档的文本检索一律先 `rg`。
   - `rg -n <pattern>` 定位行号；`rg -l <pattern>` 只列文件；`rg -c` 计数。
   - 常用排除：`-g '!work/**' -g '!build/**' -g '!node_modules/**' -g '!**/*.apk' -g '!upstream/**'`
     （`work/`、`build/`、`upstream/`、部署副本属于可重建或第三方内容，按需显式包含）。
   - 中文/多字节模式加 `-F`（字面量）或注意编码；`rg` 默认按 UTF-8，Windows 生成的 GBK 日志先转码。
3. **先定位再精读**：用 rg 找到文件与行段后，再用 Read 读取该区段；禁止为了找几个符号而整目录逐文件读取
   或使用 PowerShell 全盘 `Select-String` 扫描。
4. **不把 rg 当二进制分析器**：APK / DEX / ARSC / SQLite / `.odl` 日志等用专用手段
   （`apktool`、`scripts/rea.sh` 的 JADX 通道、`python zipfile`、`sqlite3` 模块）。
5. **rg 不能替代核验**：命中行只是线索，仍需源码调用链、smali/REA 取证与运行测试；
   Android 侧同时受 §6 的 REA 规则约束（REA 与 rg 互补：rg 找位置，REA 给可读调用链）。


## 6.4. 充分利用 REA 反编译取证（2026-10-29 用户确立，长期有效，**本节是 REA 使用强度的唯一源**）

> 用户原话：「要充分利用 REA 反编译。」
> 与 Android `AGENTS.md §0-I`（REA 强制前置的流程细则）互补：§0-I 规定**什么时候必须跑**，
> 本节规定**跑完之后必须用到什么程度**。执行顺序、失败处理、证据记录仍以 §0-I 为准。

1. **REA 是取证工具，不是打卡工具**。跑过 `rea.sh doctor` 不等于用好了 REA。
   凡涉及 Android 侧以下判断，**必须**先取 REA 证据再下结论：
   混淆类名 / 方法签名 / 字段与常量取值 / 调用链与引用者数量 / 运行期行为 /
   某个分支是否真的存在。禁止只凭 `rg` 命中行、类名猜测或「看起来像」就改 smali。
2. **优先用 REA 解决「找不到、对不上、不敢改」三类问题**：
   - 找不到：原版类被 R8 混淆成 `a` / `qk4` / `n43` / `jw0` 这类短名，`rg` 搜语义名必然落空，
     用 `search-android-classes` 按语义名反查真实类名；
   - 对不上：搞不清 smali 里哪个方法对应源码语义时，用 `inspect-android-method` 拿反编译体比对；
   - 不敢改：改共享常量/字段前，用 REA 反查**引用者清单与数量**（例如某常量被 6 处引用、
     其中含其他子系统的 `<clinit>`，就足以否决一次改动）。
3. **结论必须可追溯到证据**：报告中引用 REA 的 `evidence_id` 与 `authority`
   （如 `shipped-artifact`、`confidence`），或贴出反编译体片段 + `文件:行号`。
   只写「已用 REA 确认」而不给证据标识的结论，按未取证处理。
4. **复用已有证据，不重复解包**：同一 APK / 同一方法已有 `evidence_id` 时优先复用；
   需要新证据时先说明为什么旧证据不足。避免每轮重新 `apktool d` 全量解包。
5. **REA 与 rg 互补，不互相替代**：`rg` 负责在已知路径上快速定位文本；
   REA 负责给出「混淆世界里的真实身份与调用关系」。两者结论冲突时以 REA 的
   反编译体 + 运行证据为准，并记录冲突原因。
6. **不是 Android 专属借口**：Web 侧遇到压缩/混淆产物（构建后的 bundle、部署站文件）时，
   同样优先用可复现的反编译/还原手段定位，而不是猜。


## 13. 迁移与状态核验：分级校验预算（2026-10-27 用户补充，取代无差别全量扫描）

**本节取代原迁移任务中「全量 SHA-256」要求；关键发布产物与重要数据的严格校验保留。**

1. **第一级 · 快速盘点（默认）**：目录结构、文件数量、相对路径、大小、修改时间；
   Git 分支 / HEAD / 已修改 / 已暂存 / 未跟踪清单；列明可再生成缓存与排除规则。
   仅用于发现明显遗漏，**不得宣称字节级一致**。
2. **第二级 · 针对性校验（按需）**：对源码、配置、AGENTS.md、交接报告、REA 证据、存档、
   发布回执抽查；优先检查元数据异常、路径缺失、大小变化、复制报错或 Git 状态异常的文件；
   抽查覆盖不同文件类型与关键目录。
3. **第三级 · 严格 SHA-256（限定范围）**：APK、原始/基线 APK、发布产物、重要存档、签名相关文件
   及有异常或明确要求的文件。优先复用已存在且可信的哈希记录（身份、来源、时间点都能对应时）。
4. **全量 SHA-256 仅在必要时**：存在明确完整性风险、需要完整审计或抽样无法支持决策时才做；
   先说明扫描范围、数据量、时间成本与收益；拖慢开发时改用分级验证并记录残余风险。
5. **表述必须准确**：区分「目录与 Git 状态已核对」「关键文件已校验」「抽样校验通过」
   「全量字节级校验通过」；未校验部分明确记录范围与原因。
6. **敏捷优先**：选足以支持当前决策的最低成本验证；不重复执行不改变决策的扫描；
   发现异常再扩大范围。


## §28 模拟器控制权：一台模拟器、一个控制者、主 Agent 自主启停、子 Agent 严格受限（用户 2026-10-31 11:25 补充令修订，**本节是唯一源**）

> 该要求已被用户明确**废止**。现行规则：**主 Agent 自主启停，无需授权、审批或 AUTH 编号**；
> 子 Agent 的严格限制全部保留。凡引用「§28 一次授权」「§21 GLOBAL_STOP 需编号才能恢复」的旧表述一律作废，
> 以本节为准。事故记录不因规则修订而删除，见项目根 `EMULATOR_CONTROL.md`。

**起因是今天发生过的实际事故，不是预防性条款**：主 Agent 在 10:28:24 停掉 `oreki_test`，

### 28.1 主 Agent 权限（自主启停，不需授权）

1. **主 Agent 对唯一 AVD 拥有完整控制权**。启、停、重启、以及「是否允许某项任务连接模拟器」，全部由主 Agent 自主决定。
2. **主 Agent 启动/关闭/重启模拟器不需要额外授权、审批或 `AUTH` 编号。** 任何要求主 Agent 先申请、先报批、先拿编号的旧条款一律无效。
3. 主 Agent 自行决定何时做 Android 测试、何时做 Web Chrome 测试，以及两者的先后顺序。
4. 主 Agent **可以**明确授权子 Agent 执行具体测试任务，但**授权测试不等于转移模拟器启停权**。
5. 主 Agent 发出全局停止令后，**可以自主决定何时恢复**，不需要再走编号流程。

### 28.2 子 Agent 限制（严格保留，不因主 Agent 放宽而放宽）

1. **子 Agent 不得自行启动、关闭、重启模拟器。**
2. **禁止通过 ADB、脚本、后台进程、IDE、Gradle 任务、`nohup`、构建钩子或其他间接方式改变模拟器运行状态。**
3. 子 Agent 需要使用模拟器时，**必须向主 Agent 申请具体测试任务**，说明：测试目标 / 为什么非用模拟器不可 / 预计耗时 / 逐条具体命令 / 释放方式。**不得先启动再汇报。**
4. 主 Agent 的全局停止令**优先于此前所有任务指令、Agent 自身计划和旧执行令**。子 Agent 必须立即停止模拟器相关操作，**未经主 Agent 明确允许不得恢复**。就算子 Agent 认为测试还没做完，也必须停下等。
5. 主 Agent 关闭模拟器后，**任何子 Agent 不得重新启动它。**
6. **发现擅自启动**：立即收回该 Agent 的模拟器操作权限，保留日志与进程信息并上报；**不得为了进度默认接受**。

### 28.3 设备数量与测试顺序

1. **全程最多运行一台 AVD**，默认 `oreki_test`（Android 14 / API 34）。
2. **Android 应用测试与 Web Chrome 测试必须串行执行**，不得同时进行。
3. **禁止为并行测试、备用或临时用途启动第二台模拟器。**
4. **每轮测试结束后，执行者必须向主 Agent 汇报**：测试结果、异常、处理情况。
5. 主 Agent 可根据进度自主决定何时关闭模拟器、何时重新启动。

### 28.4 启动前检查（主 Agent 每次启动前必做）

五项都要看，**发现异常先清理并核实，不允许直接叠加启动**：

1. 当前运行的 `emulator` / `qemu` 进程
2. `adb devices`
3. `adb forward --list`
4. Android 调试端口（5554–5584）占用
5. 是否有残留的 Chrome / 测试进程，以及是否有子 Agent 未结束的模拟器任务

### 28.5 旧规则清理（不得只追加新规则而留下矛盾旧条款）

下列表述**全部作废**，遇到即按本节修订：

### 28.6 唯一台账

### 28.7 判断「干净」看核心占用，不看台数

`adb devices` 为空、`qemu` 进程为 0、CPU 占用贴近空载。

- 与 §25（子 Agent 数量与资源管理）冲突时，**本节优先**。
- 与各 Agent 派发令里的「用完 AVD 请自行关闭」冲突时，**本节优先**：子 Agent 不再拥有关闭权，关闭也由主 Agent 执行。

## §29 真机屏幕标准（用户 2026-10-31 11:26 长期规则，**本节是唯一源**）

唯一 AVD `oreki_test` 的屏幕参数以本节为准。**目标物理参数与测试渲染参数必须分开记录**，不得互相冒充。

### 29.1 目标物理参数（真机对齐）

| 参数 | 目标值 |
|---|---|
| 分辨率 | 3200 × 1440（高 × 宽） |
| 屏幕比例 | 20:9 |
| 对角线 | 约 6.67～6.69 英寸 |
| 物理尺寸 | 70 × 155 mm |
| 屏幕密度 | 560 dpi（`xxxhdpi`） |
| X DPI / Y DPI | 526 / 526 |
| PPI | 526 |
| 刷新率 | 120 Hz |
| HDR | Dolby Vision、HDR10、HLG、HDR10+ |
| 色域 | 广色域 |
| EDID 型号 | QCM |
| EDID 构建日期 | 06.2006 |

### 29.2 AVD 配置要求

- 唯一 AVD 默认 `oreki_test`，Android 14 / **API 34**。
- 屏幕按 **1440 × 3200、560 dpi** 配置（`config.ini` 里 `hw.lcd.width=1440` / `hw.lcd.height=3200` / `hw.lcd.density=560`）。
- **默认竖屏**，保持 20:9。
- **不允许只调整模拟器外框尺寸来冒充真机屏幕** —— 必须有系统实际报告佐证。
- `120 Hz / HDR / 广色域` 属于真机能力参考：普通 AVD **不保证能完整模拟**，`hw.lcd.vsync=120` 只影响模拟器合成节拍，
  **不得据此声称「已验证 120 Hz 显示」**；HDR 与广色域在 AVD 上**一律标「模拟器不支持 / 未验证」**。

### 29.3 必须核验的实际显示数据（不得只看外框）

每次屏幕相关验收，必须记录下列**原始命令输出**：

| 项 | 命令 / 来源 |
|---|---|
| 物理显示分辨率 | `adb shell dumpsys display`（`DisplayDeviceInfo` 的 `real` 尺寸） |
| Android 实际逻辑分辨率 | `adb shell wm size` |
| density / densityDpi | `adb shell wm density` + `dumpsys display` 的 `density` |
| 应用窗口可用区域 | `dumpsys window displays` / `WindowMetrics` |
| 状态栏、导航栏 Insets | `dumpsys window` 的 `mStableInsets` / `InsetsSource` |
| 应用实际可用宽高与宽高比 | 由上述两项相减得出，写明算式 |
| 屏幕旋转后的尺寸变化 | `adb shell settings put system user_rotation` 后再取 `wm size` |

### 29.4 降采样规则

若 1440 × 3200 在软件渲染（`swiftshader`）下负载过高，**允许降采样测试，但必须同时满足**：

1. `config.ini` 里保留**目标物理参数**（1440 × 3200 / 560 dpi），不被降采样值覆盖；
2. 降采样只通过 `adb shell wm size` / `wm density` 在运行时施加；
3. 报告里**同时写明**「目标物理参数」与「本次测试渲染参数」两个数字，并注明后者是降采样；
4. **降采样结果不得冒充原生分辨率验证结论**。

### 29.5 验收结论写法

- 可写「已验证」：分辨率、density、逻辑窗口、Insets、应用可用区域、旋转 —— 这些 AVD 能如实报告。
- **必须写「模拟器不支持 / 未验证」**：HDR（Dolby Vision / HDR10 / HLG / HDR10+）、广色域、真实 120 Hz 面板刷新、EDID 型号与构建日期。
- 禁止把「设了 `hw.lcd.vsync=120`」写成「120 Hz 已验证」。

## §30 浏览器与标签页控制权（用户 2026-10-31 11:44 下达，**本节是唯一源**）

**起因是实测事故，不是预防性条款**：11:42:10 有子 Agent 启动了一个自动化 Edge 实例
（临时配置目录 `oreki-cdp-*`、调试端口 9376），到 11:49 累计 **57 个 msedge 进程 / 24 个子进程**，
CDP 报 21 个 target，其中 **2 个是空白 `/` 页**，另有 chatgpt.com、darkreader 帮助页等与任务无关的页面。
同期还并存着用户自己的 Edge（PID 14148，27 个子进程）。排查记录见 §30.5。

### 30.1 浏览器控制权

1. **主 Agent 统一管理 Edge 浏览器及其标签页。**
2. **子 Agent 不得在没有明确任务需要的情况下自行打开 Edge、新建标签页或新建浏览器窗口。**
3. **子 Agent 不得通过快捷键、命令行、脚本、自动化工具或其他间接方式绕过此规则。**
4. 主 Agent **可以**明确授权子 Agent 使用**指定标签页**完成**指定任务**。
5. **授权仅限指定任务**，不允许无限创建标签页或窗口。
6. **子 Agent 不得擅自关闭主 Agent 或其他 Agent 正在使用的标签页。**
7. **不得通过反复刷新、重复导航或循环打开标签页制造无效浏览器活动。**

### 30.2 标签页使用规则

- **优先复用**已打开的项目页面和测试页面。
- **同一个任务原则上使用一个标签页。**
- 需要多个页面时，**先向主 Agent 说明用途和数量**，批准后再开。
- **测试结束后汇报标签页用途及当前状态**（保留哪些、关掉哪些、为什么）。
- **禁止为了保持任务运行而持续新建空白标签页。**
- **禁止将浏览器标签页数量当作并行工作能力。**

### 30.3 主 Agent 的调度权

主 Agent 可以：查看当前 Edge 窗口和标签页；判断哪些标签页属于有效任务；要求子 Agent 停止创建标签页；
关闭**确认无用且不被其他任务占用**的标签页；为 Web 桌面、移动端、Android Chrome 测试分配独立时段。

**不得误关正在执行的有效任务或尚未保存的页面内容。** 关闭前必须先确认该 target 的 URL 与所属 Agent。

### 30.4 浏览器是共享测试资源

不是子 Agent 可以无限扩张的个人工作区。**优先复用、统一调度、避免重复打开。**

**实例身份必须唯一**（2026-10-31 13:10 修订，原「每个实例自带临时目录 + 端口」已废止）：
全系统只允许存在**一个**自动化实例，身份钉死共享端口 `OREKI_CDP_PORT`（默认 `9300`），
配置目录固定为 `%TEMP%\oreki-cdp-shared-9300`。细则与实现见 §30.7。

没有可追溯标识的浏览器实例一律视为违规；**每次运行换一个临时目录/端口同样视为违规**
（它物理上无法复用，等于强制新建）。

### 30.7 实现契约：单实例 + 按 tag 复用（2026-10-31 13:10 落地并自证）

**唯一实现入口**：`web/_tools/lib/edge-launch.mjs`（`launchBrowser` / `openGame`）与
`web/_tools/lib/patch-launch.mjs`（猴补丁替换 `puppeteer.launch`）。**任何脚本都不许自己 `spawn` msedge。**

四条硬约束：

1. **实例身份与调用方解耦**。`launchBrowser()` 忽略调用方传的 `port`，一律用
   `SHARED_CDP_PORT = Number(process.env.OREKI_CDP_PORT || 9300)`。传进来的 port 只作为
   「共享端口探不到时的备选探测」，**永远不决定实例身份，永远不用于 spawn**。
   这样老脚本里写死的 9355/9356/9376 不再制造新实例。
2. **复用优先**。先 `GET /json/version`（1500 ms）探测，通了就 `puppeteer.connect`，
   返回 `reused: true`；复用分支的 `cleanup()` **只 `disconnect`，绝不 close/kill**。
3. **新建有硬上限**。新建前数 `tasklist /FI "IMAGENAME eq msedge.exe"`，超过
   `OREKI_MAX_EDGE_TOTAL`（默认 70，≈2 个实例）直接抛错拒绝启动。
4. **页面按 tag 复用，到上限就失败而不是抢占**。`openGame({ tag })` 把 tag 写进
   `index.html?orekiTag=<tag>`，下次同 tag 命中即复用；页面数超过 `OREKI_MAX_PAGES`（默认 6）
   直接抛错，**不抢占别人的页面**。
   —— 这一条是血换的：曾经有过「都没有就复用第一个页面」的档位，复用路径紧接着 `page.goto()`，
   跨 Agent 命中同一 Tab 会把对方正在跑的游戏页导航掉，受害方看到的是
   「采样断流 / `evaluate` hang 但 node 进程存活」，**极易被误判成游戏代码卡死**，
   从而把终局结论写反。宁可显式失败，也不能静默抢占。

**清理语义**：`cleanup()` 默认**只断开连接、不关闭共享实例**（`OREKI_CLOSE_ON_CLEANUP=1` 才真关）。
旧实现 cleanup 会 close + kill，于是「跑一次→建一个→用完关掉→下次再建」，虽然同一时刻只有 1 个实例，
但每次运行都是一次全新进程树，既慢又挡不住并发时各自新建。**收尾清场由主 Agent 显式执行。**

**自证用例**（改这个库必须跑，`pass: true` 才算改对）：

```bash
cd web/AD-Oreki-Edition && node serve.mjs 8099 &   # 静态服务
cd web && node _tools/_r42c/verify-reuse.mjs
```

实测读数（2026-10-31 13:05，同一进程连跑三次）：

| 调用 | reusedInstance | 页面总数 | 本 tag 页面 | 游戏可读 |
|---|---|---|---|---|
| 第 1 次 | false（新建） | 1 → 2 | 1 | true |
| 第 2 次 | **true** | 2 → 2 | 1 | true |
| 第 3 次 | **true** | 2 → 2 | 1 | true |

（页面总数含 1 个 Edge 内置页，所以「总数 = 1」不是有效判据，判据是「本 tag 页面恒为 1 且总数不增长」。）

**三次修正的教训，按顺序记下来**：

1. 只写规则不改代码 → 复发（12:15）。规则管不住 `Date.now()`。
2. 改了 `edge-launch.mjs` 但留了「复用第一个页面」的抢占档位 → 差点造出更隐蔽的假故障（误判为游戏卡死）。
3. `cleanup()` 仍会 close 自建实例 → 每次运行重新建实例，「复用」形同虚设，第 2、3 次全落空。
4. 主 Agent 每杀一次进程，下一次运行就必须重建实例 → **看起来像「一直在开浏览器」，其实有一半是止损动作自己造成的**。
   止损要一次性做到位，不要反复杀。

### 二、识别顺序（每次环境变化后按此顺序查，不许跳）

1. 操作系统代理设置 → 2. 终端环境变量（大小写都查）→ 3. `git config` 的 proxy → 4. 浏览器代理 → 5. 代理客户端进程与公开配置 → 6. `netstat -ano | rg LISTENING` 确认端口**真的在监听**。
   - 不得仅凭配置文件存在就认定代理可用；**必须用实际连接测试确认**。
   - 没有可用代理就明说，**不得伪造代理成功状态**。

### 三、分流策略

1. 大陆可正常访问的 → **直连**。
2. GitHub、Releases、海外代码托管、依赖源，直连失败或明显不稳 → 用现有代理。
3. 国内镜像、国内云服务、局域网 → 直连。
4. **`localhost` / `127.0.0.1` / 局域网 / 模拟器本地服务不得走外部代理**，`NO_PROXY` 必须设好，否则本地构建与模拟器调试会被自己的代理打断。
5. 不为单个站点失败改全局代理模式；有规则模式就用规则模式。

### 四、按工具分别配置（不许「设个环境变量就以为全都生效」）

- **Git**：`git -c http.proxy=… -c https.proxy=…` 单次命令级优先；持久化前先确认不影响其他仓库。
- **Gradle**：Wrapper 走 `gradle.properties` 的 `systemProp.http(s).proxyHost/Port`，或 `JAVA_TOOL_OPTIONS`；依赖仓库是否可达要单独判断。
- **npm / pip**：`npm config set proxy` / `pip --proxy`，单次命令级优先。
- **curl**：`-x/--proxy` 单次参数；`--noproxy '*'` 显式绕过。
- **浏览器**：区分系统代理与浏览器独立代理，二者可能不同。
- 优先**进程级 / 单次命令级**代理；改持久化配置前先备份，且不得把代理地址、账号、密码、令牌写进仓库。

### 五、验证与故障处理

每次经代理访问关键服务都要验证**实际结果**，至少区分：DNS 解析 → TCP 连接 → TLS 握手 → HTTP 状态码 → 业务是否真的完成（Git Push / 文件下载 / Pages 部署）。

故障处理顺序：测直连 → 测代理 → 对比两者 → 按错误类型选最小修复 → 修完用**真实业务操作**复验。

**禁止**：无限重试、频繁切换节点、无依据改 DNS/证书/系统网络、关闭 TLS 校验、把「代理连通测试成功」当成「Push / 下载 / 部署成功」。

### 六、凭据与安全

1. 日志、截图、提交、报告里**不得输出**代理账号/密码/令牌。
2. 不把代理凭据硬编码进源码或仓库配置。
3. 用户已有的代理配置**只读**，不擅自删除或覆盖。
4. 不擅自购买代理服务、不安装来源不明的代理客户端或证书。

### 七、与发布流程（§32）结合

1. GitHub 操作失败先判断是否需代理；**Push、Pages 部署、依赖下载必须分别验证**，不能互相替代。
2. Gradle 依赖下载失败，先判断具体仓库可达性，再决定代理或镜像。
3. 访问 `https://oreki.net/` 失败时，**先区分「部署失败」与「本地网络访问失败」**。
4. 代理导致的等待与失败要记实际耗时，**不重复走已知无效路径**（§32 四）。
5. 网络恢复后继续原任务，**不因为网络故障重跑已经成功的构建或测试**。

### 八、已知的真实坑（本轮实测）

- 同一份 `oreki.net/src/core/oreki-tutorial-data.gen.js`（198 KB）两次取值耗时 **15 s / 81.8 s**，内容 SHA-256 完全一致 ⇒ **直连可用但速度波动极大，慢不等于部署失败**；核验线上内容用「取回后比 SHA-256」，不要用耗时判断。
- `gradlew` 在 Windows 上自带的 `tools/jdk` 探测用 `-x "$dir/bin/java"`，而 Windows 只有 `bin/java.exe`，**`-x` 恒假 → JAVA_HOME 不被注入 → 构建直接退出**。仓库内有两个 JDK：`tools/jdk/jdk-17.0.20.1+1`（与 R43 基线一致）与 `jdk-21.0.13+9`。**每次构建前显式 `export JAVA_HOME=<仓库>/tools/jdk/jdk-17.0.20.1+1`**，系统 PATH 里没有 `java`。

6. 关闭前先保存日志、截图、frame-observer 会话与测试结果，**避免丢证据**。
7. 用正常 ADB / Emulator 方式关闭并**确认进程真的退出**；**禁止用强制杀进程代替正常关机**。
8. 下个测试马上开始时可以保留运行，但必须写明**当前使用者 / 任务 / 预计释放时机**。
9. 同一时间只允许**一个** AVD，启动、使用权、关闭全部由**主控**统一管理。
10. 模拟器关闭后，静态扫描、代码开发、网络操作、文档整理**继续**，不得让流程等模拟器。
11. 不为省资源频繁重启模拟器；**集中做完一批再统一关闭**。

## §38 Microsoft Edge 性能与生命周期管理（用户 2026-10-31 20:19 下达，长期有效，**本节是浏览器资源的唯一源**）

### 一、核心原则

1. WorkBuddy 必须**主动管理** Microsoft Edge 的进程、标签页、内存、CPU 和后台活动。
2. **Edge 是开发机共享资源，不是可以无限创建的自动化工具。**
3. 必须优先复用现有浏览器实例和标签页，**禁止为每项任务重复启动浏览器**。
4. 不得为了追求自动化并行度而牺牲开发机整体性能。

### 二、浏览器实例管理

1. 优先复用已经运行的 Edge 和现有 CDP 实例。
2. 当前项目优先复用 `OREKI_CDP_PORT=9300`，但**必须先确认端口实际可用及对应进程**。
3. **禁止每个子 Agent 各自启动独立 Edge。**
4. 禁止为同一个 Web 页面重复创建多个浏览器实例。
5. 测试时优先复用现有标签页，及时关闭无用测试标签。
6. **不得擅自关闭用户正在使用的 Edge 窗口或标签页。**
7. 不得把用户浏览器与 WorkBuddy 自动化浏览器混为一谈。
8. 如果无法确认某个 Edge 实例是否属于用户，**先保留，不得直接终止**。

### 三、资源监控（浏览器自动化密集阶段主动检查）

- Edge 进程数量及进程树；
- 浏览器总内存占用；
- CPU 使用率；
- 标签页数量；
- 是否存在崩溃、无响应或持续高占用标签页；
- 是否存在重复的后台浏览器进程；
- CDP 实例是否被多个任务争抢。

**区分浏览器主进程、GPU 进程、渲染进程和后台服务进程，不得仅凭进程数量就判断异常。**

### 四、性能控制

1. 优先使用单个 Edge 实例和最少必要标签页。
2. 不需要的测试页面及时关闭。
3. 不要让多个 Agent 同时对同一浏览器实例执行互相冲突的操作。
4. 浏览器测试与 Android AVD 测试按共享资源锁定规则协调。
5. 对持续高 CPU 或内存占用的任务进行定位，**先判断是否为必要负载**。
6. 不得为了节省资源直接关闭用户的重要窗口。
7. **不得使用强制结束进程作为常规清理手段。**
8. 结束自动化任务后，清理其专属标签页和可确认归属的浏览器进程。

### 五、浏览器生命周期

1. 浏览器启动前**先盘点现有实例**。
2. 自动化任务结束后，优先释放任务创建的标签页和临时资源。
3. 如果浏览器仍承担后续**明确排期任务**，可以继续保留。
4. 如果浏览器无任务且属于 WorkBuddy 专用实例，应正常退出。
5. 用户自己的 Edge 实例**默认保持运行**。
6. CDP 端口释放前确认没有其他任务依赖。
7. 禁止无目的地让多个 Edge 实例长期驻留。

### 六、Agent 协作

1. **主 Agent 统一管理 Edge 实例和 CDP 端口。**
2. 子 Agent **不得擅自启动**新的共享浏览器实例。
3. 多个 Agent 需要浏览器时，由主 Agent 安排串行使用或明确的互不冲突操作。
4. Agent 结束时必须报告自己创建的标签页、浏览器进程及尚未结束的自动化任务。
5. 回收 Agent 时检查其浏览器资源是否已经释放。

### 七、性能异常处理

发现 Edge 出现异常高占用时：

1. 确认进程归属；
2. 定位对应标签页或自动化任务；
3. 检查是否存在重复实例、死循环、页面持续重载或无意义轮询；
4. **优先停止造成异常的自动化任务**；
5. 仅关闭明确属于 WorkBuddy 且不再需要的页面或实例；
6. 保存必要的测试日志和结果；
7. 恢复后继续项目开发，**不得让性能排查无限阻塞交付**。

### 八、每轮报告必答

- Edge 实例数量；
- WorkBuddy 专用实例数量；
- 用户实例是否保持原状；
- 标签页数量；
- 浏览器内存和 CPU 占用；
- CDP 端口及使用者；
- 是否存在异常进程或待清理资源；
- 下一轮是否需要继续占用 Edge。

### 九、与现有规则协同

遵守 §34 AVD 生命周期、§35 子 Agent 生命周期、§36 主 Agent 主动推进、§37 双小时强制交付。
**Edge、AVD、Gradle 和共享工作树均属于需要统一调度的开发资源。**

> 最终原则：浏览器够用即可，不重复启动；任务结束及时释放；用户正在使用的浏览器绝不擅自干扰。


## §43 Android SDK / AVD / adb 下载走国内官方源（用户 2026-10-31 22:51 下达，长期有效，**本节是 Android 工具链下载路径的唯一源**）

### 一、规则

下载 **AVD 系统镜像 / Android SDK / Build-Tools / Platform-Tools(adb) / Emulator / cmdline-tools** 时，
**直连 `developer.android.google.cn`，不使用代理**（`127.0.0.1:7897` 在这条链路上关掉）。

这是官方提供的中国大陆镜像域名，直连比走代理更快也更稳。

### 二、容易踩的坑：看到 google 就开代理

§33 写的是「GitHub 等海外域名直连失败才走代理」，但 `google.com` 系列域容易被**下意识**套上代理，
结果反而变慢甚至超时。判断依据只有一个 —— **看后缀**：

| 域名 | 走法 |
|---|---|
| `developer.android.google.cn` | **直连**（官方大陆镜像） |
| `dl.google.com`（SDK 实际下载的 CDN） | **直连**（§33 已实测可达，根路径 404 属正常） |
| `maven.google.com` / `dl.google.com/dl/android/maven2` | **直连** |
| `github.com` / `githubusercontent.com` / Releases | 直连失败或明显不稳时走代理 |

### 三、操作要求

1. **先清代理环境变量再调 `sdkmanager`**，否则会继承 shell 里的 `http_proxy` 走代理：
   ```
   unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY all_proxy
   ```
2. `sdkmanager` **不要**加 `--proxy=http --proxy_host=... --proxy_port=...`；不加就是直连。
3. **AVD 与系统镜像**：
   ```
   sdkmanager "system-images;android-34;google_apis;x86_64" "emulator" "platform-tools"
   ```
   下载完用 `avdmanager create avd` 建 AVD；镜像体积大（1~2 GB），**下载前先确认磁盘余量**。
4. adb 单独更新：`sdkmanager "platform-tools"`，装完用
   `C:/Users/Oreki/Android/sdk/platform-tools/adb.exe version` 核验版本真的变了（**不能只看安装日志**）。
5. Gradle 若需 Google 仓库，优先用直连地址；国内网络下 `maven.aliyun.com/repository/google` 可作备选。
   **改仓库地址要写进该仓的 `build.gradle` 并留痕**，不要只在本机改。

### 四、失败处理

- 直连 `developer.android.google.cn` 失败时，先换 `dl.google.com` 再试；两者都失败才考虑代理。
- 走代理也失败，就明确报「本次下载失败」并附实际报错原文，**不许写成「已下载」而实际没有**。
- 下载完成后必须核验落地：文件存在 + 体积合理 + `sdkmanager --list_installed` 或 `adb version` 输出包含目标版本。

### 五、与其它节的关系

- 本节是 §33（代理网络与大陆环境适配）在 **Android 工具链下载**这一具体场景上的细化，冲突时**以本节为准**。
- §33 的「端口必须实探、不得假设」仍然有效：代理端口变了照样要重新探测。
- 本条只覆盖**下载**；`git push`、Release 附件、网盘上传等仍按 §33 判断是否用代理。

> 最终原则：Android 工具链优先走 `developer.android.google.cn` 直连；判断走不走代理看域名后缀，不看是不是「google」。


## 48. 时间信息真实性与时区规范（2026-11-01 用户确立，长期有效，**本节是时间记录的唯一源**）

### 一、基本立场

**时间是测量数据，不是语言模型可以自由创作的文本。**
任何时间必须来自系统时钟、程序日志、Git 元数据或其他可验证记录。

### 二、时间来源（硬约束）

1. 当前时间**必须从实际系统时钟读取**，不得由模型凭记忆、上下文或推测生成
2. 需要当前时间时，优先读操作系统时间；需要精确时间戳时，用程序实际生成的值
3. **不得把模型自身的时间感知当作系统时间来源**
4. 无法读取可靠时钟时，**明确标记时间未知**，不得补造

### 三、统一时区

- 项目默认本地时区：**`Asia/Shanghai`（UTC+08:00）**
- UTC 时间必须带 `Z` 后缀；本地时间必须带偏移或明确标注时区
- **不允许只写一个容易产生歧义的时间**（例如裸写「15:05」而不说明时区）
- 不得用 VPN、IP 归属地或模型推测的地理位置决定时区

### 四、本机取时间的正确方法（实测，2026-11-01）

| 用途 | 命令 | 实测输出 |
| --- | --- | --- |
| 本地时间 | `date +"%Y-%m-%dT%H:%M:%S%:z"` | `2026-11-01T12:40:43+08:00` |
| 本地时间（等价） | `date --iso-8601=seconds` | 同上 |
| UTC 时间 | `date -u +"%Y-%m-%dT%H:%M:%SZ"` | `2026-11-01T04:40:43Z` |

**⚠️ 禁止使用 `TZ=Asia/Shanghai date`**：本机 Git Bash 下实测会给出**错误结果**——
输出 `2026-11-01T04:39:52+08:00`，即把 UTC 时刻标上了 +08:00 偏移（早 8 小时且时区标注错误）。
系统时区本身已正确配置为 +0800，**直接用 `date` 即可，不要覆盖 `TZ`**。

`date +%Z` 在本机返回空串，**不要用它判断时区**。

### 五、五类时间字段必须区分

任务单与报告必须分别标注，**不得混用**：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| 创建时间 | 任务文件实际创建时间 | 文件系统 / 可验证记录 |
| 开始时间 | 实际开始执行时间 | 系统时钟 / 进程日志 |
| 完成时间 | 实际完成时间 | 系统时钟 |
| 验证时间 | 实际执行验证的时间 | 系统时钟 / 测试日志 |
| 报告时间 | 报告实际生成时间 | 系统时钟 |

**没有发生的事件不得提前填写时间。**

### 六、时间戳真实性

1. 时间戳必须来自系统时钟、程序日志、Git 元数据或其他可验证记录
2. **不得根据 Agent 回复时间反推实际执行时间**
3. **不得把文件修改时间直接当作任务完成时间**
4. **不得把 Git commit 时间直接当作代码实际完成时间**
5. 时间精度不得超过来源实际提供的精度
6. 发现系统时钟异常、时间倒退或时区不一致时，**标记异常并保留原始记录**

7. **取时的三级降级顺序（2026-11-01 由 android-scheduler-agent 的自我更正引出，强制）**：
   ① 能用取时脚本就用（`python scripts/oreki_time.py --human`）；
   ② 拿不到就用**文件 mtime**（`ls -la --time-style=+%H:%M`）或日志时间戳；
   ③ **两者都拿不到就写「未记录」，绝不写推测值**。

   **回写历史记录时，若无法核验当时时间，宁可不填，也不要用「大约」「差不多」填充。**
   编出来的时间不是「不准确」，是**伪装成证据**——后续 Agent 会拿它排序、推断因果，
   一旦基线是假的，所有下游结论都是假的，而且查不出来。

   **实际事故**（2026-11-01）：某份任务单的执行记录表整体偏了 1.5 小时以上，
   因为时间是回写时按「大概什么时候」填的。主 Agent 亦有同类错误，
   曾凭上下文推出「现在 15:52」，而系统时钟为 12:31，偏差 3 小时 20 分。

### 七、多 Agent 时间记录

- 各 Agent 使用**同一台开发机的系统时间基准**
- 子 Agent **不得自行猜测**其他 Agent 的开始或完成时间
- 主 Agent 汇总时**保留各来源原始时间戳**，不得为凑成整齐时间线而修改
- 并行任务**允许时间重叠**，不得强行排列成虚假的串行时间线

### 八、定时器时间

- 触发时间以**实际调度器记录**为准，执行时间以**实际进程/脚本记录**为准
- 必须区分**计划执行时间**与**实际执行时间**
- 延迟、跳过、重复触发**必须如实记录**

### 九、发现时间错误时的处理

1. 保留原始错误记录（不得篡改历史日志）
2. 标记错误字段及原因
3. 使用可靠来源重新核实
4. 修正报告，但**不得篡改历史原始日志**
5. 无法核实时保留未知状态

### 十、统一时间工具

跨仓库脚本统一使用 `scripts/oreki_time.py`（工作区根目录下），输出 ISO 8601：

```bash
python scripts/oreki_time.py              # 2026-11-01T12:40:43+08:00
python scripts/oreki_time.py --utc        # 2026-11-01T04:40:43Z
python scripts/oreki_time.py --stamp      # 文件命名用的 20261101-124043
```

脚本内部用 `datetime.now().astimezone()`，跟随系统时区，**不硬编码 +08:00**，
以避免「机器时区不是 +08:00 时给出错误偏移」。

## 49. 时间格式：机器通信与人类阅读分离（2026-11-01 用户确立，长期有效，**本节是时间格式的唯一源**）

> **本节修正 §48 的一处过度要求。** §48 曾要求报告也使用 ISO 8601，这是错的——
> ISO 8601 是**机器之间**传递时间的标准格式，不是所有文档都必须采用的展示格式。

### 一、核心原则

**机器读 ISO 8601，人读自然时间。**

四类场景必须区分，不得混为一谈：

| 场景 | 格式 | 示例 |
| --- | --- | --- |
| **Agent 之间通信** / API / 结构化数据交换 | **ISO 8601 带时区** | `2026-11-01T12:44:52+08:00` |
| **文件存储与文档展示**（任务单、README、开发记录、执行报告、交付文档） | **自然时间** | `2026年11月1日 12:44` |
| **文件名** | 紧凑可排序 | `20261101-124452` |
| **程序内部存储** | 时间戳 / ISO / 数据库原生类型（按技术需要） | — |

### 二、Agent 之间的时间通信

1. 必须明确时区或 UTC 偏移量
2. UTC 使用 `Z`
3. **不允许省略时区让接收方自行猜测**
4. 保留原始精度，**不得擅自补充不存在的秒/毫秒**
5. 转发时间信息时**不得改变原始时间含义**

### 三、文件与文档展示（人类阅读）

任务单、Markdown、README、开发记录、执行报告、交付文档、**巡检报告**，
默认使用可读性高的自然时间：

- `2026年11月1日 12:44`
- `2026年11月1日 12:44:52`
- `11月1日 12:44`（同年内简写）

精度按记录需要决定。

**禁止为了格式统一，把所有文档中的时间都强制写成 ISO 8601。**

### 四、程序内部存储

可选 Unix 时间戳 / 带时区 ISO / 数据库原生时间类型，但必须保证：

1. 时间值能准确还原
2. 时区信息明确
3. 本地时间与 UTC 不发生混淆
4. 输出到人类文档时**转换为可读格式**
5. 输出到 Agent 通信时**转换为 ISO 8601**

**不得为了格式统一而牺牲时间准确性。**

### 五、定时器与多 Agent

- Agent 之间交换时间 → ISO 8601
- 定时器配置 → 机器可解析格式（RRULE 等）
- 定时器执行日志与**面向用户的巡检报告 → 自然时间**
- 必须区分**计划触发时间**与**实际执行时间**
- 多 Agent 并行时**保留各自真实时间**，不得拼接虚假串行时间线
- 用户查看进度时**优先展示自然时间**，不直接暴露大量机器时间戳

### 六、时间来源真实性继续有效

本节不改变 §48 的任何真实性要求：必须读系统时钟、默认 `Asia/Shanghai`、
不得推测时区、五类时间字段分开记录、不得用回复时间/mtime/commit 时间冒充完成时间、
无法核实标未知、发现错误保留原始记录。

### 七、统一工具

`scripts/oreki_time.py`（工作区级，跨仓库共用）：

| 命令 | 输出 | 用途 |
| --- | --- | --- |
| `python scripts/oreki_time.py` | `2026-11-01T12:53:33+08:00` | Agent 通信 / 程序 |
| `... --human` | `2026年11月1日 12:53:33` | **文档 / 报告（默认选这个）** |
| `... --human-short` | `11月1日 12:53` | 同年内简写 |
| `... --stamp` | `20261101-125333` | 文件名 |
| `... --utc` | `2026-11-01T04:53:33Z` | UTC |
| `... --tz-check` | 诊断 | 核对偏移是否 +08:00 |

**已实测**：ISO 与自然时间两种输出代表同一时刻（解析回 datetime 后差值 0 秒）。

### 八、最终原则

> **时间的真实性由时钟和证据保证，时间的展示形式由阅读场景决定。**

## 53. 新增/修改的条件分支必须配可观测日志（2026-11-01 由 android-scheduler-agent 建议确立）

### 一、规则

**任何新增或修改的条件分支，必须配一条可观测日志**，且日志要**带上判定所依赖的实际值**。

不是「进入分支」这种空话，而是：

```
OREKI_CRUNCH: mode=0 amount=1e1000 am=1e1388 cmp=1 entered
OREKI_CRUNCH: mode=0 amount=1e1000 am=1e1388 cmp=-1 skipped
```

走进、走出各一条，带值。**没有日志的分支视为未验证。**

### 二、为什么是这条，而不是「做静态闸门」

**2026年11月1日一天内出现三次极性错误**：

| # | 位置 | 错误 | 发现方式 |
| --- | --- | --- | --- |
| 1 | `tryBuyId1` 循环头 | `if-le` 写成恒真 → 循环一次不执行 | `OREKI_ID_LOOP` **一行都没有** |
| 2 | `OrekiAutomationScheduler.allow` | wide 寄存器高半被当 int 读 → ART 拒收整类 | 装机启动崩溃 |
| 3 | `applyCrunchPolicy` 的策略分档 | `if-ne` 写反 → `mode==2` 也被挡掉 | `OREKI_AU4B` **一行都没有** |

**三次里有两次靠「日志缺失」发现**——这是最有判别力的信号：日志不该空的时候空了，说明代码根本没执行到。

而「静态检测极性错误」在技术上误报率极高（要判断 `if-*` 前一条 `cmp` 的语义、分支目标的命名意图），
**一个误报率高的闸门没人会认真看，等于没有**。

### 三、配套要求

1. **日志要节流**：高频路径不能用「每次打一条」，用静态计数器每 N 次打一条，或只在判定翻转时打
   （参考 `OREKI_HOLD` 的 `sHold` 翻转记录法）
2. **日志要能区分「没进去」和「进去了但条件不满足」**：前者没有日志，后者有带值的日志
3. **判定翻转才打**是首选形态——它天然节流，且能直接看出状态变化时机
4. 探针在问题定位后**可以移除，但结论必须写进 FACTS**，不要留下无注释的一次性日志

### 四、适用边界

- **不要求**每一行代码都打日志；只要求**新增或修改的分支**
- 既有代码不动（今天不改历史代码，避免混入第二个变量）
- 日志文案用中文，标签用 `OREKI_` 前缀便于 `rg` 过滤

### 五、与 §51 的关系

§51 禁止任务单使用第一人称；本节要求**代码日志可观测**。两者不冲突：
任务单是给人读的正式记录，日志是给排查用的运行期证据。

## 54. 环境安全与时间读取容错（2026-11-01 用户确立，长期有效）

### 一、时间读取的三级方案（按优先级）

| 级别 | 方案 | 说明 |
| --- | --- | --- |
| **主方案** | `python scripts/oreki_time.py` | **纯 Python `datetime.now().astimezone()`，不调用任何外部二进制**，不受杀软误报影响 |
| 备用 A | Windows PowerShell 的 `Get-Date -Format "yyyy-MM-ddTHH:mm:sszzz"` | 系统原生 |
| 备用 B | .NET `[DateTimeOffset]::Now.ToString("yyyy-MM-ddTHH:mm:sszzz")` | 系统原生 |
| 兜底 | **标记时间为【未知】** | 三者都失败时，绝不推测 |

**§48 的三级降级（脚本 → 文件 mtime → 未记录）在此升级为**：
**时间工具 → 系统原生接口 → 未记录**。mtime 只作为「事件发生时刻」的旁证，不替代当前时间。

### 二、Bash 里不要裸用 `date`

`date` 在 Git for Windows 下解析到 `/bin/date`（MSYS2 的 GNU coreutils），
属第三方二进制，可能被杀软拦截。**一律改用 `python scripts/oreki_time.py`。**

- 失败是「安全失败」：命令无输出，不会产生错误时间
- 但会导致该回合的时间记录缺失，故应主动避免

### 三、杀软误报的处理原则（硬约束）

**发现第三方工具被安全软件拦截时：**

1. **不得**关闭实时防护
2. **不得**恢复未经核验的隔离文件
3. **不得**把整个开发目录加入排除列表
4. **不得**批量放行未知程序
5. **不得**删除检测日志
6. **不得**下载来源不明的同名文件替换
7. **不得**把尚未确认的文件标记为「误报」
8. **不得**输出或泄露签名私钥、密码等敏感信息

**正确做法**：核验文件来源（路径、版本串、SHA-256）→ 记录检测名称与处理状态 →
由用户决定是否提交官方误报样本 → 期间改用**不依赖该工具**的等价方案。

### 四、已核验的环境事实（2026年11月1日，实测）

| 项 | 值 |
| --- | --- |
| `date` 路径 | `/bin/date`（Git for Windows / MSYS2） |
| 版本 | `GNU coreutils 8.32` |
| SHA-256 | `743228ae082e1128a2aff02414e114dc45a51f7461775bc5750d89307f3ccdac` |
| 大小 / mtime | 120177 B / 2026年10月27日 17:31 |
| 签名状态 | 【未知】 |
| 在装杀软 | Kaspersky、ESET、Windows Defender |
| Defender 威胁记录 | 无 |
| 卡萨斯基检测记录 | **【未知】**——未授权读取其私有日志 |
| 系统时区 | `China Standard Time`，`BaseUtcOffset = 08:00:00` |

**未宣称 `/bin/date` 为误报**——只记录它来源于 Git for Windows 且版本串与官方一致。

### 五、时间工具的抗干扰验证（实测）

```bash
# 模拟第三方工具完全不可用
PATH=/nonexistent python scripts/oreki_time.py --human
→ 2026年11月1日 14:04:59
exit=0
```

**结论**：即使 PATH 内所有外部命令都不可用，时间工具仍能正常输出。
**这条保证了「不因某个工具被误报就失去可靠时间来源」。**

### 六、Bash 工具报 `spawn EPERM` 时的降级

2026年11月1日实测出现：`Bash` 工具返回 `spawn EPERM`，连 `echo probe` 都无法执行，
而同会话的 Windows PowerShell 工具工作正常。

**降级顺序**：
1. 先重试一次 Bash（区分瞬时故障与持续故障）
2. 仍失败 ⇒ **改用 PowerShell 工具**执行 git / python / adb 等命令
3. **在任务单与报告中如实标注「本回合 Bash 不可用，已降级」**，不得静默切换
4. 不得因工具受限而跳过验证、简化证据或改变结论

**判断是不是宿主级问题**：多个 Agent 同时出现同一现象即为宿主级，需报告用户，不自行归因。

### 七、最终原则

> **杀毒软件负责保护系统，WorkBuddy 负责适应安全环境。**
> 不能为了自动化方便而降低系统安全标准，也不能因为某个工具被误报就失去可靠的时间来源。


## 58. AI 工作负载与资源健康监控（2026-11-01 用户下达，P3/P4 长期有效，**本节是「资源健康看什么、达到多少要降载」的唯一源**）

**规则编号**：§58
**名称**：AI 工作负载与资源健康监控
**优先级**：P3（多 Agent 协作效率）+ P4（开发执行与资源管理）；「不得未核验归属就杀进程」部分同时受 P0（安全）约束
**适用范围**：本工作区全部 Agent；Gradle 构建、Android 模拟器、REA 反编译、Web 截图与任何资源密集型任务
**创建时间**：2026年11月1日 15:50
**最近更新时间**：2026年11月1日 15:50
**当前状态**：生效
**实际生效位置**：工作区根 `AGENTS.md`（三处硬链接同步）+ `RULES_INDEX.md` + 主 Agent 每轮自检项
**来源或提出原因**：用户 2026-11-01 15:50 明确下达「新增长期规则：AI 工作负载与资源健康监控」
**关联项目或任务**：R51 及其后全部轮次

### 58.1 八条正文（用户原文，不得改写语义）

1. 所有 Agent 优先使用简体中文输出阶段性决策摘要，便于主 Agent 观察工作状态。
2. 主 Agent 定期检查 CPU、内存、磁盘 I/O、GPU、进程数量和后台任务状态。
3. 区分正常计算负载、资源竞争、工具等待、Agent 长时间推理和疑似死循环，不得仅凭缺少回复判定超负荷。
4. 当内存达到 80% 时，不增加并发；达到 85% 时，不启动新的重型任务；达到 90% 时，暂停资源密集型任务；达到 95% 时，进入保护模式。
5. Gradle 重型构建、Android 模拟器、REA 和其他资源密集型任务必须遵守项目已有并发限制。
6. Agent 汇报应包含当前任务、阶段、最近实际成果、阻塞原因和下一步，不要求持续刷屏或高频轮询。
7. 发现资源异常时，优先停止新增任务、降低并发、保留现有工作成果；禁止未经进程归属核验就杀进程。
8. 定期将资源状态与实际任务产出关联，识别低产出高消耗的任务。

### 58.2 四档内存阈值与对应动作（可执行化）

| 内存占用 | 动作 | 本轮实例 |
|---|---|---|
| ≥ 80% | **不增加并发**：不再派新子 Agent，不新开 AVD / 浏览器实例 | — |
| ≥ 85% | **不启动新的重型任务**：新 Gradle 构建、新 REA 全量扫描一律排队 | — |
| ≥ 90% | **暂停资源密集型任务**：让非关键 Agent 停手并落盘；已在进行且接近完成的重型任务允许跑完（中断成本高于收益） | 2026-11-01 15:50 实测 92.9%，已通知 web-agent 关闭 Edge 并落盘停手 |
| ≥ 95% | **保护模式**：只保留主线单线程最小任务，其余全部暂停并保存状态 | — |

### 58.3 判定纪律（防误判）

- **CPU 100% + 磁盘持续写 + 日志在增长 = 正常计算负载**，不得判为死循环。
- **无输出但进程在跑 = 先看日志文件大小是否变化、有无子进程**，再判「工具等待」或「Agent 长时间推理」。
- **禁止仅凭「某 Agent 长时间没回消息」就判定其过载或卡死**。
- **杀进程前必须核验进程归属**（PID + 命令行 + 日志路径三者对应），核验不通过不得杀。

### 58.4 汇报格式（与第 6 条配套）

Agent 阶段汇报固定五项：**当前任务 / 阶段 / 最近实际成果 / 阻塞原因 / 下一步**。不求高频，只在阶段完成、状态变化、阻塞或交付时汇报。

### 58.5 低产出高消耗识别

每轮收尾时，把「资源占用」与「实际产出」并列对照一次：占用高但无代码/构建/部署/APK 产出的任务，下轮降优先级或改为按需调用。


## 63　Gradle 在线/离线策略（2026-11-04 起长期生效，P2）

### 63.1 日常默认离线

- 日常开发、增量构建、Release 构建**默认**执行：`gradlew assembleRelease --offline`
- 优先复用本地 Gradle 缓存与已安装工具链。
- 不因习惯或"顺手检查一下"反复联网。
- **不得**为绕过构建错误而无差别清理 Gradle 缓存（`--refresh-dependencies`、删除 `~/.gradle/caches` 均属禁止动作，除非已定位到具体损坏缓存项）。

### 63.2 允许在线的四种情形

1. 离线构建**明确提示**缺少依赖（错误信息含 artifact 坐标）。
2. Gradle / Kotlin 编译器 / 构建依赖版本升级。
3. 新增了本地尚未缓存的依赖。
4. 需要首次下载或同步必要的构建工具。

在线构建前必须先确认缺的具体依赖/工具，避免无差别下载。

### 63.3 在线与离线衔接

- 在线模式**只负责补齐**依赖、工具和缓存。
- 依赖补齐后**重新执行离线构建**，确认缓存完整。
- 后续日常构建恢复离线。
- **网络下载失败、仓库不可达、依赖缺失不得误判为代码编译错误**——必须在报告中区分"构建环境问题"与"代码问题"。
- 不得擅自更换依赖版本、构建仓库或引入不必要的远程依赖。

### 63.4 每轮必须记录

| 项 | 要求 |
|---|---|
| 构建模式 | 离线 / 在线，逐次写明 |
| 依赖下载 | 是否发生、下载了什么、耗时 |
| 构建耗时 | 实际墙钟，分阶段 |
| 离线恢复 | 是否已验证"补齐后离线可构建" |
| 缓存复用 | 增量命中情况（哪些任务 UP-TO-DATE） |

# Agent 并行开发与持续交付契约

权威：本文件；范围：主 Agent、获派子 Agent 与轮次调度；状态：R97 生效。它替代旧的“单 Agent 主导生产、子 Agent 仅辅助/只读、小补丁后等待”倾向；历史编号和归档只保留历史证据，不恢复旧限制。

## 1. 总体职责

- 主 Agent（当前 R97 为 DeepSeek 主 Agent）负责整体目标、任务拆分与调度、跨模块集成、共享资源协调、冲突解决、正式门禁和最终交付。
- 子 Agent 在获得明确的目标、文件/模块写入所有权、输入证据和验收标准后，是可以独立交付生产成果的实施者，不是只读审计员或报告生成器。
- 一个子任务完成不代表整轮完成。只要仍有已授权、安全、有效、可执行的工作，子 Agent 必须保存成果、报告状态并领取下一个不冲突的生产任务；不得以等待主 Agent 回复停止全部工作。确无可执行工作时，报告具体阻碍并释放资源。

## 2. 子 Agent 的授权范围

获得任务授权和写入所有权的子 Agent 可以：

- 大幅修改负责的生产模块，新增多个相关 Kotlin、JavaScript 或其他必要文件；
- 独立完成较大的功能链、必要重构和跨多个函数/类/文件的真实缺陷修复；
- 将需要修改的 Android 业务路径完整迁移至 Kotlin，并完成 Kotlin → kotlinc → D8 → DEX → APK 链路上的针对性验证；
- 完成 Android/Web 对等功能、EC、Dilation、Reality、自动购买器、剧情调度等专项开发；
- 编写必要的定向测试、诊断工具和运行证据采集；
- 在当前任务完成后继续领取其他不冲突的生产工作。

不得设置人为的代码行数、文件数量或修改规模上限。大规模修改仍必须有明确目标、写入所有权、禁止触碰范围和验收标准，不得顺手改动无关模块、伪造购买/扣费/资源结算/奖励，或用静态结果冒充真实生产行为。

## 3. 并行角色与派发

根据当前 Harness 并发能力，优先维持约五个有效角色，按真实任务动态拆分、合并、替换和补位，不机械凑实例：

1. Android 核心业务与 Kotlin 实现；
2. Web 对等功能实现；
3. EC、Dilation、Reality 等关键机制专项开发；
4. 自动购买器与剧情调度专项开发；
5. 构建集成、定向测试和运行验收协调。

派发必须真实调用可用 Agent 通道。任务消息至少包含：目标、授权文件/模块、禁止修改范围、输入证据、验收标准、独占资源、交付格式和停止节点。禁止只派只读审计而让主 Agent 独揽所有重要编码；审计只有在能解除具体风险或服务于当前交付时才单独派发。

同一文件或模块同一时刻只有一个修改责任方。发现任务重叠时，先调整文件所有权并完成交接，再开始跨模块修改；安全任务已在执行时无需强制中断，下一次调度机会按新规则重新分配。

## 4. 隔离、保存与集成

- 大规模修改优先使用独立 worktree、隔离分支或 Harness 可靠隔离机制。不得覆盖主 Agent 或其他子 Agent 的未提交改动，不得破坏硬链接、存档、构建缓存或历史成果。
- 子 Agent 完成或失败都必须保存当前修改和证据，报告真实 diff、验证命令、结果、阻碍和后续建议；需要跨模块修改时先提出所有权交接请求。
- 每项可交付成果必须可追溯到真实 Git diff 和提交。中文提交 subject/body，正常 push main，禁止 force push；提交不等于稳定版发布。
- 主 Agent 集成已完成成果，不允许多个 Agent 在同一工作区同时覆盖相同文件。共享规则、单一正式产物和共享资源按 GIT.md/RELEASE.md 协调。

## 5. 构建、设备与运行权限

- 子 Agent 可进行独立 Kotlin 编译、静态检查、定向测试、诊断工具运行及不冲突的局部/候选构建。APK 候选构建允许多次，不因旧的构建次数限制阻碍开发，也不需要为普通候选构建反复申请用户授权。
- 候选构建不是稳定版：候选仅用于本地验证，必须保留真实 Kotlin → D8 → DEX → APK 证据，不得上传四渠道、覆盖正式产物或冒充稳定版。
- 单个 AVD、正式 Release 签名、最终 APK 输出目录和发布资源必须统一协调；不得多个 Agent 同时争抢 AVD 或覆盖同一正式构建产物。正式稳定版仍遵循必要门禁、每两小时至少一次已验证稳定版和 Android 四渠道同包要求。
- 共享资源被占用或构建等待时，推进不依赖该资源的已授权生产代码、测试或证据工作；记录任务 ID/PID、启动时间、commit、命令、日志、状态、退出码、产物路径和哈希。

## 6. 质量与平台边界

- Android 新增或修改的业务路径必须完整 Kotlin 化，遵守清晰命名、ABI 兼容和真实 Kotlin → D8 → DEX → APK 要求；不得把 Java/Smali 或 Kotlin 空壳留作实际执行逻辑。
- Android/Web 保持 MOD 核心行为等价；原版真实购买、扣费、资源结算和挑战奖励必须来自真实生产路径，不得伪造。
- 验收优先依据实际生产行为、资源增长、目标成长效率、里程碑时间和必要运行测试；定向验证应覆盖正向与反向边界。禁止因为允许大规模修改而进行无意义架构重写、机械全量回归或过度审计。
- 环境故障按 TOOLCHAIN/RELEASE 处理：记录证据、释放独占资源，并转向不依赖故障环境的授权工作；不得重复无证据的失败操作。

## 7. 持续接力与停止

- 子 Agent 在当前交付完成后主动回报“已完成/受阻/待交接”，由主 Agent 更新队列并立即分配下一项不冲突工作；等待单个构建或主 Agent 集成期间仍应推进独立工作。
- 只在用户明确停止、当前 R97 已完成全部授权目标且没有剩余安全工作，或确实没有可执行任务并已报告具体阻碍时停止。不得把一个小检查、一次提交、一次构建、单端部署或等待回复误判为整轮完成。
- 清理仅限本轮有权管理的 Agent 和进程；先保存成果，不得终止其他 Harness、主控或无关进程。不得开启新轮次、重置任务编号或用换模型/重启工具重置开发计时。

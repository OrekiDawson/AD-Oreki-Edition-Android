## §26 断言设计规范

### 26.1 断言必须有会 raise 的入口

**反例（真实踩过）**：把旁路断言写成 `expect_fail(lambda: helper())`，而 `helper()`
只**返回问题清单**、不抛异常 —— 于是自测永远显示「没有被拦住」，断言形同不存在。
作者还以为自己测过了。

规范：
- 每个断言必须有一个**失败即抛异常或非零退出**的入口函数（`validate_xxx()`）。
- 「返回清单」的辅助函数（`_xxx_problems()`）**不得直接配 `expect_fail`**。
- 自测里每条断言至少一条**必须失败**的负例，且负例失败信息要能贴出来给人看。

### 26.2 断言的有效性不能依赖调用者记得怎么调

这与 `OREKI_TUTORIAL_STRICT` 默认关闭是同一类错误：守则写对了，但默认不生效等于没有守则。
**默认必须是 fail closed**（`OREKI_TUTORIAL_ALLOW_DRAFT` 默认严格，`=1` 才放行）。

### 26.3 只校验「内容的正确位置」不够，必须管住「内容可能出现的位置」

真实事故（两条，同一天）：
1. Web `src/core/oreki-tutorial.js:108` 写着「把 RM **灌注**给特蕾莎换**时间定理**」——
   一句话两个禁用译名。而译名断言只扫 JSON，完全看不见它。
2. Android `tutorial/TutorialProgress.smali:202` 写着「用**时间定理**点时间研究」——
   玩家每次进入永恒阶段都会在教程界面顶部看到，而它同样不在 JSON 里。

规范：新增「玩家可见但不在内容源里」的中文文案时，必须同时把它登记进扫描面
（Web：`validate_tutorial.mjs` 的 `PLAYER_VISIBLE_SOURCES`；Android：smali 全包旁路扫描）。
扫描面宁可宽——106 条全扫的代价可以忽略，漏一个文件的代价是不可见缺陷。

## §41 frame-observer 主动授权与观测（用户 2026-10-31 21:52 下达，长期有效，**本节是 Android 观测的唯一源**）

### 一、定位

- frame-observer 是 Android 端**唯一的画面 + 控件树观测通道**，不是可选项。
- 凡涉及 Android UI 验收（教程页是否深色、顶栏、两行 `ScrollableTabLayout`、按钮是否真的可点、画面是否卡死），
  **一律先用它取证据**，不允许凭「应该没问题」写结论。
- **「主动获取授权」= 主 Agent 自己把整条授权链路走完**，不把「你去点一下开始捕获」这类动作留给用户。

### 二、授权链路（每次 AVD 重启或投影被收回后必须重走）

1. adb 全路径：`C:/Users/Oreki/Android/sdk/platform-tools/adb.exe`（**不在 PATH**，必须写全）。
2. `adb devices` 必须看到 `emulator-5554  device`。
3. `adb forward tcp:8731 tcp:8731`，再用 `adb forward --list` 确认。
4. `curl -s -m 5 http://127.0.0.1:8731/stats` 探活。连不上或 `capturing=false` → 进第 5 步。
5. 冷启动：`am force-stop com.oreki.frameobserver` → `am start -n com.oreki.frameobserver/.MainActivity`。
6. **冷启动场景下 `/ui` 必定 503**（HTTP 服务随进程一起停，实测返回 `{"无障碍服务未连接"}`），
   所以这一步**必须用 `uiautomator dump`**，且 Git Bash 会做 MSYS 路径转换，**必须 `export MSYS_NO_PATHCONV=1`**，
   否则 `/sdcard/fo.xml` 会被改写成 `.../PortableGit/sdcard/fo.xml` 而静默失败：
   `adb shell uiautomator dump /sdcard/fo.xml` → `adb shell cat /sdcard/fo.xml`。
   按钮是 `com.oreki.frameobserver:id/btn_start`（文本「开始捕获」）。
7. 系统投影对话框由 `com.android.systemui` 弹，**文案是英文**：`START NOW`（`android:id/button1`）/ `CANCEL`（`android:id/button3`）。
   在这里才可以用 `/ui`（此时进程已起、a11y 若正常）或继续 `uiautomator dump` 拿 bounds → tap。
8. `/stats` 复核三项，全过才算授权成功：`capturing=true`、`frames_processed` 在增长、`actual_fps>0`。
9. **授权成功后必须把无障碍服务写回**：`am force-stop` 会把 `settings secure enabled_accessibility_services`
   清成 `null`、`accessibility_enabled` 变成 `0`（实测），不写回则 `/ui` 一直返回
   `503 {"error":"无障碍服务未连接"}`。命令：
   ```
   adb shell settings put secure enabled_accessibility_services      com.oreki.frameobserver/com.oreki.frameobserver.a11y.ObserverA11yService
   adb shell settings put secure accessibility_enabled 1
   ```
   写回后再用 `/ui` 复核一次，返回 JSON 数组才算恢复。

### 三、不可绕过的边界

- **不允许**用 `pm grant` 或任何等价手段伪造投影权限；MediaProjection 只能走系统对话框。
- 工具刻意**不提供** `POST /capture/start`，禁止我给它加远程触发接口来「省掉确认这一步」。
- 授权对话框只在设备前台可见：动手前用 `dumpsys window | rg mCurrentFocus` 确认 `MainActivity` 在前台。

### 四、自愈与失效判定

- 投影被系统收回（`MediaProjection.onStop`）表现为 `/stats` 的 `capturing=false`，或 `/stats` 直接不可达。
- AVD 重启、app 被 force-stop、系统回收前台服务 —— 这三种都要重走第二节。
- **连续两次走完第二节仍拿不到 `capturing=true`**，才允许报「frame-observer 不可用」，
  并附 `/stats` 原文 + `logcat` 相关行，不许只写一句失败。

### 五、观测纪律

- 控件树用 `/ui`：它**不等 idle**，专治 `uiautomator dump` 在动画画面上报 `could not get idle state`。
- 画面用 `/snapshot.jpg`（响应头带 `X-Frame-Id` / `X-Frame-Mono-Ns`）；**没看图不得断言画面正常**。
- 时序问题用 `/frame_at?t=<ns>` 回放；无障碍事件用 `/events?since=N`。
- **bounds 是物理像素 1440×1600，画面是 720×1600 半分辨率**，换算别搞错。
- 截图与控件树要落到 `android/reports/` 对应轮次目录，作为验收证据。

### 六、与采集中会话的关系

- 正在采集（`capturing=true` 且 `frames_processed` 持续增长）时，不得为图省事 force-stop；
  确需重启，先记录原因与当时的 `frames_processed`。
- 采集会话本身不是交付物，但它是 Android 端 UI 结论的**唯一证据源**，丢证据比丢帧严重。

> 最终原则：Android 端要看的、要点的、要证明的，先用 frame-observer 拿到证据再下结论；授权这一步由主 Agent 自己走完，不推给用户。


## §42 frame-observer 按需求可修改（用户 2026-10-31 22:00 下达，长期有效，**本节是修改该工具的唯一源**）

### 一、授权范围

- 用户已明确授权：**可以按需求修改 frame-observer**（源码、资源、构建脚本、文档均可改）。
- 这项授权是**长期有效**的，不需要每次再问。§41 里「禁止给它加远程触发接口」的条款**仍然有效**。

### 二、必须守住的底线（不可改）

- **投影授权必须由人在设备上确认**：`POST /capture/start` 之类远程触发接口**永远不许加**。
- 不许用 `pm grant` / 系统签名伪造 `CAPTURE_VIDEO_OUTPUT` 或绕过系统对话框。
- 不许为了「观测方便」去改游戏包（`com.oreki.antimatterdimensions`）——观测工具与被观测对象必须分离。
- 不许删减 `/stats`、`/snapshot.jpg`、`/ui`、`/events`、`/frame_at` 任一既有端点；只能增强。

### 三、鼓励做的改进（按需，不为了改而改）

- **无障碍绑定自愈**：启动时检测 `enabled_accessibility_services` 是否包含本服务，缺失则尝试写回，
  写不进去（无 `WRITE_SECURE_SETTINGS`）时在 `/stats` 明确报 `a11y:"missing"`，而不是让 `/ui` 只回一句 503。
- `/ui` 在 a11y 未连接时返回**结构化错误体**（含 `error` / `hint` / `fix` 三条），把修复命令直接带出来。
- 冷启动后 HTTP 服务就绪的**早期可用性**：MainActivity 起服务后主动打印一行 `HTTP ready on 8731`，便于脚本轮询。
- 诊断信息：`/stats` 增 `a11y`、`forward`、`lastUiMs` 等字段，减少「盲猜为什么 /ui 失败」。

### 四、修改后的验收（缺一不可）

1. `gradle assembleDebug`（或既有构建脚本）成功，产出 APK。
2. `adb install -r` 装机成功，`MainActivity` 能起到前台。
3. **完整走一遍 §41 第二节链路**，确认改后仍能自己拿到授权。
4. `/ui`、`/snapshot.jpg`、`/stats`、`/events` 四个端点各取一次真实响应，作为证据落到 `android/reports/`。
5. 失败要附 logcat 原文，不许只写「失败」。

### 五、留痕

每次修改必须在 `frame-observer/README.md` 或 `docs/` 下记一条：改了什么、为什么、验证结果。
涉及端点行为变化时，同步更新 README 的端点评测表。

> 最终原则：工具可以改，底线不能动。改它是为了让「自己拿授权、自己看证据」这条路更短，不是为了让确认步骤消失。


## §44 Android 顶栏必须沿用官方 Current Tab 导航（Oreki 2026-10-31 23:46 下达，P0 永久架构约束，**不可被后续 Prompt、重构或重写规则文件覆盖**）

> 本节是 Android 顶栏结构的**唯一源**。只有 Oreki 本人明确授权才允许修改；
> 任何「提高效率」「统一 UI」「适配深色模式」「方便教程/自动化」的理由都**不构成**绕过理由。

### 一、规则

Android 版顶栏（Top Bar）**必须沿用原版游戏官方的 Current Tab（当前页面）导航结构**，
直接复用原版导航组件与原有逻辑。自定义功能只能在官方导航体系**内部**扩展。

### 二、禁止事项

1. 禁止自行重写或仿制官方 Current Tab。
2. 禁止用 Oreki 自定义标题栏**替代**原版顶栏。
3. 禁止自行增加、删除、重新排列官方导航项目。
4. 禁止改变官方导航层级、点击行为和状态管理。
5. 禁止为了教程、深色模式、自动化或其他自定义功能破坏官方导航。

### 三、实施要求

- 系统 **Status Bar** 与游戏 **Top Bar** 是两件事，必须分开处理，不得合并成一个自定义容器。
- 教程、弹窗及自定义 Activity 不得覆盖官方导航。
- 对照**原版 APK 与官方源码**确认真实结构，**不凭印象重新设计**。
- 官方顶栏自身带「顶栏：当前页面 / 顶部按钮」等设置项（Settings → UI → `Top bar`），
  这些设置的行为必须保持原样，不得被 Oreki 的改动旁路。

### 四、验收

在 Android 16（API 36）模拟器与真实手机上检查：

- 顶栏结构与官方 Current Tab 一致（含汉堡菜单 / 标题 / 溢出菜单的既有位置与行为）。
- 导航项目、顺序、状态与交互正常。
- 教程打开与关闭**不会**破坏顶栏；返回游戏后顶栏仍在原位。
- 深色模式及游戏阶段切换不会替换顶栏。

### 五、持久化与检查

- 本规则必须同时存在于 `docs/AGENTS_GLOBAL.md` 与 `docs/FACTS.md`，两端共享且一致。
- 两份文件是**硬链接同一 inode**，只能用「原地 `r+b` → `seek` → `write` → `truncate`」方式修改，
  **禁止 `cp`、原子替换、删除重建**，否则链接会断、两端内容立刻分叉。
- 每轮开始与结束各检查一次：`python scripts/check_agents_sync.py`。

### 六、与其它节的关系

- 与 §39/§40（子 Agent 收放）、§41/§42（frame-observer 观测）、§43（工具链下载）**并列，互不覆盖**。
- 本节优先级高于任何「界面统一」「视觉一致」类要求；冲突时以本节为准。
- 不得为了消除规则冲突而擅自降低本节优先级。



## 62　Android 验收策略：日常实机优先，版本更新完整回归（2026-11-04 起生效）

| Web 对应功能 | 同步验证 |

**不得**仅凭"APK 构建成功"或"应用能启动"就宣布版本升级完成。

### 62.4 特殊情况（按风险决定范围）

| 场景 | 验证范围 |
|---|---|
| Gradle / AGP / Kotlin / JDK 等工具链升级 | 完整 Release 构建 + 实机启动 + 关键流程，**不强制**完整游戏机制回归 |

### 62.5 执行原则

1. 实机验证优先于无意义的静态测试数量。
2. 测试范围与修改风险匹配。
3. **不允许**通过跳过必要验证掩盖真实缺陷。
4. 版本更新必须完整回归。
5. 不得把日常开发与版本更新混为一谈。
6. 不得为追求测试数量牺牲生产功能开发时间。

## 64　Android 全量 Kotlin 转译（2026-11-04 起长期强制，P0）

### 64.1 核心原则

**Android 端本轮所有修改内容，只要能够转译成 Kotlin，就必须全部使用 Kotlin 实现。**
这是长期强制规则，不是建议，也不只适用于新功能。

### 64.2 禁止扩大 Smali 业务逻辑

- 禁止新增 Smali 业务逻辑。
- 禁止为省事直接改 Smali 方法体实现新功能或修问题。
- 禁止把本轮修改拆成 Kotlin + Smali 两套业务实现。
- 禁止只写 Kotlin 外壳、把实际业务逻辑留在 Smali。

### 64.3 修改已有 Smali 逻辑时（五步，缺一不可）

1. 分析对应方法、调用关系、数据结构和原有行为。
2. 把本轮涉及的可迁移逻辑**完整**转译到 Kotlin。
3. 保持原有功能语义与必要的 ABI、方法签名、调用兼容性。
4. 调整原有调用路径，使其**实际进入** Kotlin 实现（不是并行两套）。
5. 避免 Kotlin 与 Smali 重复实现同一业务功能。

不得只迁移表面代码；必须确保**实际执行路径**已迁移。

### 64.4 Kotlin 构建与 APK 集成

链路固定为：`Kotlin 源码 → kotlinc → D8 → DEX → APK`。

- Kotlin 源码必须实际参与构建。
- D8 必须生成对应 DEX。
- 最终 APK 必须包含本轮修改后的 Kotlin 代码。
- **不得出现源码已改、编译结果没进 APK 的情况。**
- 构建后必须检查 DEX 内的类与方法、调用关系及兼容性。
- 可保留必要的原版兼容入口，但不得借此继续扩大 Smali 业务逻辑。

### 64.5 允许保留 Smali 的三种例外（必须事先说明）

1. 必须保持的原生兼容入口。
2. 无法获得源码或无法合理转译的第三方二进制实现。
3. 明确受工具链或运行时限制的特殊代码。

遇到例外，**修改前**必须写明：无法迁移的具体原因、涉及的类/方法/文件、
对应调用关系、可行替代方案、为什么不能用 Kotlin 实现。
**不得**以"工作量大、时间不够、沿用旧实现"为由继续写 Smali。

### 64.6 已知工具链限制（实测，2026-11-04）

`kotlinc -classpath` **不接受 dex 输入**（报 `error: source entry is not a Kotlin file`）。
因此 Kotlin 层不得在编译期直接引用游戏类，一律通过
`Class.forName` + 反射访问（见 `OrekiAutomationScheduler.originalAutobuyersOn`）。
这不算"无法迁移"的例外——只是访问方式约束。

### 64.7 每轮 Android 报告必须列出

- 本轮修改的 Kotlin 文件和功能。
- Kotlin 编译、D8 转换、DEX 集成结果（含 dex 体积、类名核对）。
- 实际迁移的原有逻辑范围。
- **本轮新增/修改的 Smali 业务逻辑数量（目标恒为 0）**。
- 遗留 Smali 及其无法迁移的具体原因。
- APK 中 Kotlin 代码的验证结果（装包后日志/类名实证）。

## 66　REA Android Analysis 长期强制使用（2026-11-05 起长期生效，P0）

### 66.1 定位

REA 是本项目 **Android APK 静态分析、反混淆、调用关系还原、版本迁移**的重要基础设施。
它**不是**业务实现语言，**不能**替代 Kotlin 业务代码、编译、DEX 集成与 AVD 运行验证。

### 66.2 必须优先评估并使用 REA 的任务

- Android APK 结构分析
- 游戏版本升级与新旧 APK 差异分析
- 混淆类 / 方法 / 字段映射
- 关键方法的反编译与 Smali 回退分析
- 关键方法调用者与调用链追踪
- 补丁锚点定位与失效原因分析
- Kotlin 转译前的原版逻辑还原
- ABI、方法描述符、外部调用关系核验
- 历史反混淆成果的复核与增量更新

**不得**只依赖人工猜测、类名搜索、全量 JADX 输出或 Smali 文本搜索完成上述任务。

REA 不可用时：先记录**具体原因**（工具缺失 / 启动失败 / 超时 / 资源限制），
再用现有 JADX / DEX / Smali 工具完成必要工作。
**不得因 REA 暂时不可用而停止实际开发，也不得虚构 REA 分析结果。**

### 66.3 工具版本：追求最新正式稳定版，不写死版本号

适用范围：REA MCP Server、REA CLI、JADX / jadx-headless-mcp、JDK、Kotlin 编译器、
D8 / Android Build Tools，以及其他 APK 分析、反编译、反混淆工具。

每次安装或升级时：

1. 查询**执行时**的最新正式稳定版本（官方 GitHub Release / 官方文档 / 官方发布渠道）。
2. 明确区分 Stable / Preview / Beta / Alpha / RC / EA / Nightly。
3. **只选正式稳定版**，禁止把实验版当常规生产工具。
4. 核对操作系统、CPU 架构、JDK、依赖与当前项目兼容性。
5. 下载后验证官方 SHA-256 或其他可信校验值。
6. 优先复用已安装且满足最新稳定要求的版本；不重复下载、不无意义升级。
7. 最新版与现有工具链不兼容时，选**能稳定协同的最新兼容正式稳定版**，并记录原因。
8. 不得为追求版本号破坏当前可构建环境。

**版本号仅作当次环境事实记录，不得作为永久锁定值。后续执行必须重新检查。**

### 66.4 APK 分析流程

**4.1 建立 APK 身份**（先做，再做类/方法分析）

记录：APK 路径、SHA-256、包名、versionName / versionCode、minSdk / targetSdk、
DEX 数量与类数量、工具链版本、REA 分析会话与 Evidence 标识。

> **APK 来源真实性与签名证书必须用独立签名工具核验。**
> REA 的 Manifest 分析**不能**替代 APK 签名验证。

**4.2 类与方法分析**

按实际需求使用（实际执行前必须查当前 REA 版本的工具名与参数，不得假设接口不变）：
`inspect-android-package` / `search-android-classes` / `inspect-android-class` /
`inspect-android-method` / `trace-android-references`。

优先检查影响游戏进度、购买、重置、挑战、结算与自动购买器的真实执行路径。
必要时检查 `<clinit>`、构造方法、内部类与状态持有对象。

**4.3 调用链分析**

追调用者 → 查调用位置与 DEX 描述符 → 读关键调用者方法体 → 逐层还原路径 →
对关键路径用 AVD 与运行时日志验证。

**必须区分静态引用与运行时调用。** 静态调用关系不能证明虚方法/接口方法的实际实现，
也不能完整覆盖反射、JNI、MethodHandle 与动态加载。
REA 的 coverage **不得**扩大解释为完整运行时覆盖率。

**4.4 反编译回退**

Java 反编译不可用时用 REA 的 Smali 回退；必要时结合独立 DEX / Smali 工具检查原始指令。
**不得**因某个方法反编译失败就认为它没有逻辑；**不得**因输出截断就认为后续代码不存在。

### 66.5 历史映射与增量分析

必须复用：已有类映射、方法与字段映射、结构匹配结果、关键调用链、补丁锚点、
反编译报告、历史 APK 与 SHA-256、分析脚本与复现命令。

增量流程：确认新旧 APK 身份 → 加载历史映射 → 复核已知关键类/方法结构 →
只分析变化或证据不足的部分 → 为失效映射找新候选 → 用方法描述符 + 字段类型 +
调用关系 + 方法体语义确认 → **保留"未确定 / 有歧义 / 已确认"三种状态**。

**禁止**只凭混淆名称、常量相同或单一结构特征确认映射。

使用 R8 / ProGuard mapping 时，必须核对来源、SHA-256、适用版本与方法描述符；
不得假设 mapping 属于当前 APK。

### 66.6 证据与长期固化

关键成果至少记录：源 / 目标 APK SHA-256、工具版本与校验值、原始与目标类名/方法名/
DEX 描述符、关键字段映射、关键调用关系、分析结论及证据边界、REA Evidence 标识或等价记录、
人工复核结果、复现请求或命令、尚未解决的歧义与风险。

重要事实写入 FACTS.md；必要时更新映射表、分析报告与任务文档。
反混淆工具脚本、关键映射与分析结论必须进 GitHub；大型反编译树与 APK 中间产物
先评估体积 / 恢复价值 / Git LFS 或独立归档，不无脑全传。

### 66.7 与 Kotlin-only 规则协同

REA 是分析工具，不是业务实现语言。Android 业务修改仍必须遵守 §64：

- 本轮涉及修改的 Android 业务逻辑必须完整迁移到 Kotlin。
- 不得新增 Smali / Java 业务逻辑。
- 不得只写 Kotlin 外壳而把实际业务实现留在 Smali。
- 保持 ABI、方法签名、调用语义与数据结构兼容。
- Smali 中仍有效的业务注释与分析成果必须迁移到 Kotlin。
- 必须走通 Kotlin → D8 → DEX → APK 全链路。
- 用 REA 和其他工具核验最终 APK 中的实际类、方法与调用路径。

**REA 分析结果不能替代编译、DEX 集成与 AVD 运行验证。**

### 66.8 性能与效率

- 同一 APK 优先复用已有 REA 分析会话。
- 优先分析关键类/方法，不重复全量加载。
- 大型 APK 用合理超时与分批分析。
- 遇到资源限制、超时、截断或部分观察，明确记录。
- 优先复用历史映射与报告；不得为分析工具反复完整反编译。
- **不得让反混淆工作长期阻塞 Android 与 Web 的通关功能开发。**
- 优先处理真正影响全新存档 3 小时通关的瓶颈。

## 67　Kotlin 可读性命名规范（2026-11-05 用户下达，P0 长期有效）

**适用范围**：Android 端**所有新增及迁移的 Kotlin 代码**，以及未来新增的 Kotlin 工具代码。
**与 §64（全量 Kotlin 转译）的关系**：§64 管「用 Kotlin 写」，本节管「Kotlin 怎么写才可维护」，
两者同时生效；冲突时以本节的可读性要求为准（§64 不要求沿用混淆名）。

### 67.1 命名必须语义明确

1. 所有新增或迁移的 **类、接口、方法、属性、变量、常量**必须采用**语义明确、可读性高的英文名称**。
2. **禁止**把原版混淆名称（如 `bq0` / `rp0` / `aw` / `G()` / `K()`）作为新 Kotlin 代码的**内部命名**。
   混淆名只能出现在「兼容适配层」的字符串常量或映射表中（见 §67.4）。
3. 命名应体现**实际职责与行为**，避免：
   - 无意义缩写（`sIpMult`、`stgA`、`au4b`）；
   - 单字母名称（`a` / `b` / `t`）；
   - 仅描述实现细节的名称（`tmpList2`、`helperB`）。

### 67.2 大小写规范

| 元素 | 规范 | 示例 |
|---|---|---|
| 类 / 接口 / object | UpperCamelCase | `AutomationScheduler`、`StageAutomation` |
| 方法 / 属性 / 变量 | lowerCamelCase | `buyInfinityUpgrades()`、`pendingCrunchCount` |
| 常量（`const val` / 顶层 `val` 不变） | UPPER_SNAKE_CASE | `MAX_INTERVAL_SECONDS`、`DEFAULT_SPEED_MULTIPLIER` |
| 包名 | 全小写 | `…oreki.automation.scheduler` |

### 67.3 包结构必须按职责拆分

1. 新增代码按**游戏功能与职责**组织包结构，禁止把所有功能堆进单一管理类。
2. 已存在的「上帝类」不得继续扩张；本轮新增职责必须落到新包 / 新类。
3. 建议分层（按实际职责命名，不照抄）：
   - `oreki.automation.*` —— 自动化决策（调度、阶段、挑战、购买）
   - `oreki.compat.*` —— 原版 ABI / 反射兼容适配层
   - `oreki.diagnostics.*` —— 日志与自诊断
   - `oreki.settings.*` —— 设置项读写

### 67.4 原版 ABI 兼容必须走显式适配层

1. 以下场景**必须**通过明确的**兼容入口或适配层**保持原有外部契约，不得把混淆名散落到业务代码：
   - 原版 ABI（被 Smali 调用的 `public static` 方法签名）
   - 反射 / JNI 目标
   - 序列化 / 存档字段名
   - 遗留调用点、固定方法描述符
2. 适配层**只负责必要的调用转发**，**不得重复实现业务逻辑**。
   - 正确：`fun addInfinityPoints(amount: BigDouble) = CurrencyApi.add(...)`
   - 错误：在适配层里自己算奖励公式。
3. **不得**为了命名美观擅自改变原版公开接口、必要签名、调用语义或数据结构。
4. 兼容入口必须在代码里显式标注契约（例如 KDoc 写明「本方法签名被 Xxx.smali 以 `invoke-static` 调用，不得改名」）。

### 67.5 混淆符号 → 业务职责的映射必须登记

1. 迁移时优先把「混淆类名 / 方法名」与**真实业务职责**建立映射，并留档（`docs/deobfuscation/`）。
2. 映射记录至少包含：混淆符号、业务职责、结构证据（方法数 / 字段数 / 方法体特征）、
   对应版本、验证方式。
3. 这份映射是后续版本升级的依据；**不得**只活在某个 Agent 的记忆或临时脚本里。

### 67.6 落地检查口径

报告 Kotlin 相关改动时必须给出：

- 新类 / 新方法的命名是否符合 §67.1~67.2；
- 混淆名是否只出现在适配层（给出文件路径）；
- 适配层是否只做转发（是否含业务计算）；
- ABI 是否保持不变（被 Smali 调用的签名逐条列出）；
- 包结构是否按职责拆分。

## 73　原版基线管理与版本升级机制（2026-11-06 用户下达，P0 长期有效）

**适用**：Android / Web 两个游戏仓库的原版版本升级。本节是「原版基线怎么管」的唯一源。

### 73.1 基线真实性

1. **Android 与 Web 独立管理上游版本基线**（R85 用户修正，2026年11月6日）：Android 以已核实的 3.21.0 APK 为本轮适配目标，Web 保留其现有稳定上游 commit；不要求平台原版版本号一致。不得因没有“Web 3.21”而阻止 Android 升级，也不得伪造该 Web 版本。各平台内部的 APK、分包、源码、资源与映射必须同源，不得混入其他原版版本。配置分别记录两端来源、版本标识、commit 和状态。双端仍须保持 MOD 核心功能、机制与资源结算、挑战奖励、智能自动购买目标/决策/开关、用户操作设置及内置教程等价；平台 API、布局及底层实现可不同。Android 3.21 的 MOD 适配与实际验收完成前，只能登记为目标/候选基线，不得宣称升级交付完成。
2. 每个原版版本必须有独立且**不可覆盖**的基线记录（`baseline/versions/<版本>/manifest.json`）。
3. 基线必须记录：来源、版本号、`versionName`/`versionCode`、签名证书 SHA-256、APK SHA-256、
   文件大小、获取时间。字段缺一不可。
4. 发现原版更新时，**先建新基线，再谈游戏逻辑迁移**；基线未固化前不得开始依赖新版本的功能开发。
5. 新版本未完成基线切换前，旧基线仍是唯一开发基线；切换后新基线成为唯一当前基线，
   历史基线保留用于对照。
6. 不得将未经核实的版本号、下载文件或第三方修改包当作官方基线。第三方站点的版本号
   必须与 APK 内 `aapt2 dump badging` 的实际值交叉验证，并且签名证书须与上一版一致。

### 73.2 单一权威构建实现（禁止版本脚本复制）

1. **每个平台只有一个构建实现**：Android 是 `scripts/build_mod.py`，不得出现
   `build_320.py` / `build_321.py` 这类按版本复制的完整脚本。
2. **版本差异只允许写在配置里**（`baseline/version-config.json`），不得散落成
   `if version == "3.x"` 分支。新增版本 = 加一条配置，不改构建流程。
3. 公共流程必须永远共用：apktool 重建、Kotlin 编译、D8 转换、DEX 合并、APK 集成、
   签名、定向验证。
4. 版本专属逻辑必须独立、可定位、可删除；删掉某一版的配置不应影响其他版本构建。
5. 旧版本脚本名如需保留，只能作为**轻量兼容转发**（内部调用统一入口，不复制逻辑），
   并且必须登记调用方与退出条件；确认无调用方后删除。
6. **不得为了消除旧文件而做大重构**；只在版本升级或确有重复实现时收敛。

### 73.3 差异分析

1. 新旧版本必须生成增量差异报告（`baseline/reports/<旧>-to-<新>.md`）。
2. Android 差异必须用 REA / JADX，并**复用历史反编译与反混淆成果**，不得每次从零重来。
3. Web 差异必须以真实源码版本（commit）为依据；源码不可得时必须标记为待确认，
   不得用其他版本的源码冒充。
4. 必须对照 Android 与 Web 同一机制的变化，判断行为是否仍然等价。
5. R8 会重排大量顶层类短名，**全量「新增/删除」数字含噪声**；判断真实升级内容以
   游戏包（`kajfosz/`）内变化为准。

### 73.4 迁移纪律

1. **不得把旧版补丁机械套到新版**。每个补丁都依赖具体类/方法/ABI 与执行路径，
   上游一改就必须重新对位到新版的真实路径。
2. 所有涉及修改的 Android 业务逻辑必须完整用 Kotlin 实现；不得新增 Java 或 Smali 业务逻辑。
3. 每次升级必须检查：存档兼容性、方法/字段 ABI、DEX 分组与方法数上限、
   原版结算路径是否改变、MOD 各功能是否仍生效。
4. 升级必须做完整回归（范围按 §62 执行），不得以静态检查代替必要的实际运行验收。
5. 升级期间必须保留上一稳定基线，确保能回滚。
6. 回滚只调整基线选择与引用关系，**不删历史文件、不用强推或硬重置**。

### 73.5 记录

1. 基线清单、差异报告、版本事实（`FACTS.md`）必须同步更新。
2. 每次升级必须有独立任务单，记录：目标、改动范围、验收结果、未完成项。
3. 后续所有版本升级复用同一套工具与流程，不再临时重复设计。

## 75　原版基线更新禁止使用 Alias（2026-11-06 用户下达，P0 长期有效，**本节是基线定位与 ABI 适配证据口径的唯一源**）

**规则编号**：§75
**名称**：原版基线更新禁止使用 Alias
**优先级**：P0（与 §73 同属基线安全底线；任何构建便利、进度压力都不得突破）
**适用范围**：Android、Web 两个游戏仓库的全部原版版本升级、基线固化、符号定位与 ABI 适配；
含 `baseline/`、`scripts/build_mod.py`、`scripts/payload/`、混淆映射表、反编译工具与任务单。
**创建时间**：2026年11月6日
**最近更新时间**：2026年11月6日
**当前状态**：生效
**实际生效位置**：工作区根 `AGENTS.md`（三处硬链接）+ `RULES_INDEX.md` + 两平台 `AGENTS.md` 的引用段
**来源或提出原因**：用户 2026-11-06 明确下达「原版基线更新禁止使用 Alias」，用于终止以历史同名投票反推新版符号的做法。
**关联项目或任务**：R85 及其后全部基线升级轮次。

### 75.1 最高原则

1. **更新原版基线时，禁止使用 alias 作为基线识别、版本判断、真实实现定位或 ABI 适配依据。**
2. 必须**以实际 APK / XAPK / Web 上游源码中的真实实现为准**。
3. 本节所称 alias，包含但不限于：
   - Android Manifest 中的 `activity-alias`；
   - 人工建立的混淆类名、方法名、字段名别名映射；
   - 用旧版本符号名称代替新版本真实符号的映射表；
   - 仅凭名称相似、命名规律或历史推测建立的符号对应关系；
   - 其他不能直接证明真实实现关系的间接命名机制。
4. **不得通过 alias 绕过真实实现定位。** 构建能通过不是证据，符号找对才是。

### 75.2 真实基线识别要求

Android 基线更新必须直接检查：

1. 原始 APK / XAPK 的真实包结构与文件内容；
2. APK 的真实版本信息、签名与 Manifest；
3. DEX 中实际存在的类、方法、字段及其描述符；
4. 真实调用关系、继承关系与字段引用；
5. 反编译结果与 DEX / 字节码证据；
6. 实际启用的 Activity、Application 及其他组件；
7. 必要时通过运行行为验证静态分析结论。

**特别注意**：

- `activity-alias` 不能代替真实 Activity。Manifest 里存在某别名，不代表它被启用。
- Manifest 声明不等于组件实际启用。判断启动入口必须看 `enabled` 状态、真实 `targetActivity`
  与运行期实际启动的组件。
- 类名相同不代表实现相同（R8 会复用旧短名指向完全无关的类）。
- 混淆名变化不代表功能变化，也不能仅凭名称判断功能一致。
- **历史版本映射只能作为调查线索，不能作为最终适配依据。**

### 75.3 混淆符号变化的处理

1. **从新版本真实 DEX 开始定位**，不从旧版映射表出发反查。
2. 检查调用者、被调用者、继承关系与字段读写关系。
3. 结合反编译源码、字节码与实际运行行为确认用途。
4. 建立**有证据支持的真实实现定位记录**（落盘到 `baseline/versions/<版本>/bindings.json`）。
5. 明确区分**已确认 / 部分确认 / 未确认**三态。

无法唯一确认时，一律按下列口径处理：

- 标记为 **`UNCONFIRMED`**；
- 记录缺失的证据与受影响的功能；
- **阻断依赖该符号的适配**（构建 fail-closed）；
- **不得猜测、不得自动补齐、不得通过 alias 强行建立映射**。

> 宁可明确报告阻塞，也不能制造虚假的适配成功。

### 75.4 版本配置与基线记录

检查并遵守：

1. 版本配置必须记录**真实上游版本、来源、文件哈希与可验证的基线信息**。
2. **不得把 alias 映射当作版本识别依据**，版本判断只允许读 APK/源码自身的真实元数据
   （`apktool.yml` / `aapt2 dump badging` / Manifest / 上游 commit），不得用别名表或符号名反推。
3. **不得依靠 `startswith()`、别名表或旧版本符号名称推断新版本实现。**
4. Android 与 Web 保持**独立上游基线**：
   - Android 按官方 Android 版本更新；
   - Web 使用现有稳定上游基线，**不追随 Android 版本号**；
   - **不得为了版本号一致伪造 Web 上游版本。**
5. 双端 MOD 功能、游戏机制、资源结算、用户可见行为与教程保持等价。

### 75.5 符号绑定的唯一合法形态

1. 目标版本的符号绑定必须以 `baseline/versions/<版本>/bindings.json` 落盘，由
   `scripts/baseline_bindings.py` 从**两版真实反编译树**推导并可复核。
2. 允许作为证据的锚点：
   - **稳定宿主字段锚点**：宿主类描述符两版逐字相同（说明该类未改名），同一字段名在两版都存在，
     字段类型由 `LX;` 变为 `LY;` —— 直接读 DEX 字段表，不经任何映射；
   - 目标描述符在目标树中唯一存在；
   - super 链、抽象方法数、方法名集合等结构约束**仅作旁证**；
   - 方法体归一化后的指令等价（把所有类描述符归一为 `L@;` 后逐条比对）**仅作旁证**。
3. **判定门槛**：
   - `CONFIRMED`：≥2 个独立稳定宿主锚点，且全部指向同一目标描述符，目标唯一存在；
   - `PARTIAL`：仅 1 个锚点，或锚点一致但目标存在歧义；
   - `UNCONFIRMED`：无锚点或锚点互相冲突。
4. **构建只允许使用 `CONFIRMED`**；`PARTIAL` / `UNCONFIRMED` 必须阻断构建并如实报阻塞。
5. 历史 diff 投票结果（同名位置统计）**只能用于生成待查清单**，不得直接写入绑定表；
   写进绑定表时必须已有第 2 条所列锚点。

### 75.6 与既有规则的关系

1. 本节是 §73.1（基线真实性）与 §73.3（差异分析）在**符号定位证据口径**上的细化与加强，
   冲突时以本节为准。
2. §73.2「版本差异只写在配置里」继续有效；但配置里登记的是**已取证的真实符号**，
   不是别名猜测。
3. §67.5「混淆符号 → 业务职责映射必须登记」继续有效；登记内容必须符合本节判定门槛，
   未确认项标 `UNCONFIRMED`。
4. 本节不改变任何发布授权边界：修复定位逻辑不等于获准构建、部署或上传。

# 常驻核心规则
权威：本文件；范围：AD Mod 全部 Agent；状态：生效。历史来源与替代关系见 ../RULES_INDEX.md。

1. 用户当前授权与明确停止条件优先。安全、权限、真实性、工作区与历史保护不得为效率或交付时限让位。规则任务只修改授权规则，开发任务才承担生产交付要求。
2. 核心目标是高效率开发、爽玩、真实交付，以及全新存档真实墙钟 3 小时（180 分钟）内抵达真实终局；Reality 不是终点。保留有意义的手动玩法，消除时间墙和重复劳动。默认加速 10000×；具体玩法语义由 ../SHARED_GAMEPLAY_STANDARD.md 唯一维护。
3. Android/Web 同步推进，机制、资源、奖励、挑战结算、自动化和用户可见行为等价；上游基线分别管理。不得虚构资源、成就、进度、操作结果或验证成绩。
4. 获准开发时优先修复已证实瓶颈，改动必须进入真实生产执行路径。按风险验证；不把模拟夹具、独立 DEX 或静态引用冒充最终运行与真实通关。已有可靠证据且相关输入未变时复用，禁止重复全量检查。
5. Android 业务修改必须完整迁移 Kotlin，并进入 Kotlin → kotlinc → D8 → DEX → APK；实际执行逻辑不得留在 Java/Smali 或 Kotlin 空壳后面。具体契约按需读 ANDROID.md。
6. Git 与硬链接保护按 GIT.md；禁止强推、硬重置、清理、丢弃已有修改或覆盖他人成果。新增代码配有意义的中文注释及可读业务命名。
7. 主/子 Agent 在授权轮次内持续执行安全有效工作；获得明确所有权和验收标准的子 Agent 可以独立承担大规模生产代码、完整模块、Kotlin 迁移及跨端功能，不受人为行数/文件数上限约束。组织方式与独占资源契约只在 AGENT_WORKFLOW.md 定义。
8. 用真实系统时钟记录轮次与双小时交付节点，不得重启工具、换模型或重建 Agent 重置计时。双小时节点指「每两小时至少交付一次真正通过验收的稳定版」：稳定版正式门禁未通过时只用本地候选继续开发与验证，不得以候选/构建成功/部署冒充稳定版交付，也不得因此停掉整轮已授权的生产工作；只有用户停止、目标完成且无安全工作或已报告具体阻碍时才停止。
9. 入口不承载任务状态、Agent ID、PID、APK 哈希或当前环境。第二级只读取本职责模块；第三级读取当前任务与所需事实。不得要求每个子 Agent 通读全部历史规范。
10. 优先实际工具调用、rg 与 Rust 辅助工具；先复用已有环境。规则查重、冲突、编号与维护方法按 GOVERNANCE.md。

## 文档文件名规范

1. 第一方新增或维护的普通文档、任务说明和项目报告，文件名默认使用简体中文；必要的轮次编号、版本号和技术标识符可以保留。
2. `AGENTS.md`、`README.md`、`FACTS.md`、`LICENSE`、`NOTICE`、规则索引及被工具或规则明确引用的固定入口文件属于兼容性入口，除非同步修改全部消费者，不得仅为中文化改名。
3. 历史归档、第三方工具/依赖、自生成报告、原始证据和外部导入资料不纳入普通文档批量改名范围。
4. 改名必须使用可追溯的 Git 重命名，先搜索并同步更新 Markdown 链接、脚本、规则索引、任务索引和跨端副本；不得只改文件名造成断链。
5. 新规则与现有文件名冲突时，以工具兼容性和当前有效规则为准；中文文件名不覆盖项目标识、任务编号或外部协议要求。

## GUI 阶段规则入口

GUI 阶段显示、原版刷新顺序、真实状态证据和“永恒层/永恒次数/永恒点数”术语边界，
统一遵循仓库根目录的 [长期规则：验证与证据](../../../../docs/长期规则_验证与证据.md) 第 9 节；
本文件不另立第二套 GUI 阶段判据。

## UI 实时刷新规则入口

正常前台运行下，所有动态 UI 必须实时反映真实游戏状态；**唯一**允许主动降频的例外是
Android 原版省电模式（`batterySaver` 选项：UI 每秒一次、游戏逻辑仍 25 毫秒）。
游戏逻辑、自动化节拍、UI 渲染三者必须解耦——**自动化节拍不得用于限制 UI 刷新**，
正常模式也**不得**以固定 1～60 秒间隔作为 UI 刷新周期。
完整规则与已取证实现链见
[长期规则：验证与证据 §11](../../../../docs/长期规则_验证与证据.md)。

### 双调度器 Tick 强制 GUI 同步

MOD 全局行动调度器与智能自动购买器调度器，**每次有效 tick 都必须完成 GUI 状态同步**，
即使本拍没有成功动作、或策略没有修改配置，也不得跳过一致性检查。
两个调度器各自计时、互不代替；同帧到点可合并绘制但不得丢失任一方的状态变化。
Android 侧：View 只在主线程更新、复用原版刷新入口、Activity 不可用时登记待同步
并在恢复后台补同步，刷新请求不得静默丢失。
完整条款见 [长期规则：验证与证据 §12](../../../../docs/长期规则_验证与证据.md)。

### GUI 验收多截图与弹窗自动处理

GUI 验收必须采集多张真实截图（启动、弹窗遮挡、进入游戏、关键操作前后、状态变化后、异常现场），
主动识别并安全处理「开始游戏」等启动弹窗，**确认真正进入游戏主体后**才继续测试；
每个关键场景至少保留操作前后两张对照截图，并记录场景、时间与实际 APK SHA-256。
危险弹窗（删除存档、重置、覆盖存档、付款、权限）禁止盲目确认。
完整条款见 [长期规则：验证与证据 §13](../../../../docs/长期规则_验证与证据.md)。

### frame-observer 按钮真实定位与 GUI 自动验收

Android GUI 自动化**首选 frame-observer** 获取真实按钮位置：先确认当前画面与控件边界，
再执行点击，点击后重新观测并保留操作前后截图；启动弹窗须主动安全处理，危险确认不得盲点。
**按钮节点存在不等于屏幕可见或可点击**；坐标必须来自本次观测，不得复用过期位置。
完整条款见 [长期规则：验证与证据 §14](../../../../docs/长期规则_验证与证据.md)。

## README 维护规范

1. README 只描述当前有效的用途、使用方式、目录边界、构建/运行入口和交付要求。
2. README 不是开发流水账、变更日志或任务交接文档；不得出现 R 开头的任务/轮次编号、归档、已废止、失效、旧版本、历史规则或被取代内容，不得复制规则正文、一次性环境事实或未验证结论。
3. 规则以规则入口为准，事实以 `FACTS.md` 或验证记录为准；README 只提供链接和简要说明。
4. 修改 README 后检查链接、路径、命令、版本描述和 Web/Android 对照信息；不把未验证内容写成已完成。
5. 按项目实际需要提供中文的项目简介、目标读者、快速开始、环境前提、用法、目录、贡献、许可证、安全和反馈入口；缺少事实依据的章节不虚构。
6. 快速开始命令必须可执行并写清前置条件和预期结果；命令、路径、依赖、链接、截图和许可证信息必须与当前仓库一致。
7. 首屏优先说明项目用途和开始方式；长内容使用清晰中文标题，命令使用代码块，危险操作明确提示，不堆叠无意义徽章、内部实现或营销语句。

## 双平台开发规范

1. 主要开发环境为 Linux（当前实测为 KDE Plasma 桌面上的 Ubuntu 26.04.1 LTS）；Windows 11 为辅助兼容环境。新开发工作优先在 Linux 执行。
2. 开发脚本优先保证 Linux Bash 可用；Windows 专用脚本只在确有替代且完成兼容验证后移除，跨平台脚本必须明确区分两端行为。
3. Linux 使用原生路径、权限、大小写敏感和 LF/UTF-8 无 BOM 约定；不得无理由批量转换既有文件的编码或换行符。
4. Linux 仓库、构建目录和缓存优先放在 ext4；Windows 分区仅作跨系统数据来源，不假设固定挂载点，迁移前不删除原始文件。
5. 涉及符号链接、硬链接或可执行权限的文件，修改前检查 inode、nlink、权限和全部使用方；具体工具版本只记录在 FACTS，不写死进通用规则。

## 条件极性检查纪律

针对多次发生的「条件写反」缺陷，修改逻辑或规则时必须执行：

1. 改动 `if` / `!` / `&&` / `||` / `>=` / `<=` / 布尔返回值 / 状态切换前，**先用一句话写清业务语义**，再落实现。
2. 语义涉及「至少/最多」「允许/禁止」「启用/关闭」「达到/未达到」「保持/释放」「成功/失败」时，**必须验证两个相反状态**。
3. 阈值判断至少覆盖**低于、等于、高于**三个边界。
4. 对 Break、坍缩（Crunch）、ID1、自动购买器总开关等关键状态，必须同时具备**正向与反向**定向测试。
5. 检查规则文本时确认「至少」「最多」没有被互换；不能只靠关键词匹配，必须读实际语义。
6. 测试中增加**反向断言**：不仅证明该执行时能执行，还要证明不该执行时不会执行。
7. 适合的关键条件做**变异测试**：临时翻转判断方向，确认测试会失败，然后恢复实现。
8. 只针对本轮涉及的代码与规则执行，不做无关全仓审计，不因此触发额外完整 APK 构建。

**验收标准**：把关键判断反过来后测试仍然全绿，说明测试没真正覆盖该业务约束，必须补足。

## Android 基线更新说明书

1. **`android/AD_Oreki_Edition_Android/docs/ANDROID_BASELINE_UPGRADE_GUIDE.md` 是所有 Android 原版基线更新知识的唯一入口**：流程、版本差异、REA/JADX 取证方法、混淆符号与 ABI 映射、Manifest/DEX/资源变化、Kotlin 迁移适配、构建故障与解决方案、验证与回滚经验，都必须及时写入该文件。
2. 每次基线更新发现新问题、新解法或重要经验，都要**增量完善**该说明书；不能只写在 FACTS、tasks、Agent 对话或临时报告里。
3. 说明书内部分「通用迁移方法」与「具体版本记录」，章节清晰，避免重复、过时或互相矛盾。
4. `FACTS.md` 与 `tasks/` 承担事实记录和任务进度；README 只承担当前用户说明；涉及基线迁移的技术细节只保留必要摘要 + 说明书链接。
5. 必须保留真实证据路径、版本号、APK SHA-256、关键 ABI 签名与验证状态，并区分「已证实结论」与「待确认问题」。
6. 禁止用 alias 或未经证明的混淆映射冒充真实版本识别证据，遵循现行基线迁移规则。
7. 不新建重复的基线更新说明书，不覆盖已有内容，不擅自修改历史任务编号。
8. Web 仓不复制整份 Android 说明书，但必须在规则中指向该路径并保持要求一致。

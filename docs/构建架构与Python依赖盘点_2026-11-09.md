# Android MOD 构建架构与 Python 依赖盘点

日期：2026-11-09

## 结论摘要

当前 Android Release 主链是：

```text
Gradle → generateKotlinBindings(Python) → kotlinc → verifyKotlinAbi(Python) → D8
       → build_mod.py → apktool → zipalign → apksigner
       → prepareVerifyRelease(AAPT2/apksigner/apktool/SHA)
       → verify_release.py(语义门禁)
       ↘ build_fingerprint.py / verify_patch_contract.py
```

本轮没有强行迁移 `build_mod.py`。它仍然承载 APK 反编译树准备、payload 注入、基线兼容、资源/Smali 补丁、apktool 重建、对齐和签名，直接替换会改变官方 APK 基线和 ABI 风险面。

同时完成了 Kotlin 工具编排的第一步迁移：Gradle 现在直接负责 `kotlinc`、`javap` 守卫阶段和 D8；Python `build_kotlin.py` 只保留基线绑定生成和共享 ABI 守卫，不再执行编译器、D8 或清理构建产物。

本轮又将 Release 校验中的外部工具编排迁入 Gradle：`prepareVerifyRelease` 负责 AAPT2 badging、apksigner v2/v3、apktool 解包和 SHA-256/大小采集；`verify_release.py` 保留跨版本基线、ABI、证书语义及补丁位置检查，不再自行启动这些 Android 工具。

本轮完成的低风险改造是：Linux 构建链的 JDK 只读解析改由 Gradle 原生完成；Windows 继续使用 `scripts/jdk_env.py`，保留系统级 `JAVA_HOME` 与 Scoop 兼容路径。该改造不自动安装 JDK，不修改系统环境，不改变下游 Python 子进程接收到的 `JAVA_HOME`/`PATH`。

## 必须保留的 Python

| 文件 | 当前职责 | 处理 |
|---|---|---|
| `scripts/build_mod.py` | 主 APK 补丁、基线兼容、apktool、签名 | 保留；后续按职责拆分 |
| `scripts/build_kotlin.py` | 基线绑定生成、共享 ABI 守卫 | 保留；不再承担 kotlinc/D8 工具编排 |
| `scripts/build_fingerprint.py` | 构建输入指纹和增量安全阀 | 保留；不能用粗糙的 Gradle up-to-date 替代 |
| `scripts/verify_release.py` | 候选 APK 的跨版本基线、ABI、证书语义和补丁位置校验；消费 Gradle 工具报告 | 保留，作为发布门禁；不再负责外部工具编排 |
| `scripts/verify_patch_contract.py` | 补丁契约和 APK 实际产物验证 | 保留，作为构建守卫 |
| `scripts/publish_four_channels.py` | 四渠道发布编排 | 保留，除非另行迁移发布系统 |

## 条件保留的 Python

- `scripts/jdk_env.py`：Linux Release 主链已不再调用；Windows 仍由 Gradle 调用，且保留手工诊断入口。
- `scripts/avd_smoke.py`：属于 Android 运行验证，不是 APK 构建核心；继续保留。
- `scripts/oreki_tutorial_gen.py`、`scripts/gen_smart_strategy.py`：生成器有明确的输入/输出和构建期守卫，暂不删除。
- `scripts/baseline_bindings.py`、`scripts/dexdiff_320.py`、`scripts/map_obfuscated.py`：属于基线/逆向工具，不能按“非 Release 入口”直接删除。

## 低风险改造记录

修改文件：

- `build.gradle`

修改内容：

1. Linux 下由 Gradle 原生检查 `JAVA_HOME`、PATH 中的 `java` 和 `tools/jdk/*`。
2. 只接受同时存在 `bin/java` 与 `bin/javac` 的 JDK。
3. Windows 继续调用 `scripts/jdk_env.py --json --no-install`。
4. 不自动安装、不写系统环境变量、不改变 APK 构建和签名流程。

本轮新增：

1. `prepareVerifyRelease` 在 Gradle 中直接调用 AAPT2、apksigner 和 apktool，并写入
   `build/gradle-reports/verify-release-tools.json`。
2. `verify_release.py` 改为读取该报告和 `build/gradle-verify-apk/`，只执行语义门禁；
   不再重复实现 SHA-256、进程调用、工具路径解析和 apktool 临时目录清理。
3. 这不是把 Python 包装成 Gradle 任务：工具执行、退出码、原始输出和中间产物均由 Gradle
   任务直接管理，Python 只消费结构化结果并做需要代码理解的检查。

## 下一批候选

按风险从低到高：

1. 为 `build_mod.py` 建立职责模块边界和契约测试，先拆出只读校验，再考虑迁移稳定的资源/ZIP 操作。
2. 复用现有 Rust 能力，先接手适合原生处理的 DEX/APK 扫描并与 Python 结果做等价性验证。
3. 继续识别 `build_mod.py` 中可由 Gradle/Android 官方工具直接完成的纯编排，但不重写
   apktool、aapt2 或已有官方工具能力。

在第 1～3 项完成前，不删除仍被构建、发布、测试或报告引用的 Python 文件。

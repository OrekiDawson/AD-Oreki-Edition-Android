# Android MOD 构建架构与 Python 依赖盘点

日期：2026-11-09

## 结论摘要

当前 Android Release 主链仍是：

```text
Gradle → build_kotlin.py → Kotlin/D8 → build_mod.py → apktool → zipalign → apksigner
       ↘ build_fingerprint.py / verify_release.py / verify_patch_contract.py
```

本轮没有强行迁移 `build_mod.py`。它仍然承载 APK 反编译树准备、payload 注入、基线兼容、资源/Smali 补丁、apktool 重建、对齐和签名，直接替换会改变官方 APK 基线和 ABI 风险面。

本轮完成的低风险改造是：Linux 构建链的 JDK 只读解析改由 Gradle 原生完成；Windows 继续使用 `scripts/jdk_env.py`，保留系统级 `JAVA_HOME` 与 Scoop 兼容路径。该改造不自动安装 JDK，不修改系统环境，不改变下游 Python 子进程接收到的 `JAVA_HOME`/`PATH`。

## 条件保留的 Python

- `scripts/jdk_env.py`：Linux Release 主链已不再调用；Windows 仍由 Gradle 调用，且保留手工诊断入口。
- `scripts/avd_smoke.py`：属于 Android 运行验证，不是 APK 构建核心；继续保留。
- `scripts/oreki_tutorial_gen.py`、`scripts/gen_smart_strategy.py`：生成器有明确的输入/输出和构建期守卫，暂不删除。
- `scripts/baseline_bindings.py`、`scripts/dexdiff_320.py`、`scripts/map_obfuscated.py`：属于基线/逆向工具，不能按“非 Release 入口”直接删除。

## 低风险改造记录

修改文件：

- `build.gradle`

修改内容：

1. Linux 下由 Gradle 原生检查 `JAVA_HOME`、PATH 中的 `java` 和 `tools/jdk/*`。
2. 只接受同时存在 `bin/java` 与 `bin/javac` 的 JDK。
3. Windows 继续调用 `scripts/jdk_env.py --json --no-install`。
4. 不自动安装、不写系统环境变量、不改变 APK 构建和签名流程。

## 下一批候选

按风险从低到高：

1. 把 `build_kotlin.py` 中“工具路径发现、进程编排”迁到 Gradle，保留 Python 的源生成和 ABI 语义守卫。
2. 把 `verify_release.py` 中可由 APK/ZIP/签名工具直接表达的纯编排迁到 Gradle，保留 Python 的跨版本兼容检查。
3. 为 `build_mod.py` 建立职责模块边界和契约测试，先拆出只读校验，再考虑迁移稳定的资源/ZIP 操作。
4. Rust 只接手适合原生处理的 DEX/APK 扫描，不重写 apktool、aapt2 或已有官方工具能力。

在第 1～3 项完成前，不删除仍被构建、发布、测试或报告引用的 Python 文件。

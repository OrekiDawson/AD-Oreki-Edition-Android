# 饱和现象归因：tick 数 vs 每 tick 产出（2026-10-27）

> 结论：**主线程实际执行次数稳定且随窗口线性增长（约 53/s），但每一帧的产出减半**。
> 即任务中的**情况 2**（tick 数稳定、每 tick 产出降低），情况 1（推进受阻）在帧粒度上被排除。
> 未改生产代码。

---

## 1. 计数方法（先说明局限）

| 候选计数源 | 结论 |
|---|---|
| logcat 每 tick 标记 | **不可用**——实跑一次 12 s 窗口，logcat 1,701 行中 `GAME_TICK*` / `gameTick` / `TickProfiler` / `Frame Time` **匹配 0 处**（TickProfiler 未开启） |
| 存档内「每次 tick +1」计数器 | **不存在**——`records.*` 都是时间累加，`auto.*.lastTick` 是时间戳而非计数 |
| `dumpsys gfxinfo` 的 `Total frames rendered` | **可用**，且只在前台增长（后台实测 5 s 内 Δ=0） |
| `/proc/<pid>/stat` 的 utime+stime | **可用**，用于判断 CPU 是否饱和 |

**必须声明的局限**：帧数 **≠** 游戏 tick 数。
「tick 是否帧驱动」本轮未证实，所以下面结论严格说是「主线程执行次数」层面的，
不能直接等同于「游戏 tick 数」。但两条旁证支持它可用：
① 若主线程被拖慢，帧率必然同步下降（实测没有）；
② `thisInfinity.time / realTime` 在四个窗口里都**精确等于 20,000.0000**，
说明时间记账与帧长严格自洽（每个 tick 的 `diff = realDiff × 20000`，帧变长则单帧 diff 变长，
总账永远对得上——所以总量指标本身无法反映 tick 数，必须靠帧数）。

## 3. 归因

### 3.1 排除：主循环推进受阻 / tick 数下降

- fps 在 12 s 与 24 s 窗口里都是 **53/s**（±2%），帧数随窗口长度**线性增长（1.95×）**。
- CPU 稳定在 **88–97%**（已饱和但**持续供货**，没有越跑越慢）。
→ 情况 1（tick 数下降）在**帧粒度**上不成立。

### 3.2 成立：每 tick（帧）产出降低

- 每帧产出从 93.42 降到 50.22（**×0.537**），而帧数只增 1.95×。
- 累计产出 1.046× ≈ 1.95 × 0.537 —— 两个因子完全对得上，内部自洽。

### 3.3 与公式对照（指向 `c()` 不再随 amount 增长）

`amount += c() × D / 1000`（`DimensionState.smali:113-200`），
帧率恒定 ⇒ 每帧 `D` 恒定 ⇒ 每帧增量 ∝ `c()`。

`Δlog10(amount)` 每帧 ∝ `c() / amount`。实测该值在 24 s 内**减半**，
意味着 **`c()` 的增长慢于 `amount`**——即「生产速率没有跟着数量一起长」。
最自然的解释是 `c()` 或其上游乘数**有限幅/上限**（还没定位是哪一个）。

> 这不是「F 没生效」，也不是「主循环卡住」，而是**速率项被压住**。

## 4. 尚未确定

| 项 | 状态 |
|---|---|
| 帧数是否严格等于游戏 tick 数 | **未验证**（tick 驱动方式未知）；但 fps 恒定 + CPU 饱和持续，间接支持「主循环未被拖慢」 |
| `c()` 的具体实现与限幅点 | **未定位**——`c()` 是抽象方法，需逐个实现类查看（`AntimatterDimensionState` 等） |
| 是数值上限、乘法因子封顶，还是 BigDouble 精度 | **未区分** |
| 该现象是否只在高 F 出现 | **未验证**（本轮只测 F=10000） |

## 5. 探针开销评估

- `gfxinfo` 采样只在窗口**两端**各一次（不是每帧采样），每次约 0.3 s，窗口占比 <3%。
- 与上轮无计数基线对比：12 s 窗口 `Δlog10` = 62,228（上轮）/ 62,311 / 62,232（本轮）——**差异 <0.15%**，
  说明采样**未显著扰动**结果。
- `CPU 占比`（88–97%）本身说明进程已接近 CPU 上限，这是**存档状态**（1e6 万量级 BigDouble）导致，
  不是探针导致。

## 6. 唯一建议的下一步

**只做一件事**：定位 `c()` 的实现与其限幅点。

具体路径：`DimensionState` 是抽象类，`c()` 无实现；沿 `dimension/antimatter/` 里的
`AntimatterDimensionState` 找 `c()` 的 override，看它返回的 BigDouble 是怎么算的、
链路上有没有 `clampMax` / `min` / 常数封顶。

判据：若 `c()` 的返回值确实被钳在某个常数上界，则「每帧产出 ∝ 1/amount」的衰减就得到解释，
届时再讨论是否属于可修缺陷（以及修了会不会破坏平衡）。**在此之前不做任何生产改动。**

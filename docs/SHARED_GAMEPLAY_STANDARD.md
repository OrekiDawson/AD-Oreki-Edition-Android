## 1. 最高设计目标：爽玩

1. **首要目标**：尽可能缩短从全新存档开局到「终局内容可达 + 关键流程完成」所需的**现实时间**，
   减少无意义等待、重复刷取与机械操作，强化成长反馈、解锁速度与自动化。
2. **忠实原版不再是最高目标**。允许在符合本规范的前提下定制数值、门槛、升级效果、自动化与进度条件；
   官方源码的作用是「确认原版行为、识别副作用、建立正确基线」，而不是限制 Mod 的平衡目标。
3. **爽玩 ≠ 全调最大**：
   - 优先消除无聊的耗时机制，保留值得玩的决策与挑战；
   - 禁止为了表面速度制造软锁、崩溃、死循环、存档损坏或实际无法抵达的终局。
4. **成功与否只看真实进度**：必须证明「同样的游戏进度现在用更短的现实时间达成」。
   **不能仅凭计时器显示变短、某个数值变大、或某个公式偏离原版就判定优化成功。**

## 2. 双端一致性（Web 与 Android 共享）

以下规则两端必须一致：

| # | 规则 |
| --- | --- |
| 2.1 | 核心玩法机制、升级效果、解锁条件、阶段推进逻辑一致 |
| 2.2 | 全局加速倍率的**定义、计算语义、预期默认设置**一致 |
| 2.3 | 现实时间、游戏时间、挑战记录与历史记录的**语义**一致 |
| 2.4 | 相同逻辑状态在两端产生一致的游戏结果（平台 UI / 输入 / 性能实现可以不同） |
| 2.5 | 采用相同的关键测试场景、预期结果与验收标准 |

**差异处理流程**：发现两端差异 → **先记录差异** → 追查原因 → 判断是否合理（平台实现差异 vs 规范分叉）
→ 不得擅自选择其中一端当正确答案 → 不得在没有证据时宣称"双方已经一致"。

**双向借鉴的执行规则见 §9**（本表只定义「什么必须一致」，§9 定义「如何互相借鉴与反馈」）。

**不得声称检查过无法访问的仓库。** 无法核验的一端，一律标记为「未验证」，并列出需要的证据。

## 3. 全局加速标准（OrekiSpeed / F）

**F 的定义**：Mod 的**游戏模拟速度倍率**，不是现实时间倍率。

1. F 只影响**游戏模拟时间**，以及真正依赖该模拟时间的生产与进度。
2. **只能在正确的计算路径上生效一次**，不得重复放大。
3. **现实时间与"现实经过时间"类记录不能简单乘以 F。**
4. **不得把所有含 `time` / `diff` 等字样的字段一律乘除 F。** 每个字段按调用场景单独判定。
5. 必须逐个核实特殊机制的独立时间路径，至少包括：
   离线结算、时间膨胀（TD / EC12）、黑洞、时间储存与释放（Enslaved）、Laitela、Eternity、Reality 等重置。
6. **不得用当前倍率换算历史记录**，除非已确认旧值语义、适用版本、转换规则与存档兼容性。

**必须区分三种时间**（三者在任何报告与 UI 中都不得混用）：

| 记号 | 含义 | 判定方式 |
| --- | --- | --- |
| **现实时间** `realTime*` | 墙钟经过时间，含离线、失焦、休眠 | `Σ realDiff / F`，或 `Date.now()` 差值 |
| **游戏模拟时间** `time*` | 游戏时钟推进量，含所有游戏内膨胀 | `Σ diff`（`diff = realDiff × speedFactor`） |
| **记录时间** `best*` / `recent*` / 挑战成绩 | 某次运行结束时固化的结果 | 双口径并存，各自独立取 min，**不得互相换算** |

**字段登记要求**：每个重要计时字段都要记录「含义 / 单位 / 来源 / 是否受 F 影响 / 对应测试证据」。
登记表见 §6，具体条目维护在各仓库的实现说明里。

**允许偏离原版，但必须标记**：需要偏离官方行为时，写入「Mod 定制」并说明理由；
**不得把设计改动伪装成原版修复**。

## 4. 统一证据规则

遇到机制或时间语义问题，按顺序取证，**不得跳步、不得把推断写成事实**：

| 级别 | 证据 | 用途 |
| --- | --- | --- |
| E1 | 项目实际版本与当前代码路径 | 先确认"我们现在是什么" |
| E2 | 官方源码（记录 文件:行 + 提交哈希） | 判断原版行为与原版缺陷 |
| E3 | 当前项目代码 + 自动化测试 + 实际运行 | 核实 Mod 当前行为 |
| E4 | wiki.gg / Fandom（给出具体页面 URL） | 机制解释与交叉核验 |
| E5 | ADfaster 等参考实现 | **仅作参考**，不作为唯一依据 |

- 用户目标、本规范、原版行为、实际实现四者**分别记录**，不得混为一谈。
- 重要结论必须能追溯到源码位置 / 测试用例 / 运行结果 / 明确外部资料。
- 出现冲突或证据不足：明确列出**未知项、风险、下一步验证方案**，不得猜测性定案。

不混淆来源的写法示例：
- ✅「官方 `normal-challenges.js:121-129` 写 `thisInfinity.time`；Fandom `/wiki/Challenges` 未提成绩口径；实测 F=1 与 F=10000 结果相同」
- ❌「Wiki 说应该这样，所以代码错了」

## 5. 性能与游戏进度验收

### 5.1 基线原则
1. 优先测量**真实时间内的游戏进度**。
2. **不得**把模拟时间、存档历史记录、UI 计时器单独当作通关效率指标。
3. 基线必须**可重复执行**，且**不能污染用户正式存档**（用隔离测试存档 / 临时 profile / 只读副本）。

### 5.2 必须覆盖的场景
- 新存档 → 首个关键阶段
- 典型中期晋升与阶段转换
- Eternity、Reality 及其相关流程
- 普通挑战、特殊挑战及特殊速度修正（EC12 等）
- 在线运行 / 离线结算 / 暂停 / 退出后重新载入
- 新旧存档兼容
- 不同全局倍率下的购买、生产、自动化、重置与记录行为
- 关键后期机制及**可能导致软锁的路径**

### 5.3 倍率覆盖
测试倍率至少覆盖 **F=1、一个中间倍率、F=10000**。
若项目实际支持范围不同，**先记录真实限制与原因**，不得假定所有倍率都能安全运行。

### 5.4 每项优化必须回答的五个问题
1. 现实时间内的进度是否更快？
2. 无意义操作是否减少？
3. 游玩反馈是否改善？
4. 双端结果是否一致？
5. 存档与特殊机制（离线/黑洞/TD/储存/重置）是否安全？

### 7.3 硬链接共享约束（v1.3）

两端 `docs/SHARED_GAMEPLAY_STANDARD.md` 是**同一文件对象的两个路径**，任何一端写入都会立即反映到另一端。

1. **会断开硬链接的操作**（之后两端将各自独立，必须人工核对）：`git checkout` / `git restore` / `git stash` /
   `git clean` 覆写该路径；编辑器「另存为 / 原子替换（写临时文件再 rename）」；`cp` 覆盖、删除后重建；
   文件系统迁移、压缩包解压、仓库重新克隆。
2. **不会断开**：原地追加 / 原地截断写入（`>>`、以同一 inode 覆写）、`stat` 显示 `links≥2` 的编辑。
3. **Git 不记录硬链接**：仓库里保存的是文件内容（blob），不是链接关系。两仓库各自提交相同内容，
   但「共享」这一事实**只存在于本机工作树**；新克隆的仓库不会自动共享。
4. **换行符**：Web 仓库 `core.autocrlf=true`，Android `false`；共享文件按 Windows 惯例存 **CRLF**。
   若 Android 后续提交该文件，其索引会存入 CRLF（与其既有 LF 文件不同），属预期差异，不要为此改写共享文件。
5. **自检**：`stat -c '%i %h' <两端路径>` 应输出**相同 inode** 且 `links≥2`；任一侧不符即视为链接已断，
   按「先比对内容 → 再决定以哪份为准 → 重新建链」处理，**不得直接覆盖有新增内容的一侧**。

## 8. 开发方法论：快速迭代（v1.1，2026-10-26 用户确立）

> 本节定义**怎么推进开发**，不改变 §1 的设计目标，也不放宽 §3 的加速语义。
> 与 §5 的关系见 §8.4：**§5 是里程碑与发布前的完整验收口径，日常小步按 §8.4 的最小充分子集执行。**

### 8.1 默认模式：尽早进入生产开发

1. 默认工作循环：**定位问题 → 修改生产代码 → 构建可运行版本 → 执行针对性测试 → 按实际结果迭代**。
2. **不作为启动前置门槛**：大规模审计、完整证据链收集、全量测试矩阵、全仓库重构。
3. **可作为启动依据**：已有证据足以支撑一个「范围可控、可验证、可回滚」的小改动。
4. 无明确问题、或预期收益明显低于成本时：简短说明并转向更值得做的任务，**不为了产出代码而改代码**。

### 8.2 每轮只解决一个主要问题

1. 单轮只改一个主要功能或问题，**不把多个子项目混进同一补丁**。
2. 选点优先级：缩短现实游玩时间 > 提高有效成长速度 > 减少重复操作 > 改善自动化体验。
3. 优先小改动、短反馈周期，**不追求一次做完**。
4. 方向收益不明显时：及时停止、回滚或换向，**不靠扩大审计范围找理由**。

### 8.3 验证服务于开发

1. 改动前只记录**必要**基线（相关代码位置 + 相关测试现状），不追求全量快照。
2. 改动后先跑**与改动直接相关**的测试，再跑**合理范围**的回归。
3. 先验证最关键行为与用户可感知收益；**不要求每轮都构建庞大测试矩阵**。
4. 测试失败先定位并修复当前问题，**不无故扩大到无关模块**。
5. **证据诚实不可放松**：必须区分「已实测 / 静态推导 / 合理推断 / 未知」；
   **禁止伪造测试结果，禁止把未验证的收益说成事实**（与 §4 一致）。

### 8.4 验证强度分级（与 §5 的关系）

| 改动类型 | 最小充分验证 | 完整矩阵时机 |
| --- | --- | --- |
| UI / 文案 / 纯展示 | 目标界面可达 + 无运行时报错 | 发布前抽查 |
| 数值 / 成本 / 解锁门槛 | 单点前后对比 + 一条关键路径可推进 | 里程碑 |
| 自动化 / 购买器 / 循环粒度 | 单场景行为对比 + 无死循环 | 里程碑 |
| 计时 / 记录 / 存档 / 时间语义 / 加速注入点 | 相关字段实测 + 至少两个倍率（含 F=1） | **必须**补 §5.2 关键场景与 §5.3 倍率覆盖 |
| 跨端共享机制 | 本端实测 + 对端标「待验证」 | 对端同步后补齐 |

- 上表是**下限**，不得据此减少 §3 / §4 的硬性要求。
- 未执行完整矩阵时，**必须在报告中写明未覆盖项**，不得表述为「已全面验证」。
- 涉及存档安全或不可逆操作时，仍按 §8.7 先停下说明风险。

### 8.5 控制工程成本

1. 不重复审计已确认结论；优先复用既有证据、测试脚手架与报告（先查 §6 登记表与各仓库文档）。
2. 避免过度设计、重复探针、重复报告、不必要的架构重构。
3. **不为追求「原版平衡」删掉用户明确要求保留的加速机制**（与 §1.2 一致）。
4. 成效以「实际成长、现实耗时、稳定性、玩家体验」衡量；
   **不以代码行数、报告篇幅、测试数量或帧率下降幅度作为目标或成功依据**。

### 8.6 双端协作

1. 两端共享目标、机制语义、测试口径与验收标准（§2）；**允许实现不同，不强求逐行一致**。
2. 一端验证有效的方案，**应及时评估另一端是否值得移植**；移植前按 §2 差异流程确认语义。
3. **不为等待双端全面审计完成而阻塞单端小步开发**；对端未核验项一律标「未验证」。
4. 公共规则只在本文件维护一份权威定义；平台专属实现与限制写在文末平台章。
5. 本节只给原则；**完整的双向借鉴流程、反馈义务与范围约束见 §9**。

### 8.7 安全与交付

1. 快速迭代不等于无视既有改动：**动手前检查工作树**，保护用户未提交与未跟踪文件。
2. 生产改动尽量**小、可测试、可回滚**。
3. **除非用户明确授权，不自动提交、不推送、不部署、不发布**。
4. 高风险或不可逆操作、可能破坏存档的改动：**先停下说明风险**，不擅自执行。
5. 安全边界用于防真实损害，**不扩成对开发的普遍阻塞**；优先寻找可控的验证路径。

### 8.8 每轮报告格式

固定四段，简短即可：

1. 改了什么、解决了什么问题；
2. 相关测试结果与实际收益；
3. 已知风险或尚未验证的部分；
4. 下一步最值得做的一件事。

- 除复杂故障或用户要求外，**不提交冗长审计报告**，不重复解释已知背景，
  不堆砌与当前决策无关的细节。

### 8.9 与既有条款的关系（冲突消解）

- **不废止**：§1 设计目标、§3 加速语义硬规则（唯一注入点、禁乘现实时间字段）、
  §4 证据诚实、§8.7 安全红线。
- **调整执行强度**：§5.2 场景清单与 §5.3 倍率覆盖，从「每轮必做」调整为
  「按 §8.4 分级；涉及计时 / 存档 / 加速语义的改动与发布前必须做全」。
- **降级为按需**：各平台 `AGENTS.md` 的「必读顺序」改为「首次进入项目读一遍，后续按需查阅」；
  双 Wiki 查证保留为用户长期要求，但**范围限于被改动机制的具体页面**，不做全站审计。
- 本节与任一平台 `AGENTS.md` 冲突时，**以本节为准**，并应同步修订该 `AGENTS.md`。

## 9. 双端双向借鉴（v1.2，2026-10-27 用户确立）

**前提**：Web（`AD-Oreki-Edition`）与 Android（`AD_Oreki_Edition_Android`）是**同一产品的两个实现**，
不再当作彼此独立的项目。共享的是**设计原理、机制语义、测试场景与经验结论**，**不要求源代码结构一致**。
本文件的权威版本由 **Web 仓库维护**（§7.1）。

### 9.1 Web → Android（必须检查）

Web 每产出一项有价值的改动或结论，Android 必须检查同一问题是否存在于本端：

| 类别 | 需要传递的内容 |
| --- | --- |
| 倍率 / 时间补偿 | 公式、单位、配对关系、被修正的旧行为 |
| 生产 / 数值 | 受影响字段、期望形状、实测数据 |
| 自动化 | 自动购买器 / Automator 的语义、边界、可回滚开关 |
| UI / 游戏体验 | 交互变化、可访问性、移动端可行性 |
| 测试结论 | 场景、判据、实测值、未覆盖项 |

**只写在报告里的「已优化」不构成可借鉴结论**；必须能定位到源码或数据。

### 9.2 Android → Web（必须评估）

Android 的有效改进与测试结论，Web 也必须评估是否值得吸收，尤其涉及：
时间补偿、自动购买器频率与批量、自动化流程、移动端 / 低帧率体验、阶段推进辅助。
评估结论只有三种：**吸收（并实施）／不适用（说明理由）／记为下一轮目标**。

### 9.3 共享机制的强制对照

凡改动涉及**游戏速度、生产、重置、自动化**（含自动购买器与 Automator），
修改前必须对照另一端的实现与已验证结论，至少回答：

1. 另一端是否已实现该机制？
2. 语义是否等价（同输入 → 同可观测结果）？
3. 是否存在**已知差异**（本文件 §2 差异表 / 各端报告）？
4. 若不处理，会使两端朝哪个方向分叉？

### 9.4 差异定性：缺陷 vs 平台差异

发现行为差异时**不得机械照搬**，必须按以下顺序处理：

1. **记录**：两端实现位置、实际观测值、测试条件。
2. **追因**：是语义错误、历史遗留、还是平台结构差异（如 Android 用双参数分离游戏时间 / 现实时间）。
3. **定性**：判定为「缺陷」需给出与官方源码或本文件规则的冲突点；判定为「合理平台差异」需说明为何不影响可观测结果。
4. **处置**：定性为缺陷才修；定性为「按爽玩目标应对齐」时，可改本端，但必须写明**被放弃的是哪一侧的旧行为**，
   并同步到 §2 的差异清单与对端报告。

### 9.5 反馈义务

1. 各端必须把「对另一端的结论、疑点、待验证项」写进**本轮报告**与 `_research/` 下的共享材料，供对端读取。
2. **不得声称检查过本次会话未实际核验的另一端代码**；未核验项一律标「未验证」，并列出所需证据。
3. Android 仓库必须**读取本文件**并在其 `AGENTS.md` 中引用 §9；其发现的改进按 9.2 反馈给 Web。

### 9.6 与快速迭代的关系（不扩大范围）

1. 双向借鉴是**每轮收尾的固定检查项**，不是扩大单轮任务的许可（§8.2）。
2. 实现成本低、风险可控的对端同类收益，可**顺手完成**；需要较大改动的，**记为下一轮目标**并写明。
3. **不为追求两端完全一致而引入抽象层或大规模重构**（§8.6）。
4. 单轮仍只解决一个明确痛点；借鉴产生的额外工作不计入本轮「已完成」。

### 9.7 目标

一端发现问题，两端获得经验；一端验证有效，另一端评估收益。
**衡量标准**：同样的游戏进度是否用更短的现实时间达成（§1），而不是两端代码是否长得一样。

## 平台专属实现说明（可追加，不改公共规则）

### Web 版（`AD-Oreki-Edition`）

- 全局倍率实现：`src/core/speed-config.js`；默认 `10000`，范围 `1 ~ 100000`，存 `localStorage["oreki-game-speed"]`。
  **Pelle 毁灭现实使用与其他阶段相同的全额倍率**（2026-10-27 起取消上游 ADfaster 的 `sqrt` 降级，与 Android 对齐；
  证据与 A/B 见 `_research/doomed-speed-parity-2026-10-27.md`）。
- 唯一注入点：`src/game.js:449-451` 的 `realDiff`。
- 「游戏内时间」累计器：`records.totalInGameTime` / `thisX.inGameTime`，读取器 `src/core/time.js` 的 `inGameTimeOf()`。
- 自动化测试：`_tools/run-all.sh`（16 组套件）。

### Android 版

- 仓库：`AD_Oreki_Edition_Android`（APK `versionCode 30190000` / `3.19.0`，包名 `com.oreki.antimatterdimensions`）。
- 全局倍率实现：`kajfosz/antimatterdimensions/OrekiSpeed.smali`；默认 `DEF = 10000.0`，
  范围 `1e-6 ~ 1e9`（越界/NaN 回退 DEF），存 `SharedPreferences("oreki_prefs").getFloat("speed_multiplier")`。
- **唯一注入点**：`a.smali#f(...)`（协程版 tick）在 `mul-double v12, v12, v37` 之后调用 `OrekiSpeed.apply(D)`，
  **作用对象是 `diff`（游戏模拟增量），不是 `realDiff`**。
  → 与 Web 版（注入 `realDiff`）**不是同一注入点**，两侧的时间字段归一化需求因此不同。
- 现实时间字段：`records.realTimePlayed` / `*.realTime` / `realTimeDoomed`，全部由 `realDiff` 累加，**天生不受 F 影响**。
- 记录归一化：`OrekiSpeed.unscale(D)`，用于 `bestInfinityTime`（×2）、`pastTenInfinities.time`、
  `pastTenEternities.time`、`pastTenRealities.time`；标记键 `records_norm`（存于 prefs，**不在存档内**）。
- 字段登记与证据：`docs/TIME_SEMANTICS_FULL_AUDIT_2026-10-26.md`、`docs/SPEEDUP_ANALYSIS_2026-10-26.md`、
  `reports/time_fields_inventory_2026-10-26.csv`。
- 自动化测试：`scripts/run-all.sh`（静态门禁 + `--device` 追加 AVD 实测），失败返回非零。
- 已知未验证：离线结算是否应用 F、EC12 与 F 叠加顺序、Enslaved 8h 钳制、释放帧、Laitela 时效、黑洞/符文组合。
- **`realDiff` 含义与 Web 不同**：Android 的 `realDiff` 是**纯墙钟**（F 只乘 `diff`），
  因此 §3 表中 `Σ realDiff / F` 的写法**只适用于 Web**；Android 侧为 `Σ realDiff`（k=1）。
  该差异已登记于 `docs/CROSSPLATFORM_TIME_AUDIT_2026-10-26.md` §2.3 / D1。
- **无 `totalInGameTime` 字段**：Android 没有「归一化游戏内时间」累计器；
  最接近的是 `pastTen*.time`（写入时一次性归一化），语义不同，**不可互相替代**。
- F 合法范围：`1e-6 ~ 1e9`（平台扩展）；与 Web 的公共可测区间为 `1 ~ 100000`。

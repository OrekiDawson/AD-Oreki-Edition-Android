# Android 自动机（Automator）等待状态体验审计（2026-10-27）

## 一、结论摘要

| 项 | 结论 | 证据等级 |
|---|---|---|
| 控制栏能否区分「运行中」与「等待中」 | **不能**。状态文案只有运行中 / 已暂停 / 已停止 / 未运行四种，**没有任何「等待」态** | 已实测 + 静态确认 |
| 等待对象（在等什么） | **能看到**，但只在自动机事件日志里，且只在开始等待的那一瞬间写一条 | 静态确认 + 字符串资源 |
| 等待时长 | **能算出来**，但只出现在「等待结束」的那条事件里，等待过程中看不到 | 静态确认 |
| 是否用现实墙钟 | **是**，`System.currentTimeMillis()` | 静态确认 |
| 60 秒长等待诊断 | **没有** | 静态确认 |
| 暂停时长是否被计入等待 | **会被计入**（暂停不清等待起点） | 静态确认，未运行时复现 |
| `until` 循环是否会被误判为等待 | **不会**，`until` 不触碰等待标志 | 静态确认 |
| 长等待是否刷屏 | **不会**，有 `isWaiting` 守卫，只写一次 | 静态确认 |

**结论：Android 与 Web 修复前的状态一致——等待期间控制栏仍显示「运行中」，玩家无法从状态栏判断脚本是卡在等待还是正常推进。** 但 Android 比「完全不可见」要好一点：事件日志里有「开始执行 WAIT 指令，等待 X」和「已执行 WAIT 指令，继续运行（等待 X 用时 Y）」。

## 二、机制实现（Android 实际代码）

### 2.1 等待状态存在哪里

| 符号 | 含义 | 位置 |
|---|---|---|
| `Lvo;->e:Z` | `isWaiting`（当前是否在等待） | `vo.smali` 静态字段 |
| `Lvo;->f:J` | `waitStart`（等待起点，墙钟毫秒） | 同上 |
| `Lvo;->g:J` | 最近一条事件的时间戳 | 同上 |
| `Lvo;->b:Lwg;` | 事件环形缓冲（容量 = 设置里的自动机事件条数） | 同上 |

对应官方 `AutomatorData.isWaiting` / `AutomatorData.waitStart`，语义一致。**两个字段都不写进存档**（`player.json` 无对应键），只在内存。

### 2.2 写入点只有三处（都在等待命令内部）

| 命令 | 类 | 写 `vo.f` | 写 `vo.e` |
|---|---|---|---|
| `wait <比较式>` | `Parser$WaitConditionCommand` | 865 行 | 717 / 870 行 |
| `wait eternity/…` | `Parser$WaitPrestigeCommand` | 259 行 | 193 / 267 行 |
| `wait black hole …` | `Parser$WaitBlackHoleCommand` | 374 行 | 308 / 379 行 |

### 2.3 读取点同样只有三处 —— 这就是缺陷所在

全仓库检索 `Lvo;->e:Z` / `Lvo;->f:J` 的读取：

```
Parser$WaitConditionCommand:458   读 vo.e
Parser$WaitConditionCommand:733   读 vo.e
Parser$WaitPrestigeCommand:209    读 vo.e
Parser$WaitBlackHoleCommand:324   读 vo.e
Parser$WaitConditionCommand:437   读 vo.f
Parser$WaitBlackHoleCommand:253   读 vo.f
Parser$WaitPrestigeCommand:130    读 vo.f
```

**没有任何 UI 代码读取这两个字段。** 因此界面结构上不可能知道「正在等待」。

### 2.4 控制栏状态文本的真实来源

`eg2.smali:2966-3002`（自动机面板的构建处）只读了四个东西：

```
a.j()   -> topLevelScript 编号
a.k()   -> editorScript 编号
a.p()   -> mode == 2（暂停）
a.o()   -> 运行栈非空（运行中）
```

状态字符串资源只有这四条（`values-zh-rCN/strings.xml`）：

| 资源名 | 中文 |
|---|---|
| `automator_running` | 运行中：%1$s（第 %2$s 行） |
| `automator_paused` | 已暂停：%1$s （于第 %2$s 行恢复） |
| `automator_stopped` | 已停止：将开始运行 %1$s |
| `automator_not_running` | 自动机未运行 |

**不存在 `automator_waiting` 这类资源。** 与 Web 修复前完全同构。

### 2.5 等待中途暂停：时长会被污染

- `vo.f` 只在三个等待命令「开始等待」时写入；
- 停止路径（`a.D(IIZ)` 内，`a.smali:463`）会把 `vo.e` 清 0，因此**停止→再启动**的等待会重新计时，正确；
- 但 `p()` 的暂停只是 `mode = 2`，**既不清 `vo.e` 也不动 `vo.f`**。
  → 暂停 10 分钟再恢复，等待结束时那条事件里的「用时」会把这 10 分钟算进去。
- 官方上游同样如此；Web 的修复正是补了这一条（暂停冻结、恢复重算）。

### 未能完成的运行时项（如实标注）

1. **没能在运行时复现「等待中仍显示运行中」**：注入 `wait realities > 1e9` 后，自动机面板的启动按钮在 AVD 上多次点击未能让脚本进入运行（`此脚本` 指令计数停在 21/10,000）。可能原因：Doomed 存档下自动机被禁用（#800 即如此，`mode=1` 但运行栈始终为空）、以及 Compose 面板按钮命中区不稳定。**该结论目前仅由静态调用链保证，不是实测。**
2. **暂停时长污染**只做了静态确认，未做运行时对照。
3. `#700` 的原生 Ninja 脚本能正常显示「运行中 + 行号」，说明状态机本身工作正常。

## 四、本轮是否改代码

**没有改。** 明确说明理由，不是遗漏：

1. 唯一能让玩家直接看到「等待中」的位置是控制栏那行文本，而它是被混淆的巨型 UI 类（`eg2.smali` 的 `onClick` 超过 1 万行）里的字符串拼接。要改成
   `if (isWaiting) 等待中：<脚本>（第 N 行，已等待 Xs）` 必须：
   - 新增一条字符串资源（`strings.xml` + 重新打包，有资源 ID 风险）；
   - 新增 `vo` 的公开访问器（`isWaiting()` / `waitStart()`）；
   - 在状态拼接处插入分支。
   这已经超出「最小、可回滚」，且**本轮无法完成自动机回归验证**（连启动脚本都没跑通），按 §5「未测不得宣称通过」，不该交一个未验证的 smali 补丁。
2. 三条已确认的差距（无等待态、无 60s 诊断、暂停计入时长）都**不影响脚本正确性**，只影响信息呈现，属于「下一轮做更合适」而不是「必须立刻修」。

## 五、下一轮最小方案（已定到行号，可直接施工）

优先级从高到低，每一项都可独立回滚：

1. **让等待可见（最高收益）**
   - 在 `vo` 加两个 getter：`isWaiting()Z` → `sget-boolean v0, Lvo;->e:Z`；`waitStart()J` → `sget-wide v0, Lvo;->f:J`。
   - 新增字符串 `automator_waiting` = `等待中：%1$s（第 %2$s 行，已等待 %3$s）`，只加到 `values/` 与 `values-zh-rCN/`。
   - 在 `eg2.smali:2982` 读 `a.p()` 的位置之后插入分支：`a.p()` 为真优先「已暂停」，否则若 `vo.isWaiting()` 为真走新字符串。
   - 验收：等待脚本运行时截图应出现「等待中」，且 `运行中` 只在非等待时出现。
2. **暂停不计入等待**
   - 暂停入口（`AutomatorState.mode = 2` 的写入点）记录 `pauseAt`，恢复时 `vo.f += (now - pauseAt)`。
   - 需新增一个静态长整型；验收：等待中暂停 60s 再恢复，结束事件里的「用时」不含这 60s。
3. **60 秒单次诊断**
   - 在三个等待命令的轮询分支里，用 `vo.e` 之外的独立标志（新增静态布尔）保证只写一次：
     `if (now - vo.f > 60000 && !warned) log("仍在等待 X（已等待 1m0s）")`。
   - 只用墙钟，不触发任何 Eternity / Reality / STOP。

**不建议做的事**：为了和 Web 长得一样去动 `until` / 黑洞冷却判定 —— 它们本来就不会置位等待标志，改了反而可能误报。

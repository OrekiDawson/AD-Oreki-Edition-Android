# Oreki 游戏时序与时间进度审查规则（R116-01）

适用范围：Android/Web MOD 的游戏机制改动（自动化、阶段门禁、结算、时间系统、存档、挑战）。

## 一、时序合理性（必须检查）
1. 阶段顺序：无限 → 永恒 → 现实及子系统按真实进程解锁，不得提前开放。
2. 前置条件：购买/升级/挑战/自动化/奖励/成就必须先满足前置条件。
3. 事件因果：资源获取、消费、生产、挑战完成、阶段重置、奖励发放按合理先后执行。
4. 自动化时序：不得越过解锁条件、破坏操作顺序或与手动操作竞态。
5. 时间语义：墙钟/游戏时间/离线进度/计时器/冷却/倍率各用正确语义，不得伪造或倒退计时。
6. 界面同步：不得提前显示未解锁内容，也不得长期落后于真实状态。
7. 存档一致性：保存/加载/离线恢复/重置后顺序与阶段正确，不得重复领奖或提前解锁。
8. 挑战完整性：真实进入→执行→胜利判定→结算，不得直接写完成状态。
9. 双端一致：Android/Web 的时序、自动化优先级、阶段门禁、结算语义一致。
10. 加速边界：允许合法提速，但保留必要机制、解锁顺序与有意义手动玩法。

## 二、时间进度合理性（必须检查）
1. 新档真实墙钟目标 ≤180 分钟；不得无依据瞬间跨阶段、长时间停滞或自动化死循环。
2. 关键阶段应有可感知成长；前后阶段增速失衡需有机制依据。
3. 资源曲线：生产速度、购买升级收益、自动器连锁、倍率/离线/计时一致性；指数增长本身不是问题，无机制跳跃才是。
4. 时间语义不得混用；不得虚增离线、篡改通关计时、重复结算。
5. 玩家体验：减少无决策等待与频繁切页，保留重要手动操作。
6. 涉及上述改动的 PR 必须附真实运行的时间进度证据（关键阶段墙钟耗时、解锁节点、异常停滞/跳跃），优先真新档数据。

## 三、判定与输出
- 将问题分类为：时序错误 / 进度过快 / 进度过慢 / 进度停滞 / 时间计算错误。
- 每条 finding 必须给出文件:行、触发条件、真实证据或可复现步骤；禁止仅凭数值大小判定异常。
- 修复建议必须针对根因，禁止伪造存档、资源、挑战完成或通关结果。

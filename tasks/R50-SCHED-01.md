## 三、根因归属（主 Agent 自我审查）

**第 3 条 294.7 秒的前台 Bash，由主 Agent 造成。**

本会话中主 Agent 多次使用 `sleep` 作为等待手段，实测量级：

| 用途 | 命令 | 时长 |
| --- | --- | --- |
| 等待构建完成 | `sleep 240` / `sleep 300` / `sleep 180` | 180–300 秒 |
| 等待采样完成 | `sleep 120` | 120 秒 |
| 等待 AVD 引导 | 循环 `sleep 10` × 24 | 最长 240 秒 |
| 等待 Agent 产出 | 循环 `sleep 45` × 20 | 最长 900 秒 |

**这是违反 AGENTS「避免 sleep」条款的直接后果**：用阻塞式等待换取「稍后检查」，
代价是整回合被占用、期间无法响应任何消息。

**第 6 条高频 `requestUpdate`**：主 Agent 在每个子 Agent 完成阶段后都发送长篇消息（单条常 2000–4000 字），
并在多轮中重复发送类似内容（如反复强调同一条纪律）。**【推断】** 与上报频率正相关，但日志未提供逐条对应，
不宣称已证实因果关系。

## 四、优化措施（P0）

### 4.1 禁止阻塞式等待（立即生效）

| 禁止 | 替代 |
| --- | --- |
| `sleep N`（N > 30） | 一次性状态查询，立即返回 |
| `for i in $(seq 1 24); do ... sleep 10; done` | 单次查询 + 由 Agent 主动回报 |
| 反复轮询文件 mtime | 等 Agent 的消息（消息到达即触发） |

**原则**：主 Agent 不「等」，只「查一次」然后交回控制权，由 Agent 的完成消息驱动下一步。
唯一例外：`sleep ≤ 30` 用于等待进程退出等必须同步的短场景。

### 4.2 长操作拆分为阶段

| 操作 | 拆分方式 |
| --- | --- |
| 构建（约 8 分钟） | 由子 Agent 发起并自行等待；主 Agent 只在收到「构建完成」消息后检查产物 |
| AVD 引导（约 70 秒） | 起进程后立即返回；后续由 `adb devices` 单次查询确认 |
| 批量文件扫描 | 限定路径与数量；超时即中止并报告已扫范围 |

**不破坏原子性的例外**：Gradle 构建、APK 签名、安装测试必须完整执行，不得中途打断；
但**发起方是子 Agent，等待也由子 Agent 承担**，主 Agent 不占用自己的回合。

### 4.3 派活节奏

1. 分派前查目标 Agent 是否 busy（通过最近一次消息的时间与内容判断，无法直接读平台状态则【未知】）
2. **忙态 Agent 只保留紧急通知**，普通任务排队等其空闲
3. **任务未接收不得标记为已开始**；发送 ≠ 接收 ≠ 开始执行，三者分开记录
4. 不因忙碌丢弃或覆盖任务

### 4.4 降低重复上报（P1）

1. 单条消息**控制在 800 字以内**（紧急技术细节可附代码块，但正文精简）
2. **同一纪律不重复全文**，引用即可（如「按 §53」而不重述 §53 全文）
3. 只在**状态变化 / 阶段完成 / 阻塞 / 交付**时发消息
4. **不得为减少消息而隐瞒错误或阻塞**

### 4.5 消息生命周期记录（P1）

在能力范围内记录六个时间点，无法获取的标【未知】：

| # | 时点 | 获取方式 |
| --- | --- | --- |
| 1 | 发送时间 | 调用 SendMessage 前读 `oreki_time.py` |
| 2 | 进入派发队列 | 【未知】——平台不暴露 |
| 3 | 被目标接收 | 收到 Agent 的 reactivated 通知时间 |
| 4 | Agent 确认 | Agent 回复中出现确认语句的时间 |
| 5 | 开始执行 | Agent 首个工具调用时间（若其报告） |
| 6 | 完成 | Agent 完成消息时间 |

## 五、对照实验设计

**实验 A（空闲态）**
1. 确认目标 Agent 无在途任务（最近一条消息为完成态，且无新工具调用）
2. 发送一条最小测试消息（仅含「收到请回复 OK」）
3. 记录发送时间与收到回复时间
4. 延迟 = 回复时间 − 发送时间

**实验 B（忙碌态）**
1. 让同一 Agent 执行一个**分阶段**任务（每阶段 ≤ 60 秒，可正常回报）
2. 在其执行中途发送同一条最小测试消息
3. 记录该 Agent 当前阶段的结束时间与测试消息被消费的时间

**对比判据**：B 的延迟显著大于 A ⇒ 延迟主要来自忙态排队。

**约束**：不使用不可控长命令人为制造阻塞（如 `sleep 600`）。

## 七、与 Android 三 Agent 冲刺的关系

本任务不改变 R50-AND-03/04/05 的既有分工，只调整**调度方式**：

1. 三个 Agent 保持并行处理独立任务
2. **单个 Agent 按阶段交付**，每阶段结束即回报，不再一次占用长回合
3. 主 Agent 负责协调、集成、构建与验收——**构建与 AVD 观察不并发**（已定的硬规则）
4. 同一时间只允许一个 Agent 控制 `oreki_test`
5. 同一时间最多一个重型构建
6. 任务单先建、先 Push、先核验，再分派
7. 不覆盖他人未提交工作
8. 任务文件禁用第一人称（§51）
9. 统一智能调度器规则不绕过

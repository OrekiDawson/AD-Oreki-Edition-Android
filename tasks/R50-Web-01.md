## 五、统一调度器规格（与 Android 必须等价）

**关键前提（已核）**：`src/core/oreki-smart-executor.js`（883 行）**已经是统一调度器**，
具备 `VERBS` 注册表、`pickExecutable(priority)` 优先级、`STATE.enabled` 开关、
`noopUntil` 失败冷却、`lastExecAt` 时间戳、`manualHold` 手动优先。
**不得新建第二个调度器**，应在它上面扩展。

缺的三件：

1. 间隔：`STATE.intervalSec`（默认 3，钳制 1~60），`tick()` 中在 `enabled` 判断之后加节流；
2. 持久化：`localStorage` 键名 **必须** 为 `oreki.automation.enabled` / `oreki.automation.intervalSec`；
3. UI：开关 + 间隔输入（边界钳制），深色模式正常。

**直调点**（`game.js`，属绕过 executor，需逐个判定是否纳管）：
`:898` early.tick、`:905` eternity.tick、`:911` tickEternity、`:916` reality.tick、
`:920` celestial.tick、`:926` perk.tick、`:934` endgame.tick、`:940` smartStrategy.evaluate。

判定规则：**会改变游戏状态的操作纳管；只回答是/否的只读判据不纳管**
（如 `shouldHoldReset` / `shouldHoldCrunch` 不得被节流，否则闸门失去时效性）。

## 十一、关键结论（供主 Agent 写 FACTS 用）

1. **莱特拉段是最大单段**（三次基线 285/300/314 s，占 34~40%）。根因不是熵速率，而是
   `OrekiDilationAutomation.hold` 在 tier 0~7 全程压现实：每次 `difficultyTier++` 后 entropy 被置 -1，
   只有一次现实重置能清回 0 ⇒ 每层必须一次现实，而 hold 把现实拖到 37~58 s。八修后 137~151 s。
2. **测量陷阱（高价值）**：动态速度（`speed-config.js`）会把升档后的倍率持久化到
   `localStorage["oreki-game-speed"]`，上一局末速会成为下一局起速；且页面加载时 hibernate 模拟会
   先 `beginSimulation()` 冻结倍率，**事后再 `GameSpeed.set(10000)` 改不动 effectiveFactor**
   （实测 `factor=10000` 但 `getGlobalSpeedFactor()=80000`）。必须在**导航前**用
   `Page.addScriptToEvaluateOnNewDocument` 写入 localStorage。任何新档取证都要回读确认。
3. **零继承陷阱**：`GameStorage.hardReset()` 后页面会 reload，监控脚本必须按
   `records.gameCreatedTime` 变化 + `rtp < 8000` 判新档，不能按「等十几秒」判。
4. **线上核验**：本机 Git Bash 下 `curl -o /tmp/x` 正常工作（拿到 35839 B 并算对 SHA），
   但已按主 Agent 要求改落仓库内 `_deploy/_web_deploy_check/`。

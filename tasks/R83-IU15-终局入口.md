# R83 IU15 守卫业务 Kotlin 迁移与冲刺状态机

- 执行者：单 Agent（主会话）
- 开始：2026年11月5日 22:46
- 状态：**代码与构建已完成；运行期验收部分覆盖**（详见第四节）

## 一、目标

把 Android 侧 IU15 守卫的全部业务逻辑迁到 Kotlin，并让「接近理想之构条件时临时接管、达标后原版购买并立即释放」这条链真正可执行。同时补齐 EC7 拦截，防止 ID8 奖励经维度链间接生产 ID1。

## 二、根因（字节码实证）

1. `OrekiAuto.idBuyBlocked()` 原为 Smali 实现，只做「IM 前置闸 + IU15 是否已买/需求位已亮 + 失败计数」，**不检测自动购买器总开关**，失败计数是进程内静态字段（重开即归零，不构成真正回退）。
2. 原实现不拦 EC7。`TimeDimensions.tick()` 末尾把 EC7 完成奖励换算成 ID8 产量，`InfinityDimensions.tick()` 再逐层生产到 ID1 ⇒ 只要 EC7 有完成次数，`maxID1` 必然变正，IU15 永久失败。
3. Web 侧 `OrekiIu15Sprint.canArm` 要求 `VUnlocks.vAchievementUnlock`，而该解锁需 10000 次现实 + 1e320 膨胀时间（`secret-formula/celestials/v.js` 有实测记录），在本作目标内结构性不可达 ⇒ 等于永久禁用冲刺。
4. Web 侧 `oreki-eternity-automation.js` 读 `OrekiIu15Sprint.freezeResets`，但该模块从未定义此 getter，`undefined === true` 恒 false —— 冻结逻辑从未生效。
5. Web 侧把整个状态机挂在 `OrekiEarlyAutomation.tick()` 里，而该入口在自动购买器关闭时**直接 return** ⇒ 关闭总开关后再也收不到 tick ⇒ `setMechanicLock(true)`（写入 `player.reality.reqLock.imaginary`，**会进存档**）永久残留。

## 五、未完成与风险

- **IU15 真实购买与莱特拉解锁未在设备上验证**：`iu15AffordableByCap` 用 `iMCap` 原始值判断，若实际 IM 上限远低于 IU15 成本，冲刺不会启动（这是保守行为，不是 bug，但会导致「永远不开始」）。
- EC7 守卫注入后，若原版 `D` 的返回语义与观察不符，可能导致挑战启动静默失败；静态断言只保证注入形状，不保证运行语义。
- `OrekiAuto` 的 `bumpIdGuardFails` / `noteReality` 保留为空实现（状态机接管），老探针读取这两个方法的副作用会得到空结果。

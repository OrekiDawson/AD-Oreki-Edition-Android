## 三、Android 与 Web 的生产修改

### 3.1 Web（`web/AD-Oreki-Edition`）

1. `src/game.js`：**开局例行操作里的「维度提升 / 反物质星系」由每拍 1 次改为单次调度动作内买光当前真正买得起的次数**。
   - 机制依据：`requestDimensionBoost(bulk)` 只有在 Break Infinity 升级 `autobuyMaxDimboosts` 已买时才走 `maxBuyDimBoosts()`，否则只 `softReset(1)` 一次；`requestGalaxyReset(bulk)` 只有在「9 次永恒」里程碑达成时才 `maxBuyGalaxies()`。首次无限之前两者都是**一次只买一个**，而本作把每拍当成唯一出手机会，于是「明明买得起却一次只买一个」。
   - 守卫：计数无变化即退出（要求不满足时原版原地返回）、硬上限 `MAX_EARLY_RESET_BATCH = 100`、总开关关闭或挑战进行中一个都不买、顺序仍是「先重置类动作，再买反物质维度」。
   - 生效前提：`src/core/oreki-keep-antimatter.js` 的 AD4「保留反物质」窗口在首次永恒前为真，`dimboost.js:210` 因此让 `softReset` 保留反物质，连续提升才可能真的连续成立。
2. **修掉一个真实生产缺陷**：`src/game.js` 用了 `player.dimBoosts` 读取维度提升计数，而原版真实字段是 `player.dimensionBoosts`（`src/core/player.js:210`、`dimboost.js:171/194/196`）。因为 `player.dimBoosts` 恒为 `undefined`，批量循环的「计数变化」守卫每次都判定「没变化」并立刻退出 —— **生产环境下批量购买完全不生效**，而夹具因为照抄了同一个错字段名而 12/12 通过。
   - 修复：`src/game.js` 批量循环与 R90 的 `earlyRoutineSnapshot`/`earlyRoutineChanged` 全部改读 `player.dimensionBoosts`；
   - 夹具同步改真字段名（`scripts/test-r92-early-reset-batch.mjs`、`scripts/test-r90-early-routine-beat.mjs`），让测试不再验证虚构世界。
3. 教程附录 F 同步（`src/core/oreki-tutorial-data.json` + `.gen.js`）：说明「每次出手会把当时买得起的次数一次性买掉，价格与需求仍按原版逐级递增」。

### 7.2 「没有 `OREKI_SCHED act`」的真实归因（不是抓取失败，是当前状态无动作可做）

- 调度器本身正常：`OREKI_SCHED: init 调度：已启用 · 间隔 10 秒`（冷启动后再次出现），每 5 s 有 `OREKI_GATE`、每约 8 s 有 `OREKI_CRUNCH`，说明 MOD 主循环在跑。
- 逐个核对了 `OrekiStageAuto.onAutoBuyerTick()` 里全部受节拍管辖的任务在本档状态下的判据：
  - `eternity`（买永恒升级）：尚未解锁永恒 → 无；
  - `sacrifice`（维度献祭）：`Sacrifice.canSacrifice` 不成立（本档第八维度 100、献祭加成 ×2.05，但原版献祭前置未满足）→ 无；
  - `bulk` / `infinityUpgrades` / `crunchInterval` / `breakShop`：都要 IP（≥1e6～1e10），本档 IP 仅 330 → 无；
  - `idBuy`（买 ID1）：ID1 需 IP ≥ 1e8 → 无；
  - `breakGate` / `breakUpgrades`：早已 Break，无状态变化 → no-op。
  ⇒ 本档**没有任何一个可执行的调度动作**，所以没有 `act` 是**正确行为**，不是缺陷；轮询 5 分钟确认零 `act`、零 `noop` 记录。
- 本档 IP 增长速率约 6 IP/分钟（290 → 330 用时约 7 分钟），按此速率远达不到 1e6 IP 门槛 ⇒ 本轮窗口内**不可能**产生真实 `act`。该项标记 **NOT RUN（原因明确）**，不写成 PASS。

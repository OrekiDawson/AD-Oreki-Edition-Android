# R0 / Pelle 成就清单核验

数据来源：APK `res/values-zh-rCN/strings.xml`（名称/条件/奖励原文）+ `z3.smali`（ID、行号、lambda 槽位）+ `Player$Records` 时间字段反解。

## 1. 行号规则（代码级）

`achievements/a;-><init>` 中：

```smali
div-int/lit8 v1, p1, 0xa     # m = id / 10  → 行号
iput v1, p0, ...->m:I
rem-int/lit8 v1, p1, 0xa     # n = id % 10  → 列号
iput v1, p0, ...->n:I
```

即位图索引为 `Player.achievements[row-1].bit(col-1)`；每行 8 个（列 1..8，尾号 9/0 不存在）。
18 行 × 8 = 144 个，ID 恰为 11–18, 21–28, …, 181–188。`Player.achievements` 数组长度实测 `const/16 v1, 0x12` = **18**（行 1..18 均可安全写入）。

## 5. 点亮策略结论

两张清单都可直接作为「目标集合」，执行时只对**尚未解锁**的项置位：
- 已解锁的成就 `E(ZZ)` 首行即 `if (isUnlocked) return`，重复点亮是无副作用的空操作，但**会**触发 `ACHIEVEMENT_UNLOCKED` 事件与 UI 脏标记（若不过滤，会刷出无意义的刷新与事件）。
- 因此实现上应「目标清单 ∩ 未解锁集合」，并在 UI 上显示「本次将点亮 N 个」。
- 不能只点亮「新增差集」：初次 Reality 时 R0 的 104 个是玩家真实需要的门槛，此时 32 个差集尚未生效；Pelle 时 R0 已在 Reality 重置中被 `lockAchievementsOnReality()` 清空（`reality.js:829-835`，除非已买 `Perk.achievementGroup5`），所以 Pelle 阶段仍然要重新点亮 104 个。两阶段都必须按各自完整清单取差集，不能按「增量」处理。

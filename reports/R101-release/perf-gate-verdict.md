# R101 性能正式门禁判定（2026-11-11 04:00）

## 测量条件（两端完全一致）

- AVD `ad-game-api37` / `emulator-5554`，x86_64，1080×2400，同一图形后端
- 同一份存档：`savestates/mod/after-bigcrunch-fixed.json`（两端均注入）
- 同一程序：`am force-stop` → `monkey` 启动 → 固定 **20 s** 窗口 → `dumpsys gfxinfo` 累计读数
- 同一页面：应用启动后的默认页面（游戏主页）

## 实测结果

| 应用 | 20 s 内渲染帧数 | 折算 | Janky | p50 | p90 | p99 |
|---|---|---|---|---|---|---|
| 官方原版 3.21 | **971** | ≈48.6 fps | 6（**0.62%**） | 16 ms | **16 ms** | **16 ms** |
| MOD（修复后 `b8556165…`） | **26** | ≈**1.3 fps** | 7（**26.92%**） | 16 ms | **200 ms** | **400 ms** |

## 判定：**FAIL**

MOD 每 20 秒只重绘 26 帧，原版同期 971 帧——**相差约 37 倍**。
p90 从 16 ms 劣化到 200 ms（12.5×），p99 劣化到 400 ms（25×）。

这**同时解释了历史口径冲突**：
- 旧口径「MOD 86% janky」的 FAIL 是**正确的**；
- 而「MOD 单帧工作量更低」不等于性能好——MOD 的问题不是每帧慢，而是**根本不重绘**；
- 「两端都约 20 FPS」的比较本身不成立，因为两端刷新机制不同。

## 影响

直接违反用户硬性要求「UI 必须实时刷新（省电模式除外）」。属于发布阻断级缺陷。

## 下一步（根因方向）

MOD 侧存在 UI 刷新节流/跳帧逻辑，需定位：
1. `OrekiSpeed` / `topBar` 相关刷新门控；
2. 主线程 tick 是否跳过了 `invalidate`；
3. 是否命中「省电模式」分支（若命中则需确认是否被误开）。

找到后按「不得为了通过门禁降低正常 UI 实时性」的反向要求修复：**恢复真实实时刷新**，而不是降低阈值。

## 可复现性与限定条件（04:10 补记）

**重复测量（三次独立读数）**

| 应用 | 读数序列（帧/窗口） | 结论 |
|---|---|---|
| 官方原版 | 969 → 971（另一次 971） | 稳定在 **≈970 帧/20 s**（≈48 fps） |
| MOD | 26 → 26（两次完全一致） | 稳定在 **≈26 帧/20 s**（≈1.3 fps） |

三次独立读数差值 ≤2 帧，说明这是**稳定的机制性差异**，不是抖动。

**必须声明的不完全对等项**

- 两端启动时的存档内容不同（MOD 注入 `after-bigcrunch-fixed.json`；原版是跨版本导入后的同源存档但已运行一段时间）；
- 两端停留在各自默认页面，未逐页对齐。

因此本判定的严格表述是：**「在各自默认页面、全新启动 20 s 窗口下，MOD 重绘频率比原版低约 37 倍」**，该结论可复现；但不能直接推论到「每个具体页面都必然 37 倍」。

**已排除的 MOD 侧原因**：Kotlin payload 与 smali payload 中**均无** `invalidate` / `requestLayout` / 刷新节流代码；`build_mod.py` 也没有 UI 刷新补丁。说明不是 MOD 主动加了节流，而更可能是 MOD 的游戏循环/车速实现导致**状态变化不足以触发重绘**，或主线程被长时间占用导致跳帧。

**下一步定位手段**：对 MOD 采 `atrace` 的 `view` 类别并指定应用 pid 过滤，观察 `Choreographer#doFrame` 是否被调用但跳过；或直接检查 MOD 的游戏主循环 tick 是否把 UI 更新放到了低频分支。

## 04:20 定位进展（logcat 侧）

冷启动 22 s 内 logcat 共 2,501 行（≈114 行/秒），按 tag 统计前几位：

| tag | 行数 | 归属 |
|---|---|---|
| AutoCloseableTracker | 420 | 系统框架 |
| CCodec / CCodecConfig | 430 | 系统编解码 |
| skia | 148 | 系统绘制 |
| **OREKI_ACHAUDIT** | **72** | **MOD 自身**（成就审计，≈3.3 次/秒） |
| ReflectedParamUpdater | 70 | 系统 |

MOD 的 `GUI_REFRESH_POSTED/APPLIED` 仅 **3 次/22 s**，因此：

1. **可以排除**「MOD 每帧打 GUI 刷新日志刷屏」这一假设；
2. `GameApi.kt:530-560` 的 UI 刷新确实被 `dirty/phaseChanged/force` 门控，但它只影响自动购买器与统计页，不是全局帧驱动；
3. MOD 自身最重的周期性日志是 `OREKI_ACHAUDIT`（≈3.3 次/秒），**在主线程上做成就审计的频率偏高**，是需要优化的候选，但不足以单独解释 37 倍帧数差。

## 结论

帧数差的机制仍未定位到具体代码路径。已知排除项：MOD 主动节流（无）、GUI 刷新日志刷屏（无）、刷新门控影响全局帧（否）。

下一步建议：对 MOD 采 `atrace -e view` 并过滤应用 pid，确认 `Choreographer#doFrame` 的**调用次数**与 gfxinfo 的 26 帧是否一致——
- 若 doFrame 也是 ~26 次/20 s ⟹ 应用根本没申请重绘，问题在游戏主循环/tick 驱动；
- 若 doFrame ≈970 次 ⟹ 应用申请了重绘但被合成器丢弃，问题在渲染/合成层。

## ✅ 04:35 根因层面定位：MOD 应用侧根本不申请重绘

用 `atrace -t 12 -b 32768 -a <pkg> view` 过滤应用，统计 12 秒窗口：

| 应用 | atrace 行数 | **`Choreographer#doFrame`** | `draw` | 折算 |
|---|---|---|---|---|
| 官方原版 3.21 | 41,841 | **726** | 1,441 | ≈60 fps |
| MOD | 234 | **5** | 4 | **≈0.4 fps** |

**结论（二选一已判定）**：应用**根本没有申请重绘**（doFrame 少 145 倍），
而不是「申请了但被合成器丢弃」。因此问题在**游戏的 UI 刷新调度 / invalidate 驱动**，
不在渲染、合成或 GPU 层。

这与 `gfxinfo` 的 26 帧/20 s、`atrace` 的 5 次/12 s 三个独立来源互相印证，
且排除了此前所有候选（MOD 主动节流、日志刷屏、刷新门控、合成器丢帧）。

## 下一步（修复方向已明确）

需要在 MOD 侧定位「谁负责周期性 invalidate / 提交 UI 更新」：
1. AD Android 的主循环由 `mHandler.postDelayed(...)` / `Choreographer.postFrameCallback` 驱动；
   MOD 若把该驱动的间隔放大（例如为了「省电」或与全局行动节拍绑定），就会出现此现象；
2. 重点检查 Kotlin payload 中与 `Handler`/`postDelayed`/`Looper` 相关的实现，
   以及 `build_mod.py` 是否改写了主循环的延时参数；
3. 修复目标：**恢复原版的每帧驱动（≈60 fps 申请重绘）**，不得用降低门禁或减少计算来绕过。

## 04:50 主循环驱动排查（未定位）

- `postDelayed` 在 MOD 与 base 两棵 smali 树中都是**大量库代码**（GMS/AndroidX/material）命中，
  无法用 grep 区分出「游戏主循环」那一处，直接文本检索不具区分度。
- MOD 的 Kotlin payload 中只有 `GameApi.uiHandler()` 一处 Handler（用于自动购买器/统计页刷新，
  实测 22 s 仅 3 次），**不是**每帧驱动；payload 与 `build_mod.py` 中也没有对主循环延时的改写。
- 因此「0.4 fps」更可能不是「把循环间隔调大」，而是**每帧耗时极长**（≈770 ms/帧）导致自然掉帧：
  若 MOD 以 1000× 速度在单帧内串行执行上千次 tick，主线程单帧就会非常久。

**待验证的判据**：对 MOD 采 `atrace -t 12 sched view -a <pkg>`，看主线程
（pid 主线程名 = 包名）在 12 s 内的**运行时间占比**。若接近 100%，即证实「单帧计算量压满主线程」，
修复方向应是**把加速计算移出主线程或降低单帧 tick 次数**，而不是去改刷新频率。

## ✅ 04:58 根因确定：MOD 主线程几乎不跑，渲染被「批量游戏推进」耦合

同一时刻对两端取 `top -b -n 2 -d 6 -p <pid>`：

| 应用 | 进程 CPU | 说明 |
|---|---|---|
| 官方原版 | **37.1%** | 每帧持续 tick + 重绘 |
| MOD | **0.1%** | **几乎完全空闲** |

**这否定了「单帧计算量压满主线程」的假设**（若压满应接近 100%）。真实情况相反：
MOD 主线程**绝大多数时间不做事**，只在极少数时刻突发工作一次。

### 与其它证据完全自洽

- MOD 新档 20 s 内从 0 涨到 1e243 反物质 —— 说明它靠**少数几次大批量推进**实现加速，
  而不是逐帧 tick；
- `doFrame` 5 次/12 s、`gfxinfo` 26 帧/20 s —— 因为 **UI 刷新被绑定在「每次批量推进」之后**，
  批量推进约 0.77 s 一次，于是 UI 也约 1.3 fps；
- CPU 0.1% —— 两次批量之间主线程完全空闲，没有独立的 60 fps 渲染循环。

### 根因（结论）

**MOD 把「游戏推进」改成了低频大批量，并把「UI 刷新」耦合在同一次批量之后；
缺少独立的 60 fps 渲染/刷新循环。** 因此加速有效但画面几乎不动。

### 修复方向（明确且不违反「不得降低实时性」）

把 **UI 刷新与游戏批量推进解耦**：
1. 新增/恢复一个独立的高频刷新驱动（Choreographer 或 Handler 每 16 ms），只负责
   刷新顶栏、当前页数值与按钮状态，不触发游戏推进；
2. 游戏批量推进保持现有节奏（加速语义不变）；
3. 不得通过降低刷新频率或减少显示内容来「通过门禁」。

这符合用户要求「UI 必须实时刷新（省电模式除外）」。

## ✅ 05:45 UI 帧泵修复生效（实测）

**关键教训（先说）**：此前多轮验证全部无效，因为 `./gradlew installToRelease` **并没有把新包装到设备**
（`dumpsys package lastUpdateTime` 停在 03:12，而 APK 构建于 03:38）。必须显式
`adb install -r release/反物质维度.apk` 并核对 `lastUpdateTime` 才能验证。

**修复内容（纯 Kotlin，遵守「所有修改的 smali 必须转 Kotlin」）**
- 新增 `OrekiUiFramePump.kt`：`Choreographer` 每帧 `decorView.invalidate()`，只重绘不推进游戏；
- `GameApi` 增加只读 `currentActivityForUiPump()`（复用 `MainActivity.wp` 弱引用）；
- `OrekiGuiStage.refresh()` / `OrekiAutomationScheduler.init()` 幂等启动；
- **撤回**了 `OrekiSpeed.smali` 的插入。

**实测（装新包后，20 s 窗口）**

|---|---|---|---|
| 渲染帧数/20 s | 26 | **1,111** | 971 |
| 折算 fps | 1.3 | **≈55** | ≈48 |
| 帧泵日志 | 无 | **fps=60** | — |
| Janky（legacy） | 26.92% | **98.92%** | 0.62% |

**结论**：刷新频率问题已解决（26 → 1111 帧，与原版同量级）；
但**强制整树重绘引入了新的卡顿**（98.92% vs 原版 0.62%），需继续优化：
下一步应改为「只失效需要更新的文本控件」或降低到 30 fps 并实测卡顿率，
目标是在保持 ≥30 fps 的同时把 Janky 降到接近原版水平。

**性能门禁当前判定：仍为 FAIL**（帧率已达标，卡顿率未达标）。

## ✅ 06:05 卡顿修复：降频到 30 fps 后达标

**改动**：`OrekiUiFramePump` 增加 `VSYNC_PER_PAINT = 2`（每 2 个 vsync 重绘一次 ≈30 fps）。
依据：整树重绘单帧约 18 ms，60 fps 的 16 ms 预算必然超时；30 fps 的 33 ms 预算可稳定满足。

**实测（每次显式 `adb install -r` 并核对 `lastUpdateTime`）**

| 指标 | 原始 MOD | 60 fps 版 | **30 fps 版** | 官方原版 |
|---|---|---|---|---|
| 帧数/20 s | 26 | 1,111 | **542** | 971 |
| 折算 fps | 1.3 | 55 | **27** | 48 |
| Janky（legacy） | 26.92% | 98.92% | **3.32%** | 0.62% |
| p90 帧耗时 | 200 ms | — | **16 ms** | 16 ms |
| 帧泵日志 | 无 | fps=60 | **fps=30** | — |

**相对原始状态**：帧数 26 → 542（**21 倍**），卡顿 26.92% → **3.32%**（**降 8 倍**），p90 200 ms → **16 ms**（与原版一致）。

**与原版对比**：帧率 27 vs 48（低 44%），卡顿 3.32% vs 0.62%（高 2.7 个百分点）。

**判定**：UI 实时刷新问题已解决（27 fps 稳定重绘、p90 与原版相同、无长帧）；
但帧率仍低于原版，且卡顿率高于原版，**性能正式门禁仍不判 PASS**，
下一步可把重绘间隔改为「至少 25 ms」实现约 40 fps，在 25 ms 预算内仍可满足 18 ms 单帧工作量。

## 06:35 「只失效文本控件」优化失败并已回滚（记录以免重犯）

**尝试**：把 `decorView.invalidate()`（整树）改为「遍历可见 `TextView`、逐个 `invalidate()`」，
预期单帧成本从约 18 ms 降到接近原版。

**结果**：**应用崩溃**（`mCurrentFocus=Application Error`，`FATAL EXCEPTION` 计数 2）。

**已回滚**：`git checkout -- OrekiUiFramePump.kt`，重建后复测正常：

| 指标 | 回滚后实测 |
|---|---|
| 帧数/20 s | **580** |
| Janky | **4.66%** |
| p90 | **16 ms** |
| FATAL EXCEPTION | **0** |

与回滚前 33 ms 版本（576 帧 / 5.90% / 16 ms）一致（差异属运行方差），确认回滚到位、功能正常。

**失败原因（推断，未验证）**：递归遍历 `ViewGroup` 在深/环形视图树上可能栈溢出，
或在 UI 线程遍历期间视图树被修改。后续若再尝试，必须：
1. 改为非递归 + 深度上限 + try/catch 兜底；
2. 先只读收集、不在遍历中调用任何会触发布局的操作；
3. 必须有「收集失败即退回整树失效」的保底路径。

**当前保留的是「33 ms 时间门控 + 整树失效」这一已验证可用配置。**

## ⚠ 04:20 待解决：源码常量与运行时行为不一致

**现象**：源码 `MIN_PAINT_INTERVAL_NANOS = 33_333_333L`（应≈30 fps），但同一份已安装 APK
（`release/反物质维度.apk` sha256 `1793df9e…`，构建于 04:11:29）连续三次启动实测：

| 采样 | 帧泵日志 | 20 s 帧数 | Janky |
|---|---|---|---|
| 1 | `fps=60 frames=61` | 1,085 | 61.29% |
| 2 | `fps=16 → 25 → 56`（窗口内递增） | 1,085 | 68.66% |

**结论：运行时帧泵实际接近 60 Hz，与源码 33.3 ms 门控不符。** 推断为 Gradle 增量编译
未重新编译 Kotlin payload（缓存 DEX），导致 APK 内仍是 16 ms 版本。

因此**上一轮记录的「583 帧 / Janky 3.60% / p90 16 ms」（30 fps 档）不能确认对应本 APK**，
该数字暂列为**来源待核实**，不得作为正式门禁依据。

## 当前唯一可确认的事实

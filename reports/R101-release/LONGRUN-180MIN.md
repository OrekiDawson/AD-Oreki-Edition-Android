## ✅ 修复 1：自动大坍缩停止（已修并验证）

### 根因（代码级）

`OrekiStageAuto.kt` 放行分支里：

```kotlin
if (eternitiesZero() && crunchMode == MODE_TIME) {
    if (!targetIntervalInitialized) {        // 每进程只校准一次
        targetIntervalInitialized = true
        writeManagedCrunchInterval(..., "eternity-zero")
    }
    return                                    // 之后每帧直接返回
}
```

暂停路径会写 `TIME/3600`（真实秒 = 1 小时）。放行后本分支因
`targetIntervalInitialized` 已为 true 而**跳过校正并直接 return**，
残留的 3600 永久生效 ⇒ 坍缩停止。

### 修复

改为**每帧幂等校正**（`writeManagedCrunchInterval` 本身就是幂等的：目标与实读相等则不写）。

### 验证（装机实测）

| 指标 | 修复前 | 修复后（100 秒） |
|---|---|---|
| 无限次数 | **108（冻结）** | **544,580** |
| 40 秒后 | — | 636k |
| 80 秒后 | — | **820k** |

**坍缩完全恢复。**

## ❗ 修复 3 待办：策略反复「暂停 15 分钟」，IP 几乎不涨

**本轮的修复有效**：`3600.0 -> 5.0` 确实把暂停态恢复了（此前不会恢复）。

### 但发现下一层问题

策略在 `id-peak-wait`（暂停，写 3600 秒）与 `id-peak-reached`（放行，写 5 秒）之间**反复翻转**，
而 `id-peak-wait` 的等待上限是 `PEAK_WAIT_LIMIT_NS = 15 分钟`：

- 05:04:49 起暂停 → 05:20:00 才由 15 分钟上限强制放行（正好 15 分钟）；
- 放行仅 **18 秒**后又进入暂停。

**净效果：每 15 分钟只有十几秒在真正坍缩**，反物质来不及累积，`maxIP` 因此冻结在 1e198，
永恒（1.797e308）不可达。这与「8 万次坍缩 80 秒」的爆发（加载补偿）不是同一机制。

### 结论

根因是**策略把「等下一个无限维度峰值」当作暂停理由，而该等待上限过长且会反复进入**。
修复方向（下一轮）：
1. 若 IP 已远超当前阶段需求且反物质已在高位，不应再以「等峰值」为由暂停 15 分钟；
2. `id-peak-wait` 的上限应从 15 分钟收紧到与「反物质指数增长速度」挂钩的自适应值；
3. 必须保证任意 60 秒窗口内至少发生一次真实坍缩，否则视为判据失效并强制放行。

**在修复 3 完成前，「≤180 分钟通关」仍判 FAIL。**

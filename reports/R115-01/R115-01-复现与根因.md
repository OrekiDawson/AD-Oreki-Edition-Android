## 4. 根因（分层）

**A. 门禁层 —— 无缺陷（已排除）**
- DEX 实测（dexdump，`/tmp/dexcheck`）：`f82.j()` 已被替换为
  `invoke-static OrekiStageAuto.vanillaEternityUnlocked()Z` 后直接 return（构建接线真实进入最终 DEX，排除历史 R100/R101/R107 的「源码有函数但没进包」）。
- `vanillaEternityTabAllowed` 在 DEX 中 5 处调用点齐全（bm4/ll2 页签选择与恢复）。
- 运行日志：EP=0 时 `timeDimensions/eternity/... allowed=false`；只有真实结算后（ep=1,bigE=1）才 allowed=true。**顺序正确**。

**B. 结算层 —— 真实结算，但由自动化在首个合法帧发起（真正根因）**
- `OREKI_ET_GATE` 显示 `boot=true / fresh=true`：命中 R104 的「新档首永恒引导窗口」（`OrekiAutoEternityGate.noteFreshSession`），该窗口允许 MOD 替玩家驱动**首次永恒**。
- `canEt=true`（原版 `canEternity`，IP ≥ 1.79e308）出现的**同一秒**内即发起结算；同帧坍缩保护（`same-frame-crunch`）只延迟约 1 帧（25 ms），不构成玩家可感知的等待。
- 打破无限（12:16:31）到永恒结算（12:16:56）= **25 秒**，其中 IP 由 MOD 的无限层增益放大到 `2.756e342`。

**C. 结论**：玩家感知的「刚打破无限就解锁永恒」= **自动化把首个永恒在可结算的瞬间结算掉**，UI 随后正确反映「已永恒」。既不是存档污染，也不是 DEX 接线丢失，也不是页面恢复绕过。

## 6. 建议的最小根治（未实施）

目标：保留自动化长跑能力，同时**不剥夺玩家首个永恒的主动权**。

1. `OrekiAutoEternityGate`：新档引导窗口增加**驻留条件**——首次永恒自动结算要求 `canEternity` 已连续为真 ≥ N 秒（建议 60 s），或玩家手动按下永恒按钮后立即解除限制（手动优先）。
2. 玩家手动永恒不受该驻留限制（走原版 UI 入口）。
3. `OrekiCrunchPolicy` 的 `eternity-ready` 分支保持「允许坍缩」，但不得因此提前发起永恒；永恒只能经 `tickEternityGated` → `eternityGateReason() == "allow"` 单一路径。
4. 附带（P1，需单独评估）：打破无限后 IP 从 5e5 跳到 9e106、25 s 内越过 1.79e308，无限层体验被压缩；该增益服务于 ≤180 分钟目标，调整需长跑回归。

上述改动会改变阶段推进路径，**必须**走独立分支 + PR + Required Checks + 同一候选 APK 的正反向 AVD 验收 + 受影响的 180 分钟回归。

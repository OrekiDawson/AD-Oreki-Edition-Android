#### ID1 解锁条件的精确构成

`p()Z`（REA R5 反编译原文）：

```java
public final boolean p() {
    dg3 dg3Var = eg3.a;
    return (eg3.r.k() || Player.a.R().j().h().compareTo(k()) >= 0) && v();
}
```

拆开：

1. `eg3.r.k()` = **Perk「跳过无限维度反物质门槛」**（原版有名有姓的 bypass），**或**
2. `thisEternity.maxAM >= k()`（该 tier 的反物质门槛）
   **且**
3. `v()Z` —— 下面单独说明

`v()Z`（smali `:2734`）：

```
v() = t()Z || (Player.D() /*infinityPoints*/ >= InfinityDimensionState.f /*初始 cost*/)
```

`t()Z`（smali `:2583`）= tier==1 时：
`eternities > 0 || realities > 0`（即「已解锁永恒或现实」→ tier1 的 IP 门槛**不再适用**）

所以对 **tier 1（ID1）**，`v()` 展开为：

```
v() = (eternities > 0 || realities > 0) || (infinityPoints >= ID1 初始 cost)
```

**Android 原版 ID1 的完整解锁条件 =**

```
(Perk bypass || thisEternity.maxAM >= 1e1100)          ← 反物质门槛（Web: amRequirement = DC.E1100）
&& (已解锁永恒/现实 || infinityPoints >= ID1 初始成本)   ← IP 门槛
```

- `InfinityDimensionState.f`（tier1 的初始 cost）= `InfinityDimensionState.c[0]` = `Llu.R1`。
  `lu.smali:3610-3620` 显示 `R1` 由 `BigDouble.<init>(IIZ)` 构造：`p1 = 0x4`（尾数）、`p2 = 0x8`（指数）、`p3 = false`（不 normalize）。
  按 `BigDouble.<init>(DDZ)V`（`BigDouble.smali:502`）语义 `mantissa = p1`、`exponent = p2` →
  **R1 = 尾数 4、指数 8 = 4×10⁸**。⚠️ 注意这与 Web 的 `1e8` **不是同一个数**（Android 侧为 `4e8`），
  详见 §4「两端差异」。
- `InfinityDimensionState.k()`（tier1 反物质门槛）= `InfinityDimensionState.b[0]` = `Llu.o3`。
  `lu.smali:5095-5097` 显示 `o3` 由 `BigDouble.<init>(IIZ)` 构造，`p2 = 0x44c = 1100`（指数），
  尾数寄存器在 `lu.smali:4890-4995` 区间被设为 `1.0` → **o3 = 1×10¹¹⁰⁰** ✅ 与 Web `DC.E1100` 一致。

&& dimension/infinity/a.c()Z     // 「永恒里程碑 autoUnlockID 或 EC8/10 完成」等门槛

### 2.4 `CrunchAutobuyerState` 的判定逻辑与重置副作用

#### 判定链（Android 原版）

```
AutobuyerState.c()Z                     = isActive && Options.c()(autobuyersOn) && g()Z
  └─ CrunchAutobuyerState.c()Z          = super.c()Z && prestige/e.b()Z      ← 额外要求 canCrunch
       └─ prestige/e.b()Z               = (挑战目标已达成) && thisInfinity.maxAM >= e.e()(挑战 goal)
AutobuyerState.g()Z                     = 「该自动购买器是否已解锁」
  └─ CrunchAutobuyerState.g()Z          = Pelle Doomed ? (strike 相关) : 普通挑战 12 已完成
```

**`CrunchAutobuyerState.q()`（tick 主体，REA R3）= Web 的 `willInfinity` + `tick`**：

```
1. if (!c()Z) return                              // 不满足基本条件 → 不坍缩
2. if (prestige/e.j()Z) → 触发坍缩                // e.j() = 已解锁永恒或现实 → 无条件坍缩
3. switch (mode):
     mode == 0 (AMOUNT)  : e.d() >= F()            // F() = amount × totalIPMult
     mode == 1 (TIME)    : thisInfinity.realTime > time
     mode == 2 (X_HIGHEST): e.d() >= thisEternity.maxIP × xHighest
4. 满足 → 调用 prestige/e.i(...) 触发大坍缩
```

注意 `prestige/e.j()Z`（smali `prestige/e.smali:1335`）= `Player.m()(brake) || !挑战中`，
其中 `Player.m()` 就是 **`brake` = Web 的 `player.break`**。
即：**Android 原版在 `player.break == true` 时，会跳过挑战相关判断**，走 `e.j()` 那条路。

#### 重置副作用（AD3b 的核心）

**大坍缩（Big Crunch）会清零反物质**。Android 原版 `prestige/c`（`Infinity` 坍缩流程）里：

- `Player.antimatter` 被重置为初始值（10），
- `Player$Records.thisInfinity.maxAM` 被**重置**（本轮无限内的最高反物质重新从 0 计），
  → **`thisEternity.maxAM` 只有在「本轮永恒内累积」才反映真实峰值**。

Web 端 AD3b 的注释（「坍缩会清零反物质/峰值」）在 Android 侧同样成立：
`thisEternity.maxAM` 是**本永恒内**的累计峰值，不随单次坍缩清零，但 `thisInfinity.maxAM` 会。
而 ID1 的解锁门槛 `p()` 用的正是 `thisEternity.maxAM >= 1e1100`，
所以**只要在永恒内不断坍缩，`thisEternity.maxAM` 仍能累积**——但每一轮坍缩都会把 `thisInfinity.maxAM` 打回低位，
而 `e.d()`（本次坍缩收益）**正是从 `thisInfinity.maxAM` 算出来的** → 收益会被压到低位，形成死循环。

这与 Web AD3b 的语义完全一致（Web 的 `gainedInfinityPoints()` 同样基于 `player.records.thisInfinity.maxAM`）。

## 4. AD3 / AD3b 的 Android 落地设计

### 4.1 AD3（首次 ID1 解锁）

Web 侧 AD3 由两部分组成：

1. **`gainedInfinityPoints()` 末尾的兜底** `if (firstInfinityDimensionBoostActive(ip)) ip = ip.max(DC.E8);`
   —— 让「本次坍缩收益」至少等于 ID1 的 IP 门槛，从而让坍缩真的发生、IP 真的入账。
2. **`tryFirstId1AutoUnlock()`** —— 在 IP 余额 ≥ 门槛时调 `InfinityDimensions.buyMax()` 把 ID1 买下来。

Android 侧对应落点：

| Web 落点 | Android 落点 | 理由 |
|---|---|---|
| `gainedInfinityPoints()` 兜底 | `prestige/e.d()Lkajfosz/antimatterdimensions/BigDouble;` 末尾 | `e.d()` 就是 Android 的 `gainedInfinityPoints()`；在 `floor()` 之后 `clampMin(4e8)` 即可 |
| `tryFirstId1AutoUnlock()` | 新增 `OrekiAuto.tryFirstId1AutoUnlock()Z`，由 `dimension/infinity/a.b()`（`InfinityDimensions$autobuy$1` 协程，即 ID 自动购买 tick）调用 | Android 上 ID 页的 tick 入口就是 `dimension/infinity/a.b()` |

**触发窗口（Android 版）**，等价于 Web 的
`已 Break / 未解锁永恒 / ID1 未解锁 / IP < 门槛 / 非挑战 / 非毁灭`：

```
Player.brake()                              == true     // 已 Break
&& (Player.eternities <= 0 && Player.realities <= 0)     // 未解锁永恒/现实
&& !ID1.isUnlocked                          // ID1 未解锁
&& Player.infinityPoints < 4e8              // 当前余额还不够买
&& !c43.f() && !py1.d()                     // 不在普通/无限挑战中
&& !pelle.c.q()                             // 不在毁灭现实
```

**奖励不得重复发放 / 不得误触发**的保证：

- `e.d()` 的兜底是 `clampMin(4e8)`，**只把「本次坍缩收益」抬到刚好够买 ID1**，
  **不改变成本表、不写阶段标志、不改历史记录**（与 Web 完全同策略）。
  一旦玩家 IP 余额 ≥ 4e8，窗口自动关闭（因为窗口条件里带 `Player.infinityPoints < 4e8`），
  **不会重复发放 4e8**。
- 「不得误触发挑战 / 永恒 / 毁灭」：窗口条件显式排除挑战中、永恒已解锁、毁灭现实三种状态。

**ID1 的购买走原版路径**：
`OrekiAuto.tryFirstId1AutoUnlock()` 内部按 Android 原版 `MainActivityInfinityDimensionsKt$…$2$1` 的顺序调用
`M()Z`（解锁）→ `i()V`（首次购买）→ `h(Z)V`（批量购买），
**不直接写 `isUnlocked` 字段**（`L(Z)V` 那个 setter 一次都不碰）。

### 4.2 AD3b（暂停自动大坍缩以累积反物质）

Web 侧 AD3b 在 `bigCrunchAutobuyer.willInfinity` 里加了：

```js
if (this.waitingForId1Peak) return false;
```

窗口：`已 Break / 未解锁永恒 / 非挑战 / 非毁灭 / IP ≥ 1e8 / thisEternity.maxAM < 1e1100`。

Android 落点：**`CrunchAutobuyerState.q()`**（tick 主体，REA R3 已取证）。
在 `q()` 的 mode 分支判定之后、触发坍缩之前，插入抑制：

```
if (waitingForId1Peak()) → 跳过触发坍缩（落到函数尾 return）
```

`waitingForId1Peak()` 判定（Android 字段名，全部来自 §2.1 的 REA 证据）：

```
Player.brake()                          == true
&& (Player.eternities <= 0 && Player.realities <= 0)
&& !c43.f() && !py1.d()
&& !pelle.c.q()
&& Player.infinityPoints >= 4e8        // IP 已达门槛
&& thisEternity.maxAM < 1e1100         // 反物质峰值还没到 ID1 门槛
```

**只在有效窗口内抑制，窗口外恢复既有行为**：判定为「只读、无副作用」，窗口外的分支一个字节都不改。

**尊重玩家主动关闭自动器**：AD3b 只抑制「该不该坍缩」，**完全不碰 `isActive`**，
所以玩家手动关掉大坍缩自动器后，AU4c 的一次性启用逻辑（`lastTick > 0` 判据）也不会把它重新打开。
AU4c 与 AD3b 互不干扰。

### 4.3 与 Web 的对应关系（一句话）

- AD3：Web「把 `gainedInfinityPoints()` 兜底到 IP 门槛 + 在 ID 页调 `buyMax()`」
  → Android「把 `prestige/e.d()` 兜底到 4e8 + 在 `dimension/infinity/a.b()` 调 `M()/i()/h()`」。
- AD3b：Web「`willInfinity` 里 `if (waitingForId1Peak) return false`」
  → Android「`CrunchAutobuyerState.q()` 里在触发坍缩前 `if (waitingForId1Peak()) return`」。
- 数值差异：Web 用 `DC.E8`（1e8），Android 原版 ID1 成本是 **4e8**，故 Android 侧全部改用 4e8。
